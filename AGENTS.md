# AGENTS.md

starlayer is a platform for building Python semantic apps on the RDF 1.2 / SPARQL 1.2 / SHACL 1.2 drafts. Read this file first; it is short on purpose.

## Layout
- `packages/starlayer/starlayer/` is the library (its `pyproject.toml` is next to it in `packages/starlayer/`):
  `graph/` (`StarLayerGraph` / `StarLayerDataset` over Oxigraph, interop, set operations, Manchester syntax), `sparql/` (SPARQL 1.2, `sqe:` query trees, SRL rules), `shacl/` (SHACL 1.2 validation, rules, UI widget selection, the engine in `shacl/engine/`, and `shacl/profiling/conformance.py`, the library's declared conformance),
  `starontology/` (bundled ontologies and shapes, as `.ttl` files in a folder per vocabulary). The code-KG tooling is outside the package, in `tools/kg/codekg/` (repo-only). `packages/starlayer-reasoning/` is the plugin that holds the OWL reasoners (OWL-RL, OWL-DL); the rdflib conversion is in the core (`graph/rdflib_bridge.py`) and imports rdflib only when it runs; `packages/starlayer-kg/` is the code-KG data package.
- Tests: `packages/starlayer/tests/{graph,sparql,shacl,starontology,kg}/` mirror the source; `tests/packaging/` (the core has no rdflib, re-exports, install), `tests/repo/` (scripts, docs, AGENTS.md) and `tests/support/` (term helpers) are the rest. Guides: `docs/guides/*.ipynb` (index: `docs/guides/README.md`). Build scripts: `scripts/`. What changed in the RDF, SPARQL and SHACL drafts and their test suites since we last looked: `python scripts/check_spec_drift.py` (records in `docs/working/spec-dates.json`).
- Each of `graph/`, `sparql/`, `shacl/` has a `CLAUDE.md` starting with "Rules that bite". Read that block, not the design history below it.

## Set up, test, lint
- `pip install -e "packages/starlayer[test]"` from the repo root, or `uv sync --all-packages` (extras: `rdflib`, `reasoning`, `notebooks`, `benchmark`; see `packages/starlayer/pyproject.toml`). `starlayer-reasoning` (`packages/starlayer-reasoning`) holds the reasoners; the core imports rdflib and the reasoners only inside the conversion module `graph/rdflib_bridge.py` (`tests/packaging/test_no_rdflib_import.py`).
- `cd packages/starlayer && pytest tests -m "not integration"` is the fast tier. Integration tests need local Oxigraph/Fuseki servers and skip without them.
- Test one area alone: `pytest packages/starlayer/tests -m shacl` (areas: graph, shacl, sparql, starontology, kg, packaging, repo). Checks of committed data that CI runs anyway are in `--deferred`; run it before a push.
- Opt-in groups (deselected by default): `--store-matrix`, `--srl-stratification`, `--sqe-coverage`, `--manchester-conformance`, `--codekg-queries` (see `packages/starlayer/tests/conftest.py`).
- `ruff check packages/` must pass (CI runs it). Formatting is not enforced; do not reformat files you are not changing.

## Generated files: never edit by hand
`docs/generated/*.generated.md`, and in `packages/starlayer/starlayer/`: the four generated files `starontology/shacl/shacl12-{shacl,vocabulary,shacl-ui}.ttl` and `starontology/skos/skos-ontology.ttl`.
Edit the source (another `.ttl` in `starontology/`, `starontology/_sources/shacl12-validation-shapes.ttl` (the build inputs are in `starontology/_sources`), `codekg/curated/functionality.ttl`) and run `python scripts/build.py`. `codekg/curated/query-library.ttl` is itself a source (hand-edited, nothing generates it).
CI runs `python scripts/build.py --check`. The code KG files (`codekg.trig`, `testskg.trig`, `starlayer-kg.trig` in `tools/kg/codekg/`) are build products, not committed. In a checkout the first query or KG test builds them (about 30 s, then about 75 s for the combined file); rebuild after source changes with `python scripts/build.py --only codekg kg`. Users do not build: at release time, with the docs, a maintainer runs `python scripts/publish_kg.py` (add `--release vX.Y.Z` to create the GitHub release), which builds `packages/starlayer-kg` (the `starlayer-kg` data wheel) from the committed source.

## Use the knowledge graph first
Do not read large files into context: `tools/kg/codekg/codekg.trig` (6 MB, built locally), `docs/generated/api-reference.generated.md` (about 5,000 lines), or any `CLAUDE.md` below its "Rules that bite" block. Ask the graph a narrow question instead.
- Three layers: the vocabulary `tools/kg/codekg/ontology.ttl` (`slkg:`), the generated dataset `codekg/codekg.trig` (one named graph per module: classes, functions, calls, overrides, tests), and the hand-written capability graph `codekg/curated/functionality.ttl`.
- Capability map in plain text: `docs/generated/functionality-overview.generated.md`. One line per public symbol: `docs/generated/api-overview.generated.md`.
- **Start with a named query**, not raw SPARQL: `python scripts/kg.py list` (or `list --topic call-graph`), then `run find-symbol text=tt_hash` or `run callers-of symbol=<dotted path>`, or `run capabilities-by-role role=ui-generate` to find what StarLayer offers for a job (storage, interchange, query, validate, infer, ui-generate, reference). From Python: `from codekg import queries`, then `queries.run_query("callers-of", symbol=...)`. Results are tables limited to 25 rows (`--limit`, `--offset` to page), with file and line. The catalogue is `docs/generated/query-library.generated.md`; queries live in `codekg/curated/query-library.ttl` (edit it directly), and `python scripts/build.py --only queries` validates it and rewrites the catalogue.
- **Without a StarLayer checkout** (the query tool is not in the installed package): `pip install starlayer-kg` (a GitHub release wheel, built from a stated commit, no build needed), then `import starlayer_kg; kg = starlayer_kg.load()` (a `StarLayerDataset`; `starlayer_kg.build_info()` says which commit it describes, `starlayer_kg.path()` is the TriG file). The 24 named queries are in it as text: `SELECT ?q ?t WHERE { ?q a slkg:NamedQuery ; slkg:queryText ?t }`; bind a parameter with `kg.query(text, initBindings={"symbol": Literal("...")})`. It holds the code graph, curated layer, vocabulary and build stamp.
- No named query fits: `queries.run_sparql("SELECT ... LIMIT 20")` (SELECT and ASK only; `slkg:`, `dcterms:`, `rdfs:` are predeclared). Raw access: `get_codekg_dataset()` returns a `StarLayerDataset`; always put a `LIMIT` on queries and select a few columns.
- Recipe: find the topic in the functionality overview, take its `implementedByIdentifier` (a dotted path), run `symbol-info` for its file and lines, then open only that range. To see which guide cell demonstrates a symbol, use `demonstratedBy` (derived from `codekg/curated/notebook-links.ttl`, checked by `scripts/build.py`; stale links are reviewed with the `review-notebook-links` skill).
- Every query result ends with how old the KG is ("KG built <date> from commit <sha>; since then N commit(s) ... changed the source", from a build stamp), and `python scripts/kg.py status` prints it alone. If code you are about to rely on has changed since, rebuild first: `python scripts/build.py --only codekg kg` (about 1 min).
- Code that exists because of a bug in rdflib, pySHACL, Fuseki or Oxigraph: `run upstream-workarounds` (optionally `project=rdflib` or `symbol=<dotted path>`); the list is `codekg/curated/upstream-issues.ttl`, the write-ups are in `docs/upstream-issues/`.
- A zero-row call-graph answer means no caller this extractor could resolve, not proof of none. Imports between starlayer modules are not in the graph (only external imports are); use the call graph for dependencies.
- (2026-10-26, GitHub issues #102 and #84) Extractor call-graph scoping now follows Python: a bare `name()` in a method never resolves to a sibling method (class scope is skipped), a parameter or local variable of the caller or an enclosing function hides a same-named module function, a nested function's calls belong to it alone (its decorators and defaults count for the enclosing function), a property's setter/deleter and `@overload` stubs add no facts of their own (the getter, or the implementation, describes the one IRI; a setter's calls are added to it). A bare `name()` call is not an edge when `name` is a comprehension variable or lambda parameter around it (2026-10-26). Still open: a `match`/`import`-bound name is only partly handled, and `build.py --check` for the codekg step ignores the build stamp but still takes minutes to compare the ~100k-triple graphs (CI keeps `--skip codekg`). `build.py --check` restores `codekg/CHANGELOG.md`; `scripts/record_benchmark_baseline.py` and `scripts/check_benchmark_regression.py` now stop or fail on a benchmark missing from a run.
- Questions the KG can answer, and which it cannot yet: the `slkg:CompetencyQuestion` nodes in `codekg/curated/query-library.ttl` (`python scripts/kg.py questions --unanswered`).
- Planned, not built yet: a public read-only KG endpoint that logs questions. See `docs/app-development-plans/repo-prep-plan.md`.

## Working agreements
- Do not push, merge, publish or delete branches without being asked. Confirm before any outward-facing action.
- Do not edit a guide notebook unless asked; describe the change and wait. If a file may be open with unsaved changes, ask the user to save first.
- Voice (decided 2026-11-27): all documentation, comments and docstrings are impersonal third person. No "you", "your", "I", "we" or "let's"; name the subject (the caller, the application, the graph). Details in `docs/guides/STYLE_GUIDE.md` section 7.
- Docs say what a reader needs (inputs, outputs, errors), not interesting side facts. No notes to the reader about how the doc was produced.
- Docstrings give the "why". Do not restate what the signature, calls or overrides already show; the code KG records those.
- Test discipline: before calling a fix done, check the new test fails without it. For SHACL behaviour the oracle is the SHACL 1.2 draft and the W3C suite (`tests/shacl/w3c_shacl12/`); for SPARQL, Oxigraph or rdflib.
- Errors (the scheme is in `starlayer/errors.py`; `tests/repo/test_error_scheme.py` pins it). Classify by cause, never by the path an error travels. Every error the library raises on purpose derives from `StarLayerError(Exception)`; none is a `ValueError`, `SyntaxError`, `RuntimeError` or `OSError`, except `EndpointError(StarLayerError, OSError)` (a network failure). The classes: `ShapeError(kind=...)` for a wrong shapes graph, rule or setup (kinds: `ShapeError.KINDS`: `"compile"` the engine cannot read or compile it, `"meta"` the meta check found it, with `problems`, `report_text`, `report_graph`, `scope`); `FormatError(kind=...)` for malformed text or data (kinds: `FormatError.KINDS`; optional `why`, `line`, `col`, `pos`, never parsed out of an engine message); `ExecutionError(kind=...)` for a failure while running or for input the library cannot handle (the kinds and their meanings are the mapping `ExecutionError.KINDS` in `starlayer/errors.py`; `unsupported` = the user asked for something StarLayer cannot do and can choose differently, `internal` = StarLayer asked itself for something it cannot do). ONE class and a kind, not a class per case: a new case is a new kind in `KINDS` with its first raise site, not a new class. Where it happened goes in the message and `context` (a short string); a handler that knows the place sets it and re-raises the same class and kind.
  - How to choose (the ladder, decided 2026-11-26): (1) the wrong Python type is `TypeError`, and only that (content of the right type that a defined format refuses is `FormatError`); (2) a thing in a defined format (text, document, tree, term, rule set) whose content cannot be read is `FormatError`, whether it arrived as an argument or inside a document (a parsed value is `FormatError`, a chosen or combined one `ValueError`: a bad direction passed to `literal()` is `ValueError`, the same text in a parsed document is `FormatError`); (3) a parameter or object the call cannot use as it stands (a value outside the choices the call defines, contradictory options, a wrong target, an object in a state the call refuses such as a closed `Materialization`) is a plain `ValueError`; otherwise the arguments are fine and the work could not be done, an `ExecutionError` by cause. In short, a bad argument at the entry of a public call (wrong value, a wrong combination, a graph or term the object refuses) is a plain `ValueError` / `TypeError`; a missing optional package is `ImportError`; a wrapper method the object does not have is `NotImplementedError`; a document, text, tree or term that is malformed is `FormatError`; a shapes graph that is wrong is `ShapeError`; valid input the library or the target notation cannot handle, nobody's mistake, is `ExecutionError` kind `"unsupported"` (a name that is not a registered entailment regime, a `DESCRIBE` or `SERVICE` query given to `relevant_subgraph`, a blank node that came from an endpoint, a literal with a base direction under the `"error"` policy, something the renderers have no form for); a cap reached is kind `"limit"` (RDFC-1.0, `max_iterations`, `max_triples`; a depth limit is `"limit"` too, its context saying what was too deep); an impossible internal state is kind `"internal"` (not an `assert` or a builtin). `ExecutionError` adds "internal error (a bug in StarLayer, please report it at <errors.ISSUES_URL>): " to the message of kind `"internal"` ONCE, in its constructor (never write it at a raise site), and `error.report_url` is that URL for `"internal"` and `None` otherwise, for applications to show. A pyoxigraph `SyntaxError` / `RuntimeError` is converted once, at `parse()`, `query()` and `update()`.
  - Imports (decided 2026-11-26): ONE rule on every path that resolves imports (`StarLayerGraph.resolve_imports()`, SHACL shapes graph and `ont_graph`, SRL `IMPORTS`, `infer()` / `query(entailment=)` with the OWL regimes): a graph, shapes graph or rule set that declares imports must resolve them or raise `ExecutionError` kind `"import"` (`error.unresolved`: the IRIs, `context` `owl:imports <iri>`). An import is satisfied when its IRI is a subject of the graph after resolution (present, a built-in ontology of the `starontology` registry, or loaded; or the `owl:versionIRI` of a present ontology; for SRL, when the loader produced a rule set); no loader, a loader that returns `None` or a graph without the IRI is the error, never a silent skip; a loader that raises is wrapped (the original is `__cause__`); `ignore_imports=True` loads and checks nothing; no retry inside the library (an application reads `starlayer.graph.unresolved_imports(graph)` and calls again). One implementation, `resolve_or_raise` in `starlayer/graph/imports.py`, which every path calls. A malformed declaration (an `owl:imports` object that is not an IRI) is `FormatError` kind `"owl"` for a graph and `ShapeError` kind `"compile"` for a shapes graph. The loader parameter is `imports_loader=` on every call (decided 2026-11-26; the old `loader=` and `shapes_graph_loader=` are gone, with no alias). **Imports live on the graph (2026-11-26, step 2).** A graph carries its own settings, `StarLayerGraph(imports_loader=..., ignore_imports=...)` and the `imports_loader` / `ignore_imports` properties (a copy, a `+` result of the left operand, `empty_like()` and a dataset's `graph()` / `default_graph` / `graphs()` / `to_graph()` carry them; pickling keeps the flag, not the loader), and ONE accessor, `graph.resolved_imports(imports_loader=None, ignore_imports=None)` (`graph.imports.graph_imports` for any graph object), returns the triples the graph's `owl:imports` closure loads (a `frozenset`; the graph does not gain them) or raises the rule above. Every consumer calls it, none has its own plumbing: `validate()` for the data graph (its imports are visible to entailment only, like `ont_graph`), the shapes graph and `ont_graph` (merged), `apply_rules()`, `evaluate()`, `target_nodes()`, `target_shapes()`, `extract_subgraph()`, `close_shape()` (shapes merged into the copy), `select_widgets()` (shapes and scoring graph merged, `data_graph` checked), `derive_shape()` (`template_graph` merged, `graph` checked), `infer()` and `query(entailment=)` for the OWL regimes, `resolve_imports()`. Not consumers: the single-shape widget calls, `candidate_values()`, `check_value()`, `form_model()`, `extract_shapes_graph()`, `meta_validate()` (it passes `ignore_imports=True`), SRL (`IMPORTS` stay a property of the rule set text), and every other read of a graph. The per-call `imports_loader=` / `ignore_imports=` stay and override the graph's setting for that call (`ignore_imports=None` means the graph's own; an explicit `False` beats a graph that ignores). Resolution is lazy (nothing is loaded until a consumer asks) and cached per store, keyed by what the graph reads, the loader object and the flag, valid while the store's write count (`graph/execution/union.py`) is unchanged: `add`, `remove`, `parse`, `clear` and any other write made through the package drop it, a loader set afterwards applies at the next consumption, a failure is never cached; `clear_imports_cache()` forgets a result when only the loader's answers changed. A dataset's imports are those of the triples it reads (the union with `default_union`, else the default graph); a named graph's own view resolves its own. One lock per store, held while a loader runs (two threads asking together load once; a loader must not wait on another thread that asks the same store).
  - Catch clauses name the failure they guard against (never bare `Exception` unless the reason is commented); an `except ExecutionError` that handles some kinds calls `only_kind(error, ...)` first so it cannot swallow another; a fallback on an engine `RuntimeError` checks the message. No deprecation aliases when a class is removed; add it to `REMOVED_CLASSES` in `tests/repo/test_error_scheme.py`. Open items: `docs/design/future_enhancements.md`, "Error handling in SHACL, and uniformity across StarLayer"; the history is `docs/working/error-handling-audit-2026-11-25.md`.
- Commit messages end with the Co-Authored-By line given to you. Keep generated-file changes in their own commit.
