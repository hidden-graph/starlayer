## Imports (2026-11-26)

The maintainer decided that every path that resolves imports follows ONE rule. Before: `graph.resolve_imports()` silently skipped an import with no loader or a loader that returned `None` (and let a loader's own `OSError` escape); SHACL `validate()` raised `ShapeCompileError` with no loader but skipped an import the loader returned `None` for; SRL `IMPORTS` raised `ExecutionError` kind `import` in two places; `infer()` and `query(entailment=)` never looked at imports.

**The rule.** A graph, shapes graph or rule set that declares imports must resolve them or raise `ExecutionError` kind `"import"`. An import is satisfied when, after resolution, its IRI is a subject of at least one triple in the resulting graph (present, built in, or loaded). Not satisfied (no loader, a loader that returns `None`, a loader that returns a graph without the IRI as a subject) is the error, with `context` `owl:imports <iri>` (several: `owl:imports <a>, <b>`) and the IRIs on `error.unresolved`, a tuple of `NamedNode`, sorted by IRI. A loader that raises is wrapped (same kind, `context` of that one import, `unresolved` that one IRI, the original as `__cause__`). `ignore_imports=True` loads nothing and checks nothing. Nothing is retried; a graph is fetched once per resolution; cycles end. `unresolved_imports(graph)` (`starlayer.graph`) lists what a graph still needs, so an application can load it and call again.

**Implementation.** Once, in `graph/imports.py`: `resolve_or_raise(graph, loader, ignore_imports, *, view=, malformed=, loader_name=)` returns the loaded triples; `StarLayerGraph.resolve_imports()` (`loader=`, `ignore_imports=` new), the SHACL engine (`shacl/engine/imports.py`, a thin wrapper that supplies the engine view, `ShapeCompileError` for a malformed declaration and the name `shapes_graph_loader`) and `infer()` / `query(entailment=)` call it. `builtin_import_keys()` / `is_builtin_import()` moved there from the SHACL engine (still re-exported from `shacl.engine.imports`). SRL is a rule set, not a graph: `srl._resolve_imports` applies the same rule with its own satisfied-test (the loader produced a rule set), collecting the imports a loader returned `None` for and raising once at the end; the run-time check in `srl_eval` raises the same error. `ExecutionError` has a keyword-only `unresolved` (default `()`), kept by `__reduce__`, so pickle and copy work.

**Breaking changes callers will notice.** `resolve_imports()` with no loader, or a loader that returns `None` or a graph without the IRI as a subject, raises (it skipped); a loader that raises is `ExecutionError` kind `import` (it was the loader's own exception); SHACL: an unresolved import is `ExecutionError` kind `import` (it was `ShapeCompileError`), an import the loader returns `None` for raises (it was skipped), a loader's graph must have the IRI as a subject (a module with no `<iri> a owl:Ontology` header is now unresolved); a shapes graph already merged with `resolve_imports()` no longer needs `ignore_imports=True` when each import is a subject or version IRI there; `infer()` and `query(entailment=)` with an OWL regime raise for an ontology with unresolved imports; `RuleSet.plan()` without a loader raises for a rule set with `IMPORTS`; a loader returning `None` for an SRL import is an error (it was an `AttributeError`). ## Review decisions Q15-Q17 and the registry (2026-11-26)

- **Q15.** A shapes graph's `sh:entailment` that names an unregistered regime (a typo, D-Entailment, an IRI that is neither a regime nor `sh:RulesEntailment` nor a `sh:RuleSet`) is `ExecutionError` kind `unsupported`, context `entailment regime`, with the message of `infer()` and `query()` (`graph/entailment/__init__.py: unsupported_regimes`, the "did you mean" text). `declared_regimes` raises it; it was `ShapeCompileError`. One answer for `infer()`, `query()`, `inference=` and a shapes graph. (A malformed `owl:imports` declaration stays `ShapeCompileError`: that shapes graph is unreadable, not asking for something StarLayer cannot do.)
- **Q16a.** `export_rdf11` given named graphs for a one-graph format (Turtle, N-Triples, RDF/XML) is `ExecutionError` kind `unsupported`, context `<format> serialize` (it was `ValueError`); the message is unchanged ("cannot hold named graphs; use TriG or N-Quads"). `serialize()` never reaches it: for a dataset and a triple format `_serial_items` already gives the triples of one graph, so no named-graph message exists in `core.py`.
- **Q16b.** `qnames.compute_qname` of an IRI that has no namespace and local name Turtle can write is `FormatError` kind `rdf`, context `prefixed name`, "cannot write <iri> as a prefixed name; write it in full as <iri>" (it was `ValueError`). `compute_qname(generate=False)` with no bound prefix stays `KeyError`. `qnames.n3` (so `qname_term`, `n3`, the SHACL message writer) catches `(KeyError, FormatError)` and still writes `<iri>`; `graph.qname()` raises the `FormatError`.
- **Q16c.** An OWL regime reaching `rewrite_for_entailment` is `ExecutionError` kind `internal`, context `entailment rewrite` ("an OWL regime reached the query rewrite: OWL regimes are answered through the entailed copy"); `StarLayerGraph.query` dispatches the OWL regimes to the entailed copy first, so it can only arrive through a StarLayer bug. It was `ValueError` ("use infer()"). An unregistered name is still `unsupported`.
- **Q17.** Reading `.rows` / `.bindings` of a result that is not a SELECT, or `.triples` of one that is not CONSTRUCT or DESCRIBE, is `ValueError` (an object in a state the call cannot use); it was `TypeError`. Unknown `serialize()` options stay `TypeError` (the wrong argument, not the wrong state).
- **The registry.** `ExecutionError.KINDS` and `FormatError.KINDS` are dicts, kind -> one-line meaning (the tables of Appendix D, sections 3 and 4); iteration, `in` and `', '.join(KINDS)` read the names; `kind` stays a plain string; messages, attributes, pickle and copy are unchanged. The `errors.py` docstring and `AGENTS.md` point at the registry instead of repeating the list. `tests/repo/test_error_scheme.py` checks that every kind has a meaning and that every kind is raised somewhere. The distinction between the two kinds that look alike: `unsupported` is the user asking for something StarLayer cannot do (they can see the limit and choose differently); `internal` is StarLayer asking itself for something it cannot do (a bug).
