User Guide

StarLayer

StarLayer extends rdflib with RDF 1.2 features and adds SHACL 1.2 validation and rule execution in a form that is consistent with the rdflib and pyshacl developer flow. This guide assumes you are familiar with RDF, SPARQL, and SHACL fundamentals and that you are familiar with the current draft specifications as they evolve. See the relevant drafts here: RDF 1.2 Concepts, SPARQL 1.2 Query, and SHACL.

This project is a research-grade RDF 1.2 stack and remains under active development.

1. Graph and literal semantics

The graph layer keeps the rdflib feel, but it extends the model to cover RDF 1.2 constructs such as triple terms, reification, and direction-tagged literals.

  • RDF 1.2 triple-term and reification support in the graph model.
  • Language-direction-aware literal handling, including direction-tagged strings and base-direction semantics.

Example: reified statement as a triple-term node

g = StarLayerGraph()
g.add((EX.claim_7, RDF.reifies, (EX.bob, EX.knows, EX.carol)))
print((EX.claim_7, RDF.reifies, (EX.bob, EX.knows, EX.carol)) in g)

Output:

True

Example: language-direction-aware literal

g = StarLayerGraph()
g.add((EX.title, EX.value, "مرحبا"))
print(g.serialize(format="turtle12"))

Output:

... ex:title ex:value "مرحبا"@ar--rtl .

The important difference from plain rdflib is that a reified statement is represented by a statement resource and the actual triple is attached to that resource using rdf:reifies. This is the canonical RDF 1.2 reification pattern and keeps the statement itself available as a first-class node.

Reification and statement metadata

g = StarLayerGraph()
g.add((EX.claim_7, RDF.reifies, (EX.bob, EX.knows, EX.carol)))
g.add((EX.claim_7, EX.source, EX.wikipedia))
g.add((EX.claim_7, EX.confidence, "high"))

for triple in g.triples((EX.claim_7, None, None)):
    print(triple)

Output:

True
(http://example.org/claim_7, http://www.w3.org/1999/02/22-rdf-syntax-ns#reifies, (http://example.org/bob, http://example.org/knows, http://example.org/carol))
(http://example.org/claim_7, http://example.org/source, http://example.org/wikipedia)
(http://example.org/claim_7, http://example.org/confidence, high)

2. SPARQL and query semantics

The SPARQL layer integrates with the graph layer and handles RDF 1.2 constructs while still keeping familiar SPARQL evaluation patterns. This is the natural next step after the graph layer.

  • RDF 1.2-aware SPARQL expression evaluation over triple terms and direction-tagged literals.
  • Support for RDF 1.2-aware Turtle/SPARQL syntax parsing and serialization.
  • SPARQL algebra encoded as RDF using a dedicated ontology and SHACL validation schema.
  • Validation of generated SPARQL RDF representations with SHACL rules.
  • RDF-graph output for query results and intermediate SPARQL representations.

3. SHACL validation and rules

Once your graph works, the next step is checking it against a shapes graph. The validator is designed to sit on top of a normal rdflib/pyshacl workflow while extending it for RDF 1.2 values, node expressions, and SHACL 1.2 UI-oriented shape behavior.

  • Validation over RDF 1.2 graphs containing triple terms, statement resources, and direction-tagged literals.
  • SHACL 1.2 node-expression and rule-based evaluation support.
  • Updated SHACL meta-shapes for SHACL 1.2 compatibility.
  • Formal SHACL 1.2 UI support for shape-driven interface generation.
  • Direction-aware uniqueness and datatype constraints for language-tagged values.

4. Backend graph-store and format support

The stack is designed to work across different RDF backends and serialization formats rather than forcing a single storage model. This matters when you want to move between local graphs, remote endpoints, and SQL-backed deployments without losing RDF 1.2 semantics.

  • Compatibility with RDF graph backends including Oxigraph, Jena/Fuseki, and SQL-backed stores.
  • Read/write support for RDF 1.2-aware formats such as Turtle and related RDF serializations.
  • Dual-mode operation across RDF 1.1 and RDF 1.2 semantics.
  • Use of backend SPARQL 1.2 capabilities when available, while preserving compatibility with older stores.
