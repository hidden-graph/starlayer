## `starlayer.shacl`'s own namespace: Core stays flat, each SHACL 1.2 spec document gets its own explicit import (2026-10-06)

Mirrors `starlayer.sparql.srl`/`sqe`'s own precedent: `starlayer.shacl`'s top-level `__init__.py` flat-exports only Core validation (`StarShaclSchema`, `validate`, `validate_each`, `ValidationResult`, `ExecutionDiagnostics`, `close_shape`) and the cross-cutting RDF 1.2/triple-term infrastructure every other module depends on (`TripleTermAdapter`/`Graph`/`Value`, `normalize_to_starlayer_graph`/`normalize_graph_inputs`, `StarLayerGraphProtocol`/`MutableStarLayerGraphProtocol`). Previously, all ~27 names across every capability were flattened together - found confusing when reviewing the doc, since it buried which names belong to which SHACL 1.2 document behind one undifferentiated namespace.

Everything else is reached via an explicit submodule import, one per SHACL 1.2 document (new thin wrapper files, each re-exporting from the real implementation file(s) under a spec-concept name rather than moving any code):
- `from starlayer.shacl import shacl_inference` → `RulesResult` (re-exported from `results.py`)
- `from starlayer.shacl import shacl_node_expr` → `EvaluationResult` (from `results.py`) and `eval_expr` (from `node_expressions.py` - this had **no reachable public import path at all** before this split, found while auditing what needed re-exporting)
- `from starlayer.shacl import shacl_profiling` → aggregates `profiles.py` (`ValidationProfile`/`available_profiles`/`get_profile`/`resolve_profile_options`) + `profiling.py` (`declared_conformance_profile`/`derive_conforms_to`) under one name, since this one spec document happens to be implemented across two sibling files

Two more names moved out of the flat namespace but *don't* get a `shacl_*` wrapper, since they aren't one of the six spec documents - they reuse their existing implementation-module name directly as the public import path:
- `from starlayer.shacl import engine` → the native-component evaluation engine (`STSH`/`ComponentRequest`/`ComponentEvaluationResult`/`target_nodes`/`evaluate_component`/`build_report`) - cuts across several spec documents, not owned by one
- `from starlayer.shacl import subgraph_extraction` → `extract_subgraph()`/`SubgraphExtractionResult` - this project's own invention, not part of any SHACL 1.2 document at all (confirmed via `docs/shacl/shacl12-gap-matrix.md` - zero mentions anywhere)

Only two real call sites needed updating for this (confirmed via `grep` across the whole repo before making the change, not assumed): `tests/shacl/integration/test_profiling.py` and `test_evaluate_virtual_values.py`, both just changing their import line to the new submodule path.

## `StarShaclSchema` binds a shapes graph (plus optional ontology graph) at construction, not per-call (2026-10-06)

**Four names in one day, same class**: `StarLayerShacl` → `StarLayerShaclProcessor` → `StarLayerShaclGraph` → **`StarShaclSchema`**. Each rename tracked a real finding, not taste alone:
- `StarLayerShacl` named the specification ("Shacl"), not what the object is.
- `StarLayerShaclProcessor`: "Processor" is the W3C SHACL spec's own term for an implementation performing its defined operations, quoted directly in `validator.py`'s own source ("SHACL processors MUST NOT..."). Better, but still implied a singleton worker - the wrong connotation, once the real design problem below was found.
- `StarLayerShaclGraph`: the design problem - the object held no meaningful state at all (confirmed via `grep`: its constructor set exactly two attributes, `adapter`/`validate_fn`, both pure test-seam dependency injection with zero real external use), and every one of its six methods (`validate`/`validate_each`/`apply_rules`/`evaluate`/`extract_subgraph`/`target_nodes`) took `shacl_graph` as a parameter on *every single call* - meaning two instances were always functionally interchangeable, and any real caller validating several data graphs against one shapes graph was re-passing the identical `shacl_graph` argument every time. Fixed by binding `shacl_graph`/`ont_graph` at construction (below) - "Graph" named the new relationship to its shapes graph (matching `StarLayerGraph`'s own convention), but this class never *holds* triples itself (composition, not inheritance), so "Graph" overclaimed.
- `StarShaclSchema`: "Schema" is already the ordinary term for "the thing you validate data against," and - unlike "Processor"/"Engine"/"Service"/"Context," all considered and rejected - it naturally supports several differently-named instances in one project (a `PersonSchema`, a `ProductSchema`), rather than reading as one shared facility. `Star` rather than `StarLayer`: deliberate, the first instance of a planned future prefix simplification (`StarLayerGraph` may become `StarGraph` later) - not yet applied project-wide, so this one class is intentionally inconsistent with `StarLayerGraph`/`StarLayerDataset` for now.

**Fix**: `shacl_graph`/`ont_graph` moved from a repeated per-call method parameter to a constructor-bound attribute (`StarShaclSchema(shacl_graph=None, ont_graph=None)`), normalized once in `__init__` via `normalize_to_starlayer_graph` (not deferred to each method call) specifically so `apply_rules()`'s own separate `normalize_graph_inputs(self.shacl_graph, ...)` call for `rule_set`/`_global_sparql_rule_triples` blank-node identity gets back the *identical* object `validate()` itself uses internally - no second, independent normalization that could silently diverge, the exact invariant the pre-existing code already depended on (see that method's own comment). Every method's body kept its existing local `shacl_graph`/`ont_graph` variable names unchanged internally - only the signature changed, plus one new line aliasing `shacl_graph, ont_graph = self.shacl_graph, self.ont_graph` at the top of each, since every method already treated them as ordinary local variables it reassigns as it goes (e.g. `_augment_shapes_with_new_target_types`). This made the actual method-body risk much lower than the call-site-migration risk (below).

**Call-site migration, the real risk**: 320 construction call sites across 49 files, ~300 of which also passed `shacl_graph=`/`ont_graph=` to a method call needing that argument *moved* to the constructor - not a trivial rename. Handled with an AST-based transformer (regex is unsafe here - multi-line calls, nested parens in argument values), scoped per-function (not per-file) to avoid false "ambiguous" flags when the same variable name like `validator` is reused fresh in every test function. Two real bugs found and fixed along the way:
- The transformer didn't dedupe when one object was reused across *multiple* calls sharing the *identical* `shacl_graph` value - it tried to insert into the constructor once per matching call, corrupting span offsets on the second insertion. Caught safely in both real occurrences (`test_rule_iteration.py`, `test_w3c_validate.py`) because duplicate keyword arguments are unconditionally a Python `SyntaxError` - the transformer's own post-edit `ast.parse()` check rejected and skipped both files whole rather than writing corrupted output. Fixed by hand (bind once at construction, drop from every call), then safely re-run the same transformer on just those two files afterward.
- A handful of tests built a value (e.g. `shapes = Graph()`) *after* the original argless constructor call, relying on it only being needed later at the `.validate()`/`.apply_rules()` call site - moving that same expression into the constructor call site (now earlier in execution order) raised `UnboundLocalError`. Fixed by either reordering the definition earlier or dropping the irrelevant `shacl_graph` argument entirely where the test wasn't actually testing shapes-graph behavior (e.g. `test_apply_rules_rejects_non_starlayergraph_data_graph`, which only cares about `data_graph` rejection).
- One file used a local `_validator()` helper wrapping the constructor with no arguments, invisible to the transformer (it only recognizes a direct `StarShaclSchema(...)` call, not one hidden inside another function) - fixed by giving the helper its own `shacl_graph` parameter and forwarding it.

Full `tests/shacl` suite (1051 tests) passes identically to the pre-redesign count - confirms nothing was silently dropped or disabled during the migration, not just that nothing errors.

### Wraps pyshacl by composition, not inheritance - and a coverage audit of pyshacl's own public surface

`StarShaclSchema` is `object`-derived (no base class) because pyshacl's own main entry point, `validate()`, is a stateless one-shot function, not a long-lived object to subclass the way `StarLayerGraph` subclasses `rdflib.Graph` - there's no "is-a" relationship available, and `StarShaclSchema` unifies four independent capabilities (`validate`/`apply_rules`/`evaluate`/`extract_subgraph`), the last two of which aren't pyshacl operations at all. Composition also matches what's actually happening at the boundary: triple-term encode/adapt, call pyshacl's own function as a black box, decode - a decorator pattern, not internal specialization.

A direct audit against pyshacl's own `__init__.__all__` (`validate`, `validate_each`, `shacl_rules`, `Validator`, `RuleExpandRunner`, `Shape`, `ShapesGraph`) found two real, confirmed gaps - things pyshacl exposes publicly that `starshacl` had no access path to at all, as opposed to the five other names, which are either wrapped (`validate`) or deliberately bypassed/used only as internal plumbing:

- **`validate_each()`** (batch-validate several independent data graphs against one shared shapes graph) - had zero `starshacl` equivalent. **Fixed 2026-10-06**: `StarShaclSchema.validate_each()` + a module-level `validate_each()` convenience function, both in `validator.py`, implemented as a loop calling `self.validate()` once per data graph (not by driving pyshacl's own multi-data-graph path directly - that path knows nothing about RDF 1.2 triple terms or any of this project's SHACL 1.2 patches, so using it would silently run a different, unpatched pipeline). Returns `dict[int, ValidationResult]`, this project's own richer result type, matching `validate()`'s own "wrap pyshacl's bare tuple" convention.
- **`shacl_rules()`/`RuleExpandRunner`** (a lighter-weight "expand rules only, skip constraint validation" path) - `apply_rules()` always routes through `self.validate(profile="rules")`, which always also runs full SHACL constraint checking (the `"rules"` profile in `profiles.py` has no flag to skip it). No data is lost (`RulesResult.data_graph` already carries the expanded graph, plus a bonus validation report `shacl_rules()` wouldn't give you), but there's no way to get rules-without-validation specifically. **Deliberately not implemented yet** (2026-10-06) - logged in `docs/future_enhancements.md` pending a check of whether the SHACL 1.2 Inference Rules draft says anything that bears on this.
- The other three (`Validator`, `Shape`, `ShapesGraph`) are used, but only as internal plumbing/monkey-patch targets (three separate process-global patches on `Shape.validate`/`value_nodes`/`focus_nodes` to fix confirmed pySHACL bugs) - never exposed as public `starshacl` symbols in their own right. Not treated as gaps; nothing currently needs to construct one of these directly.

When adding a new pyshacl-wrapping capability, check pyshacl's own `__all__` against what's actually reachable from `starlayer.shacl` the same way - don't assume parity.

## `apply_rules()` becomes a module-level function; `StarShaclSchema.apply_rules()` delegates to it (2026-10-07)

Direction flip from `validate()`/`validate_each()`'s own convention, on explicit user instruction: "I think the wrapping is the wrong direction. we have the bare function, and then StarShaclSchema.apply_rules calls that function with its stored shapes graph." `validate()`/`validate_each()` wrap `StarShaclSchema` (bare function constructs a throwaway instance, the instance method holds the real logic) because pyshacl's own `validate()` is a one-shot function and the class exists only to bind `shacl_graph`/`ont_graph` once. `apply_rules()` is different: pyshacl's own module-level analog, `shacl_rules()`, is itself a bare function - so `apply_rules()` should follow that shape too, not `validate()`'s.

Implemented: the real `apply_rules(data_graph, shacl_graph=None, ont_graph=None, include_source_rule_provenance=False, rule_set=None, **kwargs)` now lives in `validator.py`, next to `validate()`/`validate_each()`; `StarShaclSchema.apply_rules()` is now a thin delegate passing `self.shacl_graph`/`self.ont_graph` through. Exported from `shacl_inference.py`, not the flat `starlayer.shacl` namespace - it's Inference-Rules-specific, same reasoning as `RulesResult` - whose own docstring previously claimed "no module-level function form to mirror"; now stale, fixed.

**Real coupling found, not just a rename**: the old method body called `self.validate(...)` and read `self.adapter` directly (for `sh:sourceRule` provenance decoding) - not a pure function of `(data_graph, shacl_graph, ont_graph)`. Flipping the direction means the bare function necessarily goes through the bare `validate()` function (which always constructs a fresh, default-adapter `StarShaclSchema`), not `self.validate()` - so a constructor-level `adapter=`/`validate_fn=` override on an instance no longer reaches that instance's own `apply_rules()`. Confirmed with the user before implementing (`adapter=`/`validate_fn=` already have zero real external callers - see the composition section above) and accepted as a deliberate trade-off, not an oversight.

**Normalization-once invariant preserved deliberately**: the bare function still normalizes `shacl_graph` exactly once (`normalize_graph_inputs(shacl_graph, None, None)[0]`) and reuses that one object for both the rule-set/global-SPARQL-rules passes and the `validate()` call inside it - the same invariant the per-instance code already depended on (see the binding section above), just computed from an explicit parameter instead of `self.shacl_graph`. When called via `StarShaclSchema.apply_rules()`, `self.shacl_graph` is already normalized once at construction, so this is an identity pass-through, not a second normalization.

Two unit tests relied on the old coupling to inject a fake `validate_fn` through the constructor (`test_apply_rules_requests_inplace_advanced_mode`, `test_apply_rules_uses_rules_profile_defaults` in `tests/shacl/unit/test_validator.py`) - updated to `monkeypatch.setattr("starlayer.shacl.validator._default_validate", fake_validate)` instead, since that's the shared fallback the fresh internal `StarShaclSchema` now actually uses. Verified live (throwaway `StarShaclSchema` + direct bare-function call, both producing the expected inferred triple) and via the full `tests/shacl` suite (1048 passed, zero regressions beyond the two intentionally-updated tests).

## `close_shape()` moves from a bare `starlayer.shacl` function to a `StarShaclSchema` method (2026-10-07)

Opposite direction from the `apply_rules()` flip above, on explicit user instruction: "lets remove close_shape from a separate public function. move it to a method of the Schema." Unlike `apply_rules()`, there was no pyshacl analog pulling `close_shape()` toward a bare-function shape in the first place - it's this project's own invention (see the subgraph-extraction design notes), and every one of `StarShaclSchema`'s other processing modes (`validate`/`apply_rules`/`evaluate`/`extract_subgraph`) is already a method binding the instance's own `shacl_graph` rather than taking it as a parameter. `close_shape(shacl_graph, shape)` as a standalone top-level function was the odd one out.

Implemented: `subgraph_extraction.py`'s `close_shape()` renamed to `_close_shape()` (private, docstring updated to say so and point to the method instead); new `StarShaclSchema.close_shape(self, shape)` method added next to `extract_subgraph()`, raising `ValueError` if `self.shacl_graph` is `None` (unlike the other processing modes, it takes no `data_graph` at all - it operates purely on the bound shapes graph). No longer exported from `starlayer.shacl.__init__` at all - reached only via `StarShaclSchema(shacl_graph=...).close_shape(shape)`.

Call-site migration: `tests/shacl/integration/test_extract_subgraph.py`'s `TestCloseShape` class (4 call sites) updated from `close_shape(prod_shapes, EX.JEShape)` to `StarShaclSchema(shacl_graph=prod_shapes).close_shape(EX.JEShape)`; `starlayer/__init__.py`'s own module docstring had a `starlayer.shacl.close_shape` import-path example, now stale - replaced with `starlayer.shacl.shacl_inference.apply_rules`. `starlayer/graph/graph/shape_derivation.py`'s own private `_close_shape()` is unrelated (confirmed via its own docstring, which explicitly says it's deliberately *not* calling this one) - not touched. Full `tests/shacl` suite: 1048 passed, unchanged from before this move (same count as after the `apply_rules()` flip above - this was a pure relocation, no behavior change).

## Testing discipline: verify coverage adversarially, not just by existence

Before marking a test - or a `docs/shacl12-gap-matrix.md` row - "done" for a native/patched behavior, don't stop at "a test exists and passes." Check whether it would still pass with the change reverted:

- **Fixture-based tests**: could the *old* form (whatever pySHACL, or whatever baseline, did before starshacl's change) already satisfy this exact test? Run the fixture through plain, unpatched `pyshacl.validate()` - no `StarShaclSchema`, no meta-shapes, no native component registration - and confirm it produces the *opposite* result from what starshacl produces. If it doesn't, the test isn't exercising starshacl's own code at all; it's redundant with pySHACL's existing behavior.
- **Meta-shacl well-formedness rules**: confirm a genuinely malformed value is actually rejected, not just that a well-formed value passes. "Passes when valid" and "rejects when invalid" are two different claims - a test covering one does not imply the other.

This is cheap (one throwaway script per feature, not a new test-writing methodology) and catches a real, repeated failure mode: a 2026-07-20 coverage audit found that `sh:ShapeClass` implicit-class-target coverage, `sh:values`'s "done" status, and 8 of the 11 new SHACL 1.2 predicates' malformed-usage tests had all passed review while quietly not testing what they claimed to (see `docs/shacl12-gap-matrix.md` for the specific fixes and reasoning). Every instance had the same root cause: the same pass that wrote the feature also wrote the test confirming it, without ever asking "would this fail if I deleted what I just added?"

**Don't treat a coverage audit's own findings as ground truth either** - verify audit claims against the actual test file before acting on them. The audit above also produced a false claim (that `owl:imports` cycle/loader-failure edge cases were untested, when they already were) - only the empirical check caught it.

## Stale references after a rename: a real, cheap-to-catch failure mode

A 2026-08 sweep found `sh:sparql` fixtures calling `isTripleTerm(...)` - a function name only the old, since-removed `sparql12_to_11.py` text-rewriter ever supported (the current grammar only recognizes `isTRIPLE`) - and the shipped meta-shapes (`starshacl/assets/*.ttl`) still declaring `stsh:` under the pre-rename `pyshacl-starlight` namespace instead of `starshacl`. Both shipped silently for a long time: nothing checks that a fixture's embedded query text, or a namespace prefix, still refers to something that actually exists in the current codebase after a rename.

`tests/unit/test_fixture_sparql_syntax.py` now guards the first half of this (parses every `sh:select`/`sh:ask`/`sh:construct` string in `starshacl/assets/*.ttl` and `tests/fixtures/shapes/*.ttl` against the real grammar - would have caught `isTripleTerm` immediately). No automated guard exists yet for the namespace half; if another rename happens, grep the whole repo (not just `.py` - `.ttl` fixtures and shipped assets too) for the old name/namespace and confirm zero hits before considering the rename done.

## Which predicates belong on a NodeShape vs a PropertyShape form: don't invent it, pySHACL and the W3C draft already encode it

A 2026-08 downstream-editor readiness pass found `stsh:nodeFormField`/`stsh:propertyFormField` (which predicates should render as fields in a NodeShape-editing vs PropertyShape-editing form) only set for 35 of 108 documented predicates. Before designing a new restriction list from scratch, check for a native/vendored one first - this project already had two:

- **pySHACL's own bundled `shacl-shacl.ttl`** (`<venv>/lib/python3.14/site-packages/pyshacl/assets/shacl-shacl.ttl`) encodes exactly this distinction via `shsh:ShapeShape` (targets both `sh:NodeShape`/`sh:PropertyShape`, lists predicates valid on either via `sh:targetSubjectsOf`), `shsh:NodeShapeShape` (explicitly forbids `sh:path`/`sh:lessThan`/`sh:lessThanOrEquals`/`sh:maxCount`/`sh:minCount`/`sh:qualifiedValueShape`/`sh:uniqueLang` on a NodeShape - i.e. PropertyShape-only), and `shsh:PropertyShapeShape` (requires `sh:path`).
- **This repo's own vendored, more complete draft**, `tests/vendor/shacl12-vocabularies/shacl-shacl.ttl` (the official SHACL 1.2 WG draft's meta-shapes, used elsewhere for `docs/shacl12-gap-matrix.md`'s gap comparisons), has the same `shsh:ShapeShape`/`NodeShapeShape`/`PropertyShapeShape` shapes but models more predicates than pySHACL's older bundled copy (`sh:memberShape`, `sh:maxListLength`, `sh:minListLength`, `sh:uniqueMembers`, `sh:singleLine`, among others) - **prefer this one** when the two disagree or when pySHACL's copy is silent on a predicate.

Neither file covers SHACL-AF rule/SPARQL-extension attachment (`sh:sparql`, `sh:rule`) or the newest RDF 1.2 predicates (`sh:someValue`, `sh:subsetOf`, `sh:rootClass`, `sh:uniqueValuesFor`, `sh:reifierShape`, `sh:reificationRequired`) - for those, judge by analogy to the nearest predicate the vendored draft *does* confirm generic or restricted (documented with reasoning in `docs/shacl-presentation-content.md`'s "17. Form-Field Membership" section).

**A predicate that's a field of a nested sub-form (a Rule, ConstraintComponent, Validator, or path/node-expression definition) isn't a NodeShape/PropertyShape form field at all**, and shouldn't be forced into this binary just because it's a `sh:` predicate. `sh:condition`/`sh:select`/`sh:ask`/`sh:construct`/`sh:subject`/`sh:predicate`/`sh:object`/`sh:parameter`/`sh:validator`/`sh:nodeValidator`/`sh:propertyValidator` (nested inside `sh:rule`/`sh:ConstraintComponent`) and the property path operators (`sh:alternativePath`, `sh:inversePath`, `sh:oneOrMorePath`, `sh:zeroOrMorePath`, `sh:zeroOrOnePath`, nested inside `sh:path`) were deliberately left without `nodeFormField`/`propertyFormField` for this reason - a downstream editor needing "which fields belong on a Rule sub-form" needs a separate, not-yet-built mechanism, not a misuse of this one. This is genuine future work, not an oversight.

## `sh:entailment` support (SHACL 1.2 Core §1.4) + closing the global-rules-never-validated gap (2026-10-07)

Built on `starlayer.graph`'s same-day migration to real W3C entailment regime IRIs (`ENTAILMENT.*`, see `starlayer/graph/CLAUDE.md`'s own dated entry) - this module needed no separate IRI↔string translation table as a result, since `infer()` already speaks the exact IRIs a shapes graph's own `sh:entailment` triples carry.

**New `starlayer/shacl/entailment.py`**: `declared_entailment_regimes(shacl_graph)` reads every `sh:entailment` triple's object anywhere in the graph (confirmed shapes-graph-scoped per spec, not per-shape - see the module's own docstring for the exact quotes). `apply_entailment(data_graph, shacl_graph, *, inplace)` resolves and materializes the declared regime(s) via `infer()`.

**Wired into `StarShaclSchema.validate()`** (`validator.py`, right after `normalize_graph_inputs()`): unconditional whenever `shacl_graph is not None` - a no-op for the overwhelmingly common case (no `sh:entailment` declared). This also gives `apply_rules()` "entailment before rule execution" for free, since shape-attached `sh:rule` runs inside this same `validate()` call.

**A real regression found via testing, not assumed correct**: the first version of `apply_entailment()` always mutated `data_graph` in place regardless of the caller's own `inplace` setting - silently breaking `validate()`'s own long-documented guarantee that the plain `"validation"` profile (`inplace=False`) never mutates the caller's data. Confirmed live (`len(data)` grew after a plain `validate()` call using `sh:entailment`) before `apply_entailment()` gained its own required `inplace` keyword, threaded through from `resolve_profile_options(...)['inplace']`: `True` mutates and returns `data_graph` itself (matches `apply_rules()`'s own established contract); `False` returns a *new* graph via `infer(mode="full")`, leaving the caller's original completely untouched. Regression test: `test_sh_entailment.py::test_plain_validation_profile_never_mutates_the_callers_data_graph`.

**`apply_rules()` also closes a second, previously-identified gap in the same change** (not sh:entailment-specific, but the same design session): `RulesResult.conforms`/`report_graph`/`report_text` used to only ever reflect state *before* the separate global `sh:RuleSet`/`sh:SPARQLRule` pass - triples that pass produces were never actually validated at all. Fixed by, after the global-rules loop: (1) re-applying `sh:entailment` on the now-complete `out_data` (`inplace=True` unconditionally - `apply_rules()` always wants the returned `data_graph` fully enriched), then (2) re-validating `out_data` once more with the plain `"validation"` profile (not `"rules"` again - confirmed via reading pyshacl's own `SHACLExecutor` construction that `advanced_mode`/`iterate_rules` are independent flags, so this correctly does NOT re-execute rules a second time) and using *that* call's conformance result instead. Net effect: `apply_rules()` now calls `validate()` twice in every real path - a deliberate, accepted cost increase, confirmed via the full `tests/shacl` suite showing identical rule-iteration counts to before (no accidental double-execution). Regression test: `test_sh_entailment.py::TestApplyRulesValidatesGlobalRuleOutput`.

Full `tests/shacl` suite: 1065 passed (was 1048 before this work - 17 new tests across `test_entailment.py`/`test_sh_entailment.py`), zero regressions. Two existing unit tests (`test_apply_rules_requests_inplace_advanced_mode`/`test_apply_rules_uses_rules_profile_defaults`) needed updating since `apply_rules()` calling `validate()` twice meant their `monkeypatch`-captured kwargs dict reflected a mix of both calls - fixed by capturing a list (one dict per call) and asserting on the first call specifically.

**Known v1 scope limitation, documented not silently assumed**: `apply_entailment()` only sees schema axioms already present in `data_graph` itself - axioms supplied only via `ont_graph` (the more idiomatic place for them) aren't picked up, since folding `ont_graph` in automatically would risk the same inplace-mutation violation just fixed above, in a different form. See `docs/future_enhancements.md`.

## Step 1 of flipping validate()/validate_each()/evaluate() to bare-function-first, matching apply_rules() (2026-10-07)

User's stated general model: every SHACL process should exist as its own public function first; `StarShaclSchema` binds `shacl_graph`/`ont_graph` and delegates to each one - matching the direction `apply_rules()` already flipped to earlier the same day. Confirmed scope directly: `extract_subgraph()`/`close_shape()` are **out of scope** - they already delegate to a private free function internally (so already satisfy the model), and stay method-only on the public surface per an earlier explicit decision this session ("remove close_shape from a separate public function, move it to a method of the Schema"); no public bare form was added or should be for either.

**This is step 1 of two, deliberately split** (user's own framing: "step 1, identify the public functions... ignore the schema class object for now... then we will make those functions methods of the Schema"): build real, standalone `validate()`/`validate_each()`/`evaluate()` bare functions that work completely independently of `StarShaclSchema` - confirmed via tests calling them directly, nothing routed through the class. **`StarShaclSchema.validate()`/`.validate_each()`/`.evaluate()` are deliberately left untouched** - their full method bodies are still there, genuinely duplicated with the new bare functions for now. Making the class delegate (step 2) is a separate, later step - don't do it opportunistically while touching this code for an unrelated reason; wait for it to be asked for explicitly.

Investigated via direct AST analysis before moving anything (not guessed): `validate()`'s 350-line body calls 7 of 12 private helper methods (5 more reached transitively); of those 12, 9 already had zero `self.` dependency at all (pure functions of their own arguments, just defined as methods - a mechanical dedent). ## `apply_rules()`'s `data_graph` becomes strictly the "inference graph" - rule output only, caller's own graph never touched (2026-10-07)

A direct follow-up question ("what graph gets returned, the new triples, or the full graph? I thought it was new triples") led to checking the spec rather than assuming the existing merge-everything-together behavior was right. It wasn't, on two independent counts:

**"New triples" is a real, named spec concept - "the full graph" never was.** The SHACL 1.2 Inference Rules spec: *"The new triples that are produced by a rules engine are called the inferred triples. The inference graph consists of these inferred triples."* That's the one thing the spec actually names. The **evaluation graph** (base ∪ inference) is only ever described as "the active query graph" used *during* rule execution and validation - a working/computational concept, not a stated deliverable. The spec doesn't explicitly say what a processor should return, but `RulesResult.data_graph` merging base + rules + entailment all together (the prior design) had no spec grounding at all - it was this project's own invention.

**Entailment-produced triples specifically should never have been persisted.** SHACL Core §1.4 scopes entailment's role to being visible "during the validation process" - a validation-time device, not domain output. The spec gives zero guidance on merging OWL/RDFS entailment into any returned result. Baking entailment output into `data_graph` means a declared `sh:entailment`/`inference=` regime (which can add a lot of structural noise - universal `rdfs:Resource` typing, reflexive `subClassOf`, etc.) pollutes what's supposed to be "what the rules said."

**User's own explicit design decision, via two rounds of `AskUserQuestion`** (recorded here since neither reads as inevitable from the spec alone):
1. `RulesResult.data_graph` = strictly the inference graph (rule-produced triples only) - not base+rules, not base+rules+entailment.
2. The caller's own `data_graph` object must remain **completely untouched** - not even mutated with rule output. A private working copy is mutated through the whole pipeline instead; only the pure rule-produced delta from that copy gets returned.

**Implementation** (`apply_rules()`, `validator.py`): `base_triples = frozenset(data_graph)` captured before anything happens; `out_data` becomes a fresh `type(data_graph)()` copy (triples + namespace bindings), used for every subsequent step instead of the caller's object. A new `entailment_triples: set` accumulator, filled via a local `_apply_and_track()` helper (snapshot before/after each entailment-producing call) at every one of the three points entailment can run: the "before rules" `sh:entailment`/`inference=` pass (now applied explicitly in `apply_rules()` itself, *before* calling the first `validate(profile="rules", ...)`, rather than left to that call's own internal handling - deliberately redundant with that call's own internal pass, which becomes a no-op since the regime is already satisfied, matching the project's existing "accept redundant idempotent re-application" pattern), and both "after rules" re-applications (`sh:entailment`, `inference=` - already explicit call sites, just wrapped with the same tracking). At the end: `inference_graph = type(out_data)()` filled with `frozenset(out_data) - base_triples - entailment_triples` - that's what `RulesResult.data_graph` now is. `conforms`/`report_graph`/`report_text` are completely unaffected - still computed by the final `validate(out_data, ..., profile="validation")` call over the complete, unfiltered evaluation graph.

The `StarLayerGraph` input-type requirement stays (rule output still needs RDF-1.2 triple-term round-tripping), but its own stated rationale changed - it's no longer "so `inplace` mutation lands on the right object" (there's no `inplace` mutation of the caller's object anymore), just "so the private working copy can hold triple terms correctly."

**Real test breakage found via the full suite, not assumed clean** - 6 failures, every one exactly the expected kind (asserting a base or entailment-produced triple was present in `result.data_graph`, or asserting `result.data_graph is data_graph`): `test_rules_flow.py` (both tests asserted the old identity-mutation contract directly - rewritten to assert the opposite: caller's graph unchanged, rule output only in the new `result.data_graph`), `test_expected_predicate.py::test_expected_predicate_does_not_override_an_existing_value` (was checking a base triple's value via `result.data_graph` - fixed to check `data` instead, which is what the test actually meant to verify), `test_rule_condition.py::test_condition_over_rdf12_triple_term_valued_property` (same pattern - a base RDF-1.2 triple term, checked via `data` now), `test_sh_entailment.py::test_rule_targeting_entailed_class_fires` and `test_pyshacl_inference_compat.py::TestInferenceSurvivesApplyRulesGlobalRulePass` (both asserted an entailed triple was present in `result.data_graph` - flipped to assert absent, since that's now correct by design).

Full `tests/shacl` suite: 1081 passed (same count - fixes, not additions, apart from one new explicit "caller's graph untouched" assertion folded into existing tests), zero regressions once the 6 above were updated. Full non-`shacl` suite also run (`tests/graph`, etc.) - one unrelated, pre-existing failure found (`test_oxigraph_backend.py::test_multi_graph_data_merges_correctly`, a `StarLayerGraph.parse()` multi-graph nquads limitation, nothing to do with this change), everything else green.

## `evaluate()` gains `sh:entailment`/`inference=` support, with a deliberately different design than `apply_rules()`'s own exclusion (2026-10-07)

Direct follow-up, same session: having just finished making `inference=` consistent across `validate()`'s two implementations, the user asked "should evaluate allow for inference? seems so to be consistent" - confirmed a real gap, not just a doc gap: `evaluate()` had no `**kwargs`, no `inference=`, and never read `shacl_graph`'s own `sh:entailment` declarations either, unlike every other processing-mode function. Concretely: a focus node that's only a member of `sh:targetClass ex:Employee` via an entailed fact (e.g. `rdfs:domain`) would never even get its virtual properties computed, since target resolution ran against raw `data_graph` with no entailment applied at all.

**A real design fork, confirmed via `AskUserQuestion` rather than assumed**: once entailment makes a node a valid target, should an entailed (non-asserted) triple also count as a "real, stored" value for a property shape's own `sh:path` in the returned subgraph? Two defensible answers - either exclude entailed triples from the result the way `apply_rules()` excludes entailment from its own "inference graph" (entailment only helps correctly compute something else, never contributes to the output itself), or let entailment feed the whole computation uniformly, the same way `validate()` already treats an entailed triple identically to an asserted one when checking constraints. **User chose the latter** - confirmed as the better fit on reflection too: SHACL Core's own "Value Nodes of Property Shapes" algorithm doesn't itself distinguish asserted from entailed triples at all, whereas `apply_rules()`'s "inference graph" is a different, additive concept (newly-produced facts) that entailment was never part of in the first place - these are two genuinely different relationships to entailment, not an inconsistency to resolve in favor of one or the other uniformly.

**Implementation**, both the bare `evaluate()` function and `StarShaclSchema.evaluate()`'s own (still-duplicated) method body: new keyword-only `inference: str | None = None` parameter (not a generic `**kwargs` - `evaluate()` has no other passthrough options, so an explicit parameter is more precise). Right after the `shacl_graph is None` check, `apply_entailment(data_graph, shacl_graph, ont_graph, inplace=False)` and (if `inference` given) `_apply_pyshacl_inference(data_graph, inference, ont_graph, inplace=False)` reassign `data_graph` to a private, non-mutating copy - `inplace=False` unconditionally, since `evaluate()` has always guaranteed it never mutates the caller's own `data_graph`, entailment or not (the common no-entailment-declared case is a no-op passthrough of the same object either way). Every subsequent step - target-node resolution, `sh:values`/`sh:defaultValue` computation, and the "stored" value reads - then runs against that entailed copy uniformly, with no special-casing needed anywhere else in the function.

Verified live: a property shape targeting `ex:Employee` with an `rdfs:domain`-only-in-`ont_graph` axiom computes nothing at all without `inference="rdfs"`, and correctly includes the real `ex:worksAt` value once given it - confirming both the targeting effect and the "entailment feeds stored values too" design choice work together. Full `tests/shacl` suite: 1083 passed, zero regressions (no existing test exercised entailment through `evaluate()` before, since the capability didn't exist).

## `extract_subgraph()` gains `sh:entailment`/`inference=` too - but with the *opposite* design choice from `evaluate()` (2026-10-07)

This module has its own pre-existing, explicit design decision 5 (its own docstring, predating this session): *"Only real, stored triples are ever included - never a synthesized triple for an `sh:values`-computed or otherwise virtual value."* An entailed triple is arguably "otherwise virtual" under that framing. **User chose to keep decision 5 strict** - the opposite choice from `evaluate()`'s own: entailment fixes the conformance check and traversal, but the extracted output stays strictly real/stored triples, matching `apply_rules()`'s own precedent (entailment as a computational device, never persisted) rather than `evaluate()`'s "feeds everything uniformly" choice. **Implementation** (`subgraph_extraction.py::extract_subgraph`): new `ont_graph: Any | None = None` positional parameter (this function had never accepted one at all until now) and keyword-only `inference: str | None = None`. `base_triples = frozenset(data_graph)` captured first, from the pristine original; `apply_entailment(data_graph, shacl_graph, ont_graph, inplace=False)` and (if given) `_apply_pyshacl_inference(...)` build a private, non-mutating `entailed_data_graph`, which `_shape_conforms()` and `_extract()` are called against instead of the original - no changes needed inside either of those functions themselves, since both already take `data_graph` as an explicit parameter and thread it through every recursive call. After extraction, `triples &= base_triples` strips any entailed-only triple back out before building the result graph.

**A real, pre-existing bug found and fixed along the way, not introduced by this work**: `StarShaclSchema.extract_subgraph()`'s own method body called `normalize_graph_inputs(data_graph, self.shacl_graph, None)` - hardcoding `None` instead of `self.ont_graph`, silently discarding whatever ontology graph the instance was actually constructed with. Found because entailment needed a real `ont_graph` to be useful here at all; fixed by passing `self.ont_graph` through properly.

Verified live: a shape requiring `sh:class ex:Employee` on `ex:alice ex:boss ex:bob` (`ex:bob` only an `Employee` via an `rdfs:domain` axiom in `ont_graph`) correctly fails to conform without `inference="rdfs"` and conforms with it - and even then, the extracted subgraph contains only the real `(alice, boss, bob)` triple, never the entailed `rdf:type` fact. ## `inference=` disconnected from pySHACL's own string vocabulary - now takes the same real `ENTAILMENT.*` IRIs `sh:entailment` does (2026-10-08)

## `target_nodes()` gains `inference=`/`ont_graph`/`sh:entailment` support, closing the last consistency gap (2026-10-08)

Direct follow-up, same conversation: the user asked why `target_nodes()` was the one processing function without `inference=`, when `docs/api-reference.md` already called this out explicitly ("not `target_nodes()`, which doesn't take entailment at all"). Checked honestly before just adding it: this was never a documented, reasoned architectural boundary - the doc line stated the fact with no rationale anywhere, and grepping `CLAUDE.md` turned up nothing. The one real argument *for* leaving it alone - `target_nodes()` is a single atomic lookup, not an orchestration of several steps that need to agree on one entailed view the way `extract_subgraph()` (conformance re-check + extraction walk) or `validate()` (target resolution + constraint checking) are - doesn't actually hold up as a reason to withhold the *parameter*: a caller wanting entailed-aware targets could technically pre-entail `data_graph` themselves via the already-public `StarLayerGraph.infer()`, but couldn't get the "shapes graph's own declared `sh:entailment` is honored automatically" half of the convenience, since `declared_entailment_regimes()`/`apply_entailment()` are private to `starlayer.shacl`. Concluded this was an oversight, not a boundary - recommended adding it, user agreed.

**`engine/core.py`'s `target_nodes()`** gained two new parameters, both optional: `ont_graph: Any | None = None` (it had none before at all - the other four processing functions all do) and `inference: Any | None = None`. Implementation: swapped the old two separate `normalize_to_starlayer_graph()` calls for one `normalize_graph_inputs(data_graph, shacl_graph if shacl_graph is not None else data_graph, ont_graph)` call (consistent with `evaluate()`/`extract_subgraph()`'s own pattern), then `data = apply_entailment(data, graph, ont, inplace=False, inference=inference)` (local import, matching this module's own import style elsewhere) before resolving targets against the entailed copy - same "computed over data_graph ∪ ont_graph, only the delta materialized, neither graph mutated" behavior as every other processing function, via the identical shared `apply_entailment()` helper, not a separate reimplementation.

**`StarShaclSchema.target_nodes()`** gained the `inference: Any | None = None` keyword and now threads `self.ont_graph` through to `native_target_nodes()` (previously always passed `None` implicitly, by simply never passing it at all) - matching every sibling method's own "bind `self.shacl_graph`/`self.ont_graph`, accept `inference=`" pattern.

**One real, minor trade-off accepted, not hidden**: `target_nodes()` is called internally, twice, by `validate()`'s own native-component fast path (`_try_native_literal_only_validation`/`_try_native_structural_property_validation`) - at both call sites, `data_graph` passed in is already the entailed copy `validate()` itself produced earlier in the same call. Neither call site passes `inference=`/`ont_graph` explicitly, so this is a no-op addition there in the common case - but if `shacl_graph` declares `sh:entailment`, those internal calls will now redundantly re-run the same entailment regime a second time, over already-closed data, every time this native fast path's target-resolution loop executes. RDFS/OWL-RL closure is a monotonic fixpoint, so the *result* is unaffected (confirmed: full suite - including every `test_sh_entailment.py` case exercising exactly this combination - stayed green), but it's wasted work in that one specific combination (triple-term graph + native fast path taken + `sh:entailment` declared). Not fixed further this round - fixing it would mean threading an "already entailed, skip my own pass" flag through two internal call sites for a case that's both rare and merely wasteful, not incorrect; flagged here for whoever next touches that fast path's own performance.

New regression coverage: `test_sh_entailment.py::TestTargetNodesRespectsEntailment` (five cases - no-entailment baseline, `inference=` keyword, declared `sh:entailment` with no keyword, `ont_graph`/`data_graph` both left unmutated, and the `StarShaclSchema` method threading its own bound `ont_graph`), reusing the same `DATA`/`SHAPES` fixture (`ex:worksAt rdfs:domain ex:Employee`) the file's existing `validate()` entailment tests use - deliberately not a vacuous `rdfs:subClassOf` case, since SHACL's own "SHACL type" closure already handles that unconditionally with no entailment regime needed at all (see `test_subclass_reasoning_scope.py`).

Full `tests/shacl` suite: 1093 passed (5 new), zero regressions.

## `StarShaclSchema` gains constructor-bound `data_graph`/`inference`, so several methods can share one data graph (2026-10-08)

Direct follow-up, same conversation: the user asked for three related changes to `StarShaclSchema` specifically (not the bare top-level functions, which are untouched): (1) move `inference` from a per-method keyword to the constructor, (2) add a default `data_graph` property, (3) let every method be called with either its own `data_graph` argument or nothing, falling back to that default - "this would allow a user to perform different methods on the same data graph."

**Constructor**: `__init__` gained two new keyword-only parameters, `data_graph: Any | None = None` and `inference: Any | None = None`. `data_graph` is normalized once at construction exactly like `shacl_graph`/`ont_graph` already are (`normalize_to_starlayer_graph(data_graph, name="data_graph")`), stored as `self.data_graph`. `inference` is stored raw as `self.inference` - no normalization needed, it's just an IRI (or iterable of them) threaded straight into `apply_entailment()` calls, same as before.

**New private helper**: `_resolve_data_graph(self, data_graph)` - returns `data_graph if data_graph is not None else self.data_graph`, raising `ValueError` ("No data_graph given, and this schema has no default data_graph bound at construction...") if both are `None`. Every processing method calls this once at the top of its own body.

**Every processing method's own `data_graph` parameter became optional** (`Any | None = None`), resolved via the helper above: `validate()`, `apply_rules()`, `evaluate()`, `extract_subgraph()`, `target_nodes()`. `validate_each()`'s own `data_graphs` (plural) became optional too, falling back to `(self.data_graph,)` - a single-element tuple, since `validate_each()` itself just loops `self.validate()` per item and that already raises if `self.data_graph` is also `None`.

**`extract_subgraph()`'s `shape`/`focus_node` moved to keyword-only** (`*, shape, focus_node` after the now-optional `data_graph`) - Python requires every parameter after the first one with a default to also have a default, and `shape`/`focus_node` are genuinely required with no sensible default. Confirmed via grep before reordering: every existing caller (all of `test_extract_subgraph.py`) already passed both by keyword, so this needed no call-site fixes.

**`inference` removed entirely from every method's own signature** - not just defaulted, actually gone - and each method now passes `inference=self.inference` explicitly wherever it used to forward a per-call `inference` value:
- `evaluate()`/`extract_subgraph()`/`target_nodes()` had no `**kwargs` catch-all in their signatures, so removing the parameter means passing `inference=` to any of them now raises a natural `TypeError: got an unexpected keyword argument 'inference'` - no extra guard code needed.
- `apply_rules()` still has `**kwargs` (forwarded to the module-level `apply_rules()` function, which reads `inference` out of it via `kwargs.get("inference")` - unchanged, still the real implementation's own mechanism). The method now explicitly passes `inference=self.inference` alongside `**kwargs` in the same call - if a caller's `kwargs` *also* contains `inference` (passed to the method), Python's own "multiple values for keyword argument" `TypeError` fires automatically on the forwarding call. No custom guard needed here either.
- `validate()` is the one case that genuinely needed an explicit guard: its own `**kwargs` flows into `resolve_profile_options(profile, overrides=kwargs)` → a plain `options` dict, not into another function call with an explicit duplicate `inference=` - so Python's automatic duplicate-keyword protection doesn't trigger on its own. Added `if "inference" in kwargs: raise TypeError(...)` at the top of the method body, with a message pointing at the constructor. The old `inference_option = options.pop("inference", None)` line (which only ever existed to intercept a per-call value before forwarding the rest of `kwargs`/`options` onward) is now just `inference_option = self.inference` directly - the guard above means `options` can never actually contain `"inference"` by the time that line runs, so the `.pop()` became unnecessary and was dropped.

**One pre-existing, already-dead line left untouched, not "fixed" further**: `validate()`'s `meta_shacl` preflight block calls `meta_validate(shacl_graph, inference=options.get("inference"), ...)` - this reads pySHACL's own *string* vocabulary (`"rdfs"`/`"owlrl"`/etc., a different meaning entirely from this project's `ENTAILMENT.*` IRIs), and was already always `None` by the time it ran even before this change (the value was popped out of `options` earlier in the same method, for an unrelated reason, well before 2026-10-08). Confirmed via `grep` that no built-in profile ever sets `"inference"` as a default option. Out of scope here - a separate, pre-existing quirk this change didn't create and doesn't make any worse.

**Fallout fixed**: two existing tests called `StarShaclSchema(...).validate(..., inference=...)`/`.target_nodes(..., inference=...)` directly - `test_starlayergraph_dataset_input.py::TestOntGraphDatasetAutoUnion::test_ont_graph_named_graph_content_visible_without_explicit_default_union` and this same session's own new `test_sh_entailment.py::TestTargetNodesRespectsEntailment::test_starshaclschema_method_threads_its_own_bound_ont_graph` - both updated to construct `StarShaclSchema(..., inference=ENTAILMENT.RDFS)` instead of passing it per call. Confirmed via grep across every `.ipynb` guide under `docs/` that no notebook calls a `StarShaclSchema` method with `inference=` either (the one `inference=` hit found in a notebook was `starsparql.validate()` - an unrelated module - not this class).

New regression coverage: `test_validator.py::TestBoundDataGraphAndInference` (eight cases - bound `data_graph` used when omitted, by both `validate()` and `target_nodes()`; a per-call `data_graph` overriding the bound default without disturbing it; the motivating multi-method workflow itself, calling `validate()`/`target_nodes()`/`evaluate()`/`apply_rules()` on one constructed schema with no `data_graph` repeated anywhere; the clear `ValueError` when neither is given; `inference` bound at construction actually feeding `validate()`'s own entailment pass; `inference=` passed per-call raising `TypeError` on all four affected methods; `validate_each()`'s own fallback).

Full `tests/shacl` suite: 1101 passed (8 new), zero regressions.
