# CLAUDE.md

Project-specific instructions for Claude Code sessions working in this repo. See `docs/guides/README.md` for the docs index (start with `packages/starlayer/docs/shacl/implementation-plan.md`).

## Rules that bite

- **This wraps pySHACL; it does not replace it.** Several pySHACL bugs are fixed by process-global monkeypatches in `validator.py` (idempotent, sentinel attributes `_starlayer_shacl_*_patch`). Triple terms reach pySHACL through `TripleTermAdapter` (`adapters.py`), which uses its own private `urn:starlayer:tt:` encoding, separate from the graph's storage encoding.
- **Shape of the API.** The processing functions are flat in `starlayer.shacl`: `validate`, `validate_each`, `apply_rules`, `evaluate`, `target_nodes`, `extract_subgraph` (a function only, no method). `StarShaclSchema(shacl_graph, ont_graph, data_graph, inference, scoring_graph)` binds the inputs once and delegates; `close_shape`, `extract_shapes_graph` and `select_widgets` are methods. Qualified-only on purpose: `starlayer.shacl.engine`, `shacl_profiling`. Do not widen `__all__` without a decision.
- **Results.** `ValidationResult`; `RulesResult(inferred_graph, validation)`, where `inferred_graph` is only what the rules produced and the caller's data is never touched; `evaluate()` and `extract_subgraph()` return a plain graph.
- **`mode=` is a validator option preset** (`validation_modes.py`), not a SHACL Profile. "Profile" means only the SHACL 1.2 Profiling spec (`shacl_profiling`).
- **`meta_shacl` is off by default.** The meta-shapes are built, not assembled at run time: edit `scripts/assets/shacl12-validation-shapes.ttl`, run `python scripts/build.py`, and the library reads the stored `starontology/shacl12-shacl.ttl`. A test fails if the stored file drifts from a fresh build. **The base is the W3C Working Group's own SHACL-for-SHACL, pinned in `scripts/assets/vendor/` and only ever added to** (never delete or edit its triples; relax a rule with `sh:deactivated true` and put the replacement in the asset). See the 2026-10-21 entry.
- **Entailment uses the graph package's IRIs** (`inference=ENTAILMENT.RDFS`, or `sh:entailment` in the shapes). pySHACL's string options (`"rdfs"`, `"owlrl"`) are rejected on purpose.
- **`owl:imports` that are not already in the shapes graph raise** in `validate()` unless you pass a loader (`shapes_graph_loader=`) or `ignore_imports=True`. Nothing is fetched on its own.
- **`shapes_graph_resource=`** selects a named `sh:ShapesGraph` module of the bound shapes graph (its IRI becomes `sh:usedShapesGraph`), or is only a provenance tag when the graph does not contain it. With no bound shapes graph it raises.
- **Reports.** `report_text` and `report_graph` must agree on what the report knows: no "Not specified" placeholders, and the `Conforms:` line is rewritten when SHACL 1.2's `sh:Debug`/`sh:Trace` severities change the result. The `sh:conformsTo` derivation is automatic when both graph identities are known.
- **A passing test is not proof.** Before calling a fix done, run the fixture through plain `pyshacl.validate()`; if it gives the same answer, the test proves nothing about our code. For meta-shapes, check that a malformed value is rejected, not only that a valid one passes.
- **The six SHACL 1.2 documents are all still moving.** Status and procedure: `packages/starlayer/docs/shacl/shacl12-gap-matrix.md`, "Tracking Upstream Spec Changes".

## Design history

## Fixes from the second hunt (2026-10-25, GitHub issue #82)

- **`sh:TripleRule`** (`triple_rule.py`, installed by `register_native_components()`): a missing `sh:subject`/`sh:predicate`/`sh:object` defaults to the focus node (Inference Rules 11.2; pySHACL raised `RuntimeError: No sh:subject`, which the spec's own Examples 11 and 12 hit), and a triple with a literal subject or a non-IRI predicate is skipped ("Skip ill-formed triples"). `TripleRule.__init__` and `.apply` are replaced; `apply` looks `nodes_from_node_expression` up in pySHACL's module at call time so the `shnex:` patch still works.
- **Single-valued `sh:nodeKind`** (`sh:IRI`, `sh:BlankNodeOrIRI`, `sh:IRIOrLiteral`, ...) no longer accepts a triple term: pySHACL's component sees the encoded triple term as an IRI, so these kinds are now matched by our component (`_UNION_NODE_KINDS`), like the list form.
- **`close_shape()`** crashed for any shape without a class (`sh:ShapeClass` is not in rdflib's `SH`): `subgraph_extraction` now has its own `Namespace`. **`rule_set=`** accepts an iterable of rule sets, as documented.
- **`^path` over a composite path** (`sh:inversePath` of a sequence, alternative, repetition or another inverse) is walked by `subgraph_extraction._walk_inverse`; `path_values` and `extract_subgraph` agree with SPARQL `^(...)` (a test compares them on small graphs). **Not fixed: `validate()` itself** still uses pySHACL's path evaluation, which follows nothing for those paths (plain pySHACL gives the same wrong answer: an upstream bug, to be written up).
- **Left, pySHACL behaviour:** `sh:lessThan` on IRIs and language strings conforms (pySHACL uses Python ordering; the spec says SPARQL `<`, so these are errors), an empty `sh:or ()` raises `ShapeLoadError`, `sh:minLength 0` on a blank node conforms, and a global `sh:SPARQLRule` ignores `sh:prefixes`. Decide before changing any of them.

## Node expression fixes from the third hunt (2026-10-25, GitHub issue #95)

`sh:nodeByExpression` evaluates its expression at **each value node** (it was evaluated once at the outer focus node, so a shape named by a value node's own triples never applied). `shnex:sum` promotes across numeric types (a `float`/`double` in the input makes a float sum; decimal and double inputs used to raise `TypeError`) and raises `ValueError` for a non-numeric literal. `shnex:min`, `max` and `orderBy` use `_sort_key`, a total order following SPARQL ORDER BY (blank nodes, IRIs, then literals; numbers by value, date and dateTime together with a missing zone read as UTC, strings by lexical form and language): mixed types, a date against a dateTime and a zoned against a zone-less dateTime no longer raise, and an IRI is below every literal. `shnex:distinct` compares language tags case-insensitively; a negative `limit`/`offset` raises `ValueError` instead of slicing from the end. **Still open in #95:** the `sparql:` function expressions take the first output of a multi-valued argument (the spec makes it an error), `sparql:logical-or/and/not` do not handle unbound or error arguments the SPARQL way, arguments of custom function calls are evaluated without the caller's scope, `shnex:instancesOf` with a non-IRI class returns `[]` instead of failing, and `shnex:conformsToShape` does not treat its shape argument as an expression.

## Fixes from the third hunt: native fast path, deactivated shapes, triple-term value nodes (2026-10-26, GitHub issues #94 and #104)

- **The native fast paths for graphs holding a triple term** (`_try_native_literal_only_validation`, `_try_native_structural_property_validation`, module functions and `StarShaclSchema` copies) checked one component per property shape and silently dropped everything else (`sh:minCount`, a second constraint, `sh:deactivated`, `sh:severity`, `sh:message`, other shapes). They now run only when `_native_fast_path_shapes_are_plain` says the shapes graph holds nothing else (node shapes with targets/`sh:property`/annotations, property shapes with `sh:path` plus the one component, and no other subject with a `sh:` predicate); otherwise pySHACL validates. `engine/core.build_report` wrote `sh:type` instead of `rdf:type` and no `sh:resultSeverity`; fixed.
- **`apply_rules()` and `evaluate()` honour a literal `sh:deactivated true`** on a node shape (its rules / its property shapes' values) and on a property shape. pySHACL only honoured a rule's own flag.
- **List-valued `sh:datatype`** now rejects an ill-typed literal (`"nope"^^xsd:date`), like the single-valued form (`_matches_any_datatype_encoded` checks `Literal.ill_typed`).
- **Triple terms as value nodes:** a triple term has no properties, so `sh:closed` (both forms) skips it and a property shape on it has no values (`_patched_value_nodes`); `sh:pattern`/`sh:minLength`/`sh:maxLength` fail it wherever they sit (they were measuring the adapter's `urn:starlayer:tt:` URI when nested in `sh:node`/`sh:or`/`sh:and`).
- **Module-level `validate()`** takes `shapes_graph_resource=` (it was silently ignored) and raises `TypeError` for a keyword neither StarLayer nor pySHACL knows (`_reject_unknown_validate_options`, also on `StarShaclSchema.validate`, skipped for a custom `validate_fn`). Validating an extracted module no longer crashes on a `sh:property` link to a named property shape that is not a member: the link is dropped for validation only (`extract_shapes_graph()` still leaves it dangling, deliberately).
- **`sh:nodeKind`** violations carry pySHACL's `sh:resultMessage` ("Value is not of Node Kind sh:IRI"); an invalid `sh:pattern` raises `ConstraintLoadError` naming the shape, not a raw `re.error`.
- **Still open:** `sh:pattern` is Python `re`, not XPath (`\p{L}` is rejected as invalid); a path that goes through a triple term (`(ex:p rdf:object)`) and an `sh:sparql` constraint on a triple-term value still see the adapter's support triples; `sh:targetWhere` never targets literals; global `sh:SPARQLRule` swallows a bad CONSTRUCT and a SELECT in `sh:construct` yields ill-formed triples; `rule_set=` for `sh:TripleRule` was fixed in #107; the Turtle 1.2 parser rejects `([a b][c d])`; `sh:lessThan`, an empty `sh:or ()` and `sh:minLength 0` on blank nodes are still undecided (see the 2026-10-25 entry).

## Forms for every kind of SHACL element; placement scheme; `sh:declare` (2026-10-26, GitHub issues #12, #89, #91, #92, #105, #67)

## `target_nodes()` covers every target form; `sh:targetNode` takes a node expression; list `sh:condition` pinned (2026-10-26, GitHub issues #66 and #67)

- **#66, `target_nodes()`** (`engine/core.py`, so also `StarShaclSchema.target_nodes()`) returns the nodes `validate()` reports on for every target form, and a test compares the two per form (`tests/shacl/integration/test_hunt3_targets.py`: every shape fails on its focus nodes so the report names them). It does not duplicate the validator: it calls the validator's own `_augment_shapes_with_new_target_types` (sh:targetNode as `sh:select` or `shnex:`/`sparql:` expression, `sh:targetWhere`, data-graph `sh:shape`, implicit class targets) on a copy of the shapes graph with the OTHER shapes' `sh:targetNode`/`sh:targetWhere` removed (so only this shape's nested validations run), then reads plain `sh:targetNode`. `sh:target [ a sh:SPARQLTarget ]` and custom target types go through pySHACL's `Shape.focus_nodes()` with `set_advanced(True)`, as `validate(advanced=True)` does. Before: `[]` for `sh:targetWhere`/`sh:target`, the expression's blank node itself for an expression, and `sh:targetClass` ignored `rdfs:subClassOf` (validate follows it). Cost: a `sh:targetWhere` shape runs its nested validation on every call. A literal node is never a `sh:targetWhere` target (open since #53).
- **#66, meta-shapes.** The Working Group's `sh:targetNode sh:nodeKind sh:IRIOrLiteral` rejected an expression. `sh:targetNode` joins `RELAXED_PATHS` (deactivated by structure in `scripts/build_meta_shapes.py`, `test_wg_overrides.py` fails when the WG relaxes it) and `stsh:ShapeShapeOverrides` has the replacement: `stsh:TargetNodeValueShape` = IRI or literal, or a blank node that is a well-formed `stsh:NodeExpressionShape` or carries `sh:select`; `sh:targetNode [ ex:random 1 ]` is still rejected. Regenerated `shacl12-shacl.ttl` and `starontology.trig` are in a separate commit.
- **#67 item 3 (`sh:condition ( ex:A ex:B )`, "Validation path too deep") could NOT be reproduced** with pySHACL as installed here: `validate()`, `apply_rules()` (TripleRule and SPARQLRule), `evaluate`, `extract_subgraph`, `close_shape`, `meta_shacl=True`, shapes-as-data, entailment with the vocabulary, deep path grammar in the condition shape, lists of 1-4 shapes, all agree with the single-shape form. pySHACL's `SHACLRule.get_conditions()` already walks a list with `shapes_graph.items()` and `filter_conditions` requires every condition to hold, which is the specified meaning ("a focus node must conform to all of the shapes in the list"); `native_components.shape_reference_nodes` already types each member. Tests pin that semantics (`TestRuleConditionList`: a focus node conforming to only one of two listed shapes gets no rule output). One real oddity found while looking: the vocabulary gives `sh:condition` `rdfs:range sh:Shape`, so `shape_types.infer_types()` types the LIST HEAD as a node shape (a list cell treated as a shape). It is harmless in every run above, and fixing it needs the layer-0 rule for `sh:condition` values in `shacl12-shacl-rules.ttl` to skip lists; left alone. If the reporter still sees the error, a reproducing shapes graph is needed.

## Public path and shapes-graph helpers (2026-10-24, GitHub issues #30 and #17)

`starlayer.shacl.paths` (`path_values(data_graph, focus, path, shapes_graph=None)` returns the value nodes at the end of a SHACL path written in one graph and followed through another; `is_inverse(shapes_graph, path)` is true for a top-level `sh:inversePath`) wraps the private `_walk_path` of `subgraph_extraction`, which also returns the traversed triples. `starlayer.shacl.shapes_graphs` (`shapes_graphs(graph)`, `shapes_graph_members(graph, iri)`) holds the Profiling section 2 membership rules (`rdfs:member`, `rdfs:isDefinedBy`, `owl:imports` among local `sh:ShapesGraph` nodes); `StarShaclSchema.extract_shapes_graph()` is built on it. Both are **qualified imports, not in `__all__`**, like `shape_types`. `shapes_graph_members` returns `None` for an IRI that is not a `sh:ShapesGraph` and raises `ValueError` for an import that is not one; members are elements of any kind, not only shapes. Use `Namespace("http://www.w3.org/ns/shacl#")`, not `rdflib.namespace.SH`: the latter has no SHACL 1.2 terms.

## Shape typing is a rule set: `shacl_shacl_rules` and `shape_types.infer_types()` (2026-10-24, GitHub issues #24, #27, #28)

Core 3.1-3.3 leave a shape's type to the engine, and a shapes graph usually states none. The user's decision: express the inference as **SHACL rules** (what the structure of a shapes graph entails about it), not as application code. `starontology/shacl12-shacl-rules.ttl` (registry `shacl_shacl_rules`, hand-edited, a companion of `shacl_shacl`) holds them: **layer 0** says what is a `sh:Shape` (subject of a target or constraint parameter; value of a shape-valued parameter; member of a list that is the value of `sh:and`/`sh:or`/`sh:xone`, found by the path `( [ sh:zeroOrMorePath rdf:rest ] rdf:first )`), **layer 1** says which kind (`sh:path` makes a property shape, a `sh:not` of that a node shape) and combines `sh:Validator` with `sh:SPARQLAskExecutable`/`sh:SPARQLSelectExecutable`. Layers matter: a list member with no constraints of its own is typed in layer 0 and then gets its kind in layer 1.

`starlayer.shacl.shape_types.infer_types(shapes_graph)` (qualified import, not in `__all__`) runs RDFS entailment over the shapes graph plus `shacl_vocabulary` (for non-shapes: `sh:PropertyGroup`, `sh:ConstraintComponent`, ...), then the rules, and returns only the new `rdf:type` triples in the `sh:` namespace. It removes the vocabulary's domain for `sh:name`/`sh:description`/`sh:order` first (a property group has them; the vocabulary says `sh:Shape`). **Drift guard:** a test fails if `shacl_shacl`'s `shsh:ShapeShape` targets a parameter the rules do not list. Needs the optional `owlrl`. Not done: dropping an inferred type when a more specific one is present (a display choice for the caller).

## A shape has at most one `rdfs:isDefinedBy`, as a warning (2026-10-23, GitHub issue #18)

Profiling 2.4/2.5 give a shape one definer (`rdfs:isDefinedBy`) and any number of users (`rdfs:member`) but state no limit, so `stsh:ShapeDefinedByOneGraphShape` (targets `sh:NodeShape` and `sh:PropertyShape` only; a validation report also uses the predicate, 5.4.1) puts `sh:maxCount 1` at **`sh:Warning`** on the property shape (severity on the node shape does not reach a nested property shape's results). **`meta_validate()` now defaults `allow_warnings=True`**, so a warning is in the report but does not make a shapes graph invalid; a form still sees the maximum of one.

## Layering of `shacl_shacl` decided (2026-10-23, GitHub issue #23)

The user's decision: **the rules, node-expression, SPARQL and constraint-component shapes stay in `shacl_shacl`** (they describe SHACL itself); **the UI goes in the UI companion.** So `stsh:ShuiPredicateShapes` and `stsh:WidgetScoreShape` moved from `scripts/assets/shacl12-validation-shapes.ttl` to `scripts/assets/shacl12-shacl-ui-overlay.ttl` (registry entry `shacl_shacl_ui`). **Consequence:** they validate only when the UI graph is loaded beside `shacl_shacl` (`meta_validate(shapes, extra_graphs=[get_ontology_graph("shacl_shacl_ui")])`); plain `meta_validate()` no longer checks `shui:` terms. This is the one place the UI graph has `sh:target*`; the form shapes still have none. The three `shui:` fields kept their `sh:nodeKind sh:IRI` by stating it in the overlay. Splitting `shacl_shacl` further by domain is a separate investigation (a new issue).

## `extract_subgraph()` is the shape fragment of the paper; the Conformance Theorem is its contract (2026-10-23, GitHub issue #11)

Compared with Delva et al., *Shape Fragments* (arXiv 2112.11796) and its companion specification; write-up in `docs/shacl/shape-fragments-comparison.md`. Four of eleven test cases failed and the target triples were missing, so three changes were made (the user agreed to all three):

- **Target triples are included by default** (`include_targets=True`; `False` returns only what the constraints read). A fragment without them passes validation vacuously, because its nodes are no longer targeted. `_close_shape` adds `sh:ignoredProperties` for `rdf:type` (and a target-subjects-of predicate) so a derived closed shape still accepts the fragment.
- **`sh:class` keeps the value's type path** (`_type_paths`).
- **`sh:not` is handled by returning a superset**: the negated shape's *full trace* (every triple it reads), not the paper's minimal witness. The Sufficiency Lemma allows returning more. The same `full_trace` flag is used for `sh:qualifiedMaxCount` (non-qualifying values), for the disjuncts of `sh:xone` that do not hold, and for every branch of `sh:or`; `qualifiedMinCount` narrows to qualifying values only when it is the only qualified constraint.

**Oracle:** `tests/shacl/integration/test_shape_fragments_paper.py`. Keep the focus node as an explicit `sh:targetNode` when checking that the fragment still conforms, or the check is vacuous. It includes a Hypothesis test over generated shapes and graphs; mutation-checked (removing class evidence, or the `sh:not` branch, fails it).

## UI companions of `shacl_shacl`: `shacl_shacl_ui` and `shacl_ui_baseline` (2026-10-21)

Two hand-edited files in `starontology/`, registered like the others (GitHub issues #12 and #10). Neither changes what validates.

- **Form shapes (2026-10-22, GitHub issue #25).** `shacl_shacl_ui` now carries **form shapes**, generated at build time: `stsh:NodeShapeForm` and `stsh:PropertyShapeForm` (and two hand-written ones, `stsh:PropertyGroupForm` and `stsh:ShapesGraphForm`), each a node shape whose property shapes are the fields of that kind of node, so a tool passes one to `select_widgets` as `shape_node` and builds nothing. **Why:** `shacl_shacl` is many small shapes that mostly target the *subjects of one predicate*, which is right for validation and wrong for a form (a shape with no `sh:name` yet has no `sh:name` field; `sh:path` sits in `shsh:PropertyShapeShape`, which only applies to values of `sh:property`; `sh:property` is in no property shape). **The source is `scripts/assets/shacl12-shacl-ui-overlay.ttl` (hand-edited); `starontology/shacl12-shacl-ui.ttl` is generated** by `scripts/build_shacl_ui.py` (called from `build_starontology.py`): a field per predicate flagged `stsh:nodeFormField` / `stsh:propertyFormField`, with its `sh:group`, `sh:order`, `sh:maxCount` (`stsh:formMaxCount`) and the `sh:datatype` / `sh:nodeKind` / `sh:in` it has in `shacl_shacl`. A form is found by `stsh:formFor` (the class it is for), not `sh:targetClass`, so it is applied to nothing and loading it never changes what validates. **The completeness check** (`missing_fields()`, run by the build and by `test_shacl_ui_forms.py`): every predicate `shacl_shacl` validates must be a field of some form or be in `build_shacl_ui.EXCLUDED` (or its node-expression namespace) with the reason it belongs to another kind of node (a widget score, a constraint component, a rule, a property path, a node expression, a validation report). Adding a validation rule for a new predicate therefore fails the build until the overlay flags it or the exclusion list says why not.
- **`shacl_shacl_ui`** (`shacl12-shacl-ui.ttl`, generated from the overlay source above) is the archived presentation file, restored and slimmed: 19 `sh:PropertyGroup` sections (the first is `stsh:TypeGroup`, for `rdf:type`), `sh:group` and `sh:order` on each SHACL predicate, and the `stsh:` form flags. **It contains no widget.** Its 66 widget preferences moved to `shacl_shacl_ui_scores`, and its 20 `stsh:widgetType` fields (path expressions, node expression lists, message lists, `sh:in`, `sh:hasValue`, `sh:constant`) were dropped on the user's instruction: widgets are standard `shui:` widgets only, and an application layer whose application understands those fields can bring them back. It could not simply be restored: the new `sh:order` rule (one value) rejected it, because `sh:name` and `sh:description` had two groups and two orders. They keep the Metadata group only. Load it beside `shacl_shacl` (`meta_validate(..., extra_graphs=[ui])` or a graph union).
- **`shacl_ui_baseline`** (`shacl-ui-baseline.ttl`, type `"scoring-catalog"`) is the generic scoring catalog, in three tiers: **1** a default that matches everything (`TextFieldEditor`, `LiteralViewer`), **2** defaults by datatype (number, boolean, date, dateTime, langString), **3** defaults by a constraint that lists the answers (`sh:in`, `sh:class`, `sh:nodeKind sh:IRI`). A constraint beats a datatype (an `xsd:string` with `sh:in` is an enumeration), and a layer on top scores higher still (the WG's files use 40). **One catalog serves both roles** (`select_widgets(role=...)` filters by each widget's class); the user rejected per-role catalogs. Opt-in: pass it as `scoring_graph=`. A layer for editing SHACL (scores by `sh:path`, plus the presentation) builds on it and is not built yet.
- **Conditions live on the score, not on a per-widget matcher (changed 2026-10-21).** The WG's own widget files put `shui:shapesGraphShape`/`dataGraphShape` on each `shui:WidgetScore` (tiers 40/20/10/0; a preference is the 40 tier) and use no `WidgetAcceptMatcher` at all, although the draft's text describes one per widget. `select_widget` now evaluates the conditions on each score node (a score with none applies to everything) and still honours a per-widget matcher if a catalog has one. The reason, from the user: a per-widget matcher is a gate shared by every layer, so a higher layer cannot add back a widget a lower one excluded without deleting the gate; a condition local to a score cannot block anyone. The baseline has no matchers. A tie in score goes to the widget IRI, so `IRIEditor`'s condition is "an IRI with no `sh:class`" (otherwise it would tie with `InstancesSelectEditor` and win).
- **`shacl_shacl_ui_scores`** (`shacl12-shacl-ui-scores.ttl`, type `"scoring-catalog"`) is the **scoring layer for editing SHACL**: 9 `shui:WidgetScore` entries at **40** (the tier the WG's own files use for a preference), one per widget, each applying when the property shape being rendered has a `sh:path` in its list (66 predicates, none in two lists, so no ties): `NumberFieldEditor` for `sh:minCount`/`maxCount`/the bounds, `BooleanEditor` for `sh:closed`, `EnumSelectEditor` for `sh:severity`/`sh:nodeKind`, `DetailsEditor` for nested shapes, and so on. Editors only; viewers fall to the generic defaults. Use it **with** the generic catalog (`scoring_graph` = the union; the caller combines, higher scores win). It works with `shacl_shacl`'s own property shapes (checked on `shsh:ShapeShape`). `sh:targetClass`, `sh:targetSubjectsOf` and `sh:targetObjectsOf` (IRIs only) use `IRIEditor`; `sh:targetNode` keeps a text field because its values may be literals (the original preference was a text field for all four).
- **Pattern for the other vocabularies (the user's plan):** an *application layer* that ships with starlayer because the vocabulary does is two files built on the generic catalog: a shapes-side presentation file (`<vocab>_ui`: groups, order, form flags) and a scoring-side file (`<vocab>_ui_scores`: scores at 40 keyed by `sh:path`). Expect it for `sqe`, `srl`, `manch` and the rest. The generic layer knows nothing about any of them.
- **Terminology:** call `shui:editor`/`shui:viewer` on a property shape a *preference* (the draft's word), not a "hint".
- **Namespaces (checked 2026-10-21):** the draft's own namespace table and JSON-LD context give `http://www.w3.org/ns/shacl-ui#` (hash), which is what we use. The WG's separate vocabulary file (`shacl12-vocabularies/shacl-ui.ttl`) and its widget score files use `http://www.w3.org/ns/shacl-ui/` (slash): the WG is inconsistent, and the draft text wins. A WG widget file loaded as is would not match our widgets. `stsh:` is our own namespace for SHACL-related terms (`https://github.com/hidden-graph/starlayer/ns/shacl#`; the prefix is a leftover from "starshacl"). The library itself reads only one `stsh:` term (`STSH.TripleTermNodeKind`).
- **Overlay preferences:** these used to win over a catalog matcher by accident; the generic catalog now has no matchers.
- **Found while doing this:** `meta_validate()` called first in a process rejected `shacl_shacl` itself, because the Working Group's file uses `sh:memberShape`, which pySHACL only knows after `register_native_components()`; `validate()` registered it, `meta_validate()` did not. It now registers it too (`test_wg_overrides.py` runs it in a fresh process).

## `select_widgets(per="shape")`: one answer per property shape (2026-10-23, GitHub issue #14)

`select_widgets` used to redo, for every node a UI showed, the checks that depend only on the shape (a condition's `shui:shapesGraphShape`: a SHACL validation of the property shape, which is the slow part). `per="shape"` returns `{property_shape: WidgetChoice}` instead: the ranked `candidates` that survive the shape conditions, ending at the first that needs no node data (nothing below it can win), each with the data conditions still to check. `choice.resolve(focus_node, data_graph)` (= `check_data_matchers`) validates only those, and gives the same widget as `select_widget` for that node (a differential test over five catalogs, both roles, every property and node). `choice.needs_data` False means one answer (`choice.widget_without_data`) serves every node; the shipped generic catalog has no data condition, so a UI can keep one answer per (shape, role). `choice.widget_without_data` equals `select_widget` with no focus node (Section 3.4 steps 1 and 3). Not done, by decision: a cache inside `StarShaclSchema` (shapes graphs are mutable, so it needs an invalidation rule). The matcher function was split into `_shape_condition_holds` and `_data_condition_holds` to make this possible; `_matcher_accepts` composes them and behaves as before.

## The meta-shapes base is the Working Group's file, extended by adding only (2026-10-21)

`shacl_shacl` used to be pySHACL's bundled 2017 `shacl-shacl.ttl` with eight rules deleted, plus our asset. It is now the W3C Data Shapes WG's own `shacl-shacl.ttl`, pinned verbatim at `scripts/assets/vendor/w3c-shacl-shacl.ttl` (provenance and SHA-256 in `VENDORED_FROM.md`), plus additions. **Reason:** the WG file is where SHACL 1.2 is being specified, and it moves; a base we delete from cannot be compared with a newer copy, a base we only add to can. The user's rule: "just add".

- **Why additions can relax a rule.** SHACL constraints combine by AND, so a looser rule next to a strict one changes nothing. The WG's own file says to customise it with `sh:deactivated true` ("this graph should be supplemented with 'shsh:xoneSubjectsShape sh:deactivated true'"). `build_meta_shapes.py` finds the WG's property shapes for `sh:nodeKind`, `sh:equals`, `sh:disjoint`, `sh:lessThan`, `sh:lessThanOrEquals` (`RELAXED_PATHS`) by structure and adds `sh:deactivated true`; the replacements are `stsh:ShapeShapeOverrides` in the asset.
- **Expression-based property shapes** (`sh:expression`, no `sh:path`): the WG's `PropertyShapeShape` requires `sh:path`, so that rule is deactivated (replacement "path or expression" is in the asset), and `NodeShapeShape` gets `sh:path sh:expression ; sh:maxCount 0`, so a node shape carries no `sh:expression` and the WG's `sh:xone` of node shape / property shape stays exclusive. Without the second part both branches would pass and the `xone` would fire.
- **Typing step.** The WG file uses `sh:memberShape`; pySHACL does not know it, so the build adds the `rdf:type` triples (`_ensure_native_component_shapes_typed`) and the stored file works with plain `pyshacl.validate`.
- **Tracking.** `scripts/check_wg_shacl_shacl.py` (network) says whether the pinned copy is the latest. `tests/shacl/integration/test_wg_overrides.py` (offline) fails when the pinned file's hash no longer matches its record, and when the WG file *accepts* something we override (an override is no longer needed). Measured 2026-10-21: from the 2026-08-01 snapshot to 2026-10-12 the WG fixed `sh:closed sh:ByTypes`, `sh:class` and `sh:datatype`, so those three overrides were removed.
- **Duplicates removed (2026-10-21):** the asset's rules for `sh:singleLine`, `sh:minListLength`, `sh:maxListLength` and `sh:uniqueMembers` were identical to the WG's and are gone; for `sh:memberShape` only our extra (`sh:nodeKind sh:BlankNodeOrIRI`, so a literal cannot vacuously pass) is kept. `test_wg_overrides.py` fails if a later WG copy drops one of those rules.
- **Warning:** the WG's recursive shape makes pySHACL emit `ShapeRecursionWarning`; `meta_validate` suppresses it.

Dated entries below record why things are the way they are. Read one when you work on that topic; the block above is what you need first.

## Path repetition steps with the path walker; fragments keep the focus node's edges (2026-10-25, GitHub issue #62)

`_walk_path` (`subgraph_extraction.py`, also behind the public `starlayer.shacl.paths.path_values`) had two bugs in `sh:zeroOrMorePath` / `sh:oneOrMorePath` / `sh:zeroOrOnePath`. (1) The edges returned for the fragment were only those between nodes the path REACHES; for `sh:oneOrMorePath` the focus node is not one of them (unless a cycle returns), so every edge leaving the focus was dropped and the fragment of `:n0 :p :n1` was empty and no longer conformed (the Conformance Theorem). (2) The repeated path was treated as a plain predicate, so a repetition over an inverse, alternative or sequence path (`( :p :q )+`, `(^:p)*`) followed nothing. Each repetition now takes one step with `_walk_path` itself, from every node reached, and keeps every edge it walked. `tests/shacl/integration/test_extract_subgraph_paths.py` has the Conformance Theorem over generated paths and `path_values()` against rdflib's SPARQL property paths. An inverse of a non-predicate is not generated (SHACL's inverse path takes an IRI; the walker assumes it).

## Small differences from pySHACL found by the hunt (2026-10-25, GitHub issues #50, #51, #52)

Oracle for all three: plain pySHACL in a separate process (`tests/shacl/integration/test_pyshacl_parity_small_differences.py`); there is no deliberate difference among them.
- **#50 `sh:uniqueLang`**: the replaced component grouped values by the language tag as written, so `'x'@en` and `'y'@EN` were not duplicates. Language tags are case-insensitive; the key is lower-cased (`_effective_language_direction_key_encoded`).
- **#51 `allow_warnings`**: pySHACL (`shape.py`) allows `sh:Info` whenever warnings are allowed. `_annotate_conformance_disallows` (one copy now; the method delegates to the function) only added `sh:Info` to the disallowed set when `allow_infos` was off, ignoring `allow_warnings`. All twelve severity x flag combinations now agree with pySHACL (with no flag an Info result blocks `sh:conforms` in both, which is also the SHACL 1.2 default `sh:conformanceDisallows`: Violation + Warning + Info). The hunter's claim that pySHACL conforms there was wrong.
- **#52 result messages**: the replaced `sh:closed`, `sh:languageIn` and `sh:uniqueLang` components never defined `make_generic_messages`, so their results had no `sh:resultMessage` (also for plain `pyshacl.validate` once the components were registered). They now give pySHACL's exact texts ("Node X is closed. It cannot have value: V", "String language is not in ( ... )", "More than one String shares the same Language").

## Recursive shapes are cut at an exact (shape, node set) revisit, not by pySHACL's shape-only heuristic (2026-10-24, GitHub issue #26)

**What was wrong.** pySHACL 0.40.1's `ConstraintComponent.recursion_triggers` decides a recursive validation has begun from the sequence of shapes alone, never the data node, and "backs out" (with a `ShapeRecursionWarning`). For `ex:P sh:property [ sh:path ex:friend ; sh:node ex:P ]` a chain of three or more nodes with a violation at the end was reported as **conforming** when the nested nodes were not themselves targets (plain pySHACL, no StarLayer: `docs/upstream-issues/pyshacl-upstream-issues.md` Issue 7, not yet filed; tracked in #48). StarLayer made it one step worse: its replacement `sh:node` component set `shacl_constraint_component` from its own `SH.NodeConstraintComponent`, and pySHACL compares that with `is`, so the lookback was never lengthened and the cut came at a chain of 2; installing `register_native_components()` made plain `pyshacl.validate` wrong too.

**The fix** is `starlayer/shacl/recursion.py`, installed by `register_native_components()` (process-global, like the other pySHACL patches): `recursion_triggers` is switched off and `Shape.validate` is wrapped so that a **nested** call (focus nodes given) whose (shape, whole set of focus nodes) is already active further up the call chain returns "conforms" and is counted (`ExecutionDiagnostics.recursion_revisits`). Acyclic data is evaluated in full (the recursive shape agrees with the same schema written as distinct copies: a Hypothesis test); cyclic data stops at the revisit (greatest-fixpoint). **Two traps found on the way:** the top-level call must NOT register its targets (they are a batch of siblings, not ancestors: alice -> bob with both targets looked like a cycle and alice's `sh:node` result vanished), and the key must be the whole focus set, not one node (`sh:node` back to the same shape on the same nodes re-enters with an identical batch and otherwise recurses until `RecursionError`). No `ShapeRecursionWarning` is raised any more. `MAX_VALIDATION_DEPTH` (500) replaces pySHACL's default 15 and meta_validate's 30, since the old cut used to keep nested structures shallow; Python's own recursion limit is the real bound (about 120 hops of a self-referencing shape, then a loud `RecursionError`).

**Not changed:** results for the same violation repeat (a nested violation is reported again for every ancestor and for each target): a nested `shacl_shacl` case is now 14/40/74/116 results for depth 0/2/4/6 where the old cut hid some. Reporting identical results once is a separate decision. A recursive shape over data with shared substructure has no memoisation (possible exponential time; the hunt's disputed finding).

## Node expressions and their argument lists are typed, so a shape targets every node under `sh:values` (2026-10-24, GitHub issue #22)

`stsh:NodeExpressionShape` only targeted the value of `sh:values`; the nested expressions and the cells of the argument lists had no shape that selected them. The same device as shape typing (#24): layer-2 rules in `shacl_shacl_rules` type the value of `sh:values`/`sh:defaultValue`/`sh:expression` `sh:NodeExpression`, then every blank-node argument of a `sh:NodeExpression` (directly or as a member of an argument list) the same, iterated to a fixpoint inside the layer so any depth is reached, and type the cells of those lists `rdf:List`. The shapes side (`scripts/assets/shacl12-validation-shapes.ttl`): `stsh:NodeExpressionShape sh:targetClass sh:NodeExpression` and a new `stsh:ExpressionArgumentListShape` (`sh:targetClass rdf:List`, `sh:node shsh:ListShape`). The arguments of `sh:path`, `shnex:pathValues`, `sh:filterShape`, `shnex:filterShape`, `shnex:conformsToShape`, `shnex:instancesOf`, `shnex:nodesMatching` and `shnex:var` are a path, a shape or a class, not an expression, and are skipped (add a predicate to the `FILTER` in the rules file if a new one takes a non-expression). **Consequence:** these targets only fire once the types are in the graph: run `shape_types.infer_types()` and merge its result, as a tool does for #24; plain `meta_validate()` on an un-inferred graph still checks only the top-level expression. The editing of an expression in a form is a separate, larger feature.

## `sh:targetWhere` validates the where-shape only (2026-10-25, GitHub issue #53)

A node is a target of `sh:targetWhere W` when it conforms to `W`. `_nodes_conforming_to` (two copies: the module function and the `StarShaclSchema` method) used to run the WHOLE shapes graph with the candidates as extra targets of `W`, so any unrelated shape failing on a candidate made it look non-conforming to `W` and it silently stopped being a target. Now `_where_shape_validation_graph` copies only `W` and what it reaches (`sh:property`, `sh:node`, `sh:not`, `sh:and`/`or`/`xone` lists, qualified/some/member/reifier shapes, `sh:prefixes`, every blank node), **removes every copied shape's targets** (explicit `sh:target*` and implicit class targets: a shape `W` refers to failing on a node it targets itself says nothing about `W`) and keeps `sh:entailment`; `_with_where_targets` adds the candidates. **Attribution limit:** a batched report names the focus node of each result, and a property shape *inside* a property shape reports on the VALUE node, not on the candidate that has it (the batch would blame the value and clear the candidate), so for a where-shape with that structure (`_has_property_shape_inside_property_shape`) each candidate is validated by itself; every other structure (sh:class/sh:node/sh:and ... and ordinary property shapes) is exact in one batch. Tests: `tests/shacl/integration/test_target_where_isolation.py`.

Mirrors `starlayer.sparql.srl`/`sqe`'s own precedent: `starlayer.shacl`'s top-level `__init__.py` flat-exports only Core validation (`StarShaclSchema`, `validate`, `validate_each`, `ValidationResult`, `ExecutionDiagnostics`, `close_shape`) and the cross-cutting RDF 1.2/triple-term infrastructure every other module depends on (`TripleTermAdapter`/`Graph`/`Value`, `normalize_to_starlayer_graph`/`normalize_graph_inputs`, `StarLayerGraphProtocol`/`MutableStarLayerGraphProtocol`). ## `StarShaclSchema` binds a shapes graph (plus optional ontology graph) at construction, not per-call (2026-10-06)

**Four names in one day, same class**: `StarLayerShacl` → `StarLayerShaclProcessor` → `StarLayerShaclGraph` → **`StarShaclSchema`**. Each rename tracked a real finding, not taste alone:
- `StarLayerShacl` named the specification ("Shacl"), not what the object is.
- `StarLayerShaclProcessor`: "Processor" is the W3C SHACL spec's own term for an implementation performing its defined operations, quoted directly in `validator.py`'s own source ("SHACL processors MUST NOT..."). Better, but still implied a singleton worker - the wrong connotation, once the real design problem below was found.
- `StarLayerShaclGraph`: the design problem - the object held no meaningful state at all (confirmed via `grep`: its constructor set exactly two attributes, `adapter`/`validate_fn`, both pure test-seam dependency injection with zero real external use), and every one of its six methods (`validate`/`validate_each`/`apply_rules`/`evaluate`/`extract_subgraph`/`target_nodes`) took `shacl_graph` as a parameter on *every single call* - meaning two instances were always functionally interchangeable, and any real caller validating several data graphs against one shapes graph was re-passing the identical `shacl_graph` argument every time. Fixed by binding `shacl_graph`/`ont_graph` at construction (below) - "Graph" named the new relationship to its shapes graph (matching `StarLayerGraph`'s own convention), but this class never *holds* triples itself (composition, not inheritance), so "Graph" overclaimed.
- `StarShaclSchema`: "Schema" is already the ordinary term for "the thing you validate data against," and - unlike "Processor"/"Engine"/"Service"/"Context," all considered and rejected - it naturally supports several differently-named instances in one project (a `PersonSchema`, a `ProductSchema`), rather than reading as one shared facility. `Star` rather than `StarLayer`: deliberate, the first instance of a planned future prefix simplification (`StarLayerGraph` may become `StarGraph` later) - not yet applied project-wide, so this one class is intentionally inconsistent with `StarLayerGraph`/`StarLayerDataset` for now.

**Fix**: `shacl_graph`/`ont_graph` moved from a repeated per-call method parameter to a constructor-bound attribute (`StarShaclSchema(shacl_graph=None, ont_graph=None)`), normalized once in `__init__` via `normalize_to_starlayer_graph` (not deferred to each method call) specifically so `apply_rules()`'s own separate `normalize_graph_inputs(self.shacl_graph, ...)` call for `rule_set`/`_global_sparql_rule_triples` blank-node identity gets back the *identical* object `validate()` itself uses internally - no second, independent normalization that could silently diverge, the exact invariant the pre-existing code already depended on (see that method's own comment). Every method's body kept its existing local `shacl_graph`/`ont_graph` variable names unchanged internally - only the signature changed, plus one new line aliasing `shacl_graph, ont_graph = self.shacl_graph, self.ont_graph` at the top of each, since every method already treated them as ordinary local variables it reassigns as it goes (e.g. `_augment_shapes_with_new_target_types`). This made the actual method-body risk much lower than the call-site-migration risk (below).

**Call-site migration, the real risk**: 320 construction call sites across 49 files, ~300 of which also passed `shacl_graph=`/`ont_graph=` to a method call needing that argument *moved* to the constructor - not a trivial rename. Handled with an AST-based transformer (regex is unsafe here - multi-line calls, nested parens in argument values), scoped per-function (not per-file) to avoid false "ambiguous" flags when the same variable name like `validator` is reused fresh in every test function. Two real bugs found and fixed along the way:
- The transformer didn't dedupe when one object was reused across *multiple* calls sharing the *identical* `shacl_graph` value - it tried to insert into the constructor once per matching call, corrupting span offsets on the second insertion. Caught safely in both real occurrences (`test_rule_iteration.py`, `test_w3c_validate.py`) because duplicate keyword arguments are unconditionally a Python `SyntaxError` - the transformer's own post-edit `ast.parse()` check rejected and skipped both files whole rather than writing corrupted output. Fixed by hand (bind once at construction, drop from every call), then safely re-run the same transformer on just those two files afterward.
- A handful of tests built a value (e.g. `shapes = Graph()`) *after* the original argless constructor call, relying on it only being needed later at the `.validate()`/`.apply_rules()` call site - moving that same expression into the constructor call site (now earlier in execution order) raised `UnboundLocalError`. Fixed by either reordering the definition earlier or dropping the irrelevant `shacl_graph` argument entirely where the test wasn't actually testing shapes-graph behavior (e.g. `test_apply_rules_rejects_non_starlayergraph_data_graph`, which only cares about `data_graph` rejection).
- One file used a local `_validator()` helper wrapping the constructor with no arguments, invisible to the transformer (it only recognizes a direct `StarShaclSchema(...)` call, not one hidden inside another function) - fixed by giving the helper its own `shacl_graph` parameter and forwarding it.

Full `tests/shacl` suite (1051 tests) passes identically to the pre-redesign count - confirms nothing was silently dropped or disabled during the migration, not just that nothing errors.

### Wraps pyshacl by composition, not inheritance - and a coverage audit of pyshacl's own public surface

`StarShaclSchema` is `object`-derived (no base class) because pyshacl's own main entry point, `validate()`, is a stateless one-shot function, not a long-lived object to subclass the way `StarLayerGraph` subclasses `rdflib.Graph` - there's no "is-a" relationship available, and `StarShaclSchema` unifies four independent capabilities (`validate`/`apply_rules`/`evaluate`/`extract_subgraph`), the last two of which aren't pyshacl operations at all. Composition also matches what's actually happening at the boundary: triple-term encode/adapt, call pyshacl's own function as a black box, decode - a decorator pattern, not internal specialization.

A direct audit against pyshacl's own `__init__.__all__` (`validate`, `validate_each`, `shacl_rules`, `Validator`, `RuleExpandRunner`, `Shape`, `ShapesGraph`) found two real, confirmed gaps - things pyshacl exposes publicly that `starshacl` had no access path to at all, as opposed to the five other names, which are either wrapped (`validate`) or deliberately bypassed/used only as internal plumbing:

- **`validate_each()`** (batch-validate several independent data graphs against one shared shapes graph) - had zero `starshacl` equivalent. **Fixed 2026-10-06**: `StarShaclSchema.validate_each()` + a module-level `validate_each()` convenience function, both in `validator.py`, implemented as a loop calling `self.validate()` once per data graph (not by driving pyshacl's own multi-data-graph path directly - that path knows nothing about RDF 1.2 triple terms or any of this project's SHACL 1.2 patches, so using it would silently run a different, unpatched pipeline). Returns `dict[int, ValidationResult]`, this project's own richer result type, matching `validate()`'s own "wrap pyshacl's bare tuple" convention.
- **`shacl_rules()`/`RuleExpandRunner`** (a lighter-weight "expand rules only, skip constraint validation" path) - `apply_rules()` always routes through `self.validate(profile="rules")`, which always also runs full SHACL constraint checking (the `"rules"` profile in `profiles.py` has no flag to skip it). No data is lost (`RulesResult.data_graph` already carries the expanded graph, plus a bonus validation report `shacl_rules()` wouldn't give you), but there's no way to get rules-without-validation specifically. **Deliberately not implemented yet** (2026-10-06) - logged in `docs/future_enhancements.md` pending a check of whether the SHACL 1.2 Inference Rules draft says anything that bears on this.
- The other three (`Validator`, `Shape`, `ShapesGraph`) are used, but only as internal plumbing/monkey-patch targets (three separate process-global patches on `Shape.validate`/`value_nodes`/`focus_nodes` to fix confirmed pySHACL bugs) - never exposed as public `starshacl` symbols in their own right. Not treated as gaps; nothing currently needs to construct one of these directly.

When adding a new pyshacl-wrapping capability, check pyshacl's own `__all__` against what's actually reachable from `starlayer.shacl` the same way - don't assume parity.

## `apply_rules()` becomes a module-level function; `StarShaclSchema.apply_rules()` delegates to it (2026-10-07)

Direction flip from `validate()`/`validate_each()`'s own convention, on explicit user instruction: "I think the wrapping is the wrong direction. we have the bare function, and then StarShaclSchema.apply_rules calls that function with its stored shapes graph." `validate()`/`validate_each()` wrap `StarShaclSchema` (bare function constructs a throwaway instance, the instance method holds the real logic) because pyshacl's own `validate()` is a one-shot function and the class exists only to bind `shacl_graph`/`ont_graph` once. `apply_rules()` is different: pyshacl's own module-level analog, `shacl_rules()`, is itself a bare function - so `apply_rules()` should follow that shape too, not `validate()`'s.

Implemented: the real `apply_rules(data_graph, shacl_graph=None, ont_graph=None, include_source_rule_provenance=False, rule_set=None, **kwargs)` now lives in `validator.py`, next to `validate()`/`validate_each()`; `StarShaclSchema.apply_rules()` is now a thin delegate passing `self.shacl_graph`/`self.ont_graph` through. Exported from `shacl_inference.py`, not the flat `starlayer.shacl` namespace - it's Inference-Rules-specific, same reasoning as `RulesResult` - whose own docstring previously claimed "no module-level function form to mirror"; now stale, fixed.

**Real coupling found, not just a rename**: the old method body called `self.validate(...)` and read `self.adapter` directly (for `sh:sourceRule` provenance decoding) - not a pure function of `(data_graph, shacl_graph, ont_graph)`. Flipping the direction means the bare function necessarily goes through the bare `validate()` function (which always constructs a fresh, default-adapter `StarShaclSchema`), not `self.validate()` - so a constructor-level `adapter=`/`validate_fn=` override on an instance no longer reaches that instance's own `apply_rules()`. Confirmed with the user before implementing (`adapter=`/`validate_fn=` already have zero real external callers - see the composition section above) and accepted as a deliberate trade-off, not an oversight.

**Normalization-once invariant preserved deliberately**: the bare function still normalizes `shacl_graph` exactly once (`normalize_graph_inputs(shacl_graph, None, None)[0]`) and reuses that one object for both the rule-set/global-SPARQL-rules passes and the `validate()` call inside it - the same invariant the per-instance code already depended on (see the binding section above), just computed from an explicit parameter instead of `self.shacl_graph`. When called via `StarShaclSchema.apply_rules()`, `self.shacl_graph` is already normalized once at construction, so this is an identity pass-through, not a second normalization.

Two unit tests relied on the old coupling to inject a fake `validate_fn` through the constructor (`test_apply_rules_requests_inplace_advanced_mode`, `test_apply_rules_uses_rules_profile_defaults` in `tests/shacl/unit/test_validator.py`) - updated to `monkeypatch.setattr("starlayer.shacl.validator._default_validate", fake_validate)` instead, since that's the shared fallback the fresh internal `StarShaclSchema` now actually uses. Verified live (throwaway `StarShaclSchema` + direct bare-function call, both producing the expected inferred triple) and via the full `tests/shacl` suite (1048 passed, zero regressions beyond the two intentionally-updated tests).

## Testing discipline: verify coverage adversarially, not just by existence

Before marking a test - or a `packages/starlayer/docs/shacl/shacl12-gap-matrix.md` row - "done" for a native/patched behavior, don't stop at "a test exists and passes." Check whether it would still pass with the change reverted:

- **Fixture-based tests**: could the *old* form (whatever pySHACL, or whatever baseline, did before starshacl's change) already satisfy this exact test? Run the fixture through plain, unpatched `pyshacl.validate()` - no `StarShaclSchema`, no meta-shapes, no native component registration - and confirm it produces the *opposite* result from what starshacl produces. If it doesn't, the test isn't exercising starshacl's own code at all; it's redundant with pySHACL's existing behavior.
- **Meta-shacl well-formedness rules**: confirm a genuinely malformed value is actually rejected, not just that a well-formed value passes. "Passes when valid" and "rejects when invalid" are two different claims - a test covering one does not imply the other.

This is cheap (one throwaway script per feature, not a new test-writing methodology) and catches a real, repeated failure mode: a 2026-07-20 coverage audit found that `sh:ShapeClass` implicit-class-target coverage, `sh:values`'s "done" status, and 8 of the 11 new SHACL 1.2 predicates' malformed-usage tests had all passed review while quietly not testing what they claimed to (see `packages/starlayer/docs/shacl/shacl12-gap-matrix.md` for the specific fixes and reasoning). Every instance had the same root cause: the same pass that wrote the feature also wrote the test confirming it, without ever asking "would this fail if I deleted what I just added?"

**Don't treat a coverage audit's own findings as ground truth either** - verify audit claims against the actual test file before acting on them. The audit above also produced a false claim (that `owl:imports` cycle/loader-failure edge cases were untested, when they already were) - only the empirical check caught it.

## Which predicates belong on a NodeShape vs a PropertyShape form: don't invent it, pySHACL and the W3C draft already encode it

A 2026-08 downstream-editor readiness pass found `stsh:nodeFormField`/`stsh:propertyFormField` (which predicates should render as fields in a NodeShape-editing vs PropertyShape-editing form) only set for 35 of 108 documented predicates. Before designing a new restriction list from scratch, check for a native/vendored one first - this project already had two:

- **pySHACL's own bundled `shacl-shacl.ttl`** (`<venv>/lib/python3.14/site-packages/pyshacl/assets/shacl-shacl.ttl`) encodes exactly this distinction via `shsh:ShapeShape` (targets both `sh:NodeShape`/`sh:PropertyShape`, lists predicates valid on either via `sh:targetSubjectsOf`), `shsh:NodeShapeShape` (explicitly forbids `sh:path`/`sh:lessThan`/`sh:lessThanOrEquals`/`sh:maxCount`/`sh:minCount`/`sh:qualifiedValueShape`/`sh:uniqueLang` on a NodeShape - i.e. PropertyShape-only), and `shsh:PropertyShapeShape` (requires `sh:path`).
- **This repo's own vendored, more complete draft**, `packages/starlayer/tests/shacl/vendor/shacl12-vocabularies/shacl-shacl.ttl` (the official SHACL 1.2 WG draft's meta-shapes, used elsewhere for `packages/starlayer/docs/shacl/shacl12-gap-matrix.md`'s gap comparisons), has the same `shsh:ShapeShape`/`NodeShapeShape`/`PropertyShapeShape` shapes but models more predicates than pySHACL's older bundled copy (`sh:memberShape`, `sh:maxListLength`, `sh:minListLength`, `sh:uniqueMembers`, `sh:singleLine`, among others) - **prefer this one** when the two disagree or when pySHACL's copy is silent on a predicate.

Neither file covers SHACL-AF rule/SPARQL-extension attachment (`sh:sparql`, `sh:rule`) or the newest RDF 1.2 predicates (`sh:someValue`, `sh:subsetOf`, `sh:rootClass`, `sh:uniqueValuesFor`, `sh:reifierShape`, `sh:reificationRequired`) - for those, judge by analogy to the nearest predicate the vendored draft *does* confirm generic or restricted (documented with reasoning in `docs/working/shacl-presentation/shacl-presentation-content.md`'s "17. Form-Field Membership" section).

**A predicate that's a field of a nested sub-form (a Rule, ConstraintComponent, Validator, or path/node-expression definition) isn't a NodeShape/PropertyShape form field at all**, and shouldn't be forced into this binary just because it's a `sh:` predicate. `sh:condition`/`sh:select`/`sh:ask`/`sh:construct`/`sh:subject`/`sh:predicate`/`sh:object`/`sh:parameter`/`sh:validator`/`sh:nodeValidator`/`sh:propertyValidator` (nested inside `sh:rule`/`sh:ConstraintComponent`) and the property path operators (`sh:alternativePath`, `sh:inversePath`, `sh:oneOrMorePath`, `sh:zeroOrMorePath`, `sh:zeroOrOnePath`, nested inside `sh:path`) were deliberately left without `nodeFormField`/`propertyFormField` for this reason - a downstream editor needing "which fields belong on a Rule sub-form" needs a separate, not-yet-built mechanism, not a misuse of this one. This is genuine future work, not an oversight.

## `sh:entailment` support (SHACL 1.2 Core §1.4) + closing the global-rules-never-validated gap (2026-10-07)

Built on `starlayer.graph`'s same-day migration to real W3C entailment regime IRIs (`ENTAILMENT.*`, see `starlayer/graph/CLAUDE.md`'s own dated entry) - this module needed no separate IRI↔string translation table as a result, since `infer()` already speaks the exact IRIs a shapes graph's own `sh:entailment` triples carry.

**New `starlayer/shacl/entailment.py`**: `declared_entailment_regimes(shacl_graph)` reads every `sh:entailment` triple's object anywhere in the graph (confirmed shapes-graph-scoped per spec, not per-shape - see the module's own docstring for the exact quotes). `apply_entailment(data_graph, shacl_graph, *, inplace)` resolves and materializes the declared regime(s) via `infer()`.

**Wired into `StarShaclSchema.validate()`** (`validator.py`, right after `normalize_graph_inputs()`): unconditional whenever `shacl_graph is not None` - a no-op for the overwhelmingly common case (no `sh:entailment` declared). This also gives `apply_rules()` "entailment before rule execution" for free, since shape-attached `sh:rule` runs inside this same `validate()` call.

**A real regression found via testing, not assumed correct**: the first version of `apply_entailment()` always mutated `data_graph` in place regardless of the caller's own `inplace` setting - silently breaking `validate()`'s own long-documented guarantee that the plain `"validation"` profile (`inplace=False`) never mutates the caller's data. Confirmed live (`len(data)` grew after a plain `validate()` call using `sh:entailment`) before `apply_entailment()` gained its own required `inplace` keyword, threaded through from `resolve_profile_options(...)['inplace']`: `True` mutates and returns `data_graph` itself (matches `apply_rules()`'s own established contract); `False` returns a *new* graph via `infer(mode="full")`, leaving the caller's original completely untouched. Regression test: `test_sh_entailment.py::test_plain_validation_profile_never_mutates_the_callers_data_graph`.

**`apply_rules()` also closes a second, previously-identified gap in the same change** (not sh:entailment-specific, but the same design session): `RulesResult.conforms`/`report_graph`/`report_text` used to only ever reflect state *before* the separate global `sh:RuleSet`/`sh:SPARQLRule` pass - triples that pass produces were never actually validated at all. Fixed by, after the global-rules loop: (1) re-applying `sh:entailment` on the now-complete `out_data` (`inplace=True` unconditionally - `apply_rules()` always wants the returned `data_graph` fully enriched), then (2) re-validating `out_data` once more with the plain `"validation"` profile (not `"rules"` again - confirmed via reading pyshacl's own `SHACLExecutor` construction that `advanced_mode`/`iterate_rules` are independent flags, so this correctly does NOT re-execute rules a second time) and using *that* call's conformance result instead. Net effect: `apply_rules()` now calls `validate()` twice in every real path - a deliberate, accepted cost increase, confirmed via the full `tests/shacl` suite showing identical rule-iteration counts to before (no accidental double-execution). Regression test: `test_sh_entailment.py::TestApplyRulesValidatesGlobalRuleOutput`.

Full `tests/shacl` suite: 1065 passed (was 1048 before this work - 17 new tests across `test_entailment.py`/`test_sh_entailment.py`), zero regressions. Two existing unit tests (`test_apply_rules_requests_inplace_advanced_mode`/`test_apply_rules_uses_rules_profile_defaults`) needed updating since `apply_rules()` calling `validate()` twice meant their `monkeypatch`-captured kwargs dict reflected a mix of both calls - fixed by capturing a list (one dict per call) and asserting on the first call specifically.

**Known v1 scope limitation, documented not silently assumed**: `apply_entailment()` only sees schema axioms already present in `data_graph` itself - axioms supplied only via `ont_graph` (the more idiomatic place for them) aren't picked up, since folding `ont_graph` in automatically would risk the same inplace-mutation violation just fixed above, in a different form. See `docs/future_enhancements.md`.

## `ont_graph` support for entailment + pySHACL's own `inference=` replaced (2026-10-07)

Two follow-ups from the same design conversation, closing a documented limitation and a confirmed duplication:

**`ont_graph` now seen by entailment.** `apply_entailment()`'s own documented v1 limitation ("entailment runs over `data_graph` alone") is closed: a new shared `_apply_entailment_regimes(data_graph, regimes, ont_graph=None, *, inplace)` in `starlayer/shacl/entailment.py` computes entailment over `data_graph` union `ont_graph` when `ont_graph` is given (so an `rdfs:domain` declared only there is actually seen - confirmed live via this session's own worked example), but only the newly-entailed **delta** is ever materialized back - `ont_graph`'s own raw triples never get copied in, and `ont_graph` itself is never mutated (same `infer(mode="delta")` pattern already proven for the no-`ont_graph` case). `apply_entailment()` is now a thin wrapper around this shared helper; both its call sites in `validate()` and `apply_rules()` thread `ont_graph` through.

**pySHACL's own `inference=` kwarg replaced with an equivalent routed through `StarLayerGraph.infer()`.** Previously a second, independent entailment engine coexisted with ours (pySHACL's own internal RDFS/OWL-RL reasoning, triggered by `inference="rdfs"/"owlrl"/"both"`, completely separate from `sh:entailment`). Confirmed directly: pySHACL has no OWL 2 DL option at all for `inference=` (`pyshacl/run_type.py::_run_pre_inference` raises `ReportableRuntimeError` for anything else).

**A real correctness wrinkle found via code reading, not assumed**: pySHACL does **not** use plain `owlrl.RDFS_Semantics` for `inference="rdfs"`/`"both"`/`"all"`/`"rdfsowlrl"` - it uses its own `pyshacl.inference.CustomRDFSSemantics`/`CustomRDFSOWLRLSemantics` (`pyshacl/inference/custom_rdfs_closure.py`), which override `one_time_rules()` to a no-op. Confirmed exactly what that suppresses: stock `owlrl.RDFSClosure.RDFS_Semantics.one_time_rules()` implements a "hidden sameAs" rule - for every pair of literals *anywhere* in the graph sharing the same semantic value but a different lexical form, it duplicates every triple using one to also use the other, across any unrelated subjects/predicates - pySHACL's own source comment: *"breaks some SHACL validation tests."* Naively substituting our own general-purpose `ENTAILMENT.RDFS` dispatch (plain `owlrl.RDFS_Semantics`) would have silently reintroduced exactly that.

**`inference="owlrl"` alone needed no such substitution** - confirmed pySHACL uses plain `owlrl.OWLRL_Semantics` directly for that one case, identical to this project's own `ENTAILMENT["OWL-RDF-Based"]` regime, so it safely delegates to the same shared helper as `sh:entailment`.

New `_apply_pyshacl_inference(data_graph, inference_option, ont_graph=None, *, inplace)` in `entailment.py`: `None`/`"none"` is a no-op; `"owlrl"` delegates to `_apply_entailment_regimes`; `"rdfs"`/`"both"`/`"all"`/`"rdfsowlrl"` get a small, separate decompose/closure/diff implementation (`_custom_rdfs_delta`) importing pySHACL's own `Custom*Semantics` classes directly and reusing `starlayer.graph.compare._decompose` - deliberately **not** exposed as a new `StarLayerGraph.infer()` profile, since this is pySHACL's own specific workaround, not a general RDF-1.2 graph capability. Wired into `validate()`: `inference` is popped out of `options` before encoding (same pattern as the existing `meta_shacl` pop) and no longer forwarded to pySHACL's own `validate_fn` - the work now happens before encoding, once, through our own engine.

Verified via this project's own oracle discipline: `test_pyshacl_inference_compat.py` compares `validate(..., inference=...)` directly against plain `pyshacl.validate(..., inference=...)` for `"rdfs"`/`"both"`/`"owlrl"`, confirming identical conformance results - not just "doesn't crash." Full `tests/shacl` suite: 1080 passed (was 1070 - 10 new tests across `test_entailment.py`/`test_pyshacl_inference_compat.py`), zero regressions.

Scope note: this entire change is confined to the bare `validate()`/`apply_rules()` functions (step 1 of the two-step `StarShaclSchema` flip, still in progress) - `StarShaclSchema.validate()`'s own class method is untouched and still has neither the `ont_graph` fix nor the `inference=` replacement; it will inherit both for free once step 2 (making the method delegate to the bare function) happens.

## `apply_rules()`'s post-rules `inference=` pass now persists, matching `sh:entailment`'s own already-correct behavior (2026-10-07)

Checked against the spec text directly (fresh `WebFetch` of both the SHACL 1.2 Core and Inference Rules documents), not just against what the current implementation happened to do: the spec mandates entailment be visible at exactly **one** point - "during the validation process" (Core §1.4), i.e. after every rule (shape-attached and global) has run, when the complete evaluation graph gets checked. It says nothing about entailment needing to be visible to rules *while* they execute - the "before rules" pass this project added (`validate()`'s own unconditional `apply_entailment()` call, which shape-attached `sh:rule` execution then sees for free) is our own extrapolation, not a cited requirement. The "after rules" point is the one the spec actually obligates.

**Found a real gap at exactly that mandated point, via a live worked example**: `apply_rules()`'s existing re-application of `sh:entailment` after the global-rules pass (`apply_entailment(out_data, normalized_shapes, ont_graph, inplace=True)`, added earlier this same day) already forces `inplace=True` so it persists into `out_data`. `inference=` had no equivalent - it only ever ran *inside* the final re-validation call, governed by the `"validation"` profile's own unrelated `inplace=False` default. Confirmed live: `conforms` correctly reflected the entailed triple (`False`), but the triple itself was never materialized into `result.data_graph` (`False`) - computed into a disposable temporary graph used only for that one conformance check, then discarded.

Fixed by giving `inference=` the identical explicit, forced-`inplace=True` treatment as `sh:entailment`, at the identical call site (`validator.py`, right after the `apply_entailment()` re-application, before building `final_options`): `if inference_option is not None and inference_option != "none": _apply_pyshacl_inference(out_data, inference_option, ont_graph, inplace=True)`. The final re-validation call still carries `inference=` through in its own `final_options` (unchanged) and re-runs it once more internally - redundant but idempotent (nothing new to entail against an already-closed graph), the same accepted redundancy `sh:entailment`'s own re-application already has with `validate()`'s internal first-pass call.

Regression test: `test_pyshacl_inference_compat.py::TestInferenceSurvivesApplyRulesGlobalRulePass` - a global `sh:SPARQLRule` asserts a new triple, an `rdfs:domain` axiom living only in `ont_graph` should entail a type from it, confirmed present in the returned `data_graph` (not just reflected in `conforms`). Full `tests/shacl` suite: 1081 passed (was 1080), zero regressions.

**Superseded by the very next entry below, same day**: the fix here (force `inplace=True` so the post-rules `inference=` pass persists into `out_data`) is still correct and still needed internally, but `out_data` stopped being what `RulesResult.data_graph` returns at all - see below. The regression test's own assertion was flipped accordingly (entailed triple now asserted *absent* from `result.data_graph`, not present).

## `apply_rules()`'s `data_graph` becomes strictly the "inference graph" - rule output only, caller's own graph never touched (2026-10-07)

A direct follow-up question ("what graph gets returned, the new triples, or the full graph? I thought it was new triples") led to checking the spec rather than assuming the existing merge-everything-together behavior was right. It wasn't, on two independent counts:

**"New triples" is a real, named spec concept - "the full graph" never was.** The SHACL 1.2 Inference Rules spec: *"The new triples that are produced by a rules engine are called the inferred triples. The inference graph consists of these inferred triples."* That's the one thing the spec actually names. The **evaluation graph** (base ∪ inference) is only ever described as "the active query graph" used *during* rule execution and validation - a working/computational concept, not a stated deliverable. The spec doesn't explicitly say what a processor should return, but `RulesResult.data_graph` merging base + rules + entailment all together (the prior design) had no spec grounding at all - it was this project's own invention.

**Entailment-produced triples specifically should never have been persisted.** SHACL Core §1.4 scopes entailment's role to being visible "during the validation process" - a validation-time device, not domain output. The spec gives zero guidance on merging OWL/RDFS entailment into any returned result. Baking entailment output into `data_graph` means a declared `sh:entailment`/`inference=` regime (which can add a lot of structural noise - universal `rdfs:Resource` typing, reflexive `subClassOf`, etc.) pollutes what's supposed to be "what the rules said."

**User's own explicit design decision, via two rounds of `AskUserQuestion`** (recorded here since neither reads as inevitable from the spec alone):
1. `RulesResult.data_graph` = strictly the inference graph (rule-produced triples only) - not base+rules, not base+rules+entailment.
2. The caller's own `data_graph` object must remain **completely untouched** - not even mutated with rule output. A private working copy is mutated through the whole pipeline instead; only the pure rule-produced delta from that copy gets returned.

**Implementation** (`apply_rules()`, `validator.py`): `base_triples = frozenset(data_graph)` captured before anything happens; `out_data` becomes a fresh `type(data_graph)()` copy (triples + namespace bindings), used for every subsequent step instead of the caller's object. A new `entailment_triples: set` accumulator, filled via a local `_apply_and_track()` helper (snapshot before/after each entailment-producing call) at every one of the three points entailment can run: the "before rules" `sh:entailment`/`inference=` pass (now applied explicitly in `apply_rules()` itself, *before* calling the first `validate(profile="rules", ...)`, rather than left to that call's own internal handling - deliberately redundant with that call's own internal pass, which becomes a no-op since the regime is already satisfied, matching the project's existing "accept redundant idempotent re-application" pattern), and both "after rules" re-applications (`sh:entailment`, `inference=` - already explicit call sites, just wrapped with the same tracking). ## `evaluate()` gains `sh:entailment`/`inference=` support, with a deliberately different design than `apply_rules()`'s own exclusion (2026-10-07)

Direct follow-up, same session: having just finished making `inference=` consistent across `validate()`'s two implementations, the user asked "should evaluate allow for inference? seems so to be consistent" - confirmed a real gap, not just a doc gap: `evaluate()` had no `**kwargs`, no `inference=`, and never read `shacl_graph`'s own `sh:entailment` declarations either, unlike every other processing-mode function. Concretely: a focus node that's only a member of `sh:targetClass ex:Employee` via an entailed fact (e.g. `rdfs:domain`) would never even get its virtual properties computed, since target resolution ran against raw `data_graph` with no entailment applied at all.

**A real design fork, confirmed via `AskUserQuestion` rather than assumed**: once entailment makes a node a valid target, should an entailed (non-asserted) triple also count as a "real, stored" value for a property shape's own `sh:path` in the returned subgraph? Two defensible answers - either exclude entailed triples from the result the way `apply_rules()` excludes entailment from its own "inference graph" (entailment only helps correctly compute something else, never contributes to the output itself), or let entailment feed the whole computation uniformly, the same way `validate()` already treats an entailed triple identically to an asserted one when checking constraints. **User chose the latter** - confirmed as the better fit on reflection too: SHACL Core's own "Value Nodes of Property Shapes" algorithm doesn't itself distinguish asserted from entailed triples at all, whereas `apply_rules()`'s "inference graph" is a different, additive concept (newly-produced facts) that entailment was never part of in the first place - these are two genuinely different relationships to entailment, not an inconsistency to resolve in favor of one or the other uniformly.

**Implementation**, both the bare `evaluate()` function and `StarShaclSchema.evaluate()`'s own (still-duplicated) method body: new keyword-only `inference: str | None = None` parameter (not a generic `**kwargs` - `evaluate()` has no other passthrough options, so an explicit parameter is more precise). Right after the `shacl_graph is None` check, `apply_entailment(data_graph, shacl_graph, ont_graph, inplace=False)` and (if `inference` given) `_apply_pyshacl_inference(data_graph, inference, ont_graph, inplace=False)` reassign `data_graph` to a private, non-mutating copy - `inplace=False` unconditionally, since `evaluate()` has always guaranteed it never mutates the caller's own `data_graph`, entailment or not (the common no-entailment-declared case is a no-op passthrough of the same object either way). Every subsequent step - target-node resolution, `sh:values`/`sh:defaultValue` computation, and the "stored" value reads - then runs against that entailed copy uniformly, with no special-casing needed anywhere else in the function.

Verified live: a property shape targeting `ex:Employee` with an `rdfs:domain`-only-in-`ont_graph` axiom computes nothing at all without `inference="rdfs"`, and correctly includes the real `ex:worksAt` value once given it - confirming both the targeting effect and the "entailment feeds stored values too" design choice work together. Full `tests/shacl` suite: 1083 passed, zero regressions (no existing test exercised entailment through `evaluate()` before, since the capability didn't exist).

## `validate()` raises by default on unresolved `owl:imports`; `ignore_imports=True` opts out explicitly (2026-10-08)

Direct follow-up, same conversation. Before this, `validate()`'s own documented behavior (see the consolidation entry above, and `starlayer/graph/CLAUDE.md`'s dated entry) was: no `shapes_graph_loader=` given → `shacl_graph` used exactly as provided, `owl:imports` silently left unresolved, no indication anything was skipped. The user correctly identified this as a real risk, not just an inconsistency: a shape referencing something only defined in the unresolved import simply never fires, silently under-validating - "using an ontology with imports without doing the import leads to incomplete results... inconsistent with the desire of the ontology owner."

**The harder design question, settled before implementing**: should `validate()` try to detect "has this already been resolved" automatically from the graph's own content, so it only raises on *genuinely* missing imports? No - and the user's own example proved why directly: `resolve_imports()` never strips the `owl:imports` triple once it merges the imported content in (it's still a true, accurate fact about the document's own dependencies, not something to erase). ## `has_import_locally()` - a real false-positive found in both `resolve_imports()` and `validate()`'s new check, not hypothetical (2026-10-08)

Direct follow-up, same conversation: the user pointed out `owl:imports` has two genuinely different shapes - the "ontology-style" external reference the whole design so far assumed (needs a loader to fetch content from somewhere else), and a second, equally real case: two shapes-graph "modules" that import each other but have simply been loaded together into one single `StarLayerGraph`, with nothing external to fetch at all. Confirmed live before touching anything, not assumed: built exactly that scenario (`ModuleA owl:imports ModuleB`, both `ModuleA`'s and `ModuleB`'s own shapes already present in one graph) and ran it through `validate()` with no loader - it raised the brand-new "unresolved owl:imports" error from the previous entry, even though `CompanyShape` (from "ModuleB") was right there and would have validated correctly if `validate()` had just proceeded. A real regression the ink had barely dried on, not a stretch.

**Went deeper than just `validate()`'s check, confirmed live**: `owl_imports()` scans the *whole* graph for any `owl:imports` triple, regardless of subject - not scoped to "this graph's own identity." So even `ModuleB`'s own `owl:imports ModuleC` (also already co-located in the same graph) got added to `resolve_imports()`'s own pending queue, and it dutifully called `loader(ModuleC)` for something that was never missing in the first place - confirmed via a live test with a logging loader before fixing anything.

**The fix**: `has_import_locally(iri) -> bool` - a new `StarLayerGraph` method, `any(True for _ in self.triples((iri, None, None)))`: true if `iri` already has its own content present in this same graph. `resolve_imports()`'s own loop now checks this *before* ever calling `loader` for a pending import - a locally-satisfied one is skipped entirely, no loader call, nothing to merge (it's already part of `self`'s own content, which `"full"`/`"in-place"` already include). This also made `loader` itself genuinely optional on `resolve_imports()` (default `None`) - not merely "allowed to be `None`" as a loose end from an earlier discussion in this same conversation, but now actually *useful*: a graph whose declared imports are all locally satisfied needs no loader whatsoever to resolve correctly.

**`validate()`'s own check updated to match**: both implementations now filter `shacl_graph.owl_imports()` through `not shacl_graph.has_import_locally(o)` before deciding whether to raise - only genuinely external, unresolved imports trigger the error; a locally-satisfied one is simply fine as-is, no `ignore_imports=True` needed for it. The error message's own wording updated to say "that aren't already locally satisfied," so a caller hitting it for a genuinely external import isn't confused by language that would otherwise also describe the (now correctly excluded) local case.

**Still correctly separate from `ignore_imports=True`, not folded into `has_import_locally()`** - the two false positives are different in kind: `has_import_locally()` only ever catches "already co-located in the very same graph," which is directly, cheaply checkable from the graph's own content. It cannot and does not attempt to catch "already resolved via a loader at some earlier point, then handed back to `validate()` without one this time" - that case is genuinely unknowable from content alone (the previous entry's own finding, unchanged), which is exactly why `ignore_imports=True` still exists as a separate, explicit, caller-stated flag rather than being subsumed by this new check.

New tests: `tests/graph/unit/test_resolve_imports.py::TestHasImportLocally` (2 cases) and `::TestResolveImportsSameGraphCoLocation` (4 cases - loader never called for a locally-satisfied import; `resolve_imports()` works with no `loader=` argument at all when everything is local; a locally-satisfied module's own further import isn't chased either, confirming the whole-graph-scan interaction specifically; a mixed case where one import is local and one is genuinely external, confirming only the external one ever reaches the loader). `tests/shacl/integration/test_shapes_graph_imports.py::test_imports_already_co_located_in_shacl_graph_need_no_loader_and_do_not_raise` - the full `validate()`-level reproduction of the original false positive, confirming both that it no longer raises *and* that the co-located shape genuinely gets applied (catches a real violation), not just that the call doesn't crash.

## `StarShaclSchema.extract_shapes_graph()`: the inverse of SHACL 1.2 Profiling §2 packaging, honoring all three membership mechanisms (2026-10-09)

Built while working on the Profiling user guide's Section 1 (demonstrating one SHACL graph containing two `sh:ShapesGraph`-typed modules side by side, then pulling one back out by IRI) - the user asked for a method on `StarShaclSchema` to do that pulling-out. New `extract_shapes_graph(shapes_graph_iri)`: returns `None` if `shapes_graph_iri` isn't typed `a sh:ShapesGraph` in `self.shacl_graph`; otherwise returns a standalone graph containing that module's own content, built from `StarLayerGraph.cbd()` calls.

**A real incompleteness in the first implementation, caught by the user before it shipped**: that first version only checked `rdfs:member` (ShapesGraph → shape, forward direction) for membership. User's own correction: *"I am not sure cbd works. There are a variety ot ways that the ShapesGraph can be formed. oe is a shape declares itself part of the ShapesGraph, or the ShapesGraph defines its members or it imports. I think those all resovle to the shapes grpah."* Confirmed directly against `docs/shacl/shacl12-gap-matrix.md`'s own prior spec research (not assumed) that this is spec-accurate, not a misunderstanding: *"Section 2's packaging recommendations (`sh:ShapesGraph`/`sh:DataGraph` grouping via `rdfs:isDefinedBy`/`rdfs:member`/`owl:imports`)"* - three real mechanisms, not one.

**Fixed to honor all three**: (1) `rdfs:member` (ShapesGraph declares its members, forward - the original), (2) `rdfs:isDefinedBy` (a shape declares *itself* part of a ShapesGraph, inverse - the gap found), (3) `owl:imports` among `sh:ShapesGraph` nodes **already locally present in the same `shacl_graph`** - a pending-queue walk (`shapes_graph_nodes`) starting from `shapes_graph_iri`, following each `owl:imports` object only if it's also typed `a sh:ShapesGraph` in `self.shacl_graph`, cycle-safe via a seen-set. Deliberately scoped like `has_import_locally()`/`resolve_imports()` elsewhere in this file - no `loader=` parameter here at all, so an import to a module not already co-located in `shacl_graph` is simply left unresolved (its bare `owl:imports` triple still appears in the result via CBD, just not expanded). For every ShapesGraph node discovered this way, members are collected from *both* directions (`sg.objects(node, RDFS.member)` and `sg.subjects(RDFS.isDefinedBy, node)`), then each ShapesGraph node and each member gets its own `cbd()` call merged into the result - same reasoning as before: CBD alone doesn't follow a named-IRI `rdfs:member` object, so each member's own content needs an explicit CBD call to come along.

**Design, confirmed against a real gap before shipping**: `shapes_graph=`, one parameter, renamed from `shapes_graph_module=` on every method that had it (`target_nodes()`, `apply_rules()`, `evaluate()`, `extract_subgraph()`, `close_shape()`, `validate()`) - mechanical rename on all but `validate()`/`validate_each()`, which alone fold in the former separate `shapes_graph_iri=`:

- Names a real module within the bound `shacl_graph` → that module is validated against, its own IRI becomes `sh:usedShapesGraph` directly - no second value possible.
- `shacl_graph` is bound but doesn't contain it as a module → read purely as a report-provenance tag (the old `shapes_graph_iri=` behavior), validate against the whole bound graph unchanged. Safe precisely because a real graph being bound makes "this must be external" a positive inference, not a guess.
- **No bound `shacl_graph` at all → raises**, not a silent tag-only fallback. Caught live, not assumed: `StarShaclSchema().validate(data_graph=..., shapes_graph=EX.Something)` with no bound shapes graph previously raised ("needs a bound shapes graph to extract from"); the first version of this redesign *removed* that raise (nothing to check membership against, so "must be external" seemed to follow) - but a live check showed pyshacl trivially "conforms" against a `None` shapes graph, so the report would end up claiming `sh:usedShapesGraph <EX.Something>` for a run that validated against nothing at all. Restored the raise for this specific case, keeping the "real graph present but doesn't contain it" case as the only tag-only fallback - the two "no module" cases needed different treatment, not one blanket rule.
- A `Literal` value (SHACL 1.2 Core explicitly allows a versioned graph IRI as one) is preserved as-is, not coerced to `URIRef` - same coercion `_annotate_used_graphs_and_configuration()` already uses, caught by a pre-existing test (`shapes_graph_iri=Literal(...)`) that would have silently started failing otherwise.

**Implementation**: new `_resolve_shapes_graph_and_provenance()` alongside the existing `_resolve_shacl_graph()` (kept, used unchanged by every method without a report to fall back on - a non-module value there still raises, since there's no sensible second meaning for it). `validate()`'s own body replaced its old `if shapes_graph_module is not None and shapes_graph_iri is None: shapes_graph_iri = shapes_graph_module` two-step with one `shacl_graph_to_use, shapes_graph_iri = self._resolve_shapes_graph_and_provenance(shapes_graph)` call; everything downstream (the `.identifier` fallback, `_merge_derived_conforms_to()`) reads the same `shapes_graph_iri` local variable as before, unchanged.

## `meta_validate()` gains a content-keyed result cache - found via a real retrospective performance audit, not a targeted investigation (2026-10-12)

Found while diagnosing why `tests/sparql/unit/test_shacl_shapes.py` (136 tests, each calling `starlayer.sparql.salg.sparql_shapes.validate_query()`) took 241s even after an unrelated `StarLayerGraph.__len__()` O(n)→O(1) fix (see `starlayer/graph/CLAUDE.md`'s same-day entry) had already cut it down from an estimated ~4200s. Profiled the remainder directly (`cProfile` on a single `validate_query()` call against a trivial 1-triple data graph): **31 seconds**, flat, with no growth across repeated calls - `meta_validate()`'s own `build_meta_shapes_graph()` call (~30ms - not the bottleneck) followed by a full, completely uncached `pyshacl.validate()` pass checking the caller's ~1700-triple shapes+ontology graph against the meta-shapes graph (deliberately deep, `max_validation_depth=30` per this function's own existing comment) - paid in full, every single call, for a check whose outcome is 100% deterministic given the same input content.

**Why this was never cached before**: nothing in this function's own design ever considered it - `meta_validate()` was written as a straightforward wrapper, not with repeated-call reuse in mind. The real-world exposure is specific to callers like `validate_query()` that call it over and over against the *same* bundled shapes/ontology content (once per test case, once per real caller invocation) - a pattern this module's own code had no visibility into.

**Cache key is content, not object identity - confirmed load-bearing, not a style choice**: a typical caller (`starontology`'s own `shapes_graph()`/`ontology_graph()`, or any function reparsing the same Turtle text) constructs a *brand-new* `Graph` object on every call, with fresh, arbitrary blank node labels every time rdflib parses the same source text. An identity-keyed cache (or a naive raw-serialization-text-keyed one) would never hit at all. Used `starlayer.graph.rdfc.rdfc10_hash()` - this project's own existing canonical-hashing tool, built for exactly this "same content, different object, different blank node labels" problem elsewhere - confirmed live that two independent reparses of identical shapes Turtle produce the identical `rdfc10_hash` despite different N-Triples text. Cost: ~20-25ms on this ~1700-triple graph, against a ~930ms-950ms cache miss - a cache hit's overhead is a small fraction of what it replaces.

**Scope deliberately narrow, not a general-purpose cache**: only engaged when `extra_graphs` is empty (`_meta_validate_cache_key()` returns `None` otherwise, falling through to the old uncached path unchanged) - hashing an arbitrary tuple of caller-supplied graphs too would add real complexity for a case this session found to be rare in practice (11 of 291 `.validate(` call sites in `tests/shacl` pass `meta_shacl=True` at all, and `extra_graphs` usage is rarer still). A bounded LRU (`_META_VALIDATE_CACHE`, `_META_VALIDATE_CACHE_MAXSIZE = 256`), same pattern as `starlayer.graph.model.encoding`'s `_TT_HASH_MEMO`. A cache hit returns a **fresh copy** of the cached `report_graph`, never the shared object itself - `meta_validate()` is called directly by test/caller code too, not just the one discard-the-result call site in `validator.py`'s own preflight, so a hit handing back a mutable object some other caller could go on to corrupt would be a real, if narrow, risk.

**A real correctness bug found and fixed during verification, not assumed safe**: `rdfc10_hash()` raised `AssertionError` ("blank node ... was never assigned a canonical identifier") on one specific real shapes graph, from `test_validate_uses_integrated_structural_property_path_for_has_value` - a genuine, pre-existing edge case in the RDFC-1.0 canonicalization algorithm, unrelated to this cache, now newly reachable because this cache is the first caller to run it against *arbitrary* caller-supplied shapes graphs rather than curated input. Fixed by wrapping the hash computation in `try/except Exception: return None` inside `_meta_validate_cache_key()` - a caching *optimization* must never be able to turn a graph that validated correctly before into one that raises; any hashing failure simply falls through to the uncached path, identical to the `extra_graphs`-present case.

**Impact, measured end to end**: `validate_query()` against trivial data: ~1.4s → ~0.2s on repeat calls (fresh graph each time, cache still hits on content). `test_shacl_shapes.py` (136 tests): 241s → 43s. Full `tests/shacl` suite (1149 tests, many of which exercise `meta_shacl=True` paths): 15.75s - confirmed this cache is very likely the single largest remaining cost that had been silently inflating *any* repeated `meta_shacl=True` caller across the whole project, not specific to this one file. Full `tests/shacl`+`tests/starontology`: 1191 passed, zero regressions once the `rdfc10_hash` edge case above was made fail-safe.

## `check_sparql_query_text()` now also validates embedded SPARQL *structure*, via SALG (2026-10-14)

Notes-file question: "when running SHACL - Sparql do we use our Sparql shacl to validate the structure of the internal sparql?" Answer was no - `check_sparql_query_text()` only ever confirmed a `sh:select`/`sh:ask`/`sh:construct` literal *parses*. Extended it to additionally encode a successfully-parsed query as a `salg:` (SPARQL-algebra-as-RDF) graph and validate it against `starlayer.sparql.salg`'s own general-purpose SPARQL-structure shapes - which already has a real check for an unbound projected variable (`salg:noUnboundProjectedVariables`), just never pointed at a SHACL shape's own embedded query text before. Runs unconditionally whenever `check_sparql_query_text()` itself runs (i.e. whenever `meta_shacl=True`, the default in every `validation_modes.py` preset) - not a separate opt-in, on explicit user direction, since `meta_shacl` already runs the plain parse check unconditionally and the whole point is to actually catch this class of bug in real shape libraries, not require remembering to turn it on. Results cached per distinct (predicate, text, prefixes, is_target - see below), mirroring `meta_validate()`'s own existing cache.

**Two real bugs found and fixed while building this, both via actually exercising the full test suite, not assumed away**:

1. **Infinite recursion**: `salg.validate_query()`'s own internal `starlayer.shacl.validate()` call didn't disable `meta_shacl`, and its own shapes graph (merging in `starontology`'s `spexpr_shacl`) genuinely contains its own `sh:select` literals (`ExpressionShape`'s supporting shapes) - so the new structural check, run against `validate_query()`'s own shapes graph, called back into `validate_query()` itself, forever (confirmed live: `RecursionError`/`maximum recursion depth exceeded`). Fixed by passing `meta_shacl=False` explicitly in that one internal call - this project's own bundled shapes/ontology are already vetted by that module's own test suite, not arbitrary caller content, so there's nothing to gain from re-running the full preflight on every `validate_query()` call anyway.
2. **A real false positive, caught by the full suite, not anticipated up front**: SHACL-SPARQL's pre-bound pseudo-variables (`$this`/`$value`/`$PATH`) are supplied externally by pySHACL's own execution machinery before a *constraint* or *rule* query ever runs - never bound by anything in the query's own pattern. `salg:noUnboundProjectedVariables` has no SHACL awareness, so an extremely common, perfectly valid `$this`-only validator (`SELECT $this WHERE { FILTER(...) }`) was flagged as a false positive. Added `_is_prebound_variable_only_report()` to suppress exactly this (only when every violation names one of these three, nothing else).

**A third, subtler correctness issue found from a direct user question after the above shipped**: does this exemption also apply to a SPARQL-based **target** (`sh:target [ a sh:SPARQLTarget ; sh:select ... ]`, SHACL-AF's `SPARQLTarget`)? No - and the exemption as first written wrongly suppressed it there too. A target query's `$this` has the *opposite* semantics from a constraint/rule's: it's not pre-bound at all, it's exactly what the query's own pattern is supposed to *compute* - an unbound `$this` in a target query is a real defect (the target would never select any candidate), confirmed live before fixing (a target query that never binds `$this` silently passed). Fixed by detecting `is_target` (whether `query_node` is itself the object of a `sh:target` triple anywhere in the shapes graph) and only applying the pre-bound exemption when `False`; the cache key now includes `is_target` too, since the same literal text could in principle appear in both roles. `sh:targetWhere` (SHACL 1.2's other new target type) is unaffected by any of this - its value is an ordinary `NodeShape`, not a SPARQL query at all, so it never reaches `sh:select`/`sh:ask`/`sh:construct` in the first place.

## The `sh:targetWhere` flake is fixed: post-processing picked the wrong `sh:ValidationReport` node (2026-10-16)

`test_new_target_types.py::test_target_where_candidate_not_excluded_by_unrelated_focus_node_data` and the W3C fixture `targetWhere-001` failed intermittently for a long time (the entries above call it a known, unexplained flake: "roughly 1 in 15-20 runs"). Reproduced in one process at 6.5%, and across `PYTHONHASHSEED` values anywhere from 0% to 85% - the dependence on hash seed is the clue that graph/set iteration order decides it.

**Root cause.** Six post-processing steps in `validator.py` each located "the report node" with `next(<first node typed sh:ValidationReport>)`. That is only correct when the report holds exactly one such node. A fixture using `sht:dataGraph <>` keeps its own expected `mf:result [ a sh:ValidationReport ... ]` block in the *data*, and when a violation's `sh:value`/`sh:focusNode` is that block, pySHACL copies it into the output report - a second, incidental `sh:ValidationReport`-typed node. One of the six steps, `_relabel_validation_report_node`, *renames* the chosen node to the short label `report` and rewrites every triple mentioning it. If the incidental copy was found first, a **data node was renamed inside the results**; the violation then named `report`, not the original node. `_nodes_conforming_to` (the batched nested validation behind `sh:targetWhere`) reads focus nodes back out of the report, so it no longer saw that node as violating, judged it conforming, made it a target of the outer shape, and the outer validation produced a spurious extra result and a second `sh:ValidationReport`. Validating that node alone reported it correctly, which is why it looked batch-specific.

**Fix.** All six sites now call `_find_genuine_report_node()`. That function was already there (added to disambiguate exactly this, but only used in one place) and was hardened: it ignores the library's own `<graph> sh:validationReport <report>` link when deciding which node nothing refers to, and it breaks any remaining tie deterministically (most `sh:result`, then label) so the answer cannot depend on iteration order. Result: 0 failures in 150 runs under each of six hash seeds that previously failed up to 128/150. Deterministic regression test: `tests/shacl/unit/test_genuine_report_node.py` (both insertion orders; run against the old code it fails by renaming the data node to `report`).

## `select_widgets()` reworked: dict result, keyword-only nodes, spec-faithful matchers, schema method (2026-10-17)

Done while rewriting `docs/guides/04d-shacl-ui.ipynb`; the notebook and the library now agree.

- **`select_widgets()` returns `{property_shape: widget}`** (a dict, not a graph of `shui:editor`/`shui:viewer` triples), with `None` for a property that has no widget, so every `sh:property` of the shape is a key. A graph carried no prefixes and printed as `ns1:`/`ns2:`; a dict is what a form needs. Ruled out for now: carrying the widgets in the graph `evaluate()` returns (flag on `evaluate`) - needs a decision on where the widget triple goes (per shape, per value triple's reifier, or per focus node/property node), see the discussion in the session.
- **`shape_node` and `focus_node` are keyword-only** on `select_widget`, `select_widgets` and the schema method. `focus_node` and `data_graph` are optional; they matter only for a matcher's `shui:dataGraphShape`.
- **Matcher function now follows SHACL 1.2 UI §3.4 step for step** (checked against the live spec text): no focus node + a `dataGraphShape` + no `shapesGraphShape` rejects the widget; `shapesGraphShape` validates the shape node *in the shapes graph* using shapes read from the scoring graph (before, it looked for the property shape in the scoring graph, so a separate scoring graph picked the wrong widget); `dataGraphShape` shapes are read from the shapes graph (the scoring graph is searched too, a deliberate widening). Equal scores are now ordered by widget IRI (§3.5).
- **`StarShaclSchema.select_widgets()`** uses the bound `shacl_graph`; `data_graph` and the new constructor argument `scoring_graph` are bound on the schema and can each be overridden per call (an empty graph switches a bound catalog off for one call).
- **No scoring catalog ships with the library**: the spec publishes none (only `score-validator.ttl`, already shipped as `stsh:WidgetScoreShape`); the built-in widgets' scores are prose in §9, and the multi-scores-per-widget rules don't map cleanly onto one matcher per widget. A pre-publish checklist (including how to regenerate the guide's static widget appendix) is in `docs/future_enhancements.md`.

## `meta_shacl` is now off by default (2026-10-17)

All three validation modes (`validation`, `rules`, `debug` in `validation_modes.py`) now set `meta_shacl=False`; pass `meta_shacl=True` to `validate()` / `StarShaclSchema.validate()` to get the shapes-graph preflight. **Why:** the preflight checks the *shapes graph itself*, which is a development-time concern - check a shapes graph when it is written, not on every call. Measured on `srl_validate` (a 119-triple tree against the shipped SRL shapes): about 310 ms with the preflight, about 110 ms without, so the preflight was roughly half of every small validation; every use of a shipped shapes graph (SRL, SQE, `salg`, ...) was re-checking graphs the project already vets in its own tests. Loading the shipped shapes graphs is not the bottleneck (about 19 ms of the 310).

**Tests:** the 25 tests that exercise the preflight (`test_meta_shapes_extensions.py`, `test_meta_shacl_integration.py`, `test_native_backend_oxigraph.py`) now request it with `meta_shacl=True`; the old "raises by default" test became `test_meta_shacl_is_off_by_default` plus an explicit-request test. Fast tier: 4080 passed. The eight guides that mention `meta_shacl` still execute, with output differences only in triple order.

**Behavior change to know about:** a malformed shapes graph is no longer rejected up front by default. Malformed shapes can now surface later, or not at all, as odd validation results. **New fast-tier test:** `tests/starontology/unit/test_shipped_shapes_meta_validate.py` runs `meta_validate()` over every registered `*_shacl` graph plus `shacl_meta` (read from the registry, so new entries are covered automatically) and has a negative case so it cannot pass vacuously; all seven shipped graphs pass (about 4 s). Not done: a construction-time check (`StarShaclSchema(shapes, ...)` validating its shapes graph once when it is created), which would match the "validate when created" intent without the per-call cost.

## `report_text` no longer prints "Not specified" provenance placeholders (2026-10-17)

The `Provenance:` appendix `validate()` adds to `report_text` (`_append_provenance_to_report_text`) used to print `Used Data Graph: Not specified`, `Used Shapes Graph: Not specified` and `Conforms To: Not specified` whenever the report had no graph identities, so every plain `validate(data, shapes)` ended with a block of statements the report had no data for (the `report_graph` itself never carried those triples in that case). Now each line is added only when there is something to say: `Used Data Graph`/`Used Shapes Graph` when the report has `sh:usedDataGraph`/`sh:usedShapesGraph`, and the `sh:conformsTo`/`dcterms:conformsTo` sentence only when the triple exists (so only for a conforming result with both identities known). When nothing is known, no `Provenance:` block is added and `report_text` is pySHACL's own text unchanged. `report_text` and `report_graph` now agree on what the report knows. Tests: `tests/shacl/integration/test_report_text_provenance.py`.

### Follow-up, same day: the `Conforms:` line of `report_text` now matches the recomputed value

Checking whether any *other* post-processing leaves `report_text` behind `report_graph` found one real divergence. `validate()` recomputes conformance itself (`_annotate_conformance_disallows`) because pySHACL has no notion of SHACL 1.2's `sh:Debug`/`sh:Trace` severities, which never block conformance. For a result of only that severity, `ValidationResult.conforms` and `report_graph`'s `sh:conforms` were correctly true, but pySHACL's own rendered `report_text` still said `Conforms: False`. `_sync_report_text_conforms` now rewrites that one line (the first `Conforms:` line) to the recomputed value in both `validate()` implementations; the result listing below it is left as pySHACL wrote it. Every other severity and `allow_warnings`/`allow_infos` combination was thought to agree with pySHACL; that was wrong for `allow_warnings` alone (an Info result still blocked), found and fixed 2026-10-25 (issue #51, see the entry on small differences from pySHACL). Other post-processing was checked: the used-graph and `sh:conformsTo` triples are covered by the `Provenance:` block, and `sh:conformanceDisallows` is extra information, not a contradiction. Tests: `test_report_text_provenance.py`.

## One profiles document; StarLayer profiles sit between shapes graphs and the public layer; `derive_conforms_to()` follows the chain (2026-10-17)

The ontology-to-shapes mapping and the library conformance declarations (`shacl12-conformance-profile.ttl`, `starlayer-conformance.ttl`) were merged into one document, `starlayer-profiles.ttl`, stored as a named graph in `starontology.trig` (and published standalone). Loaded by `starontology.get_conformance_profiles()`; the registry key for fetching it is `"starlayer_profiles"`. `scripts/assets/`, `starlayer.shacl.asset_urls` and the old mapping file are gone. `starlayer.conformance.declared_conformance()` and `declared_conformance_profile()` now only read the three module resources (`pkg:graph`, `pkg:sparql`, `pkg:shacl`) out of it; all claims are plain Turtle (a test checks the entailment regimes against `SUPPORTED_REGIMES`).

**Model.** The public layer (W3C specifications, public SHACL profiles) is only labelled. StarLayer defines its own profiles (`slp:Manchester`, `slp:Skos`, `slp:SparqlQuery`, `slp:SparqlRL`, `slp:Shacl`), each a `prof:Profile` that is `prof:isProfileOf` the public specification or SHACL profiles and lists its ontology (`role:schema`) and shapes (`role:validation`) files with `prof:hasResource`. A shapes graph is no longer declared `prof:isProfileOf` the public specification itself.

**`derive_conforms_to()` extension (deviates from SHACL 1.2 Profiling §5.5, which is MAY-level).** The second rule keeps the §5.5 branch (`shapes prof:isProfileOf ?spec`) and adds a branch: shapes graph listed as a `role:validation` artifact of a profile -> `dcterms:conformsTo` that profile and everything up its `prof:isProfileOf*` chain. So data validated against `skos_shapes` now reports conformance to `slp:Skos` and to the SKOS Reference.

UI claims, resolved 2026-10-17: the SHACL UI *Profile* (`profile/ui`) is neither claimed nor excluded - Profiling A.3 defines it as an unlisted subset of SHACL Core with no conformance requirements (TODO), and the earlier `doesNotConformTo profile:ui` rested on confusing it with the UI specification's widget-selection algorithm; that triple was removed. `starlayer.shacl` now `dcterms:conformsTo <https://www.w3.org/TR/shacl12-ui>` (the specification), on the owner's decision, with its scope limits in an `rdfs:comment`: `shui:propertyRole` is accepted but not interpreted, and no default widget scoring catalog ships.

## starontology files are the source; the meta-shapes build moved to `scripts/` (2026-10-17)

**Direction flipped.** The per-entry `.ttl` files in `starlayer/starontology/` are now the source, and `starontology.trig` is generated from them (it used to be the source, with the `.ttl` files generated from it by `publish_starontology_files.py`). Why: the trig conflicted on every merge (it did twice in the `appendix-a` merge), the publish step was not byte-stable, and three copies of the same triples had to be kept in step. `get_ontology_graph()` and `get_conformance_profiles()` now parse only the one file asked for, once, and cache it (`_file_graph()`); the trig is not read by the library. `_PREFIXES` in `starontology/__init__.py` is the one prefix table (bound onto every returned graph, and written into the trig header). The `.ttl` files are packaged (`starontology/*.ttl` in `package-data`; `skos.rdf` and the validation shapes are not).

**One build script, `scripts/build_starontology.py`** (`--check` changes nothing and exits 1 if stale), replacing `publish_starontology_files.py`, `import_skos_ontology.py` and `refresh_shacl_meta.py`. It regenerates the two generated files (`skos-ontology.ttl` from `skos.rdf`; `shacl12-shacl.ttl` from the meta-shapes build), assembles the trig, and rewrites a file only when its graph changed (compared by isomorphism, since rdflib labels blank nodes randomly). `scripts/build.py` runs it with `build_codekg.py` and `generate_api_docs.py`. `starlayer-profiles.ttl` gained its explanatory header comment in the process (it had lived only in the trig).

**Build code out of the library.** `build_meta_shapes_graph()` and the pySHACL-adjustment helpers moved to `scripts/build_meta_shapes.py`, and `shacl12-validation-shapes.ttl` to `scripts/assets/`. The library keeps only `load_meta_shapes_graph()` and `meta_validate()`; the validation shapes are no longer packaged. Tests that exercise the build add `scripts/` to `sys.path`. `test_fixture_sparql_syntax.py` was globbing a stale path (`starlayer.shacl/assets`) and so checking nothing from the assets; it now points at `scripts/assets`.

**Skipped tests are environmental.** The fast tier now reports ~450 skips (`oxigraph not running` / `fuseki not running`) where earlier runs showed 11, because no local Oxigraph/Fuseki server was up; not caused by these changes.

### Follow-up, same day: packaging audit, uniform `--check`, single cache

- **Wheel trimmed from 2.07 MB to 0.75 MB.** `pyproject.toml` now ships only what the library reads: `py.typed` and `starontology/*.ttl`. Dropped: `starontology.trig` (generated copy), `codekg/codekg.trig` (6 MB, repo tooling) and the codekg ontology/curated files. `include-package-data = false` makes that list authoritative; before, a stale `*.egg-info/SOURCES.txt` silently added the files it listed, and a stale gitignored `build/` directory (August-era `starshacl`, `starsparql`, `starlayergraph` packages) was being copied into every locally built wheel. Verified by unpacking the wheel and running the library from it with `-I`. `starlayer.codekg` (the extractor code) still ships as Python; nothing in the library imports it, so excluding the whole subpackage is a further, undecided step.
- **`scripts/build.py --check` treats every step alike** (run it, compare with the committed output, restore) and CI runs it. Making that possible exposed a real bug: `generate_api_docs.py` ordered a class's methods by the dataset's iteration order, so two correct builds of the code KG produced differently ordered docs. It now sorts. The code KG itself is only isomorphic, not byte-identical, across builds (blank-node labels), hence the isomorphism comparison for `.trig`. The committed generated API docs and code KG were stale and have been regenerated.
- **One cache for the meta-shapes file**: `load_meta_shapes_graph()` no longer keeps its own copy; it copies from `starontology`'s per-file cache.
- Tests import `scripts/build_meta_shapes.py` through pytest's `pythonpath = ["scripts"]` instead of editing `sys.path`.
- **`starlayer.codekg` is not shipped, and the code KG is not checked in CI** (decided later the same day). `pyproject.toml` excludes `starlayer.codekg*` from the wheel; scripts and tests use it from the repo. CI runs `build.py --check --skip codekg`, so a code change no longer forces a 90,000-line `codekg.trig` regeneration to keep CI green. Rebuild it on demand with `python scripts/build.py --only codekg apidocs`.
