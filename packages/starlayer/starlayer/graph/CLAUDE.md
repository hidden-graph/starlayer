# CLAUDE.md

Project-specific instructions for Claude Code sessions working in this repo. See `docs/guides/README.md` for the docs index (start with `packages/starlayer/docs/graph/starlayergraph.md`).

## Rules that bite

- **Two representations, one class.** `backend="rdf-1.1"` (default; in-memory rdflib store) stores a triple term as a content-addressed `tt:` node. `backend="rdf-1.2"` is native (Oxigraph in-process, or Oxigraph/Fuseki over HTTP) and has no encoding. Branch on `self._is_native`; a change to one path usually needs a twin in the other.
- **Never write the `tt:` encoding by hand.** Each triple term is a node typed `rdf:PropositionForm` with `rdf:propositionFormSubject/Predicate/Object`, written only through `encoding_triples()` in `model/encoding.py` (which `add`, `addN`, the SPARQL lowering and the Turtle parser use). Reads hide it (`_is_encoding_triple`) and `_restore()` turns a hash URI back into a `TripleTerm`. Reads find triple terms by the type; only a value built inside a query (`TRIPLE()`) is recognised by its name.
- **Do not import the SPARQL grammar lazily while pytest is collecting.** It corrupts the shared grammar for the rest of the run. `tests/conftest.py` imports and installs it eagerly; if `TRIPLE()` syntax stops parsing mid-run, look there first.
- **Entailment regimes are the W3C IRIs**, `ENTAILMENT.RDFS`, `ENTAILMENT["OWL-Direct"]` and so on, for both `infer(entailment=...)` and `query(entailment=...)`. Not strings.
- **rdflib is patched on `import starlayer.graph`** (`query/*_patches.py`: arithmetic, `BIND`/`FILTER` evaluation, `GROUP BY`, casts, `sameTerm`, `STRLANG`). Each patch is idempotent with a sentinel attribute. The bugs are listed with repros in `docs/upstream-issues/rdflib-upstream-issues.md`.
- **Oxigraph aborts the whole process on `=` between two `dirLangString` terms.** `backends/dirlang_equality.py` rewrites such equalities before they reach the engine. The tests that really abort are opt-in (`STARLAYER_RUN_ENGINE_ABORT_TESTS=1`).
- **Blank-node labels are not stable across Fuseki queries.** `native.blank_node_ids_are_stable()` measures it; on Fuseki, blank nodes are written as skolem IRIs and queries are rewritten (`backends/skolem_semantics.py`) so they still behave as blank nodes.
- **Some strings are infrastructure, not names.** The Fuseki dataset path `starlayergraph` is a dataset someone provisioned; renaming it breaks the integration tests. Namespace IRIs in bundled data are data identity, so renaming one is a breaking change.
- **Test tiers.** The W3C suites are pinned to a commit (bump `PINNED_SHA` deliberately and read the diff). The store-matrix tests are opt-in (`--store-matrix`). Integration tests need local servers and skip without them.
- **Check the spec before RDF/SPARQL 1.2 work:** from `packages/starlayer`, `python tests/graph/vendor/spec_snapshots/refresh_snapshots.py` and `git diff` the snapshots. Nothing watches the specs automatically.
- **`rustdl` is young and has changed behaviour between versions** (a silent incomplete answer became a hang). Re-verify any claim about it against the installed version.

## Gotcha: don't let a lazy grammar import corrupt the SPARQL 1.2 grammar mid-run

SPARQL 1.2 query/update parsing goes through the `starlayer.sparql`'s real grammar/algebra pipeline (same package), not vendored code. Importing and installing that grammar lazily - i.e. letting the first test module that happens to touch it trigger the import - during pytest's assertion-rewrite-hook-active collection phase corrupts the grammar installation for the rest of the run. `tests/conftest.py` works around this by eagerly importing and installing the grammar at collection time, before any test module can trigger it lazily. If `TRIPLE()`-family syntax ever mysteriously stops parsing partway through a test run, that eager import is the first thing to check - see `packages/starlayer/docs/graph/testing-strategy.md` tier 1 for the full account.

## Tracking upstream spec changes (RDF 1.2 / SPARQL 1.2 are still pre-Recommendation)

Before starting any work that touches RDF 1.2/SPARQL 1.2 behavior specifically (not every routine change), check whether the upstream spec text has moved since this project last verified against it: run `python3 tests/graph/vendor/spec_snapshots/refresh_snapshots.py` and `git diff tests/vendor/spec_snapshots/*.txt` - a non-empty diff is the trigger to re-run the relevant section of `packages/starlayer/docs/graph/rdf12_sparql12_gap_analysis.md` against the new text. Full procedure and the 4-step "what to do as the spec progresses toward Recommendation" plan: `docs/future_enhancements.md`'s "Keeping in step with RDF 1.2/SPARQL 1.2 as the spec finalizes" section. No CI job watches the W3C TR-track automatically - this is a manual check, not something that happens on its own.

## Tracking `rustdl`'s own evolving capabilities (a young, pre-1.0 native library, not a spec)

`starlayer/graph/graph/owl_dl_rustdl.py` (`infer(profile=ENTAILMENT["OWL-Direct"], engine="rustdl")`) documents `rustdl`'s completeness fragment, its disjunctive-property-assertion behavior, and which constructs it rejects/hangs on/under-approximates - all based on empirical testing against whatever `rustdl` version happened to be installed at the time, not a stable published spec. **This has already been found to drift silently**: a claim in that module's own docstring ("confirmed live" that a specific logic-puzzle ontology causes `materialize_inferred_property_assertions()` to silently return an incomplete-but-sound answer) turned out to be stale - re-running that exact same ontology against `rustdl` 0.4.31 hangs indefinitely instead, a confirmed regression in failure mode (silent incompleteness → hang) that this project's own docs hadn't caught up to until a guide re-execution surfaced it (see `docs/future_enhancements.md`'s RustDL entry for the full account and the fix - a pre-flight SHACL check that now rejects that exact pattern outright, `rustdl.UnsupportedAxiomError`, before it can hang).

Before relying on any specific claim in `owl_dl_rustdl.py`'s docstring or `docs/future_enhancements.md`'s RustDL entries (what it's complete on, what it silently drops vs. rejects vs. hangs on), **re-verify empirically against the actually-installed `rustdl` version first** (`pip show rustdl`) rather than propagating an old characterization forward - a `pip install --upgrade rustdl` between sessions is exactly the kind of silent-drift trigger that caused the regression above. No CI job or version-pin alert watches `rustdl`'s own releases automatically - this is a manual check, same discipline as the RDF 1.2/SPARQL 1.2 one above, just against a library's shifting behavior instead of a shifting spec text.

## Design history

Dated entries below record why things are the way they are. Read one when you work on that topic; the block above is what you need first.

## Entailment fixes from the third hunt (2026-10-25, GitHub issue #97)

The query-time RDFS rewrite (`sparql/entailment_rdfs.py`) now composes rdfs7 with rdfs2/rdfs3/rdfs9: a type test also matches a triple asserted with a *sub*property of the property that has the domain or range, and a property that is a subproperty of `rdf:type` (`:typedBy rdfs:subPropertyOf rdf:type`) types its subject. It agrees with the materialized `infer()` closure on those cases (a differential test). A BGP the rewrite produced is never rewritten again (it contains `rdfs:domain` / `rdfs:range` as predicates, which a second pass would rewrite as rdfs7). **`infer()` runs owlrl to a fixpoint** (up to 8 passes): one pass is not a closure, its axiomatic triples are typed `rdfs:Resource` only on the next pass, so the closure of the closure grew; `test_infer.py` compares against owlrl run to a fixpoint for the same reason. `FILTER [NOT] EXISTS` patterns are rewritten too: an rdflib `Expr` holds its pattern twice, as a dict item and as an instance attribute set by `translateExists`, and the evaluator reads the *attribute*, so the rewrite sets both (it had been changing only the dict item, which is why the entailed branches never matched inside `EXISTS`; this was our bug, plain rdflib evaluates the same pattern correctly). **Still open in #97:** `entailment=RDFS` does not include the RDF regime's `rdf:Property` typing of predicates.

## `StarLayerDataset` fixes from the third hunt (2026-10-25, GitHub issue #99)

`remove_graph()` now clears `_sg_cache` and the cached execution graph (queries kept returning the removed graph); `parse()` accepts rdflib's names `trig`, `nquads`/`nq` and `trix` and routes them to the `*12` parsers (the rdflib per-context delegation passed an already-wrapped source that `StarLayerGraph.parse()` cannot read; the `<iri> { }` TriG form without `GRAPH` is still #47); `(s, p, o) in ds` and `(s, p, o, g) in ds` work; `add()`/`remove()` take quads, and `remove((s, p, o))` removes from every graph when `default_union` is set; `len(ds)` counts what the graphs show instead of the store (it counted the triple-term encoding); the default graph is written without a name in TriG/N-Quads/TriX (it was `<urn:x-rdflib:default>`, so it came back as a named graph). **Still open in #99:** blank-node graph names (TriG `GRAPH _:g` becomes an IRI; the serializers write such a graph into the default graph), an empty named graph is lost in a round trip, JSON-LD drops triple terms, `triples()` duplicates under `default_union`, and `URIRef('x')` / `BNode('x')` share one cache entry (the cache is keyed by `str`).

## RDFC with triple terms and datasets (2026-10-25, GitHub issue #103)

`rdfc10_hash()` / `to_canonical_nquads()` crashed on any graph with a triple term: the quads were normalized twice (once to build the canonical state, once to write the output) and decomposing a triple term mints fresh blank nodes each time, so the second set had no canonical label. The state now keeps the quads it was built from. A `StarLayerDataset` (whose `quads()` yields a graph object, not an identifier, as the fourth item) is accepted. **Left, unconfirmed against a reference:** a blank node with a self-loop quad has that quad in its quad list twice (`_canonicalize` step 2); the RDFC test vectors pass, so it was not changed without an independent oracle. Also open in #103: `compare.isomorphic` and friends raise `ValueError` on an `rdflib.Dataset`, and canonical N-Quads keep language-tag case.

## SPARQL Update graph management is patched to use the true default graph (2026-10-25, GitHub issue #78)

rdflib's update code takes `ctx.graph` for "the default graph", which is the union of every graph when the dataset has `default_union` (the setting `StarLayerDataset` forwards so a `GRAPH`-less `WHERE` sees all data). So `CLEAR DEFAULT`, `COPY ... TO DEFAULT` and friends wiped the whole dataset, `ADD`/`COPY`/`MOVE` with `DEFAULT` crashed, `CREATE` always raised, `DELETE WHERE { GRAPH ?g ... }` deleted nothing and `USING` tried to fetch the IRI. `query/update_patches.py` replaces those six functions plus `DELETE WHERE`, and `QueryContext.load` now reads a graph already in the dataset instead of fetching it (an IRI that is not a graph of the dataset still goes through rdflib's loader). `WHERE` evaluation and the default-graph triples of `DELETE WHERE` keep using `ctx.graph` on purpose (the union rule above). Also fixed: `_build_raw_execution_graph()` only copied graphs already wrapped in `_sg_cache`, so a named graph created by an Update was invisible to the next `GRAPH` query. Tests: `tests/graph/unit/test_update_graph_management.py`.

## Parser and writer fixes from the second hunt (2026-10-25, GitHub issue #73)

- **SPARQL-style `PREFIX`/`BASE`/`VERSION` ends with its operand**, not at the next `.`: `PREFIX : <http://e/> :a :p :z .` on one line used to drop the triple (`syntax._scan_directive_end`). A directive is still only recognised at the start of a line; one after a statement on the same line is not (known, left). An empty IRI (`PREFIX : <>`, `@base <>`) is a declaration.
- **Turtle does not normalise newlines in strings**: `_strip_blank_and_comment_lines` returns the separators too and keeps `\r` / `\r\n` inside a string; the RDF/XML and TriX writers write `&#13;` (and the RDF/XML parser re-escapes it before handing the tree to rdflib), or the CR read back as LF.
- **Writers never print an invalid prefixed name**: `turtle12._valid_qname` checks the local part against `PN_LOCAL` (no trailing `.`, no `#`) and falls back to `<IRI>`. RDF/XML refuses a predicate whose IRI has no NCName tail (`p#`) with a `ValueError` instead of writing malformed XML, and skips registering an `nsN` prefix (ElementTree reserves those).
- **A blank node that is inside a triple term is never written inline** (`[ ... ]`), or the parse back makes two nodes.
- **Brackets in strings**: `lexer._bracket_end` skips strings (escapes, long strings) and `<IRI>`s when finding the end of `[ ]` / `( )`.
- N-Triples blank node labels may contain an inner `.`.

Not fixed yet from the hunt (still open in #73): TriG blocks without `GRAPH` (#47), `~ []` as a reifier, a doubled direction suffix in a language tag, a missing final `.`.

## Triple terms are not IRIs in SPARQL (2026-10-25, GitHub issue #74)

The rdf-1.1 representation stores a triple term as a `tt:` IRI, which leaked through SPARQL: `isIRI(?t)` was true and `STR(?t)` returned the internal text (`operator_patches.patch_triple_terms_are_not_iris`: false and an error, as in Oxigraph), and a negated property set `?x !(:p) ?y` matched the encoding triples (`evaluate_patches.patch_negated_path_skips_encoding_triples`). The lowered form of `isTRIPLE(x)` is now the custom function `tt:fn/isTripleTerm` (it was `STRSTARTS(STR(x), TT_NS)`, which a user-visible `STR` error would have broken; a flag on the STR node did not survive the lowered query's round trip through RDF). `TripleTermNode` now orders against any other term (after all of them): a pattern with a triple term and an IRI object on the same subject and predicate used to crash rdflib's `reorderTriples`. **Left, still open in #74:** `=`/`IN` on triple terms *built inside the query* (`TRIPLE(...)`, `<<(...)>>` constants) compare lexically, so `<<(:s :p 1)>> = <<(:s :p 1.0)>>` is false (stored triple terms compare by value); a `TRIPLE(...)` with a triple term as an argument raises a generic `Exception` instead of an unbound value (rdflib's `value()` meets an unevaluated `TripleTermNode`); and removing the last use of a triple term leaves its encoding triples in the store.

## A `BIND` sees only its own group; two rdflib "fixes" removed (2026-10-25, GitHub issue #54)

SPARQL 1.1 section 18.2.2.6 evaluates each `{ }` group on its own and joins the results, so a `BIND` cannot read a variable bound in a sibling or enclosing group (`VALUES ?x {1 2} { BIND(?x+1 AS ?y) }` leaves `?y` unbound). StarLayer used to patch rdflib to make it work (`patch_evalextend_forgotten_bind_vars`, upstream-issues items 3 and 5-era trace, and `patch_lazy_join_expr_dependency_order`, item 4), on the strength of "expected" results in `docs/upstream-issues` that no spec section supports. Both patches are gone; plain rdflib is correct. `tests/graph/unit/test_bind_scoping.py` pins it. **Not re-examined:** `patch_evalfilter_forgotten_vars` (items 8 and 16) is the same question for `FILTER`; check it against section 18.2.2.6 before trusting it. The written "expected" in the upstream-issues docs has been wrong before: verify against the spec.

## A reduced copy behaves like its source (2026-10-25, GitHub issue #63)

`reduce_prefixes()` returns a copy with fewer bindings and nothing else different. The dataset copy now keeps `default_union` (it was built with the default, so `SELECT * WHERE { ?s ?p ?o }` returned the source's rows on the source and none on the copy), and the copy of a named graph keeps its name (the graph's identity, and what validation reports as the data graph). A blank-node identifier means nothing, so such a copy gets its own.

## `used_prefixes()` and graphs that start with fewer prefixes (2026-10-24, GitHub issue #29)

Every rdflib graph is bound to ~29 default prefixes; the Turtle writers print only those an IRI of the graph is in. That rule is now `starlayer.graph.used_prefixes(graph)` (`graph/graph/prefixes.py`; `rdf:type` as a predicate does not count, it is written `a`), and the writers share its `select_prefixes()`. **Decision (user): keep rdflib's default bindings for `StarLayerGraph`**; nothing was changed for graphs that do not ask. But a graph created with `bind_namespaces="core"` could not run `query()` or `update()` (they built `Graph(store=self.store)` with the defaults and bound into the shared store while iterating it: `RuntimeError: dictionary changed size`), and the Turtle 1.2 parser built two intermediate `Graph()` objects with all the defaults and copied them into the target. Both now use `bind_namespaces="none"`. Known and left alone: a file declaring `geo:` for its own IRI is written `geo1:` on a default-bound graph (rdflib's `geo` is taken); create the graph with `bind_namespaces="core"` to keep the file's prefix.

## Parser and serializer fixes from the adversarial hunt (2026-10-25, GitHub issues #55 to #61 and #64)

An automated hunt (two independent verifiers per finding) found these silent-corruption bugs in the Turtle 1.2 / TriG 1.2 / N-Triples 1.2 code; all reproduce against rdflib as the oracle and are fixed with tests in `tests/graph/unit/test_parser_fixes.py`:
- **Prefixes are positional (#56, #60, #61).** A prefix declaration applies from where it is written: `turtle_parser.parse()` keeps the prefix map in effect and stamps it on each triple (like the base), and `trig12._split_trig_blocks_with_ids` gives each GRAPH block only the declarations written before it (the default graph's content keeps its own inline). A relative IRI in a declaration is resolved against the base in effect there. **An undeclared prefix is now a `Turtle12SyntaxError`**; `rdf:` and `sl:` stay predeclared because the triple-term expansion uses them. This is what exposed that a collection as a *subject* (`( 1 2 ) :q 3 .`) was never expanded (it errored, or with `<<..>>` inside became a made-up IRI); `expand_triple_set` now expands it (once per statement) and `_parse_collection_elements` treats `<<..>>` as one element.
- **Escapes (#59).** `\uXXXX` / `\UXXXXXXXX` in an IRIREF are decoded; `PN_LOCAL_ESC` (`ex:c\.d`) loses its backslash. The statement splitter, `_split_on_delimiter` and the bare-token lexer all treat a backslash outside a string as escaping the next character.
- **A `.` that starts a token ends the statement (#64)**, even when a name follows with no space (`'x' .ex:b ex:p 'y' .`); a `.` inside a number or a dotted local name is unchanged.
- **N-Triples (#57):** the closing quote of a literal was found by looking at the previous character, wrong for an escaped backslash; it now walks the escapes.
- **Writers (#55, #58):** a blank node written inline is only safe if its parent is written; `_demote_unreachable_inline` checks reachability from the top-level subjects and gives one node of any unreached cycle or self-loop its own labelled block. A multi-line literal's quote runs are escaped in one pass (a trailing run was escaped twice).
Known and left: `"x"^^xsd:string` is how the nt12 writer writes a plain string (valid; rdflib treats it as a different Literal, the existing documented in-memory difference).

## Which prefixes matter is a method of the graph and the dataset (2026-10-24, GitHub issue #29)

"Which namespaces are relevant to this graph or dataset" and "reduce the prefixes to those used" come up again and again (a UI offering prefixes, a writer, a copy for sharing), so they are methods, not a helper to copy: `StarLayerGraph.used_prefixes()` / `.reduce_prefixes(keep=())` and the same two on `StarLayerDataset` (a dataset counts every graph's triples and the names of the named graphs, which TriG writes). The function is `starlayer.graph.used_prefixes` (`graph/graph/prefixes.py`), also given to plain rdflib graphs and datasets. **`reduce_prefixes()` returns a copy**: rdflib has no way to remove a binding from a store, so a graph's bindings can only be reduced by building a new graph (created like its source, see `empty_like()`; a dataset copy is in-memory). `StarLayerDataset` now accepts `bind_namespaces=` like `Graph` does ("none", "core", default "rdflib"); rdflib's `Dataset` has no such parameter, so it sets the attribute rdflib reads when the namespace manager is first created. A prefix that is used but unbound still works (the writers add `rdf:` only when something in the output uses it; this used to be added whenever unbound).

**Found on the way, fixed:** the TriG parser read a prefix declaration only when a space separated the prefix from the IRI, so `@prefix ex:<http://e/> .` (valid TriG) was silently ignored and the names in `GRAPH` blocks came out as the literal IRI `ex:a`. **Not fixed, noticed:** the `<iri> { ... }` and `ex:name { ... }` TriG forms (a graph name without the `GRAPH` keyword) raise a syntax error in `format="trig12"`.

## `infer()`/`query()` migrated from starlayer-internal strings to real entailment regime IRIs (2026-10-07)

Found while designing `sh:entailment` support for `starlayer.shacl` (that spec's values are the real, fixed W3C SPARQL 1.2 Entailment Regimes IRIs - confirmed via direct fetch: `http://www.w3.org/ns/entailment/{RDF,RDFS,D,OWL-RDF-Based,OWL-Direct}`) - but `infer(profile=...)`/`query(entailment=...)` used their own, unrelated starlayer-internal string keywords (`'rdfs'`/`'owl-rl'`/`'rdfs+owl-rl'`/`'owl-dl'`/`'direct'`/`'rdf'`). Rather than add a translation layer at the SHACL boundary, replaced the strings with the real IRIs everywhere - a full breaking change (~197 call sites across source/tests/6 guide notebooks), on explicit user instruction, not an additive alias.

New `starlayer/graph/graph/entailment_regimes.py`: `ENTAILMENT = Namespace("http://www.w3.org/ns/entailment/")` (re-exported from `starlayer.graph`) - a `Namespace`, not individual constants, since `ENTAILMENT.RDF`/`ENTAILMENT.RDFS` would otherwise collide by bare name with `rdflib.namespace`'s own commonly-imported `RDF`/`RDFS`. `ENTAILMENT["OWL-RDF-Based"]`/`ENTAILMENT["OWL-Direct"]` need bracket access (hyphens aren't valid in a Python attribute name).

**A real, pre-existing inconsistency found and fixed along the way**: `infer()` called the OWL 2 Direct Semantics (tableau) regime `'owl-dl'`; `query()` called the identical regime `'direct'` - two different names for the same thing. Both now unify onto the one real `ENTAILMENT["OWL-Direct"]` IRI.

**API shape change, not just a value swap**: the old `'rdfs+owl-rl'` combined-profile string is gone - `infer()`'s `profile=` now accepts a single IRI or an iterable of more than one, combining naturally (e.g. `{ENTAILMENT.RDFS, ENTAILMENT["OWL-RDF-Based"]}`), matching `sh:entailment`'s own "declare several, combine into one pass" model rather than inventing a starlayer-specific combined keyword.

**Two real bugs found via testing, not assumed correct**:
1. Normalizing `profile` checked `isinstance(profile, URIRef)` - a plain leftover string like `'rdfs'` isn't a `URIRef`, so it fell through to `frozenset(profile)`, silently splitting it into individual characters (`{'r','d','f','s'}`) instead of being rejected cleanly. Fixed with an `isinstance(profile, str)` check instead (`URIRef` is itself a `str` subclass, so this correctly catches both).
2. The mechanical sweep's replacement text (`ENTAILMENT["OWL-Direct"]`, containing a literal `"`) corrupted several already-double-quoted host strings (docstrings, error messages, a `pytest.raises(match=...)` regex where `[`/`]` are also regex metacharacters). Fixed by switching to single-quote bracket access (`ENTAILMENT['OWL-Direct']`) at every such site, and shortening the affected `match=` patterns to bracket-free stable prefixes.

Verified: `tests/graph` 1527 passed (1 pre-existing, unrelated failure - `test_oxigraph_backend.py`), `tests/sparql` 351 passed, zero regressions. All 4 touched guide notebooks (`02b-graphs-inferencing`, `05e-owl-dl-reasoning`, `03b-sparql-inferencing`, `05b-backend-graph-databases`) re-executed via `nbconvert` with zero errors - which surfaced a separate, pre-existing, unrelated bug (see below).

**`infer()` gained a new regime while here**: `ENTAILMENT.RDF` (plain RDF entailment - one step weaker than RDFS) had no materialization path at all before this (`query(entailment=...)` could query-time-rewrite for it via `starlayer.sparql.entailment_rdf`, but `infer()` couldn't materialize it). Implemented natively in `_infer_rdf_before_and_delta()` - no `owlrl` dependency, just rdfD2 (every predicate used is entailed `rdf:type rdf:Property`) plus the finite RDF axiomatic triples actually relevant to the data (looked up from the RDF 1.2 Semantics spec directly, not guessed). Datatype literal value-space well-typing (rdfD1/rdfD1a) is a deliberate, documented v1 scope reduction, not built.

**Separate, unrelated, repo-wide bug found while verifying notebooks via `nbconvert`**: `from starlayergraph import ...`/`from starlayergraph.graph.owl_dl import ...` - a stale package name from before this project's own `starlayergraph`→`starlayer` merge - appears in 20+ guide notebooks across `docs/`, not just the ones this work touched. Fixed only in the 3 notebooks this work actually touched (`03b-sparql-inferencing`, `05b-backend-graph-databases`, `05e-owl-dl-reasoning`) - scoped deliberately, on explicit user instruction, not a repo-wide fix. The other ~17 affected notebooks are still broken and unrelated to this work - worth a dedicated pass later, not opportunistically expanded into here.

## `_resolve_owlrl_semantics()`'s `ENTAILMENT.RDFS`-alone dispatch suppresses owlrl's "hidden sameAs" rule (2026-10-08)

Found via a real downstream test failure (`tests/sparql/unit/test_srl_shapes.py::test_assignment_and_filter_roundtrip_conforms`), surfaced while `starlayer.shacl` disconnected its own `inference=` keyword from pySHACL's string vocabulary onto this project's real `ENTAILMENT.*` IRIs (see `starlayer/shacl/CLAUDE.md`'s same-day entry) - that work moved a caller off a path that happened to carry a protective workaround, exposing a bug that had been latent in this module since `ENTAILMENT.RDFS` support first shipped (2026-10-07).

**The bug**: owlrl's own `RDFSClosure.RDFS_Semantics.one_time_rules()` implements a "hidden sameAs" rule - for every pair of literals *anywhere* in the graph that compare equal by Python value despite different lexical form/datatype (confirmed live: `Literal(True)` and `Literal(1)`, since Python's own `1 == True`), it duplicates every triple using one literal to also use the other, across any unrelated subjects/predicates. pySHACL's own `pyshacl.inference.CustomRDFSSemantics` (`pyshacl/inference/custom_rdfs_closure.py`) overrides this same method to a no-op specifically to avoid it, with its own source comment: "breaks some SHACL validation tests." This project's `_resolve_owlrl_semantics()` used plain, unmodified `owlrl.RDFS_Semantics` for `ENTAILMENT.RDFS` alone, so every `sh:entailment`/`inference=`/direct `infer(profile=ENTAILMENT.RDFS)` caller was exposed to this bug the whole time - just never hit by an existing test until `srl_validate()`'s own migration happened to touch a literal-type collision (an `xsd:integer`/`xsd:boolean` pair compared via `"1" == True`).

**Fix, confirmed by checking rather than importing**: a small local subclass (`_NoHiddenSameAsRDFSSemantics(owlrl.RDFSClosure.RDFS_Semantics)`, `one_time_rules()` overridden to `pass`) is used for `ENTAILMENT.RDFS` alone, defined inline (not imported from `pyshacl`, to avoid a layering violation - this is `starlayer.graph`'s own general-purpose reasoning, and `pyshacl` is an optional dependency of a different, downstream package). **The combined `ENTAILMENT.RDFS` + `ENTAILMENT["OWL-RDF-Based"]` regime needed no such override** - a self-caught correction, not assumed by analogy: an initial version of this fix also no-op'd `owlrl.RDFS_OWLRL_Semantics.one_time_rules()`, which immediately broke `tests/graph/unit/test_infer.py::TestInferCombinedProfile::test_matches_owlrl_run_directly` with dozens of missing legitimate OWL-RL axioms (e.g. `xsd:byte rdf:type owl:Thing`). ## `StarLayerGraph.owl_imports()`/`.resolve_imports()` + `can_resolve_import()` - generalizing SHACL's own shapes-graph import resolution into a plain graph capability (2026-10-08)

Grew directly out of adding SHACL 1.2 Profiling §2 packaging (`sh:ShapesGraph`/`rdfs:member`) to `starontology`'s own shapes files (see `starlayer/shacl/CLAUDE.md`'s dated entry) - which surfaced a real, found-not-assumed gap: `sqe_shapes.ttl`/`srl_shapes.ttl` both genuinely reference `salg:ExpressionShape`/`salg:VariableShape` (confirmed via `grep`, not inferred from file names) without defining them, and nothing in this project loaded that dependency automatically. `validator.py` already had `_resolve_shapes_graph_imports()` solving exactly this problem, but scoped only to `shacl_graph` inside `validate()` - the user asked for the same capability as a plain, reusable `StarLayerGraph` operation instead, not something bolted onto SHACL specifically.

**Design, settled across several direct questions, not assumed up front**:
- **Where does `owl:imports` normally appear, conceptually?** Overwhelmingly: one OWL ontology document importing another - this is a document-level property of "treat this resource as ontology-like," formally independent of whatever *other* `rdf:type` the subject carries (SPIN's own, pre-SHACL constraint-library convention did the identical "constraint library imports constraint library" thing SHACL 1.2 now formalizes - not a new idea, an extension of established practice).
- **Does resolving it ever happen automatically, anywhere in this project?** No, and that's deliberate - checked against the project's existing discipline (`data_graph` never mutated without `inplace=True`, no IRI ever invented without opt-in, `validate()` never fetches on its own). Confirmed live: `infer()` already treats `owl:imports` as completely inert data - an entailment that would require resolving an import simply doesn't fire, the triple just passes through unchanged.
- **Should resolution be opt-in everywhere, with no exceptions?** No - corrected mid-discussion on a direct challenge ("using an ontology with imports without doing the import leads to incomplete results... inconsistent with the desire of the ontology owner"). The real dividing line isn't automation vs. not, it's whether resolving requires reaching *outside* what's already known and local. An arbitrary caller-supplied `shacl_graph`/`ont_graph` genuinely can't be resolved safely by default (unknown IRI, network dependency, non-determinism) - but `starontology`'s own bundled files carry none of that risk, so defaulting to *not* resolving them bought no safety, only silently wrong/incomplete results for free.

**New in `starlayer_graph.py`** (added right after `infer()`, reusing its own `VALID_INFER_RETURN_MODES` constant):
- `owl_imports(self) -> tuple[Any, ...]` - direct `owl:imports` objects, deduplicated, first-seen order. A pure read; resolves nothing.
- `resolve_imports(self, *, loader, mode="full"/"delta"/"in-place", target_graph=None) -> StarLayerGraph` - the exact same three-way `mode=` contract `infer()` already established (full = self plus resolved imports in a new graph; delta = true set difference, just the newly-pulled-in triples; in-place = mutate self, return self). Recursive by construction (that's what "import" means - §3.4's imports closure - not an opt-in extra), with cycle protection and the identical `^owl:versionIRI?/owl:imports` canonical-ID handling `_resolve_shapes_graph_imports()` already got right (a graph fetched under its own declared `owl:versionIRI` is deduplicated, and further-imports-following continues from its *base* IRI, not the version IRI it was fetched under). `loader` has no default - this library still never decides retrieval policy on anyone's behalf; an unresolvable import (`loader` returns `None`) is skipped, not an error.
- `can_resolve_import(iri, *, loader) -> bool` - module-level function, not a method: it's a question about the *loader*'s own knowledge, not about any graph's data. Implemented the only honest way possible - actually calling `loader(iri)` and checking for a non-`None` result; for a loader that makes a real network request this has the identical cost as actually resolving, there's no cheaper way to ask "would this work."

**New in `starontology/__init__.py`**: `local_loader(iri) -> StarLayerGraph | None` - a `resolve_imports()`-compatible loader that only ever reads this package's own bundled files. **A real identity mismatch found and fixed while wiring it up, not assumed to just work**: `local_loader()` has to resolve against each shapes file's own *real* `sh:ShapesGraph` node (e.g. `salg:ShapesGraph`, in the vocabulary's own namespace - confirmed via direct inspection that `sqe_shapes.ttl`'s actual `owl:imports` triple points there) - which is a completely different IRI than `get_resource_iri()`'s own GitHub-blob-URL scheme (built earlier the same day for an unrelated purpose, `prof:isProfileOf`/`derive_conforms_to()`). Confirmed live before fixing: `get_resource_iri("sparql_shacl")` and `sqe_shapes.ttl`'s real import target are two different strings entirely. `docs/generated/api-reference.generated.md`'s `starlayer.starontology` section now carries an explicit note so a future reader doesn't assume these two identities match either.

**Verified live, not just unit-tested in isolation**: `get_ontology_graph("sqe_shacl")` alone is 142 triples and genuinely missing `salg:ExpressionShape`'s own `sh:NodeShape` definition; `.resolve_imports(loader=starontology.local_loader, mode="full")` returns 1,323 triples including it - the real gap, closed, confirmed before and after.

New tests: `tests/graph/unit/test_resolve_imports.py` (20 cases - direct imports, dedup, unresolvable-import-is-skipped-not-an-error, all three modes including delta's true-set-difference semantics and in-place's `target_graph` rejection, invalid `mode=`, a 3-hop transitive chain, an import cycle that must terminate without duplicating content, and the `versionIRI`-redirected-import reconvergence case specifically). `tests/starontology/unit/test_starontology.py::TestLocalLoader` (6 cases, including the specific "`sqe_shacl` alone is missing the definition" / "resolving closes the gap" pair, and confirming an entry with no `owl:imports` at all - `skos_shacl` - is an unaffected no-op).

## `StarLayerGraph.from_rdflib()` now preserves the source graph's own `.identifier` (2026-10-09)

Found while discussing a `starlayer.shacl` feature request (auto-filling SHACL validation-report provenance from a graph's own identity - see `starlayer/shacl/CLAUDE.md`'s same-day entry for the full design): `from_rdflib()` always built the converted graph via a bare `g = cls()`, which gives every new graph a fresh random `BNode` identifier - silently discarding whatever real `.identifier` the source graph had (e.g. `Graph(identifier=URIRef(...))`, or - more consequentially - any named graph retrieved from a `Dataset`/`StarLayerDataset` via `.graph(iri)`, which always carries that real IRI as its own identifier). Confirmed live before fixing: `StarLayerGraph.from_rdflib(some_real_identified_graph).identifier` came back a completely unrelated `BNode`, every time.

**Fixed**: `g = cls(identifier=source_graph.identifier)` instead of `g = cls()` - a correctness fix to this method's own stated "wrap" contract (its docstring already says "Wrap a plain rdflib.Graph"), not scoped to any one caller. This is the mechanism that makes `StarShaclSchema.validate()`'s new identifier-based provenance fallback actually work when a data/shapes graph flows through `normalize_graph_inputs()` (which calls `from_rdflib()` for any non-`StarLayerGraph` input) - without this fix, a plain `rdflib.Graph(identifier=...)` or dataset-sourced named graph would have lost its identity before `validate()` ever got a chance to read it.

**One deliberate exception, found via a live deprecation warning, not assumed**: when `source_graph` is itself a whole `Dataset`/`ConjunctiveGraph` (not one of its named graphs), `.identifier` is **not** read or preserved - confirmed live that `Dataset.identifier` is itself deprecated in this rdflib version, and a `Dataset`/`StarLayerDataset()` can't even be constructed with `identifier=` directly anymore (`TypeError`). A whole dataset has no single meaningful identity of its own the way one graph does, so there's nothing worth preserving there, and reading it would needlessly trigger the deprecation warning on every dataset-to-graph conversion. A named graph *retrieved from* a dataset (`ds.graph(iri)`) is a completely different object with its own real, non-deprecated identifier, and is unaffected by this exception.

New tests, `TestFromRdflib` in `test_starlayer_graph.py`: identifier preserved for a plain `Graph(identifier=...)`; the ordinary no-identifier (`BNode`) case still works unchanged; a whole `Dataset` source doesn't trigger the preservation (or the deprecation warning); a named graph pulled out of a `Dataset` via `.graph(iri)` does preserve its own real identifier.

Full `tests/graph` suite: 1553 passed (4 new - 1 pre-existing, unrelated `test_oxigraph_backend.py` failure, unchanged), zero regressions. Deprecation warning count dropped from 273 to 271 (the two `Dataset.identifier` warnings the unguarded version would have triggered during the suite).

## `__len__()` fast path for the no-triple-terms case - found via a real retrospective performance audit (2026-10-12)

Found while diagnosing why the test suite ran far slower than expected - `cProfile` on one `starlayer.sparql.salg.sparql_shapes.validate_query()` call (against a trivial, triple-term-free shapes+ontology graph, ~1700 triples) showed `StarLayerGraph.__len__()` called **21,049 times** by pySHACL's own internal shape/constraint-evaluation bookkeeping, each call doing `sum(1 for _ in self.triples((None, None, None)))` - a full scan-and-filter of every triple, regardless of whether there was anything to filter. 28.9 million `triples()` iterations, ~104s of a 114s total call.

**The fix**: when `self._tt_registry` is empty - no triple term has ever been registered in this graph instance - there is nothing for `triples()`'s own encoding-triple filtering to do, so `len(graph)` can just be the underlying store's own count (`super().__len__()`, which for the default in-memory `Memory` store is a plain dict length, genuinely O(1) - confirmed by reading `rdflib.plugins.stores.memory.Memory.__len__`'s own source) instead of re-deriving the same number via a full filtered iteration. This reuses an *already-established, already-trusted* invariant in this exact class - `infer()`'s own `fast_path = not self._is_native and not self._tt_registry` (treats an empty-registry graph as safe to read directly, no triple-term-aware handling needed) - rather than inventing a new one; `_is_encoding_triple()`'s own check (`str(s).startswith(TT_NS)`) can only ever be `True` for a triple the registry would already know about, so an empty registry really does mean "nothing to filter," not just "probably nothing."

**Impact, measured**: the one call above: 31s → 1.4s (~22x) before the sibling `meta_validate()` cache fix (see `starlayer/shacl/CLAUDE.md`'s same-day entry) cut the remainder further. `tests/graph/unit/test_starlayer_graph.py`+`test_dataset.py`: 201 passed, zero regressions (pure performance fix, no observable behavior change - `__len__()`'s own contract, "count of visible triples," is unchanged for every graph, including ones that *do* have triple terms registered, which still take the original, correct, filtered path).

## W3C Turtle/SPARQL 1.2 fetch scripts moved to a pinned-SHA tarball pattern, surfacing a real `false`-literal bug in `turtle_parser.py` (2026-10-13)

Triggered by a user question about whether `benchmarks-graph`/`benchmarks-shacl` were still relevant, which led to reviewing `scripts/sync_w3c_shacl12_suite.py` and noticing the Turtle 1.2 downloader (`tests/graph/w3c_turtle12/download_w3c_turtle_tests.py`) and both SPARQL 1.2 downloaders (`tests/graph/w3c_sparql12/`, `tests/sparql/w3c_sparql12/`) still used the older design: N individual live `requests.get()` calls, skip-if-already-on-disk, no pinned commit, no provenance record. Rewrote all three to match the SHACL script's own pattern instead: one tarball fetch from `codeload.github.com` at a pinned `PINNED_SHA` (bump deliberately, never auto-follow `main`'s tip), stdlib-only (`urllib.request`/`tarfile`, no `requests`), always overwrite (the source is pinned and immutable, so skip-if-exists buys nothing and actively hides upstream drift), and a `VENDORED_FROM.md` provenance stamp per `data/` directory. Each script's destination layout and downstream-consumed file formats (`manifest.csv`, `index.tsv`) are unchanged - only the fetch mechanism changed, not what gets written or how the test files read it.

**The whole point of pinning is to make a deliberate bump surface exactly what changed, and it did immediately**: pinning to that day's live `main` tip (via `git ls-remote`) and re-running the Turtle downloader pulled in 3 fixtures that didn't exist in the old live-fetched snapshot (`turtle12-eval-annotation-13`, `turtle12-eval-rt-09`, `turtle12-eval-tt-05`) - the suite grew from 103 to 106 tests. Two of the three (`-rt-09`, `-tt-05`) failed immediately, triaged per this project's own established "fix or reasoned xfail" discipline rather than left red:

1. **Real production bug in `turtle_parser.py`'s `_Expander.qt_to_json()`**: the `rdf:object` triple for a triple-term/reifier-shorthand expansion was built as `'object': obj_str or ''`. `obj_str` can legitimately be the Python bool `False` (from `coerce_object()`'s own `"false"` → `False` coercion) - and `False or ''` evaluates to `''` in Python, silently discarding the boolean value entirely for exactly that one literal. `<< :s1 :p1 false >> :p :o .` crashed downstream with `Turtle12SyntaxError: unrecognized term ''` when the resulting encoding triple's empty-string object later got converted back to an RDF term. `True` never tripped this (`True or '' == True`), so the bug was invisible until a fixture specifically exercised `false`. Fixed by dropping the `or ''` guard entirely for this one field (`coerce_object()` never returns `None`, so there was nothing to guard against) - `subj_str`/`pred_str`'s own `or ''` guards are untouched since those two are always plain strings, never susceptible to this.
2. **Two separate, compounding bugs in the test harness's own `test_w3c_turtle.py`** (not production code - this suite's `parse_nt12()`/`expand_triple_term()`/`resolve_token()` build the *expected* graph from the `.nt` file for isomorphism comparison): (a) `expand_triple_term()` only called `next_token()` three times (s/p/o) and discarded whatever remained, silently dropping a typed/lang-tagged literal's suffix (`^^<dtype>`/`@lang`) whenever it followed a bracketed-IRI-form datatype specifically - `next_token()` keeps a *prefixed-name* datatype suffix (`^^:dt`) as one token but splits a *bracketed-IRI* one (`^^<http://...>`) into a separate `^^` token plus the IRI, an inconsistency in the shared lexer itself that had never been exercised this way before (no prior fixture nested a typed/lang-tagged literal as a triple term's object inside an `rdf:reifies` statement read from a `.nt` file, which - unlike `.ttl` - only ever uses the bracketed-IRI form, having no prefixes to abbreviate with). (b) `resolve_token()`'s `^^`-typed branch built `Literal(text, datatype=...)` without `normalize=False`, so rdflib's constructor silently rewrote a numeric lexical form to its own canonical spelling (`"1e0"^^xsd:double` → `"1.0"`) - the exact gotcha `turtle_parser.py`'s own `_to_node()` already guards against and documents (RDF 1.2's lexical-form-sensitive literal term-equality), just never carried over into this test-support file. Fixed both: merge the full remainder of `rest3` once it starts with `^^`/`@` (N-Triples' own grammar guarantees nothing else follows), and added `normalize=False`.

**Also found, not a bug**: the pinned-SHA bump's SPARQL-manifest diff (`syntax-triple-terms-positive`/`-negative`/`eval-triple-terms`/`expression`) was a cosmetic-only upstream refactor - per-test `mf:specVersion "sparql-1.2"` string literals consolidated into one manifest-level `mf:specVersion sparql:version-1.2` IRI declaration, no test entries added/removed/reclassified. ## VERSION directive: a real gap in `sparql_api.py`/`.update()`/the remote rdf-1.1 update path, not the "completely unsupported" first impression (2026-10-13)

Follow-up to the string-function retrofit above, investigating the other finding from the same `lang-basedir` retrospective: a quick test of `starlayer.sparql.parse12.prepare_query_12('VERSION "1.2"\n...')` failed outright, suggesting the whole `VERSION "1.2"` prologue directive (SPARQL 1.2 Query sec 4.3) was unimplemented. **The real gap, found by then checking every other caller of `parse12.py`'s four entry points** (`grep` across the whole package, not assumed complete from `query_cache.py` alone): `strip_version_directive()` is called from exactly one place, `query_cache.py` (`.query()`'s own backing function). - `starlayer.graph.query.sparql_api`'s four public functions (`parseQuery`/`prepareQuery`/`parseUpdate`/`prepareUpdate`) - this module's own docstring explicitly advertises them as drop-in replacements for rdflib's originals "when working with SPARQL 1.2 queries," the same advertised purpose `.query()`/`.update()` already satisfy correctly.

**Deliberately not fixed, judged out of scope**: `starlayer/shacl/meta_shapes.py`'s own `_validate_sparql_function_syntax()`, which calls `starlayer.sparql.prepare_query_12()` directly on `sh:select`/`sh:ask`/`sh:construct` text extracted from a SHACL shape. ## The W3C suites now run through the in-process Oxigraph store - and found a real bound-blank-node bug (2026-10-16)

Prompted by a gap in what the test suite actually covered: the W3C suites all begin by creating a graph or dataset, so a store axis is just a different factory. Wired in as sibling tests (existing test ids unchanged): `test_w3c_sparql12_eval.py` gains `*_oxigraph_store` select/construct tests (55 entries, same as live Oxigraph); the three SHACL suites (`validate`, `infer`, `node_expr`) take a `new_graph` factory through `manifest.clone_graph()` (`tests/shacl/w3c_shacl12/stores.py`) with `test_w3c_*_oxigraph_store` siblings and a separate `KNOWN_FAILURES_OXIGRAPH_STORE` map; `test_w3c_sparql12_oxigraph_roundtrip.py` gets an `oxigraph-store` backend parameter. None of these needs a server.

**Real bug found and fixed: the native bound-blank-node content join.** To look up a bound `BNode`, `StarLayerGraph._native_triples()` re-identified the node by one of its own discovery triples ("the node whose `rdf:first` is `"big"`"). That pattern is not unique - two list nodes can share it - so the join returned *another node's* rows too, and `Graph.items()` took whichever row came first: lists silently lost elements, intermittently, depending on engine row order. 22 of the first run's 32 store-axis failures were this one cause (confirmed by disabling the join: they all vanished). The join exists for Fuseki, which renumbers blank nodes per query; Oxigraph's ids are stable, so the plain label comparison is exact. Fix: no provenance recording or join for an in-process Oxigraph store (`_in_process(self.store)`); the HTTP path is unchanged. This is the long-standing "`objects(bnode, predicate)` returns the wrong value" bug.

Also fixed: a plain 3-tuple in a native write/read now renders as a triple term in `sparql_term()` (documented in `add()`, missing on the native path). Regression tests in `test_oxigraph_store_rdf12.py` (`TestBoundBlankNodeLookups`, `TestPlainTupleIsATripleTerm`) were run against the pre-fix source and fail there.

**Known limitation, not a bug: Oxigraph normalizes literals on storage** (upstream `oxigraph/oxigraph#526`; `"04"^^xsd:integer` becomes `"4"`, etc. - details in `docs/upstream-issues/oxigraph-upstream-issues.md`). The six remaining store-axis fixtures depend on exact lexical forms; each was checked against its own data and is recorded in `KNOWN_FAILURES_OXIGRAPH_STORE`.

**The `dirLangString` abort tests are now opt-in** (`STARLAYER_RUN_ENGINE_ABORT_TESTS=1`): each makes a subprocess really `SIGABRT`, and on macOS that files a crash report and can pop a "Python quit unexpectedly" dialog on every ordinary test run (30 were filed in one afternoon).

**Not yet covered:** the W3C Turtle suite is parser-only (no store involved); the HTTP backends are not run through the SHACL suites; the store axis for `tests/sparql/w3c_sparql12/test_w3c_sparql12.py`'s own in-memory eval tests duplicates the graph-package eval suite, which already has it.

**Follow-up, same day: the SHACL W3C suites also run against the two servers and an on-disk Oxigraph.** `test_w3c_{validate,infer,eval_node_expr}_other_stores` take a `store_under_test` fixture (`tests/shacl/w3c_shacl12/conftest.py`, factories in `stores.py`) over `oxigraph-http`, `fuseki-http` and `oxigraph-persisted` (a RocksDB directory opened in-process). Both servers must be running or those parameters skip. Against a server, the data graph is the server's *default* graph (cleared on creation and at the end) and the shapes graph a uniquely-named graph - the default graph matters because a native graph sends query text unscoped, so a `sh:select` inside a fixture can only see default-graph data. Note what is exercised: `validate()` reads both graphs back through the store and re-encodes them for pySHACL, so the server is the storage/read source and SHACL itself still runs in memory.

Results (per ~325 entries): default, in-process, **on-disk Oxigraph and Oxigraph over HTTP all pass** (only the six recorded literal-normalization fixtures are expected failures); Fuseki has 40 expected failures, 35 of them blank-node and 3 literal-normalization.

**Blank-node identity now depends on a measured property, not a guess.** `native.blank_node_ids_are_stable(store, backend)`: in-process is always stable; a remote endpoint is probed once (two blank nodes written to a scratch graph, read in two query shapes, labels compared; the scratch graph is cleared; any error means "not stable") and cached per query URL. **Oxigraph's ids are stable** (long content-derived ids) so the bound-blank-node content join is skipped there; **Fuseki labels blank nodes with a per-query counter** (a node is `b1` as the second of two rows and `b0` alone) so a bound blank node cannot be identified exactly on Fuseki, the join stays, and the lists/nested-blank-node fixtures that depend on that identity fail (recorded in `KNOWN_FAILURES_FUSEKI_HTTP`). Fixing Fuseki properly means writing blank nodes as skolem URIs on engines with unstable ids, which gives up real-blank-node `isBLANK()`/`ORDER BY` semantics for that engine - a design decision, not made here.

`StarLayerGraph._native_add_many()` gained `skolemize_bnodes=` (default off, unchanged for `parse()`/`addN()`); `clone_graph()` uses it so a copy is one request but existing `BNode` labels stay addressable. A batched write with real blank nodes gives them engine-assigned ids, so a `BNode` object held from before the write no longer names the stored node - why that option exists.

**The store-matrix tests are opt-in.** Everything above that runs a W3C suite through a non-default store (the SHACL `*_oxigraph_store` / `*_other_stores` tests, the SPARQL evaluation `*_oxigraph_store` tests, and the in-process parameter of the algebra round-trip suite) carries `@pytest.mark.store_matrix` and is **deselected from every ordinary run**, including a bare `pytest` and `pytest -m "not integration"` - about 1400 tests, several minutes, real HTTP calls. Run them with `pytest --store-matrix`, `STARLAYER_STORE_MATRIX=1 pytest`, or only them with `pytest -m store_matrix`. Implemented in `tests/conftest.py` at collection time rather than as a default `-m` in `addopts`, because a command-line `-m` (the usual `-m "not integration"`) would replace an `addopts` one and silently bring them back. The pre-existing live-server SPARQL evaluation tests, the cross-backend parity axes and `test_oxigraph_store_rdf12.py` are unchanged and still run normally.

**Why Fuseki's blank-node labels behave this way - not a bug.** SPARQL 1.1 scopes blank-node labels to the result set: "Use of the same label in another SPARQL Results JSON object does not imply it is the same blank node" and the label "is not an indication of any internal system identifier" (Query Results JSON sec 3.2.2; also Query sec 2.4, and sec 4.1.4: blank nodes in a query pattern are variables, not references to stored nodes). Fuseki's per-query counter is therefore conforming; Oxigraph's stable ids are an engine-specific extra, which is why `blank_node_ids_are_stable()` measures the property instead of assuming it. The spec-sanctioned way to refer to a blank node across queries is skolemization (RDF 1.1 Concepts sec 3.5) - what the single-`add()` path already does.

## Fuseki: blank nodes are stored as skolem IRIs, and queries are rewritten so they still behave as blank nodes (prototype, 2026-10-16)

The fix for the Fuseki failures found by the W3C store matrix. Fuseki labels blank nodes with a per-query counter (spec-permitted - see the entry above), so a blank node held from one query cannot be named in the next; RDF lists lost elements or raised "recursive rdf:rest", and two reifiers of one triple were silently merged. Everything below is gated on `native.blank_node_ids_are_stable()` (a measured, cached per-endpoint probe), so Oxigraph is unchanged.

- **Write.** On an engine with unstable ids, `_native_add_many()` (the `parse()`/`addN()` path) skolemizes blank nodes (`skolemize_bnodes=None` means "decide from the probe"). Reads already turn skolem IRIs back into `BNode`s.
- **Look up.** `_native_triples()` names a bound `BNode` by its skolem IRI first (exact). An *empty* exact answer is trusted if the node exists as a skolem node (`_native_skolem_node_exists()`); only a node that is not stored that way falls back to the old provenance-join / label-filter heuristics. (A first version fell back on any empty answer and returned a look-alike node's values.)
- **Rewrite.** `native_query()` passes query text through `backends/skolem_semantics.rewrite()` so the engine computes what it would for real blank nodes: `isBLANK(x)` is also true for a skolem IRI, `isIRI`/`isURI` false, and `ORDER BY` ranks blank/skolem before IRI before literal (SPARQL 1.1 sec 15.1). A small tokenizer skips strings, IRIs and comments; it is text-level, not a parser, and handles `ORDER BY` conditions that are a variable, `ASC()/DESC()`, a bracketed expression or a function call. `tests/graph/unit/test_skolem_semantics.py` checks the original query on real blank nodes against the rewritten query on skolem IRIs (rdflib on both sides; the unrewritten query is wrong on 11 of 12 shapes).

Results: Fuseki on the SHACL W3C suites went from 30-36 failures to 5, all literal normalization (recorded). The four SPARQL fixtures recorded as the Jena ARQ inconsistent-label bug now pass (stored skolem IRIs avoid it) and were retired from `_FUSEKI_KNOWN_DIVERGENCES`; `order-1`/`order-2`, the original reason real blank nodes were written, still pass. Focused regression tests: `tests/graph/integration/test_blank_node_identity.py` (lists, two reifiers of one triple, an empty exact answer, `ORDER BY`, `isBLANK`/`isIRI`) on in-process Oxigraph and both servers.

Limits: reading only - changing or deleting triples about a blank node that already exists on the server (loaded some other way, as real blank nodes) is still inexact. Data written by this library on Fuseki is stored as IRIs, so another SPARQL client sees skolem IRIs, not blank nodes.

## `xsd:integer()` casts from decimal, double, float and boolean now work (2026-10-17)

rdflib casts to `xsd:integer` through `int(<lexical form>)`, so `xsd:integer(16.0934)` and `xsd:integer(true)` were evaluation errors (a `SELECT` row with such an error is also silently dropped, see `rdflib-upstream-issues.md` item 6). `query/operator_patches.py::patch_integer_cast_from_numeric_and_boolean`, applied with the other operator patches on `import starlayer.graph`, truncates a number toward zero and maps `true`/`false` to 1/0; `NaN`, the infinities and a non-integer *string* stay errors. ## Equality over `dirLangString` is rewritten before it reaches Oxigraph, so it no longer aborts the process (2026-10-17)

Oxigraph's SPARQL `=` panics, and aborts the whole Python process, when it compares two `rdf:dirLangString` terms (oxigraph/oxigraph#1982; a missing match arm in `spareval`'s `PartialEq for ExpressionTerm`, so only that case, not `sameTerm()`). It cannot be caught, so `backends/dirlang_equality.py::guard()` rewrites the query text first. Each equality `L = R` where neither side is provably not a `dirLangString` becomes `(IF(COALESCE(hasLANGDIR(L), false) && COALESCE(hasLANGDIR(R), false), sameTerm(L, R), L = R))`; `!=` uses `!sameTerm`, and `x IN (a, b)` / `NOT IN` are expanded into guarded `=` / `!=`. The engine's own `=` then only runs when at least one side is not a `dirLangString`, the case it handles. An equality with an IRI, prefixed name, number, boolean, plain/language/typed string literal (no base direction) or a call to a function that never returns one (`STR`, `LANG`, `STRLEN`, ...) on either side is left unchanged, so most queries are untouched and keep the engine's optimizations.

Applied in the `execute_select/ask/update/construct` seam (`native.py::_guard_for_engine`), so it covers `query()`, `update()`, the SHACL paths and `StarLayerDataset` alike. `engine_aborts_on_dirlang_equality(store)` is true for an in-process Oxigraph; a remote endpoint cannot be probed (the probe is the abort), so a caller who knows it is `oxigraph serve` sets `store.starlayer_engine = 'oxigraph'`. Other engines (Fuseki) are not rewritten.

**Method:** text-level with the `skolem_semantics` tokenizer (strings, IRIs and comments skipped), operand boundaries by SPARQL precedence (an unmatched parenthesis, `,`, `&&`, `||`, braces, `;`, `.` or a clause keyword), rewriting the rightmost needing equality repeatedly (a placeholder character stands for an already-guarded comparison). **Considered and rejected:** refusing the query when the store holds any dirLangString (blocks many safe queries and needs a full-store scan per mutation); a probe (the probe aborts); rewriting through the algebra and regenerating text (rdflib's `translateAlgebra` is known to produce invalid text for some queries).

**Differences from `=`, and limits:** two unequal `dirLangString` terms give `false` where a strict reading of `=` gives an error (only visible under `!`/`!=`); an operand that calls `RAND`, `NOW`, `UUID`, `STRUUID`, `BNODE` or `EXISTS` cannot be evaluated twice, so that comparison is left as written. Tests: `tests/graph/unit/test_dirlang_equality.py` (34, pure text) and `TestDirLangStringEqualityGuard` in `tests/graph/integration/test_oxigraph_store_rdf12.py` (the formerly-aborting queries through `StarLayerGraph`, in a subprocess, with the right rows checked). The opt-in abort tests now run against raw `pyoxigraph`, so they still document the engine bug and will report when it is fixed (then retire this guard).

## Triple terms are stored in the RDF 1.2 Interoperability vocabulary (2026-10-18)

Branch `triple-term-encoding`. Replaces the old internal encoding (a content-addressed `tt:` node described by the classic reification terms `rdf:subject/predicate/object`, with no type triple) with the standard's vocabulary: each `tt:` node is typed `rdf:PropositionForm` (`TT_CLASS`) and described by `rdf:propositionFormSubject/Predicate/Object` (`TT_SUBJECT/PREDICATE/OBJECT`), all defined once in `model/encoding.py` together with `encoding_triples(node, s, p, o)`, which every write site now uses (`_intern_tt`, `addN`, `_reencode_tt`, `_unfold_native_triple_terms`, the SPARQL lowering of templates and INSERT data, the Turtle parser's skolemization). **Only the node name differs from the spec**: a stable content hash URI rather than a blank node (the spec's rules match blank-node subjects only, so a spec decoder would ignore our URIs); `serialize()` to plain formats already replaced `tt:` URIs by blank nodes (`_deskolemize_to_graph`), which now produces exactly the spec's basic encoding.

**Reads use the type, not the name.** `_build_registry_from_store()` is one indexed lookup of `(None, rdf:type, rdf:PropositionForm)`; nested components are recognised by membership in that set. `_is_encoding_triple()` (graph and dataset), the BGP/CONSTRUCT row filters (`ENCODING_MARKERS` = the three predicates plus the class) and the leak check in `evaluate_patches.py` test the vocabulary and no longer require the node to be in the `tt:` namespace. The name test remains only where a value never reached the store (a hash URI built by `TRIPLE()` in a query: `_restore`, the accessor functions, the `isTRIPLE` lowering) because no type triple exists for it. The user's own `rdf:type` triples stay visible, and real `rdf:Statement` reification is no longer confused with the encoding.

**Import.** `parse()` of a plain format (Turtle, RDF/XML, N-Triples, ...) now calls `_adopt_basic_encoding()`: a blank node typed `rdf:PropositionForm` with exactly one subject, predicate and object becomes the content-addressed node (nested ones first); a node missing a property is left untouched (the spec calls that an error; we do not guess). Round trip tested, including nesting.

**What did not change.** Native backends (Oxigraph, Fuseki) store triple terms natively and never use the encoding. `shacl/adapters.py` (its own `urn:starlayer:tt:` encoding for pySHACL) and `compare._decompose` (private canonicalization namespace) are separate private encodings and were left alone. No migration for stores written with the old encoding (the user confirmed it is not needed).

**Measured** (22,000 plain + 2,000 triple-term statements, `bench_tt.py`): stored triples 28,000 -> 30,000, parse 2.27 s -> 2.55 s, `triple_terms()` 0.2 ms (registry) unchanged, registry rebuild 15 -> 13 ms, `FILTER(isTRIPLE(?o))` 553 -> 576 ms (no gain: the lowering is still `STRSTARTS(STR(?o), TT_NS)`), a pattern query 149 -> 157 ms. Against plain rdflib on the raw store, `{ ?s ?p ?o . ?o a rdf:PropositionForm }` took 27 ms against 343 ms for the string filter, so rewriting `FILTER(isTRIPLE(?x))` on a variable bound by a graph pattern into that join is the optimization the type makes possible, and it is now done (next section).

Tests: `tests/graph/unit/test_proposition_form_encoding.py` (14). Existing tests that asserted the old predicates were updated. Fast tier: 3843 passed.

### Follow-up, same day: `FILTER(isTRIPLE(?x))` is answered as a typed join

`lower_rdf11._filter_is_triple_as_join()` (called from `_lower_expr` for a `Filter` node) rewrites `Filter(isTRIPLE(?x) [&& ...], BGP)` into the BGP with the pattern `?x rdf:type rdf:PropositionForm` placed **first**, so the index-backed typed pattern drives the evaluation and the rest of the pattern is matched with `?x` already bound; any other `&&` conjuncts stay as a filter around the join. The general lowering (`STRSTARTS(STR(x), TT_NS) || STRSTARTS(STR(x), "<<")`, a string test on every row) is used otherwise. It applies only where the two are exactly equivalent: the operand is a bare variable that is the subject or object of a triple in the filter's own BGP (a value from `BIND`/`TRIPLE()` never reaches the store and has no type triple); `isTRIPLE` is a top-level `&&` conjunct (not negated, not under `||`); and the BGP has no triple-term syntax of its own. Measured on the 22,000-triple graph: `FILTER(isTRIPLE(?o))` 576 ms -> 32 ms (about 18 times), same 2,000 rows. `_REWRITE_IS_TRIPLE_FILTERS` switches it off, which is how `tests/graph/unit/test_is_triple_filter_join.py` (14 tests: 11 query shapes, a named-graph query, and a check of exactly where the rewrite applies) compares each query against the string-test form. Not covered: the native backends (the query text goes to the server unchanged, so nothing is lowered).
