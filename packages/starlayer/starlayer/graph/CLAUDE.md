## Gotcha: don't let a lazy grammar import corrupt the SPARQL 1.2 grammar mid-run

SPARQL 1.2 query/update parsing goes through the sibling `starsparql` package's real grammar/algebra pipeline, installed editable (see `pyproject.toml`), not vendored code. Importing and installing that grammar lazily - i.e. letting the first test module that happens to touch it trigger the import - during pytest's assertion-rewrite-hook-active collection phase corrupts the grammar installation for the rest of the run. `tests/conftest.py` works around this by eagerly importing and installing the grammar at collection time, before any test module can trigger it lazily. If `TRIPLE()`-family syntax ever mysteriously stops parsing partway through a test run, that eager import is the first thing to check - see `docs/testing-strategy.md` tier 1 for the full account.

Before starting any work that touches RDF 1.2/SPARQL 1.2 behavior specifically (not every routine change), check whether the upstream spec text has moved since this project last verified against it: run `python3 tests/vendor/spec_snapshots/refresh_snapshots.py` and `git diff tests/vendor/spec_snapshots/*.txt` - a non-empty diff is the trigger to re-run the relevant section of `docs/rdf12_sparql12_gap_analysis.md` against the new text. Full procedure and the 4-step "what to do as the spec progresses toward Recommendation" plan: `docs/future_enhancements.md`'s "Keeping in step with RDF 1.2/SPARQL 1.2 as the spec finalizes" section. No CI job watches the W3C TR-track automatically - this is a manual check, not something that happens on its own.

## Tracking `rustdl`'s own evolving capabilities (a young, pre-1.0 native library, not a spec)

`starlayer/graph/graph/owl_dl_rustdl.py` (`infer(profile=ENTAILMENT["OWL-Direct"], engine="rustdl")`) documents `rustdl`'s completeness fragment, its disjunctive-property-assertion behavior, and which constructs it rejects/hangs on/under-approximates - all based on empirical testing against whatever `rustdl` version happened to be installed at the time, not a stable published spec. **This has already been found to drift silently**: a claim in that module's own docstring ("confirmed live" that a specific logic-puzzle ontology causes `materialize_inferred_property_assertions()` to silently return an incomplete-but-sound answer) turned out to be stale - re-running that exact same ontology against `rustdl` 0.4.31 hangs indefinitely instead, a confirmed regression in failure mode (silent incompleteness → hang) that this project's own docs hadn't caught up to until a guide re-execution surfaced it (see `docs/future_enhancements.md`'s RustDL entry for the full account and the fix - a pre-flight SHACL check that now rejects that exact pattern outright, `rustdl.UnsupportedAxiomError`, before it can hang).

Before relying on any specific claim in `owl_dl_rustdl.py`'s docstring or `docs/future_enhancements.md`'s RustDL entries (what it's complete on, what it silently drops vs. rejects vs. hangs on), **re-verify empirically against the actually-installed `rustdl` version first** (`pip show rustdl`) rather than propagating an old characterization forward - a `pip install --upgrade rustdl` between sessions is exactly the kind of silent-drift trigger that caused the regression above. No CI job or version-pin alert watches `rustdl`'s own releases automatically - this is a manual check, same discipline as the RDF 1.2/SPARQL 1.2 one above, just against a library's shifting behavior instead of a shifting spec text.

## `infer()`/`query()` migrated from starlayer-internal strings to real entailment regime IRIs (2026-10-07)

Found while designing `sh:entailment` support for `starlayer.shacl` (that spec's values are the real, fixed W3C SPARQL 1.2 Entailment Regimes IRIs - confirmed via direct fetch: `http://www.w3.org/ns/entailment/{RDF,RDFS,D,OWL-RDF-Based,OWL-Direct}`) - but `infer(profile=...)`/`query(entailment=...)` used their own, unrelated starlayer-internal string keywords (`'rdfs'`/`'owl-rl'`/`'rdfs+owl-rl'`/`'owl-dl'`/`'direct'`/`'rdf'`). Rather than add a translation layer at the SHACL boundary, replaced the strings with the real IRIs everywhere - a full breaking change (~197 call sites across source/tests/6 guide notebooks), on explicit user instruction, not an additive alias.

New `starlayer/graph/graph/entailment_regimes.py`: `ENTAILMENT = Namespace("http://www.w3.org/ns/entailment/")` (re-exported from `starlayer.graph`) - a `Namespace`, not individual constants, since `ENTAILMENT.RDF`/`ENTAILMENT.RDFS` would otherwise collide by bare name with `rdflib.namespace`'s own commonly-imported `RDF`/`RDFS`. `ENTAILMENT["OWL-RDF-Based"]`/`ENTAILMENT["OWL-Direct"]` need bracket access (hyphens aren't valid in a Python attribute name).

**A real, pre-existing inconsistency found and fixed along the way**: `infer()` called the OWL 2 Direct Semantics (tableau) regime `'owl-dl'`; `query()` called the identical regime `'direct'` - two different names for the same thing. Both now unify onto the one real `ENTAILMENT["OWL-Direct"]` IRI.

**API shape change, not just a value swap**: the old `'rdfs+owl-rl'` combined-profile string is gone - `infer()`'s `profile=` now accepts a single IRI or an iterable of more than one, combining naturally (e.g. `{ENTAILMENT.RDFS, ENTAILMENT["OWL-RDF-Based"]}`), matching `sh:entailment`'s own "declare several, combine into one pass" model rather than inventing a starlayer-specific combined keyword.

**Two real bugs found via testing, not assumed correct**:
1. Normalizing `profile` checked `isinstance(profile, URIRef)` - a plain leftover string like `'rdfs'` isn't a `URIRef`, so it fell through to `frozenset(profile)`, silently splitting it into individual characters (`{'r','d','f','s'}`) instead of being rejected cleanly. Fixed with an `isinstance(profile, str)` check instead (`URIRef` is itself a `str` subclass, so this correctly catches both).
2. The mechanical sweep's replacement text (`ENTAILMENT["OWL-Direct"]`, containing a literal `"`) corrupted several already-double-quoted host strings (docstrings, error messages, a `pytest.raises(match=...)` regex where `[`/`]` are also regex metacharacters). Fixed by switching to single-quote bracket access (`ENTAILMENT['OWL-Direct']`) at every such site, and shortening the affected `match=` patterns to bracket-free stable prefixes.

Verified: `tests/graph` 1527 passed (1 pre-existing, unrelated failure - `test_oxigraph_backend.py`), `tests/sparql` 351 passed, zero regressions. All 4 touched guide notebooks (`02b-graphs-inferencing`, `05e-owl-dl-reasoning`, `03b-sparql-inferencing`, `05b-backend-graph-databases`) re-executed via `nbconvert` with zero errors - which surfaced a separate, pre-existing, unrelated bug (see below).

**`infer()` gained a new regime while here**: `ENTAILMENT.RDF` (plain RDF entailment - one step weaker than RDFS) had no materialization path at all before this (`query(entailment=...)` could query-time-rewrite for it via `starlayer.sparql.entailment_rdf`, but `infer()` couldn't materialize it). Implemented natively in `_infer_rdf_before_and_delta()` - no `owlrl` dependency, just rdfD2 (every predicate used is entailed `rdf:type rdf:Property`) plus the finite RDF axiomatic triples actually relevant to the data (looked up from the RDF 1.2 Semantics spec directly, not guessed). Datatype literal value-space well-typing (rdfD1/rdfD1a) is a deliberate, documented v1 scope reduction, not built.

**Separate, unrelated, repo-wide bug found while verifying notebooks via `nbconvert`**: `from starlayergraph import ...`/`from starlayergraph.graph.owl_dl import ...` - a stale package name from before this project's own `starlayergraph`→`starlayer` merge - appears in 20+ guide notebooks across `docs/`, not just the ones this work touched. Fixed only in the 3 notebooks this work actually touched (`03b-sparql-inferencing`, `05b-backend-graph-databases`, `05e-owl-dl-reasoning`) - scoped deliberately, on explicit user instruction, not a repo-wide fix. The other ~17 affected notebooks are still broken and unrelated to this work - worth a dedicated pass later, not opportunistically expanded into here.

## `_resolve_owlrl_semantics()`'s `ENTAILMENT.RDFS`-alone dispatch suppresses owlrl's "hidden sameAs" rule (2026-10-08)

Found via a real downstream test failure (`tests/sparql/unit/test_srl_shapes.py::test_assignment_and_filter_roundtrip_conforms`), surfaced while `starlayer.shacl` disconnected its own `inference=` keyword from pySHACL's string vocabulary onto this project's real `ENTAILMENT.*` IRIs (see `starlayer/shacl/CLAUDE.md`'s same-day entry) - that work moved a caller off a path that happened to carry a protective workaround, exposing a bug that had been latent in this module since `ENTAILMENT.RDFS` support first shipped (2026-10-07).

**The bug**: owlrl's own `RDFSClosure.RDFS_Semantics.one_time_rules()` implements a "hidden sameAs" rule - for every pair of literals *anywhere* in the graph that compare equal by Python value despite different lexical form/datatype (confirmed live: `Literal(True)` and `Literal(1)`, since Python's own `1 == True`), it duplicates every triple using one literal to also use the other, across any unrelated subjects/predicates. pySHACL's own `pyshacl.inference.CustomRDFSSemantics` (`pyshacl/inference/custom_rdfs_closure.py`) overrides this same method to a no-op specifically to avoid it, with its own source comment: "breaks some SHACL validation tests." This project's `_resolve_owlrl_semantics()` used plain, unmodified `owlrl.RDFS_Semantics` for `ENTAILMENT.RDFS` alone, so every `sh:entailment`/`inference=`/direct `infer(profile=ENTAILMENT.RDFS)` caller was exposed to this bug the whole time - just never hit by an existing test until `srl_validate()`'s own migration happened to touch a literal-type collision (an `xsd:integer`/`xsd:boolean` pair compared via `"1" == True`).

**Fix, confirmed by checking rather than importing**: a small local subclass (`_NoHiddenSameAsRDFSSemantics(owlrl.RDFSClosure.RDFS_Semantics)`, `one_time_rules()` overridden to `pass`) is used for `ENTAILMENT.RDFS` alone, defined inline (not imported from `pyshacl`, to avoid a layering violation - this is `starlayer.graph`'s own general-purpose reasoning, and `pyshacl` is an optional dependency of a different, downstream package). **The combined `ENTAILMENT.RDFS` + `ENTAILMENT["OWL-RDF-Based"]` regime needed no such override** - a self-caught correction, not assumed by analogy: an initial version of this fix also no-op'd `owlrl.RDFS_OWLRL_Semantics.one_time_rules()`, which immediately broke `tests/graph/unit/test_infer.py::TestInferCombinedProfile::test_matches_owlrl_run_directly` with dozens of missing legitimate OWL-RL axioms (e.g. `xsd:byte rdf:type owl:Thing`). Reading owlrl's actual source confirmed why: `RDFS_OWLRL_Semantics.one_time_rules()` is a *completely different* method body (`full_binding_triples` plus `OWLRL_Semantics.one_time_rules(self)`) that never calls the literal-comparison logic at all - and confirmed against pySHACL's own `CustomRDFSOWLRLSemantics` too: despite the "Custom" name, its `one_time_rules()` is copied verbatim from stock `RDFS_OWLRL_Semantics`, not overridden to a no-op - pySHACL itself only ever needed the suppression for the RDFS-alone case.

Verified live (both directions): `infer(profile=ENTAILMENT.RDFS)` over `{(x, flag, Literal(True)), (y, counter, Literal(1))}` no longer produces the fabricated `(x, flag, Literal(1))`/`(y, counter, Literal(True))` cross-contamination; `infer(profile={ENTAILMENT.RDFS, ENTAILMENT["OWL-RDF-Based"]})` still produces every legitimate combined-regime axiom (`xsd:byte rdf:type owl:Thing`, universal `rdfs:Resource` typing, etc.), unchanged. `tests/graph` (excluding network-dependent integration): 1374 passed, 7 xfailed, zero regressions. `tests/sparql/unit/test_srl_shapes.py`: 5 passed (was 1 failed, 4 passed).

## `StarLayerGraph.owl_imports()`/`.resolve_imports()` + `can_resolve_import()` - generalizing SHACL's own shapes-graph import resolution into a plain graph capability (2026-10-08)

Grew directly out of adding SHACL 1.2 Profiling §2 packaging (`sh:ShapesGraph`/`rdfs:member`) to `starontology`'s own shapes files (see `starlayer/shacl/CLAUDE.md`'s dated entry) - which surfaced a real, found-not-assumed gap: `sqe_shapes.ttl`/`srl_shapes.ttl` both genuinely reference `salg:ExpressionShape`/`salg:VariableShape` (confirmed via `grep`, not inferred from file names) without defining them, and nothing in this project loaded that dependency automatically. `validator.py` already had `_resolve_shapes_graph_imports()` solving exactly this problem, but scoped only to `shacl_graph` inside `validate()` - the user asked for the same capability as a plain, reusable `StarLayerGraph` operation instead, not something bolted onto SHACL specifically.

**Design, settled across several direct questions, not assumed up front**:
- **Where does `owl:imports` normally appear, conceptually?** Overwhelmingly: one OWL ontology document importing another - this is a document-level property of "treat this resource as ontology-like," formally independent of whatever *other* `rdf:type` the subject carries (SPIN's own, pre-SHACL constraint-library convention did the identical "constraint library imports constraint library" thing SHACL 1.2 now formalizes - not a new idea, an extension of established practice).
- **Does resolving it ever happen automatically, anywhere in this project?** No, and that's deliberate - checked against the project's existing discipline (`data_graph` never mutated without `inplace=True`, no IRI ever invented without opt-in, `validate()` never fetches on its own). Confirmed live: `infer()` already treats `owl:imports` as completely inert data - an entailment that would require resolving an import simply doesn't fire, the triple just passes through unchanged.
- **Should resolution be opt-in everywhere, with no exceptions?** No - corrected mid-discussion on a direct challenge ("using an ontology with imports without doing the import leads to incomplete results... inconsistent with the desire of the ontology owner"). The real dividing line isn't automation vs. not, it's whether resolving requires reaching *outside* what's already known and local. An arbitrary caller-supplied `shacl_graph`/`ont_graph` genuinely can't be resolved safely by default (unknown IRI, network dependency, non-determinism) - but `starontology`'s own bundled files carry none of that risk, so defaulting to *not* resolving them bought no safety, only silently wrong/incomplete results for free.

**New in `starlayer_graph.py`** (added right after `infer()`, reusing its own `VALID_INFER_RETURN_MODES` constant):
- `owl_imports(self) -> tuple[Any, ...]` - direct `owl:imports` objects, deduplicated, first-seen order. A pure read; resolves nothing.
- `resolve_imports(self, *, loader, mode="full"/"delta"/"in-place", target_graph=None) -> StarLayerGraph` - the exact same three-way `mode=` contract `infer()` already established (full = self plus resolved imports in a new graph; delta = true set difference, just the newly-pulled-in triples; in-place = mutate self, return self). Recursive by construction (that's what "import" means - §3.4's imports closure - not an opt-in extra), with cycle protection and the identical `^owl:versionIRI?/owl:imports` canonical-ID handling `_resolve_shapes_graph_imports()` already got right (a graph fetched under its own declared `owl:versionIRI` is deduplicated, and further-imports-following continues from its *base* IRI, not the version IRI it was fetched under). `loader` has no default - this library still never decides retrieval policy on anyone's behalf; an unresolvable import (`loader` returns `None`) is skipped, not an error.
- `can_resolve_import(iri, *, loader) -> bool` - module-level function, not a method: it's a question about the *loader*'s own knowledge, not about any graph's data. Implemented the only honest way possible - actually calling `loader(iri)` and checking for a non-`None` result; for a loader that makes a real network request this has the identical cost as actually resolving, there's no cheaper way to ask "would this work."

**New in `starontology/__init__.py`**: `local_loader(iri) -> StarLayerGraph | None` - a `resolve_imports()`-compatible loader that only ever reads this package's own bundled files. **A real identity mismatch found and fixed while wiring it up, not assumed to just work**: `local_loader()` has to resolve against each shapes file's own *real* `sh:ShapesGraph` node (e.g. `salg:ShapesGraph`, in the vocabulary's own namespace - confirmed via direct inspection that `sqe_shapes.ttl`'s actual `owl:imports` triple points there) - which is a completely different IRI than `get_resource_iri()`'s own GitHub-blob-URL scheme (built earlier the same day for an unrelated purpose, `prof:isProfileOf`/`derive_conforms_to()`). Confirmed live before fixing: `get_resource_iri("sparql_shacl")` and `sqe_shapes.ttl`'s real import target are two different strings entirely. `docs/api-reference.md`'s `starlayer.starontology` section now carries an explicit note so a future reader doesn't assume these two identities match either.

**Verified live, not just unit-tested in isolation**: `get_ontology_graph("sqe_shacl")` alone is 142 triples and genuinely missing `salg:ExpressionShape`'s own `sh:NodeShape` definition; `.resolve_imports(loader=starontology.local_loader, mode="full")` returns 1,323 triples including it - the real gap, closed, confirmed before and after.

New tests: `tests/graph/unit/test_resolve_imports.py` (20 cases - direct imports, dedup, unresolvable-import-is-skipped-not-an-error, all three modes including delta's true-set-difference semantics and in-place's `target_graph` rejection, invalid `mode=`, a 3-hop transitive chain, an import cycle that must terminate without duplicating content, and the `versionIRI`-redirected-import reconvergence case specifically). `tests/starontology/unit/test_starontology.py::TestLocalLoader` (6 cases, including the specific "`sqe_shacl` alone is missing the definition" / "resolving closes the gap" pair, and confirming an entry with no `owl:imports` at all - `skos_shacl` - is an unaffected no-op).

Full `tests/graph/unit` suite (excluding two files already confirmed, independently of this work, to hang in this particular environment - see below): 1158 passed, zero regressions. `tests/starontology`: 37 passed.

## `StarLayerGraph.from_rdflib()` now preserves the source graph's own `.identifier` (2026-10-09)

Found while discussing a `starlayer.shacl` feature request (auto-filling SHACL validation-report provenance from a graph's own identity - see `starlayer/shacl/CLAUDE.md`'s same-day entry for the full design): `from_rdflib()` always built the converted graph via a bare `g = cls()`, which gives every new graph a fresh random `BNode` identifier - silently discarding whatever real `.identifier` the source graph had (e.g. `Graph(identifier=URIRef(...))`, or - more consequentially - any named graph retrieved from a `Dataset`/`StarLayerDataset` via `.graph(iri)`, which always carries that real IRI as its own identifier). Confirmed live before fixing: `StarLayerGraph.from_rdflib(some_real_identified_graph).identifier` came back a completely unrelated `BNode`, every time.

**Fixed**: `g = cls(identifier=source_graph.identifier)` instead of `g = cls()` - a correctness fix to this method's own stated "wrap" contract (its docstring already says "Wrap a plain rdflib.Graph"), not scoped to any one caller. This is the mechanism that makes `StarShaclSchema.validate()`'s new identifier-based provenance fallback actually work when a data/shapes graph flows through `normalize_graph_inputs()` (which calls `from_rdflib()` for any non-`StarLayerGraph` input) - without this fix, a plain `rdflib.Graph(identifier=...)` or dataset-sourced named graph would have lost its identity before `validate()` ever got a chance to read it.

**One deliberate exception, found via a live deprecation warning, not assumed**: when `source_graph` is itself a whole `Dataset`/`ConjunctiveGraph` (not one of its named graphs), `.identifier` is **not** read or preserved - confirmed live that `Dataset.identifier` is itself deprecated in this rdflib version, and a `Dataset`/`StarLayerDataset()` can't even be constructed with `identifier=` directly anymore (`TypeError`). A whole dataset has no single meaningful identity of its own the way one graph does, so there's nothing worth preserving there, and reading it would needlessly trigger the deprecation warning on every dataset-to-graph conversion. A named graph *retrieved from* a dataset (`ds.graph(iri)`) is a completely different object with its own real, non-deprecated identifier, and is unaffected by this exception.

New tests, `TestFromRdflib` in `test_starlayer_graph.py`: identifier preserved for a plain `Graph(identifier=...)`; the ordinary no-identifier (`BNode`) case still works unchanged; a whole `Dataset` source doesn't trigger the preservation (or the deprecation warning); a named graph pulled out of a `Dataset` via `.graph(iri)` does preserve its own real identifier.

Full `tests/graph` suite: 1553 passed (4 new - 1 pre-existing, unrelated `test_oxigraph_backend.py` failure, unchanged), zero regressions. Deprecation warning count dropped from 273 to 271 (the two `Dataset.identifier` warnings the unguarded version would have triggered during the suite).

## `__len__()` fast path for the no-triple-terms case - found via a real retrospective performance audit (2026-10-12)

Found while diagnosing why the test suite ran far slower than expected - `cProfile` on one `starlayer.sparql.salg.sparql_shapes.validate_query()` call (against a trivial, triple-term-free shapes+ontology graph, ~1700 triples) showed `StarLayerGraph.__len__()` called **21,049 times** by pySHACL's own internal shape/constraint-evaluation bookkeeping, each call doing `sum(1 for _ in self.triples((None, None, None)))` - a full scan-and-filter of every triple, regardless of whether there was anything to filter. 28.9 million `triples()` iterations, ~104s of a 114s total call.

**The fix**: when `self._tt_registry` is empty - no triple term has ever been registered in this graph instance - there is nothing for `triples()`'s own encoding-triple filtering to do, so `len(graph)` can just be the underlying store's own count (`super().__len__()`, which for the default in-memory `Memory` store is a plain dict length, genuinely O(1) - confirmed by reading `rdflib.plugins.stores.memory.Memory.__len__`'s own source) instead of re-deriving the same number via a full filtered iteration. This reuses an *already-established, already-trusted* invariant in this exact class - `infer()`'s own `fast_path = not self._is_native and not self._tt_registry` (treats an empty-registry graph as safe to read directly, no triple-term-aware handling needed) - rather than inventing a new one; `_is_encoding_triple()`'s own check (`str(s).startswith(TT_NS)`) can only ever be `True` for a triple the registry would already know about, so an empty registry really does mean "nothing to filter," not just "probably nothing."

**Impact, measured**: the one call above: 31s → 1.4s (~22x) before the sibling `meta_validate()` cache fix (see `starlayer/shacl/CLAUDE.md`'s same-day entry) cut the remainder further. `tests/graph/unit/test_starlayer_graph.py`+`test_dataset.py`: 201 passed, zero regressions (pure performance fix, no observable behavior change - `__len__()`'s own contract, "count of visible triples," is unchanged for every graph, including ones that *do* have triple terms registered, which still take the original, correct, filtered path).

Fixed both: merge the full remainder of `rest3` once it starts with `^^`/`@` (N-Triples' own grammar guarantees nothing else follows), and added `normalize=False`.

## VERSION directive: a real gap in `sparql_api.py`/`.update()`/the remote rdf-1.1 update path, not the "completely unsupported" first impression (2026-10-13)

Follow-up to the string-function retrofit above, investigating the other finding from the same `lang-basedir` retrospective: a quick test of `starlayer.sparql.parse12.prepare_query_12('VERSION "1.2"\n...')` failed outright, suggesting the whole `VERSION "1.2"` prologue directive (SPARQL 1.2 Query sec 4.3) was unimplemented. The user pointed at an existing guide notebook (`docs/guides/03-sparql.ipynb` §1.3) before any fix started - it already demonstrates `StarLayerGraph.query('VERSION "1.2"\n...')` working correctly, including the `SPARQL12ConformanceWarning` mismatch case. So the real first finding was that `parse12.py`'s own entry points were never *meant* to understand `VERSION` directly - `version_directive.py`'s own module docstring already says it "must always be stripped before ordinary parsing," and the established pattern (`query_cache.py`, the function backing `.query()`) is exactly that: the caller strips it first, then calls `prepare_query_12()` on the stripped text. Testing `prepare_query_12()` directly, bypassing that caller, was testing the wrong layer - not a real gap on its own.

**The real gap, found by then checking every other caller of `parse12.py`'s four entry points** (`grep` across the whole package, not assumed complete from `query_cache.py` alone): `strip_version_directive()` is called from exactly one place, `query_cache.py` (`.query()`'s own backing function). Every other caller skips it and calls `prepare_query_12`/`prepare_update_12`/`parse_query_12`/`parse_update_12` directly on raw, unstripped text - confirmed live that each one genuinely crashes on a leading `VERSION` line:
- `StarLayerGraph.update()`/`StarLayerDataset.update()`'s own local-store text branch (`starlayer_graph.py`, `starlayer_dataset.py`).
- `starlayer.graph.query.sparql_api`'s four public functions (`parseQuery`/`prepareQuery`/`parseUpdate`/`prepareUpdate`) - this module's own docstring explicitly advertises them as drop-in replacements for rdflib's originals "when working with SPARQL 1.2 queries," the same advertised purpose `.query()`/`.update()` already satisfy correctly.
- `native.py`'s `native_update()`, specifically its `backend='rdf-1.1'` (remote, non-native) branch - it locally parses text via `prepare_update_12()` to re-render it as plain SPARQL 1.1 before POSTing to an endpoint with no triple-term notion at all. The sibling `backend='rdf-1.2'` branch is correctly unaffected (sends text straight through unmodified to a real SPARQL-1.2-aware endpoint, see `check_native_version_conformance()`'s own docstring).

**Deliberately not fixed, judged out of scope**: `starlayer/shacl/meta_shapes.py`'s own `_validate_sparql_function_syntax()`, which calls `starlayer.sparql.prepare_query_12()` directly on `sh:select`/`sh:ask`/`sh:construct` text extracted from a SHACL shape. A shape author writing `VERSION "1.2"` inside an embedded SPARQL query is a genuinely rare case, and the function already fails with a clear, actionable `ConstraintLoadError` naming the predicate and the underlying parse error - not a silent or confusing crash. New tests, `tests/graph/unit/test_conformance.py` (16 new, alongside the existing `.query()`-only coverage that motivated checking this at all): `TestSparqlUpdateVersionDirective` (both classes' `.update()`), `TestSparqlApiVersionDirective` (all four `sparql_api` functions), `TestNativeBackendRemoteRdf11UpdateVersionDirective` (the `native_update()` remote-rdf-1.1 branch, exercised with a `SimpleNamespace` fake store + a monkeypatched `http_update()` capturing the final POST body - no live endpoint needed, same "pure logic, no network dependency" testing precedent `TestNativeBackendVersionConformance` already established for the sibling `rdf-1.2` branch's own conformance check).

## Embedded-pyoxigraph transport for the native (`backend='rdf-1.2'`) backend - a second way to reach native RDF 1.2 semantics, with no HTTP at all (2026-10-16)

Grew out of a user question about how `infer()` handles a backend-stored graph (answer: it reads once into memory first, specifically to avoid `owlrl`'s own naive per-cycle full-rescan behavior - see the `infer()` docstring), which led to the adjacent question of whether `pyoxigraph` (Oxigraph's embeddable, in-process Python binding - the same Rust engine the HTTP native backend already talks to over a wire, confirmed by reading `owlrl`'s own `__init__.py`, which lists `pyoxigraph` as an *embedded* store option, not a remote-server client) could back `StarLayerGraph` directly.

**Confirmed live before designing anything, not assumed**: `pyoxigraph.Store` natively supports real RDF 1.2 triple terms (`<<( s p o )>>`, not RDF-star's old `<<>>`) and `dirLangString` base-direction literals - round-tripped both directly against a bare `pyoxigraph.Store()`. `oxrdflib` (the existing third-party rdflib `Store` adapter wrapping `pyoxigraph`) **cannot** carry that fidelity through rdflib's generic `Graph`/`Store` API - its own `_converter.py`'s `to_ox()`/`from_ox()` have no case for a triple-term-valued term at all (one direction raises `ValueError`, the other returns a bare, unusable tuple) - so `StarLayerGraph(store=<oxrdflib store>)` only ever reaches this project's own `tt:HASH` synthetic encoding (the default `backend='rdf-1.1'` path), never real `backend='rdf-1.2'` semantics. Also confirmed live: `pyoxigraph`'s storage is RocksDB-based with a real single-writer lock per on-disk directory (`OSError: ... LOCK: Resource temporarily unavailable` for two simultaneous read-write opens) - the embedded transport and a separately-running `oxigraph serve` HTTP server can never both be read-write owners of the same directory at once; accepted as a property of the storage engine, not something to design around.

**Design, confirmed by a dedicated validation pass (a fresh agent instructed to find holes, not just agree) before implementing**: `_is_native` (`starlayer_graph.py`, `self._backend == 'rdf-1.2'`) is a *semantic* flag, independent of transport - every one of its ~27 gated call sites already funnels through a handful of chokepoints (`resolve_store_http()`, `native_query()`, `native_update()`) rather than doing HTTP inline, so only those chokepoints needed to learn a second transport, not every call site. `sparql_term()`/`_native_scoped()` (term/pattern → SPARQL text) are already 100% engine-agnostic - `pyoxigraph` parses the identical `<<( )>>`/`@lang--dir` syntax `native.py` already emits for a real endpoint.

## Entailment fix: a term that exists only *inside* a triple term was getting spuriously typed `rdfs:Resource`/`owl:Thing` (2026-10-16)

Found while explaining how `infer()`/`query(entailment=...)` handles triple terms at all - walking through the mechanism live surfaced a real, confirmed bug, not a hypothetical. Repro: `ex:manages rdfs:domain ex:Manager ; rdfs:range ex:Employee`, with `ex:bob`/`ex:alice` appearing **only** inside a triple term (`ex:claim1 rdf:reifies <<( ex:bob ex:manages ex:alice )>>`) - nowhere else in the graph. `infer(entailment=ENTAILMENT.RDFS)` produced `ex:bob a rdfs:Resource`/`ex:alice a rdfs:Resource`, even though neither term was ever asserted as a subject or object of any real triple - they only exist as components of a *quoted, unasserted* triple the triple term names.

**Root cause**: every reasoning entry point (`_infer_before_and_delta()` for owlrl-backed RDFS/OWL-RL, `owl_dl.py::classify_owl_dl()` for HermiT, `owl_dl_rustdl.py::classify_owl_dl_rustdl()` for RustDL) called `starlayer.graph.compare._decompose()` before handing data to a reasoner (none of owlrl/HermiT/RustDL understand RDF 1.2 triple terms - one in subject position would crash them outright). `_decompose()` replaces a triple term with a fresh blank node **plus synthetic `tt:subject`/`tt:predicate`/`tt:object` triples describing its contents** - triples that were never actually asserted. RDFS's universal "every subject/object of every triple is `rdfs:Resource`" rule (and OWL's analogous universal `owl:Thing` typing) then fires on these synthetic triples as if they were real data - a conclusion the rule never licensed from the real graph. The rule's actual target was "the triple term itself is a resource" - true under RDF 1.2 semantics, but **unwritable**, since RDF 1.2 forbids a triple term in subject position of any triple, entailed or not. **Confirmed not at fault**: `_infer_rdf_before_and_delta()` (the native, no-owlrl rdfD2 rule) never calls `_decompose()` at all and was already correct.

**Fix, agreed with the user before implementing**: don't decompose a triple term's full inner structure for entailment purposes - replace it with an **opaque** placeholder blank node (no `tt:subject`/`tt:predicate`/`tt:object` edges at all), so the reasoner never sees `ex:bob`/`ex:alice` as "appearing" anywhere. The placeholder itself still picks up spurious facts this way (e.g. `_:ph a rdfs:Resource`, since it's genuinely the object of the real triple `ex:claim1 rdf:reifies _:ph`) - those get filtered out of the final delta afterward, equally unwritable back in terms of the real triple term.

**New dispatching function, `compare.py::_decompose_for_entailment(graph) -> (Graph, frozenset)`** - the one entry point all three reasoning call sites now use, replacing their own `_decompose()` calls. `_decompose()` itself is untouched - `isomorphic()`/`graph_diff()`/`to_isomorphic()`/`to_canonical_hash()` and `rdfc.py`'s RDFC-1.0 canonicalization genuinely need the full recursive expansion (two graphs with different triple-term *content* must compare as non-isomorphic/hash differently), confirmed as the only other callers via `grep`. Dispatches on `_is_native`:

- **Generic (`compare.py::_decompose_for_entailment_generic()`)** - in-memory or any non-native backend. A local dict maps each **distinct `TripleTerm` value** (the class already implements `__eq__`/`__hash__` via its own `_key()`, so the object works directly as a dict key) to one freshly-minted placeholder `BNode`, deduplicated within the one call - no recursion into the triple term's own structure at all (handles nesting "for free," since nothing inside it is ever visible). Dedup matters for real correctness, not just tidiness: two different reifiers of the *identical* triple-term value need to map to the *same* placeholder for an `owl:InverseFunctionalProperty`-style rule to still correctly derive `reifier1 owl:sameAs reifier2` between them - a conclusion about two real subjects that must survive the delta filter below.
- **Native-optimized (`native.py::decompose_for_entailment()`)** - direct user request, found while discussing the fix: for a native graph, an ordinary read (`triples()` → `_native_triples()`) fetches a triple term's *full* nested structure across the wire/FFI boundary only to immediately discard it - wasted cost that scales with how large/deeply-nested the triple term is, unlike an in-memory graph where the `TripleTerm` object is already sitting in RAM for free. Fixed with **two queries instead of one**: `SELECT ?s ?p ?o WHERE { ... FILTER(!isTRIPLE(?o)) }` for ordinary data, then `SELECT ?s ?p WHERE { ... FILTER(isTRIPLE(?o)) }` for triple-term rows - **`?o` is deliberately never projected** in the second query, so the engine only confirms the pattern matches and never serializes the triple term's content back to the client at all. `isTRIPLE()` is already relied on elsewhere in this project (`test_cross_backend_parity.py`'s `_scenario_is_triple_fn`) and works identically against Fuseki/ARQ, Oxigraph-HTTP, and embedded pyoxigraph. **Documented trade-off, accepted deliberately**: since `?o`'s value is never fetched, this path cannot deduplicate placeholders by value the way the generic path does - two reifiers of the identical triple-term value, read from a native graph, will *not* get `owl:sameAs` derived between them (confirmed via a dedicated test asserting the *absence*, so a future accidental fix to this gap doesn't go unnoticed either way). Doesn't affect the actual bug fix - both paths produce placeholders that get filtered identically.

**All three call sites updated identically**: `before, placeholders = _decompose_for_entailment(graph)` instead of `before = _decompose(graph)`, and the existing `before_set`-diffing loop that builds `delta` gained one more check - `if t[0] in placeholders or t[2] in placeholders: continue`. The subject-position check matters even though a placeholder only ever starts out in *object* position in the real data: once the reasoner runs, a derived triple can legally put the placeholder (an ordinary BNode) in subject position (`_:ph a rdfs:Resource` - rdfs4b typing it as the object of the real reifying triple). Nothing else needed to change - `before` is never surfaced to a caller directly (`infer()`'s `mode="full"` branch already reads real triple terms back from `self`, not from `before`), so only `delta` needed filtering, and every one of `infer()`'s `mode=`/`query()`'s OWL-RL/OWL-Direct fallback-path consumers inherited the fix automatically with zero changes of their own.

**HermiT/RustDL verified safe but not sharply provable**: live-tested both engines directly against the exact repro shape - confirmed the fix doesn't crash either and that `ex:bob`/`ex:alice` never leak into the closure. Could not construct a repro proving a *behavior difference* for either, though: confirmed live (including against completely ordinary, triple-term-free data) that neither `classify_owl_dl()`'s own class-assertion extraction nor `classify_owl_dl_rustdl()`'s currently materializes `rdfs:domain`/`rdfs:range`-driven class membership at all - a separate, orthogonal, pre-existing limitation of the current integration, unrelated to this fix, so there was no live case available where the old code would have actually produced a spurious fact to compare against. The fix is still correctly, defensively applied to both (same architecture, same root cause), and the native-path optimization's benefit is unconditional regardless.

**Test fixes**: two existing tests (`test_infer.py::TestInferDelta::test_triple_term_case_still_correct`, `TestInferWithTripleTerms::test_delta_matches_owlrl_run_on_the_same_decomposition`) built their own "oracle" by calling `_decompose()` directly with no filtering - both needed updating to use `_decompose_for_entailment()` + the same placeholder filter, since the old oracle faithfully reproduced the bug and was no longer a valid reference for what the fixed `infer()` should produce. No other existing test depended on the buggy interaction (confirmed via `grep` across every triple-term-bearing test file for `Resource`/`owl.Thing` assertions).

**New test coverage**: `test_infer.py` gained the core bug-fix repro (confirms `ex:bob`/`ex:alice` absent, `ex:claim1`/domain/range unaffected) and the `sameAs`-dedup payoff test (two reifiers of the identical value, `owl:InverseFunctionalProperty`, confirms `sameAs` still derived). `test_oxigraph_embedded_backend.py` gained the same bug-fix repro against the native-optimized path, the documented trade-off asserted explicitly (`sameAs` *not* derived for a native graph's two reifiers of the identical value), and a direct structural check that `decompose_for_entailment()`'s placeholder carries zero leaked edges. `test_infer_owl_dl.py`/`test_infer_owl_dl_rustdl.py` gained honestly-scoped smoke coverage for HermiT/RustDL (no crash, no leak - see the "verified safe but not sharply provable" note above for why these can't assert a behavior difference).

Verified: `test_infer.py`/`test_infer_owl_dl.py`/`test_infer_owl_dl_rustdl.py`/`test_entailment.py` 100 passed; `test_oxigraph_embedded_backend.py` 17 passed; `test_compare.py`/`test_rdfc.py` (confirming `_decompose()`'s own isomorphism/canonicalization callers are completely untouched) unchanged and passing.

## Terminology cleanup ("backend" was three different things) + `set_default_representation()` (2026-10-16)

While designing a process-global default for native in-memory Oxigraph, a user question surfaced that the word "backend" had been used, across this codebase's own docs and this session's conversation, for three genuinely independent things - confirmed and settled with the user directly, not just asserted:

- **Representation** - how a triple term is stored: `rdf-1.1` (synthetic `tt:HASH` encoding) vs. `rdf-1.2` (genuine native triple-term storage). This is the real, shipped `StarLayerGraph(backend=...)` parameter's *only* job; `_is_native` is `True` exactly when representation is `rdf-1.2`.
- **Transport** - where the store physically lives relative to this process: in-process (Python `Memory` dict, or embedded pyoxigraph) vs. remote (HTTP to a separate Fuseki/Oxigraph server).
- **Persistence** - whether a store writes to disk: ephemeral vs. persisted.

**Confirmed independent, not assumed**: a remote Fuseki/Oxigraph server can be run `--mem` (ephemeral) - this project's own `benchmarks-graph/README.md` already does exactly this; `embedded_oxigraph_store(path=...)` is in-process yet persisted to a real RocksDB directory (proven by this session's own `TestEmbeddedCloseReopen`). Neither Transport value implies a Persistence value.

**Decision, explicit**: the real, shipped `backend=` constructor parameter is *not* renamed - that's a separate, much larger breaking-change effort (same discipline as the historical `profile=`→`entailment=` rename, same file, earlier entries). What changed: the new API below uses "representation" explicitly rather than adding a fourth overloaded sense of "backend," and prose across the guide notebooks/docs was corrected wherever it said "backend" but actually meant Transport or a blend. New "## Terminology" section added to `docs/graph/starlayergraph.md` as the one authoritative home; every other edit links back to it rather than re-deriving the table. Files corrected: `starlayergraph.md` itself (the "Backends" Core Concepts bullet, the blank-nodes section, the Package Structure table - all previously stated "native rdf-1.2 talks via HTTP" as if inherent to Representation, which the embedded-pyoxigraph path already contradicts), `starlayergraph_vs_rdflib.md` and `sparql12_design.md` (same stale HTTP-is-inherent claim, two and three sentences respectively), `shacl/compatibility.md`'s "Backend Compatibility" table (was a Transport×Representation matrix mislabeled as one axis, missing the now-real "in-process, rdf-1.2 native" column entirely), `docs/guides/06b-backend-graph-databases.ipynb` (title/intro/section 2/3 reworded; section 1's intro had an outright contradiction - "native RDF 1.1 modes" - fixed; section 1.2's `entailment="native"` flagged as a second, unrelated sense of "native" coexisting in the same notebook), `docs/guides/README.md`'s 06b index entry, `performance.md`'s five section headers and closing footnote (was a flat "backend" list conflating all three axes across six real configurations, only four of which `bench_scaling.py` actually measures), and `docs/guides/04f-shacl-subgraph-extraction.ipynb` (one minor "backend iteration order" → "store iteration order" slip).

**A real, confirmed-live finding surfaced while writing the `shacl/compatibility.md` table update, not assumed**: `validate()` (any `meta_shacl` setting, including a real BNode focus/value node) works correctly against an embedded (`embedded_oxigraph_store()`-backed) graph - confirmed live with both a plain class-based violation and a BNode-focus-node violation, neither hitting the known HTTP-specific gap from the earlier embedded-backend entry above. `apply_rules()` against the same graph, however, *does* hit that known gap - but only with `meta_shacl=True` (the default for most profiles), and only because meta-shacl's own structural check of the shapes/rules graph itself can contain a blank-node rule/shape structure (e.g. `sh:rule [ a sh:TripleRule ; ... ]`) that triggers a violation-report-rendering path needing `pySHACL`'s `find_node_named_graph` - confirmed by reproducing the exact `RuntimeError` the earlier guard now raises, and separately confirming `apply_rules(g, meta_shacl=False)` works cleanly against the identical graph. The compatibility table now states this precisely rather than a blanket status.

**New API, `starlayer_graph.py`**: `set_default_representation(store_factory, representation='rdf-1.2')`/`get_default_representation()` - a plain, permanent, process-global `(store factory, representation)` pair `StarLayerGraph()`/`StarLayerDataset()` pick up when constructed with no explicit `store=`/`backend=` of their own. Deliberately a *factory* (zero-arg callable returning a fresh `Store` each call, e.g. `embedded_oxigraph_store` itself, whose own `path=None` default already matches the required shape) - never a `Store` instance directly, since every "new" graph needs its own independent store. **Deliberately a plain global, not a context-manager-scoped one, on explicit user instruction**: *"I would like the simpler global version. a developer using this platform would set the global default for what they want. Not expected that they would shift between types."* An earlier draft of this feature wrongly proposed a second mechanism (`oxrdflib`'s `OxigraphStore` under the default `backend='rdf-1.1'`) for the "always want Oxigraph" case - corrected by the user: that would throw away real triple-term fidelity in favor of the `tt:HASH` encoding, exactly backwards from why anyone would reach for Oxigraph in-memory in the first place. The existing `embedded_oxigraph_store()` + `backend='rdf-1.2'` combination (already in-memory when `path=None`) is already the right answer for both per-graph and default use - nothing new needed there.

**The real implementation wrinkle**: `StarLayerGraph.__init__`/`StarLayerDataset.__init__` both had `backend: str = 'rdf-1.1'` hardcoded into the signature - meaning by the time code runs inside `__init__`, there's no way to distinguish "caller explicitly chose `'rdf-1.1'`" from "caller said nothing at all," and those must be treated differently (an explicit choice must never be silently overridden by a global default; omission should pick it up). Fixed by changing the signature default to `backend: str | None = None` and resolving `None` early - confirmed via the full suite that this is behavior-identical to the old hardcoded default for every one of ~3800 existing bare constructions, since none of them call `set_default_representation()`. `store` needed no equivalent treatment - it's never a named parameter of either `__init__` at all (flows through `*args`/`**kwargs` to `super().__init__()` untouched), so the pre-existing `len(args) < 1 and 'store' not in kwargs` check (already used one line below, in `StarLayerGraph.__init__`, for the unrelated rdf-1.2-identifier-defaulting case) already correctly detects "caller gave no store at all." The resolution logic is identical in both classes, confirmed deliberately so a bare `StarLayerDataset()` and a bare `StarLayerGraph()` always agree on what a configured default means - an explicit `backend='rdf-1.2'` with no store still picks up the configured default's store (incidentally fixing today's pre-existing gap where that combination alone just fails the first time a native method runs); an explicit `backend='rdf-1.1'` or any explicit `store=` always fully overrides the default, never silently clobbered.

New test file `tests/graph/unit/test_default_representation.py` (11 cases, autouse fixture resetting the global after every test - necessary given it's a genuinely unscoped process global): no-default baseline for both classes, default picked up by both classes, explicit `backend='rdf-1.1'` override never clobbered, explicit matching `backend='rdf-1.2'` with no store still gets the default's store, explicit `store=` overrides entirely, two graphs get independent stores (not a shared one), reset-to-`None` restores ordinary behavior, and `representation=` validation (including that it's ignored, not validated, when `store_factory=None`). `starlayer/graph/__init__.py` gained `set_default_representation`/`get_default_representation` re-exports. `docs/guides/06b-backend-graph-databases.ipynb` gained a new "3.1 Setting this as the process-global default" subsection demonstrating the one-liner.

## The embedded-transport gap in `starlayer.shacl`'s `_patch_stringify_for_native_backend_bnodes()` (left unsupported in the entry above) is now fixed (2026-10-16)

Direct follow-up, same day: the entry above's own HTTP-only `find_node_named_graph` fallback, guarded with a `RuntimeError` for embedded stores, got challenged directly - "isn't embedded inconsistent with http?" - before just swapping in a fix on the assumption it would be safe. Investigated two concrete candidate asymmetries before concluding it was actually safe: (1) the fallback constructs several throwaway `StarLayerGraph` wrappers sharing the *same* underlying store object - `EmbeddedOxigraphStore.close()` has real teeth (drops the reference, releases pyoxigraph's RocksDB lock) unlike `SPARQLUpdateStore.close()`, so closing one wrapper could break every other graph sharing that store, including the caller's own - ruled out because neither `rdflib.Graph` nor `StarLayerGraph` defines `__del__`, so no GC-triggered auto-close can reach it, and nothing in the fallback's own code calls `.close()` on a wrapper either; (2) the discovery query (`SELECT DISTINCT ?g WHERE { GRAPH ?g {...} }`) can never find a node sitting in the store's own true default graph (a plain SPARQL-semantics fact, not transport-specific) - confirmed symmetric across both transports, not a new embedded-specific blind spot.

**The fix**: `_patched_find_node_named_graph`'s own discovery query - previously hardcoded to `resolve_store_http(dataset.store, "rdf-1.2")` + `http_select(...)`, HTTP-only - now goes through `starlayer.graph.backends.native.execute_select(dataset.store, "rdf-1.2", sparql)`, the same transport-agnostic dispatcher `StarLayerGraph` itself already uses for every native operation (`_native_add`/`_native_triples`/etc., see the first entry in this file). `execute_select()` branches internally on `_is_embedded(store)` between the HTTP path (unchanged) and `native_pyoxigraph._ox_select()` for an embedded store - nothing else in the fallback (the per-graph `StarLayerGraph` reconstruction, the subject-then-object search order, the `LookupError` on a genuine miss) needed to change at all, since all of that already worked through `StarLayerGraph.triples()`, which was never HTTP-specific in the first place. The Phase-1 `hasattr(dataset.store, '_ox_store')` → `RuntimeError` guard is removed outright, not just loosened.

**Confirmed, via a live spy on `pyshacl.rdfutil.stringify.find_node_named_graph`, exactly which path actually reaches this fallback for an embedded store** - not assumed symmetric with the HTTP case: ordinary `validate()`/`apply_rules()` always re-encode `data_graph`/`shacl_graph` through `TripleTermAdapter` into a plain in-memory graph before handing anything to pySHACL, so pySHACL's own internal `rdflib.Dataset` is never built directly around the real `EmbeddedOxigraphStore` in that path - a BNode value/focus node in an *ordinary* validation report never reaches `find_node_named_graph`'s broken original implementation at all for an embedded graph, so there was nothing to regression-test there. `meta_validate()` (`meta_shapes.py`) is different: it passes `shapes_graph` straight to `pyshacl.validate()` with no snapshot/re-encode step (the snapshot-first branch is scoped to `StarLayerGraph._needs_bnode_skolemization`, `True` only for the unrelated rdf-1.1+`SPARQLUpdateStore` combination) - so pySHACL's `Dataset` really is built directly around the embedded store there, and a blank node inside the shapes graph itself (e.g. a `sh:rule [ a sh:TripleRule ; ... ]` blank node) is exactly what reaches the fix.

Verified live: `apply_rules(meta_shacl=True)` against an embedded graph whose shapes carry exactly that blank-node `sh:rule` structure - the precise repro that motivated the original guard - now conforms and infers correctly instead of raising `RuntimeError`. `docs/shacl/compatibility.md`'s "Backend Compatibility" table's `apply_rules()` column updated from ⚠️ to ✅, and its own explanatory footnote rewritten to describe the fix rather than the gap.

New test, `tests/shacl/integration/test_native_backend_embedded_oxigraph.py` (no live server needed, unlike its HTTP/remote sibling `test_native_backend_oxigraph.py`) - confirmed adversarially, not just written and trusted: fails with the exact pre-fix `RuntimeError` when run against `validator.py` as it stood before this entry's fix (checked via `git stash` on just that one file), passes cleanly after.

Full `tests/` suite (`-m "not integration"`): 3832 passed (1 new), zero regressions - the only failure observed (`test_target_where_candidate_not_excluded_by_unrelated_focus_node_data`) is the same pre-existing, order-dependent flake already documented elsewhere in this file, unrelated to this change.

## A real pyoxigraph/Oxigraph engine crash found by forcing the embedded transport on as the global default for the whole suite (2026-10-16)

Direct follow-up to a user question - "have we run all the tests with an oxigraph embedded?" - answered by actually doing it: a temporary, diagnostic-only `conftest.py` fixture calling `set_default_representation(embedded_oxigraph_store)` before every single test (function-scoped, not session-scoped - `test_default_representation.py`'s own autouse teardown resets the global to `None` after each of its tests, so a session-scoped "set once" fixture would get silently clobbered for the rest of the suite the moment that file ran, a real contamination mistake caught and fixed mid-investigation before trusting any result), then running the full `pytest` suite with it in place. Not something to leave in the repo - removed again once the investigation finished.

**Found a real, confirmed upstream engine bug, not a test artifact**: the suite aborted entirely (`Fatal Python error: Aborted`) at `tests/graph/unit/test_dirlangstring.py::test_strlangdir_constructs_matching_value` - a SPARQL query comparing a stored `dirLangString` value against one constructed via `STRLANGDIR(...)` for equality. Isolated to a 6-line repro, then reduced further to **bare `pyoxigraph`, zero starlayer code involved at all**: `thread '<unnamed>' panicked at lib/spareval/src/dataset.rs:350:27: internal error: entered unreachable code` - a hard process abort (`SIGABRT`), not a Python exception, uncatchable with `try`/`except`.

**The real trigger is narrower and more general than the first repro suggested - confirmed by testing several variants directly, not assumed from the first reproduction's own shape.** User asked directly: is there a scenario where `STRLANGDIR()` does *not* crash? Testing found: plain construction via `STRLANGDIR()` (no comparison) works fine; plain reading of a stored `dirLangString` value works fine; `sameTerm(?t, ?t)` on one works fine. But `FILTER(?t = ?t)` - self-equality on a *single* stored value, no `STRLANGDIR()` involved anywhere - crashes identically, as does comparing two independently stored values, and comparing two `STRLANGDIR()`-constructed values with no stored data at all. **The actual bug: SPARQL `=` (value equality) panics on *any* `dirLangString`-typed term, unconditionally** - an `unreachable!()` in `spareval`'s per-datatype value-equality dispatch missing a case for `rdf:dirLangString`. `STRLANGDIR()` was simply the first way this got exercised, not the cause. `sameTerm()` (exact term equality, a different operator) is unaffected and is a viable workaround.

**Confirmed against both released forms of the engine, not just the embedded binding**: the identical query, sent over HTTP to this project's own local Oxigraph test container (`ghcr.io/oxigraph/oxigraph`, reporting itself as `0.5.9` - the embedded binding here is `pyoxigraph` `0.5.11`), crashed the **server process itself** (`docker ps` showed `Exited (133)`, `133 = 128 + SIGABRT` - the identical signal). The client saw nothing but a `ConnectionError`/`RemoteDisconnected`, since the server died before writing any response at all. Recovered with a plain `docker restart` (confirmed healthy again via a follow-up request) - not a destructive or unrecoverable action, but a real one worth being deliberate about before trying.

**Why the existing test suite never already caught this**: `test_dirlangstring.py`'s own `TestSparqlFunctions` tests run correctly today only because the suite's *actual* default representation is the ordinary, non-native `rdf-1.1` (tt:HASH-encoded, plain `rdflib.Memory` store) backend - no Oxigraph engine involved at all unless a test opts into one explicitly. Nothing in the existing, narrowly-scoped embedded tests (`test_oxigraph_embedded_backend.py`, `test_native_backend_embedded_oxigraph.py`, etc.) ever combined a `DirLangString` value with an embedded/native Oxigraph graph - this specific combination had simply never been exercised before this diagnostic.

**Confirmed as Oxigraph-specific, not a spec ambiguity, via a direct user request to check Fuseki too**: ran the identical scenario table against this project's own local Apache Jena Fuseki test server (`atomgraph/fuseki:6.1.0`) - both via raw HTTP and via `StarLayerGraph(store=SPARQLUpdateStore(...), backend="rdf-1.2")` (the project's own native code path, not bypassed). Every case - construction, plain read, `sameTerm()`, self-equality (`?t = ?t`), and `?t = STRLANGDIR(...)` - returned a correct result through either access path, server staying healthy throughout. Rules out "the SPARQL 1.2 spec is ambiguous and both engines reasonably disagree" - Jena/ARQ implements `dirLangString` value-equality correctly, so this is specifically a gap in Oxigraph's `spareval` crate. Added to the notebook as a (gracefully-skipping-if-no-server) runnable section and to the doc's own Issue #2.

## `use_baseline_representation=True` - internal scratch graphs stop silently inheriting a process-global default (2026-10-16, same day)

Direct follow-up, same investigation: the "full suite under embedded Oxigraph" diagnostic above didn't just surface the dirLangString engine crash - it also uncovered what looked like a hang at 94% progress. Live profiling (macOS `sample`, since `py-spy` wasn't installed) showed 100% CPU with no I/O wait - not a deadlock - and bisecting down to the exact stuck call found the real cause: `starlayer.sparql`'s `to_rdf.py::_new_starlayer_graph()` (the default graph for `query_to_rdf()`'s own query-as-RDF encoding) called bare `StarLayerGraph()` - which, with a global default configured, silently became an embedded-Oxigraph-backed graph instead of the intended fast `Memory` store. That scratch graph (792 triples for one real W3C fixture's query algebra) gets walked back out by `rdf_to_query()` via many small, individual triple-pattern lookups - each paying a full SPARQL-engine round trip instead of a near-free Python dict lookup once backed by Oxigraph. Measured directly: 0.004s (Memory) vs. 35+ seconds and still climbing (embedded Oxigraph) for the identical 792-triple round-trip - several thousand times slower, not actually infinite, which is why it looked like a hang in a 2-minute test run.

**User's framing, confirmed correct**: Oxigraph is genuinely useful and fast for real data, but a blanket global default also silently reaches internal, performance-sensitive library plumbing that was never meant to represent "the user's own data" at all - `_new_starlayer_graph()`'s own docstring already called itself out as exactly this kind of internal utility. The fix needed to let that plumbing opt out, without hardcoding *which* representation it opts into (a direct user objection to an earlier draft of this fix that pinned `backend='rdf-1.1'`: "I don't like this to be backend=1.1... we might in the future upgrade rdflib to handle 1.2 and then this would not make sense."

**New keyword-only constructor flag, `use_baseline_representation: bool = False`**, on both `StarLayerGraph.__init__`/`StarLayerDataset.__init__` - named around the *concept* ("the baseline representation"), not a specific backend string, on direct user instruction (`ignore_default_representation=True` was the first proposal, rejected in favor of framing this as opting into a named thing rather than opting out of something). A calling site never says "rdf-1.1" anywhere - only `__init__` itself knows what the baseline currently resolves to (today: `backend='rdf-1.1'` + bare `Memory()`), so if that baseline implementation ever changes, every internal call site needs zero changes. Deliberately **exclusive** with an explicit `backend=`/`store=` of the caller's own - raises `ValueError` rather than guessing a precedence order, since "give me the baseline" and "but also use this other thing" are a contradiction, not two preferences to rank.

**A second, more serious class of risk found during the audit, not just a performance one**: several existing internal uses of bare `StarLayerGraph()` are explicitly-documented *snapshots that exist to escape a native/remote-store limitation* - `shacl/meta_shapes.py`'s `_needs_bnode_skolemization` snapshot (sidesteps `SPARQLUpdateStore`'s bound-BNode restrictions for a one-time structural preflight), `shacl/validator.py`'s unscoped-CONSTRUCT snapshot (sidesteps the native backend's own unscoped-query limitation), and `shacl/subgraph_extraction.py`'s copy feeding pySHACL's own `ShapesGraph` wrapper. A process-global native/Oxigraph default would have silently handed each of these a *native*-backed graph instead of the fast, safe one they exist specifically to produce - quietly re-introducing the exact bug each snapshot was built to avoid, not just slowing it down. `shacl/adapters.py::TripleTermAdapter._new_output_graph()` (the decode side of the encode/decode round trip that already, by design, shields `validate()`/`apply_rules()` from ever exposing pySHACL to a native store at all - see the earlier entry in this file establishing that architecture) was the same risk from the opposite direction: its *output*, not pySHACL's input, would have started paying a native round trip per triple on every single `validate()`/`apply_rules()` call. `shacl/sparql_node_expressions.py`'s tiny per-call scratch graph (feeding rdflib's own expression evaluator for `sparql:` node expressions) got the same fix for the pure-performance reason alone.

**Audit methodology, not a one-shot fix**: `grep -rn "StarLayerGraph()\|StarLayerDataset()"` across all of `starlayer`'s own library code (not tests) found ~30 bare-construction call sites. Each was read in context and classified into exactly two categories - never a third "maybe": (1) **user-facing data**, returned directly to the caller as their own result (`cbd()`'s `target_graph` default, `infer()`'s result graph, `skolemize()`/`de_skolemize()`, every `StarLayerDataset` reifier-query method, `execute_construct()`'s CONSTRUCT-query result, codekg's own knowledge-graph build/load functions, `starontology`'s bundled-asset loaders) - left untouched, since a caller who configured a global default plausibly *wants* their own derived/returned data represented that way; or (2) **internal scratch/plumbing**, never exposed to the caller as "their data" and/or explicitly built to escape a backend limitation - the six fixed above. Confirmed each classification by reading the actual code and its own docstring, not by guessing from variable names.

New tests, `tests/graph/unit/test_default_representation.py`: `TestUseBaselineRepresentation` (7 cases - bypasses a configured default on both classes, works identically with no default configured at all, the exclusivity `ValueError` on both `backend=`/`store=` for both classes) and `TestInternalScratchGraphsStayBaselineUnderAConfiguredDefault` (3 cases - `query_to_rdf()`'s own scratch graph confirmed baseline under a configured default, the real 3-branch `UNION`/`ORDER BY`/`OFFSET` reconstruction confirmed to complete in well under a second rather than the 30+ seconds the pre-fix bug produced, `TripleTermAdapter.decode_graph()`'s output confirmed baseline). Full `tests/` suite (`-m "not integration"`): 3843 passed (10 new), zero regressions - not even the usual intermittent `targetWhere` flake this run.

**Documented, not fixed**: there is no safe way to catch a process abort from Python - any real mitigation would mean either avoiding `=`-based equality comparisons over `dirLangString` data entirely (using `sameTerm()` instead where exact-term rather than value equality is acceptable) when targeting a native Oxigraph-backed graph, or pre-validating/rewriting a query before it reaches the engine, neither of which this project has designed yet. Logged as a confirmed Issue #2 in `docs/upstream-issues/oxigraph-upstream-issues.md` (full repro, both transports, the full crash-vs-no-crash scenario table) - with a runnable companion notebook, `docs/upstream-issues/oxigraph_dirlangstring_crash_repro.ipynb` (real kernel-executed output for every working scenario; the four crashing scenarios' real captured subprocess output - stderr panic trace + exit code - embedded as pre-recorded cell output, since executing them in the notebook's own kernel would kill it) - and flagged as the concrete reason `set_default_representation(embedded_oxigraph_store)` should not (yet) be configured as a real, unconditional global default for a codebase that relies on `dirLangString` value-equality (`=`) anywhere in its own queries - pending an upstream fix or a project-side guard, whichever comes first.
