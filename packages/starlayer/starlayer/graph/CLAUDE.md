# CLAUDE.md

Project-specific instructions for Claude Code sessions working in this repo. See `docs/guides/README.md` for the docs index (start with the Oxigraph-backed graph guide, `docs/guides/02.03-oxigraph-wrapper.ipynb`). The older notes in `docs/design/graph/` describe the deleted rdflib-based class.

## Rules that bite

- **One class, one backend.** `StarLayerGraph` (one graph) and `StarLayerDataset` (a store of named graphs) are composition wrappers over a `pyoxigraph.Store`, defined in `core.py` and re-exported by `starlayer.graph` and `starlayer`. Terms are pyoxigraph terms. The old rdflib-based classes, hand-written parsers and serializers, `tt:` encoding, rdflib stores and the rdflib evaluator patches were deleted at D1.
- **rdflib is optional and only in the conversion.** A function that takes a graph does not take an rdflib `Graph` (`engine_view` raises `TypeError` naming `from_rdflib`). `from_rdflib` / `to_rdflib` (out is the RDF 1.2 Interoperability basic encoding, as `serialize(rdf_version="1.1")`) are in `graph/rdflib_bridge.py` and `graph/rdflib_model/` (`TripleTerm`, `DirLangString`), which import rdflib inside functions; `core.py::_rdflib_bridge` reaches them only when a conversion runs and raises an `ImportError` saying `pip install "starlayer[rdflib]"`. `owlrl` and the OWL-DL engines are in the separate `starlayer-reasoning` package (`infer.py::_reasoning`, with `pip install starlayer-reasoning`). `tests/packaging/test_no_rdflib_import.py` keeps every other import of rdflib or a reasoner out of the core.
- **Oxigraph's store methods are called through `.ox`; a writer keeps the write counter.** `g.ox.<method>(...)` (`ox_store.py`, `OxStore`) runs `Store.<method>` with Oxigraph's own arguments and result. The names the rdflib-style methods also use (`add`, `extend`, `remove`, `query`, `update`) keep their rdflib form on the class; Oxigraph's form is `.ox` only, and the other store methods (`load`, `flush`, ...) are on `.ox` only, except the graph-management ones a class also offers in its own form (dataset: `named_graphs`, `add_graph`, `clear_graph`, `remove_graph`, which take a name or a graph; graph: `named_graphs`, `remove_graph()`); a method may be on both when it suits the class. A method in `ox_store.WRITERS` calls `union.touch(store)` after it ran (`union.version_of(store)` is the write count of one store, shared by every wrapper of it; the entailment cache, the deduplicated union copy and `Materialization.stale` compare it, so a write to another store does not make them recompute); a new writing method must be added to that set and must name its store. A write on a raw store reference calls `union.touch()` with no store, which counts as a write to every store. On a `StarLayerGraph` a call that would reach another graph raises `ValueError` (the checks are in `ox_store._CHECKS`); on a dataset nothing is checked. `update` text on a graph (`g.update` and `g.ox.update`) is parsed with `parse_sparql_update` and aimed at the graph or refused (`execution/update_scope.py`: unqualified triples, `WITH` / `USING` and `CLEAR ALL` go to the graph; a graph named by IRI, or a variable graph in a template, other than its own is a `ValueError`); `query` text is never parsed. `read_only` makes a store, so it is a classmethod (`StarLayerGraph.read_only(path)`), not under `.ox`. A write on `.store` itself needs `union.touch()` (or `as_store()`, which does it first).
- **Entailment regimes are the W3C IRIs**, `ENTAILMENT.RDFS`, `ENTAILMENT["OWL-Direct"]` and so on, for both `infer(entailment=...)` and `query(entailment=...)`. Not strings.
- **Literals are normalised by the Oxigraph store** (`04` becomes `4`, a decimal `4.0` becomes `4`); the datatype and meaning are kept, the spelling is not (starlayer #190, Oxigraph PR #2010). Accepted for now.
- **StarLayer needs Oxigraph >= 0.5.13** (pyoxigraph): older versions abort the whole process on SPARQL `=` between two `dirLangString` terms (oxigraph/oxigraph#1982). The installed pyoxigraph is checked at import (`_versions.py::require_supported_pyoxigraph`).
- **Do not import the SPARQL grammar lazily while pytest is collecting.** It corrupts the shared grammar (still used by the `sparql/` parsers) for the rest of the run. `tests/conftest.py` imports and installs it eagerly.
- **Some strings are infrastructure, not names.** Namespace IRIs in bundled data are data identity, so renaming one is a breaking change.
- **Test tiers.** The W3C suites are pinned to a commit (bump `PINNED_SHA` deliberately and read the diff). Integration tests need local servers and skip without them.
- **Check the spec before RDF/SPARQL 1.2 work:** from `packages/starlayer`, `python tests/graph/vendor/spec_snapshots/refresh_snapshots.py` and `git diff` the snapshots. To see what moved upstream (specs, the pinned W3C test suites, the vendored vocabularies): `python scripts/check_spec_drift.py`; after a review, `--record`. It runs only when you run it.
- **`rustdl` is young and has changed behaviour between versions** (a silent incomplete answer became a hang). Re-verify any claim about it against the installed version.

## How the code is laid out

- **Classes** (`core.py`): `_Base` holds what the two share. `StarLayerGraph` is one graph of a store (the default graph, or the named graph `identifier`); `StarLayerDataset` is the whole store, with `default_union` to read all graphs as one. A graph or a dataset also has `relevant_subgraph(query)` (the triples, or for a dataset the quads, an answer depends on) and `check_query(text)` (`starlayer.sparql`, with its prefixes). `path=` opens an on-disk RocksDB store; `store=` wraps an existing `pyoxigraph.Store` (`as_store()` hands it back; call `oxgraph.union.touch()` after writing to it directly).
- **Terms** are pyoxigraph `NamedNode`, `BlankNode`, `Literal` and `Triple` (a triple term is a `pyoxigraph.Triple`). `terms.py::term` takes pyoxigraph terms, 3-tuples (triple terms); **an rdflib term is a `TypeError`** (convert a whole rdflib graph with `from_rdflib`). `starlayer.graph` ships `Namespace` and `RDF`, `RDFS`, `XSD`, `OWL` (and `starlayer.shacl.SH`) as `NamedNode` constants. Reifiers and triple terms are read and written through `reification.py`.
- **Parse and serialize** are Oxigraph's. The wrapper adds the `@version` / `VERSION` declaration (`ntversion.py` validates it in N-Triples and N-Quads, which Oxigraph rejects), the `rdf_version="1.1"` export in the Interoperability basic encoding (`interop.py`), pretty Turtle (`pretty.py`) and Manchester syntax (`parsers/manchester_parser.py`, `serializers/manchester.py`). There are no other parsers or writers.
- **`query()` / `update()`** send the text to `Store.query` / `Store.update` unchanged (`execution/run.py`): `custom_functions` / `custom_aggregate_functions` (Python functions callable from the query, Oxigraph's own) go straight through, also for `update()` and an entailment session; `Result.serialize()` writes SPARQL Results JSON, XML, CSV and TSV (Oxigraph's writers over the rows) or RDF for CONSTRUCT and DESCRIBE; `initNs` becomes `prefixes=`, `initBindings` becomes `substitutions` (a `VALUES` clause when the variable is not projected), a `VERSION` directive is checked (`execution/sparql_text.py`; text that contradicts its own `VERSION`, or names an unknown one, raises a `FormatError` (kind `"sparql"`, `context="VERSION"`) before anything is run or sent). Text reaches Oxigraph through `run._oxigraph_boundary`: its `SyntaxError` becomes `FormatError(kind="sparql", context="Oxigraph query"/"Oxigraph update")` and its `RuntimeError` (that exact class; a subclass such as `NotImplementedError` passes through) `ExecutionError(kind="query")`, with the engine's message and no position (Oxigraph gives none as an attribute); the `"projection"` fallback reads the raw `RuntimeError` inside it. The SPARQL parser's syntax errors are `FormatError(kind="sparql")` with `line`/`col`/`pos`/`why`, a query nested deeper than the stack is `ExecutionError(kind="nesting")`; a tree that breaks the `sqe:` shapes still loads (`sqe_parse_to_tree` does not validate), and `sqe_validate` reports it. Nothing is lowered or rewritten, except for an update on a `default_union` dataset (last sentence below) and for `entailment=`: RDF and RDFS rewrite the query (`sparql/sqe/entailment.py`); the OWL regimes run the query on a copy of the store plus the entailed triples, which are kept per store (`graph/entailment/cache.py::entailed_store_view`, on `union.StoreVersion.entailed`: every wrapper of the store shares them, and SHACL validation uses the same copies: its OWL regimes share them with SPARQL; its RDF and RDFS use a copy too, while SPARQL's RDF and RDFS stay on the rewrite and never make or read one) per regime set, engine (`OWL-Direct`) and ontology graph (SHACL only), at most 4 per store (least recently used dropped), and made again as `recompute=` says (`"always"` keeps none and drops what was kept; `"onChange"` compares the write count of the store (`union.version_of`); `"never"` reuses any copy, data included; a write on a raw store reference needs `union.touch()`). `clear_entailment_cache()` drops the copies, SHACL's too (they hold the whole store in memory). A `default_union` dataset that holds a triple in several graphs queries a deduplicated copy of the store (`execution/union.py`), because Oxigraph counts such a triple once per graph. An update on a `default_union` dataset reads a copy of the union kept in a scratch graph (`run.update`).
- **`infer()`** (`graph/entailment/infer.py`): RDF and RDFS natively (`graph/entailment/rdfs_closure.py`, equal to owlrl's `RDFS_Semantics` as configured here, tested against it); OWL-RL and combined regimes (`owlrl` on an rdflib copy) and OWL-Direct (HermiT or `rustdl`, with a subprocess timeout) through `starlayer-reasoning` (`owl_rl_delta`, `owl_direct_delta`). `infer()` rejects OWL-Direct combined with another regime (pinned by a starlayer-reasoning test), but the shared closure function `_delta_for` (SHACL, via `cache.build_entailed_copy`) accepts it: the Direct delta first, then the other regimes over data plus that delta, the union returned; every regime's entailments, the others also seeing what OWL-Direct inferred, not a fixpoint over all. The regime IRIs are `graph/entailment.py::ENTAILMENT`.
- **Blank nodes in `diff` and the operators:** they compare labels, and a parse relabels (`rename_blank_nodes=True`), so graphs that are the same apart from labels differ. `bnode_align.py::align_blank_nodes(graph, to=reference, min_overlap=0.5, max_changes=1)` pairs the blank nodes of `graph` with those of `reference` (exact: same content and context by colour refinement; then approximate: shared edges over the larger node's edges, or at most `max_changes` of them missing, with the incoming edge from an IRI or paired node as an anchor) and returns a copy that uses the reference's labels, plus every pairing with its kind. Any one-to-one pairing is sound (an empty delta means the graphs are isomorphic), and a poor pairing only makes the delta larger. It does not pair datasets.
- **Ordered children** (`ordinals.py`, next to the `rdflist.py` list helpers): the syntax trees that do not use an `rdf:List` put `tree:ord` (a non-negative `xsd:integer`) on each child; a literal, named node or nested sequence sits in a `tree:Item` wrapper. `ordered_items` / `ordered_children` read in ascending ordinal (gaps allowed; a tie, a missing or non-integer ordinal raises `FormatError` kind `"rdf"`, never broken by blank node label), `append` / `insert_at` / `remove_at` / `replace_at` edit, `renumber_dense` closes gaps (run it before an RDFC-1.0 hash: ordinals are data). A blank node child has one parent only; a named node is shared through Items (shapes: `starontology/tree/tree_shapes.ttl`, registry names `tree_owl` / `tree_shacl`).
- **Other helpers:** `rewrite.py` (`skolemize`, `de_skolemize`, `cbd`, `empty_like`), `imports.py` (`owl_imports`, `resolve_imports`), `qnames.py` (`qname`, `expand_curie`), `setops.py` (`union`, `intersection`, `difference`), `rdfc_native.py` (Oxigraph's RDFC-1.0 canonical forms and hash, with a guard that raises `CanonicalizationComplexityError` on a symmetric blank-node structure), `compare.py` (`isomorphic`) and `rdfc.py` (`rdfc10_hash`, `to_canonical_nquads`, thin fronts over `rdfc_native`).
- **Not in the core:** `owlrl` and the OWL-DL engines (in `starlayer-reasoning`; its tests are in `packages/starlayer-reasoning/tests`). Manchester syntax is native.
- **Remote endpoints:** `StarLayerGraph(endpoint=Endpoint(query_url, update_url), identifier=...)` holds one graph, and `StarLayerDataset(endpoint=...)` all the graphs, of a SPARQL endpoint (Oxigraph server, Fuseki; tested against both). `BackedStore` (`endpoint.py`) stands in for the `pyoxigraph.Store`: a full local copy, pulled as a stream when the object is made, in memory or on disk with `path=` (an in-memory store is about 500 to 650 bytes a triple, on disk about 70 and a fixed small amount of memory), `pull=False` to open an existing copy. Reads are local. Every write goes to the endpoint first, then the copy, so the copy cannot get ahead of the endpoint; `update()` text runs on the endpoint only and the copy is pulled again; `sync()` / `max_age=` see other writers. Blank nodes in a write are skolemized (the endpoint would rename them); one that came from the endpoint cannot be written. There is no lazy or per-call copy: a graph too big for disk would need the work done on the server. A query can also read an endpoint with `SERVICE` (guide 06b).
- **Tests:** `tests/graph/unit/` (the classes), `unit/`, `integration/` (servers; skipped without) and the pinned W3C suites `w3c_rdf12/`, `w3c_sparql12/`, `w3c_turtle12/`. Past decisions are in git history (`git log -- packages/starlayer/starlayer/graph`) and `docs/working/`.
- **Upstream workarounds** (Oxigraph, rdflib): `python scripts/kg.py run upstream-workarounds`; write-ups in `docs/upstream-issues/`.
