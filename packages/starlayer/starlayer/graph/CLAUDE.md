## Gotcha: don't let a lazy grammar import corrupt the SPARQL 1.2 grammar mid-run

SPARQL 1.2 query/update parsing goes through the sibling `starsparql` package's real grammar/algebra pipeline, installed editable (see `pyproject.toml`), not vendored code. Importing and installing that grammar lazily - i.e. letting the first test module that happens to touch it trigger the import - during pytest's assertion-rewrite-hook-active collection phase corrupts the grammar installation for the rest of the run. `tests/conftest.py` works around this by eagerly importing and installing the grammar at collection time, before any test module can trigger it lazily. If `TRIPLE()`-family syntax ever mysteriously stops parsing partway through a test run, that eager import is the first thing to check - see `docs/testing-strategy.md` tier 1 for the full account.

## Tracking `rustdl`'s own evolving capabilities (a young, pre-1.0 native library, not a spec)

`starlayer/graph/graph/owl_dl_rustdl.py` (`infer(profile=ENTAILMENT["OWL-Direct"], engine="rustdl")`) documents `rustdl`'s completeness fragment, its disjunctive-property-assertion behavior, and which constructs it rejects/hangs on/under-approximates - all based on empirical testing against whatever `rustdl` version happened to be installed at the time, not a stable published spec. **This has already been found to drift silently**: a claim in that module's own docstring ("confirmed live" that a specific logic-puzzle ontology causes `materialize_inferred_property_assertions()` to silently return an incomplete-but-sound answer) turned out to be stale - re-running that exact same ontology against `rustdl` 0.4.31 hangs indefinitely instead, a confirmed regression in failure mode (silent incompleteness → hang) that this project's own docs hadn't caught up to until a guide re-execution surfaced it (see `docs/future_enhancements.md`'s RustDL entry for the full account and the fix - a pre-flight SHACL check that now rejects that exact pattern outright, `rustdl.UnsupportedAxiomError`, before it can hang).

Before relying on any specific claim in `owl_dl_rustdl.py`'s docstring or `docs/future_enhancements.md`'s RustDL entries (what it's complete on, what it silently drops vs. rejects vs. hangs on), **re-verify empirically against the actually-installed `rustdl` version first** (`pip show rustdl`) rather than propagating an old characterization forward - a `pip install --upgrade rustdl` between sessions is exactly the kind of silent-drift trigger that caused the regression above. No CI job or version-pin alert watches `rustdl`'s own releases automatically - this is a manual check, same discipline as the RDF 1.2/SPARQL 1.2 one above, just against a library's shifting behavior instead of a shifting spec text.

## `infer()`/`query()` migrated from starlayer-internal strings to real entailment regime IRIs (2026-10-07)

Found while designing `sh:entailment` support for `starlayer.shacl` (that spec's values are the real, fixed W3C SPARQL 1.2 Entailment Regimes IRIs - confirmed via direct fetch: `http://www.w3.org/ns/entailment/{RDF,RDFS,D,OWL-RDF-Based,OWL-Direct}`) - but `infer(profile=...)`/`query(entailment=...)` used their own, unrelated starlayer-internal string keywords (`'rdfs'`/`'owl-rl'`/`'rdfs+owl-rl'`/`'owl-dl'`/`'direct'`/`'rdf'`). Rather than add a translation layer at the SHACL boundary, replaced the strings with the real IRIs everywhere - a full breaking change (~197 call sites across source/tests/6 guide notebooks), on explicit user instruction, not an additive alias.

New `starlayer/graph/graph/entailment_regimes.py`: `ENTAILMENT = Namespace("http://www.w3.org/ns/entailment/")` (re-exported from `starlayer.graph`) - a `Namespace`, not individual constants, since `ENTAILMENT.RDF`/`ENTAILMENT.RDFS` would otherwise collide by bare name with `rdflib.namespace`'s own commonly-imported `RDF`/`RDFS`. `ENTAILMENT["OWL-RDF-Based"]`/`ENTAILMENT["OWL-Direct"]` need bracket access (hyphens aren't valid in a Python attribute name).

**A real, pre-existing inconsistency found and fixed along the way**: `infer()` called the OWL 2 Direct Semantics (tableau) regime `'owl-dl'`; `query()` called the identical regime `'direct'` - two different names for the same thing. Both now unify onto the one real `ENTAILMENT["OWL-Direct"]` IRI.

**API shape change, not just a value swap**: the old `'rdfs+owl-rl'` combined-profile string is gone - `infer()`'s `profile=` now accepts a single IRI or an iterable of more than one, combining naturally (e.g. `{ENTAILMENT.RDFS, ENTAILMENT["OWL-RDF-Based"]}`), matching `sh:entailment`'s own "declare several, combine into one pass" model rather than inventing a starlayer-specific combined keyword.

**Two real bugs found via testing, not assumed correct**:
1. Normalizing `profile` checked `isinstance(profile, URIRef)` - a plain leftover string like `'rdfs'` isn't a `URIRef`, so it fell through to `frozenset(profile)`, silently splitting it into individual characters (`{'r','d','f','s'}`) instead of being rejected cleanly. Fixed with an `isinstance(profile, str)` check instead (`URIRef` is itself a `str` subclass, so this correctly catches both).
2. The mechanical sweep's replacement text (`ENTAILMENT["OWL-Direct"]`, containing a literal `"`) corrupted several already-double-quoted host strings (docstrings, error messages, a `pytest.raises(match=...)` regex where `[`/`]` are also regex metacharacters). Fixed by switching to single-quote bracket access (`ENTAILMENT['OWL-Direct']`) at every such site, and shortening the affected `match=` patterns to bracket-free stable prefixes.

Verified: `tests/graph` 1527 passed (1 pre-existing, unrelated failure - `test_oxigraph_backend.py`), `tests/sparql` 351 passed, zero regressions. All 4 touched guide notebooks (`02b-graphs-inferencing`, `05e-owl-dl-reasoning`, `03b-sparql-inferencing`, `05b-backend-graph-databases`) re-executed via `nbconvert` with zero errors - which surfaced a separate, pre-existing, unrelated bug (see below).

**`infer()` gained a new regime while here**: `ENTAILMENT.RDF` (plain RDF entailment - one step weaker than RDFS) had no materialization path at all before this (`query(entailment=...)` could query-time-rewrite for it via `starlayer.sparql.entailment_rdf`, but `infer()` couldn't materialize it). Implemented natively in `_infer_rdf_before_and_delta()` - no `owlrl` dependency, just rdfD2 (every predicate used is entailed `rdf:type rdf:Property`) plus the finite RDF axiomatic triples actually relevant to the data (looked up from the RDF 1.2 Semantics spec directly, not guessed). Datatype literal value-space well-typing (rdfD1/rdfD1a) is a deliberate, documented v1 scope reduction, not built.

**Separate, unrelated, repo-wide bug found while verifying notebooks via `nbconvert`**: `from starlayergraph import ...`/`from starlayergraph.graph.owl_dl import ...` - a stale package name from before this project's own `starlayergraph`→`starlayer` merge - appears in 20+ guide notebooks across `docs/`, not just the ones this work touched. Fixed only in the 3 notebooks this work actually touched (`03b-sparql-inferencing`, `05b-backend-graph-databases`, `05e-owl-dl-reasoning`) - scoped deliberately, on explicit user instruction, not a repo-wide fix. The other ~17 affected notebooks are still broken and unrelated to this work - worth a dedicated pass later, not opportunistically expanded into here.

## `_resolve_owlrl_semantics()`'s `ENTAILMENT.RDFS`-alone dispatch suppresses owlrl's "hidden sameAs" rule (2026-10-08)

Found via a real downstream test failure (`tests/sparql/unit/test_srl_shapes.py::test_assignment_and_filter_roundtrip_conforms`), surfaced while `starlayer.shacl` disconnected its own `inference=` keyword from pySHACL's string vocabulary onto this project's real `ENTAILMENT.*` IRIs (see `starlayer/shacl/CLAUDE.md`'s same-day entry) - that work moved a caller off a path that happened to carry a protective workaround, exposing a bug that had been latent in this module since `ENTAILMENT.RDFS` support first shipped (2026-10-07).

**The bug**: owlrl's own `RDFSClosure.RDFS_Semantics.one_time_rules()` implements a "hidden sameAs" rule - for every pair of literals *anywhere* in the graph that compare equal by Python value despite different lexical form/datatype (confirmed live: `Literal(True)` and `Literal(1)`, since Python's own `1 == True`), it duplicates every triple using one literal to also use the other, across any unrelated subjects/predicates. pySHACL's own `pyshacl.inference.CustomRDFSSemantics` (`pyshacl/inference/custom_rdfs_closure.py`) overrides this same method to a no-op specifically to avoid it, with its own source comment: "breaks some SHACL validation tests." This project's `_resolve_owlrl_semantics()` used plain, unmodified `owlrl.RDFS_Semantics` for `ENTAILMENT.RDFS` alone, so every `sh:entailment`/`inference=`/direct `infer(profile=ENTAILMENT.RDFS)` caller was exposed to this bug the whole time - just never hit by an existing test until `srl_validate()`'s own migration happened to touch a literal-type collision (an `xsd:integer`/`xsd:boolean` pair compared via `"1" == True`).

**Fix, confirmed by checking rather than importing**: a small local subclass (`_NoHiddenSameAsRDFSSemantics(owlrl.RDFSClosure.RDFS_Semantics)`, `one_time_rules()` overridden to `pass`) is used for `ENTAILMENT.RDFS` alone, defined inline (not imported from `pyshacl`, to avoid a layering violation - this is `starlayer.graph`'s own general-purpose reasoning, and `pyshacl` is an optional dependency of a different, downstream package). **The combined `ENTAILMENT.RDFS` + `ENTAILMENT["OWL-RDF-Based"]` regime needed no such override** - a self-caught correction, not assumed by analogy: an initial version of this fix also no-op'd `owlrl.RDFS_OWLRL_Semantics.one_time_rules()`, which immediately broke `tests/graph/unit/test_infer.py::TestInferCombinedProfile::test_matches_owlrl_run_directly` with dozens of missing legitimate OWL-RL axioms (e.g. `xsd:byte rdf:type owl:Thing`). Reading owlrl's actual source confirmed why: `RDFS_OWLRL_Semantics.one_time_rules()` is a *completely different* method body (`full_binding_triples` plus `OWLRL_Semantics.one_time_rules(self)`) that never calls the literal-comparison logic at all - and confirmed against pySHACL's own `CustomRDFSOWLRLSemantics` too: despite the "Custom" name, its `one_time_rules()` is copied verbatim from stock `RDFS_OWLRL_Semantics`, not overridden to a no-op - pySHACL itself only ever needed the suppression for the RDFS-alone case.

Verified live (both directions): `infer(profile=ENTAILMENT.RDFS)` over `{(x, flag, Literal(True)), (y, counter, Literal(1))}` no longer produces the fabricated `(x, flag, Literal(1))`/`(y, counter, Literal(True))` cross-contamination; `infer(profile={ENTAILMENT.RDFS, ENTAILMENT["OWL-RDF-Based"]})` still produces every legitimate combined-regime axiom (`xsd:byte rdf:type owl:Thing`, universal `rdfs:Resource` typing, etc.), unchanged. `tests/graph` (excluding network-dependent integration): 1374 passed, 7 xfailed, zero regressions. `tests/sparql/unit/test_srl_shapes.py`: 5 passed (was 1 failed, 4 passed).

## `StarLayerGraph.owl_imports()`/`.resolve_imports()` + `can_resolve_import()` - generalizing SHACL's own shapes-graph import resolution into a plain graph capability (2026-10-08)

Grew directly out of adding SHACL 1.2 Profiling §2 packaging (`sh:ShapesGraph`/`rdfs:member`) to `starontology`'s own shapes files (see `starlayer/shacl/CLAUDE.md`'s dated entry) - which surfaced a real, found-not-assumed gap: `sqe_shapes.ttl`/`srl_shapes.ttl` both genuinely reference `salg:ExpressionShape`/`salg:VariableShape` (confirmed via `grep`, not inferred from file names) without defining them, and nothing in this project loaded that dependency automatically. `validator.py` already had `_resolve_shapes_graph_imports()` solving exactly this problem, but scoped only to `shacl_graph` inside `validate()` - the user asked for the same capability as a plain, reusable `StarLayerGraph` operation instead, not something bolted onto SHACL specifically.

**Design, settled across several direct questions, not assumed up front**:
- **Where does `owl:imports` normally appear, conceptually?** Overwhelmingly: one OWL ontology document importing another - this is a document-level property of "treat this resource as ontology-like," formally independent of whatever *other* `rdf:type` the subject carries (SPIN's own, pre-SHACL constraint-library convention did the identical "constraint library imports constraint library" thing SHACL 1.2 now formalizes - not a new idea, an extension of established practice).
- **Does resolving it ever happen automatically, anywhere in this project?** No, and that's deliberate - checked against the project's existing discipline (`data_graph` never mutated without `inplace=True`, no IRI ever invented without opt-in, `validate()` never fetches on its own). Confirmed live: `infer()` already treats `owl:imports` as completely inert data - an entailment that would require resolving an import simply doesn't fire, the triple just passes through unchanged.
- **Should resolution be opt-in everywhere, with no exceptions?** No - corrected mid-discussion on a direct challenge ("using an ontology with imports without doing the import leads to incomplete results... inconsistent with the desire of the ontology owner"). The real dividing line isn't automation vs. not, it's whether resolving requires reaching *outside* what's already known and local. An arbitrary caller-supplied `shacl_graph`/`ont_graph` genuinely can't be resolved safely by default (unknown IRI, network dependency, non-determinism) - but `starontology`'s own bundled files carry none of that risk, so defaulting to *not* resolving them bought no safety, only silently wrong/incomplete results for free.

**New in `starlayer_graph.py`** (added right after `infer()`, reusing its own `VALID_INFER_RETURN_MODES` constant):
- `owl_imports(self) -> tuple[Any, ...]` - direct `owl:imports` objects, deduplicated, first-seen order. A pure read; resolves nothing.
- `resolve_imports(self, *, loader, mode="full"/"delta"/"in-place", target_graph=None) -> StarLayerGraph` - the exact same three-way `mode=` contract `infer()` already established (full = self plus resolved imports in a new graph; delta = true set difference, just the newly-pulled-in triples; in-place = mutate self, return self). Recursive by construction (that's what "import" means - §3.4's imports closure - not an opt-in extra), with cycle protection and the identical `^owl:versionIRI?/owl:imports` canonical-ID handling `_resolve_shapes_graph_imports()` already got right (a graph fetched under its own declared `owl:versionIRI` is deduplicated, and further-imports-following continues from its *base* IRI, not the version IRI it was fetched under). `loader` has no default - this library still never decides retrieval policy on anyone's behalf; an unresolvable import (`loader` returns `None`) is skipped, not an error.
- `can_resolve_import(iri, *, loader) -> bool` - module-level function, not a method: it's a question about the *loader*'s own knowledge, not about any graph's data. Implemented the only honest way possible - actually calling `loader(iri)` and checking for a non-`None` result; for a loader that makes a real network request this has the identical cost as actually resolving, there's no cheaper way to ask "would this work."

**New in `starontology/__init__.py`**: `local_loader(iri) -> StarLayerGraph | None` - a `resolve_imports()`-compatible loader that only ever reads this package's own bundled files. **A real identity mismatch found and fixed while wiring it up, not assumed to just work**: `local_loader()` has to resolve against each shapes file's own *real* `sh:ShapesGraph` node (e.g. `salg:ShapesGraph`, in the vocabulary's own namespace - confirmed via direct inspection that `sqe_shapes.ttl`'s actual `owl:imports` triple points there) - which is a completely different IRI than `get_resource_iri()`'s own GitHub-blob-URL scheme (built earlier the same day for an unrelated purpose, `prof:isProfileOf`/`derive_conforms_to()`). Confirmed live before fixing: `get_resource_iri("sparql_shacl")` and `sqe_shapes.ttl`'s real import target are two different strings entirely. `docs/api-reference.md`'s `starlayer.starontology` section now carries an explicit note so a future reader doesn't assume these two identities match either.

**Verified live, not just unit-tested in isolation**: `get_ontology_graph("sqe_shacl")` alone is 142 triples and genuinely missing `salg:ExpressionShape`'s own `sh:NodeShape` definition; `.resolve_imports(loader=starontology.local_loader, mode="full")` returns 1,323 triples including it - the real gap, closed, confirmed before and after.

New tests: `tests/graph/unit/test_resolve_imports.py` (20 cases - direct imports, dedup, unresolvable-import-is-skipped-not-an-error, all three modes including delta's true-set-difference semantics and in-place's `target_graph` rejection, invalid `mode=`, a 3-hop transitive chain, an import cycle that must terminate without duplicating content, and the `versionIRI`-redirected-import reconvergence case specifically). `tests/starontology/unit/test_starontology.py::TestLocalLoader` (6 cases, including the specific "`sqe_shacl` alone is missing the definition" / "resolving closes the gap" pair, and confirming an entry with no `owl:imports` at all - `skos_shacl` - is an unaffected no-op).

Full `tests/graph/unit` suite (excluding two files already confirmed, independently of this work, to hang in this particular environment - see below): 1158 passed, zero regressions. `tests/starontology`: 37 passed.

## `StarLayerGraph.from_rdflib()` now preserves the source graph's own `.identifier` (2026-10-09)

Found while discussing a `starlayer.shacl` feature request (auto-filling SHACL validation-report provenance from a graph's own identity - see `starlayer/shacl/CLAUDE.md`'s same-day entry for the full design): `from_rdflib()` always built the converted graph via a bare `g = cls()`, which gives every new graph a fresh random `BNode` identifier - silently discarding whatever real `.identifier` the source graph had (e.g. `Graph(identifier=URIRef(...))`, or - more consequentially - any named graph retrieved from a `Dataset`/`StarLayerDataset` via `.graph(iri)`, which always carries that real IRI as its own identifier). Confirmed live before fixing: `StarLayerGraph.from_rdflib(some_real_identified_graph).identifier` came back a completely unrelated `BNode`, every time.

**Fixed**: `g = cls(identifier=source_graph.identifier)` instead of `g = cls()` - a correctness fix to this method's own stated "wrap" contract (its docstring already says "Wrap a plain rdflib.Graph"), not scoped to any one caller. This is the mechanism that makes `StarShaclSchema.validate()`'s new identifier-based provenance fallback actually work when a data/shapes graph flows through `normalize_graph_inputs()` (which calls `from_rdflib()` for any non-`StarLayerGraph` input) - without this fix, a plain `rdflib.Graph(identifier=...)` or dataset-sourced named graph would have lost its identity before `validate()` ever got a chance to read it.

**One deliberate exception, found via a live deprecation warning, not assumed**: when `source_graph` is itself a whole `Dataset`/`ConjunctiveGraph` (not one of its named graphs), `.identifier` is **not** read or preserved - confirmed live that `Dataset.identifier` is itself deprecated in this rdflib version, and a `Dataset`/`StarLayerDataset()` can't even be constructed with `identifier=` directly anymore (`TypeError`). A whole dataset has no single meaningful identity of its own the way one graph does, so there's nothing worth preserving there, and reading it would needlessly trigger the deprecation warning on every dataset-to-graph conversion. A named graph *retrieved from* a dataset (`ds.graph(iri)`) is a completely different object with its own real, non-deprecated identifier, and is unaffected by this exception.

New tests, `TestFromRdflib` in `test_starlayer_graph.py`: identifier preserved for a plain `Graph(identifier=...)`; the ordinary no-identifier (`BNode`) case still works unchanged; a whole `Dataset` source doesn't trigger the preservation (or the deprecation warning); a named graph pulled out of a `Dataset` via `.graph(iri)` does preserve its own real identifier.

Full `tests/graph` suite: 1553 passed (4 new - 1 pre-existing, unrelated `test_oxigraph_backend.py` failure, unchanged), zero regressions. Deprecation warning count dropped from 273 to 271 (the two `Dataset.identifier` warnings the unguarded version would have triggered during the suite).

## `__len__()` fast path for the no-triple-terms case - found via a real retrospective performance audit (2026-10-12)

Found while diagnosing why the test suite ran far slower than expected - `cProfile` on one `starlayer.sparql.salg.sparql_shapes.validate_query()` call (against a trivial, triple-term-free shapes+ontology graph, ~1700 triples) showed `StarLayerGraph.__len__()` called **21,049 times** by pySHACL's own internal shape/constraint-evaluation bookkeeping, each call doing `sum(1 for _ in self.triples((None, None, None)))` - a full scan-and-filter of every triple, regardless of whether there was anything to filter. 28.9 million `triples()` iterations, ~104s of a 114s total call.

**The fix**: when `self._tt_registry` is empty - no triple term has ever been registered in this graph instance - there is nothing for `triples()`'s own encoding-triple filtering to do, so `len(graph)` can just be the underlying store's own count (`super().__len__()`, which for the default in-memory `Memory` store is a plain dict length, genuinely O(1) - confirmed by reading `rdflib.plugins.stores.memory.Memory.__len__`'s own source) instead of re-deriving the same number via a full filtered iteration. This reuses an *already-established, already-trusted* invariant in this exact class - `infer()`'s own `fast_path = not self._is_native and not self._tt_registry` (treats an empty-registry graph as safe to read directly, no triple-term-aware handling needed) - rather than inventing a new one; `_is_encoding_triple()`'s own check (`str(s).startswith(TT_NS)`) can only ever be `True` for a triple the registry would already know about, so an empty registry really does mean "nothing to filter," not just "probably nothing."

**Impact, measured**: the one call above: 31s → 1.4s (~22x) before the sibling `meta_validate()` cache fix (see `starlayer/shacl/CLAUDE.md`'s same-day entry) cut the remainder further. `tests/graph/unit/test_starlayer_graph.py`+`test_dataset.py`: 201 passed, zero regressions (pure performance fix, no observable behavior change - `__len__()`'s own contract, "count of visible triples," is unchanged for every graph, including ones that *do* have triple terms registered, which still take the original, correct, filtered path).
