# CLAUDE.md

Project-specific instructions for Claude Code sessions working in this repo.

## Rules that bite

- **`sqe:` is the public "SPARQL query as RDF" vocabulary** (a flat, editable tree from the raw parse tree). `salg:` is the internal full-algebra encoding; do not expose it in public docs or output.
- **Import order matters.** `sparql/__init__.py` imports `parse12` first; it extends rdflib's shared grammar in place (`_grammar12.install()`), and `from_rdf.py` snapshots that grammar at import. Importing the package another way silently breaks later query evaluation.
- **Execution goes: SPARQL 1.2 text -> `parse12` -> 1.2 algebra (real `TripleTermNode`s) -> `lower_rdf11` -> a runnable 1.1 `Query`.** A ground triple term in a pattern is computed in Python and substituted as a constant, never through `BIND` (rdflib's `evalExtend` overwrites an existing binding). `FILTER(isTRIPLE(?x))` over a variable the same pattern binds is lowered to a typed join for speed; it is exact only there.
- **A bare Python `str` in the algebra is not a `Literal`** (`Literal("=") == "="` is `False`). `RelationalExpression.op`, `UNDEF` and similar are bare strings; the encoder converts them.
- **`translateAlgebra` ignores `query.prologue`**, and rdflib's version of it fails on some queries (see `docs/upstream-issues/rdflib-upstream-issues.md`, item 2). The project's own `serialize12.py` carries fixes.
- **`_vars` and `lazy` must be recomputed after decoding a Query's algebra, but not an Update's.**
- **A triple term can never be the subject or predicate of another triple term**, enforced at construction (`InvalidTripleTermError`), not just in the grammar.
- **Use bracket access for namespace terms that collide with methods:** `SALG["term"]`, not `SALG.term`.
- **A "conforms" test is not an execution test.** A query that only passes `query_to_rdf` plus SHACL validation has not been shown to decode and run. Every new query shape needs a test that runs it through the real path and compares the result with plain rdflib.
- **SRL (SPARQL Rules).** `parse_ruleset()` validates against the `srl:` shapes by default (about 140 ms; `validate=False` skips). `evaldata` is the spec's polarity: `WHERE DATA` and `NOT DATA` match the base graph. `IMPORTS` need a caller-supplied loader and nothing is fetched on its own. `RuleSet.plan()` shows the rule order. Aggregation and SRL-to-SPARQL are waiting on the spec.
- **sqe holds no `salg:` terms.** salg may use sqe's vocabulary, never the reverse. The shared encoder/decoder (`to_rdf.py`/`from_rdf.py`) has two per-call hooks (`_NS_OVERRIDES`, `_ENCODE_HOOK`/`_DECODE_HOOK`) that sqe sets to give triple terms, aggregates and `EXISTS` sqe/`spexpr:` terms; a new construct that leaks a `salg:` term fails `test_no_salg_terms_in_any_tree`.
- **The sqe coverage tests are an opt-in set**, left out of a normal run: `pytest tests/sparql/sqe_coverage --sqe-coverage` (about 4 minutes). It runs every W3C SPARQL 1.2 query fixture and 90+ per-feature queries through sqe, comparing with the same query on a `StarLayerGraph`/`StarLayerDataset`. The fixtures sqe cannot round-trip are in `packages/starlayer/tests/sparql/sqe_coverage/sqe_known_gaps.txt` as strict xfails; after a change, refresh it with `python -m tests.sparql.sqe_coverage.test_w3c_through_sqe --regenerate`. Add a feature query to `FEATURES` in `packages/starlayer/tests/sparql/sqe_coverage/test_sqe_features.py` when you add a construct. The same directory holds a Hypothesis suite (random valid queries must parse, render stably and return the same rows), differential suites against plain rdflib and against Oxigraph (the SPARQL 1.2 referee, via `pyoxigraph`), and a shape audit (corrupt each property of rich trees and require the shapes to notice); see the test file names there. Give a new sqe property its own shape and do not declare an `rdfs:domain` on a property several node types share.
- **Run the tests with** `cd packages/starlayer && pytest tests/sparql`. The W3C SPARQL 1.2 suite is pinned; seven subject-position fixtures are marked `xfail(strict=True)` because the suite itself is wrong (`docs/sparql/w3c-sparql12-test-suite-issues.md`).

## Remainders of issue #93 (2026-10-26)

- **Annotations and reifiers are an `Object` suffix**, not a whole-statement production. `_grammar12.py` replaces the alternatives of `TriplesSameSubject`, `TriplesSameSubjectPath`, `BlankNodePropertyList` and `BlankNodePropertyListPath` (assignment, so it does not depend on pyparsing having streamlined the originals) with property lists whose objects are `GraphNode Annotation*`. An annotated object parses to an `_Annotated` marker; `_expand_triples12` is rdflib's `expandTriples` plus one branch that adds `r rdf:reifies <<( s p o )>>` and the `{| |}` triples (expanded by the same function, so blocks nest). So `~ r` and `{| |}` work after `,` and `;`, on `a`, after `[ ]` and `( )` objects, inside an annotation block, and in CONSTRUCT templates and INSERT DATA. A reifier is `Var | iri | BlankNode` (a literal or `()` is a syntax error); a bare `~` works inside `<< >>`. A real property path as the predicate of an annotated triple (`^:p`, `:p/:q`) is a `ValueError` (SPARQL 1.2 Query 19.7, grammar note 16: "A reifier or annotation syntax is only permitted after a triple when the property position is a simple path (an IRI, the keyword `a`, or a variable), and not for other path expressions." The grammar productions do not enforce it by themselves; Oxigraph accepts `^:p`. Rejection is the spec reading, so do not "fix" it). The old `AnnotationSuffixed*` productions are gone.
- **Syntax checks** (`_syntax_checks.py`): a `VALUES` triple term must be `TripleTermData` (no variable or blank node, IRI subject); a triple term in `BIND` has no blank node; `BIND` onto a variable already in scope before it (scope excludes FILTER and the right side of MINUS; a sub-select counts only an explicit projection); `SELECT *` with `GROUP BY` or an aggregate in `HAVING`/`ORDER BY`.
- **Lowering:** `MINUS` lowers its right side with only its own plain variables as "already bound", so a triple-term pattern there binds the shared variable and MINUS removes the match; the arguments of `TRIPLE()` are lowered too (a triple term as subject or predicate is an unbound result, not a crash); `rdf11_to_sparql11_text` raises `NotImplementedError` for ASK and DESCRIBE instead of returning `''`.
- **Left from #93:** `MIN`/`MAX`/`GROUP_CONCAT` over triple terms return the internal `tt#` IRI as a plain literal (rdflib's `Extremum.set_value` wraps the value in `Literal`; fixing it needs a patch of rdflib, which this repo is removing); zero-length property paths (`:p*`) list internal encoding terms (`rdf:PropositionForm`, the predicate of an encoded triple term) as nodes. `STRDT`/`STRLANGDIR` with a language-tagged argument, the Turtle `~ .` forms, blank nodes inside triple terms in patterns, INSERT DATA variables and DELETE blank nodes were already fixed.

## Purpose

Translate SPARQL 1.2 queries into and out of an RDF representation of their algebra, so a query can be stored, versioned, annotated, and queried about at the same granularity as any other RDF data — and eventually, so a query can be *produced* as structured RDF (e.g. by an LLM) rather than as an opaque string.

Sibling package: `../graph` (`starlayergraph`), this project's own RDF 1.2 triplestore/execution engine. The two packages have an intentional two-way dependency — `starsparql` is treated as part of `starlayergraph`'s own SPARQL engine layer, not an independent generic library, and `starlayergraph` depends back on `starsparql` to consume `parse12`/`to_rdf`/`from_rdf`/`lower_rdf11` directly. Don't try to "fix" this into a one-way dependency — it's a deliberate design decision, not an oversight.

## Tracking upstream spec changes (SPARQL 1.2 is still pre-Recommendation)

This package has no spec-tracking infrastructure of its own yet — SPARQL 1.2's actual spec-text snapshots (`sparql12-query.txt`/`sparql12-update.txt`) and refresh tooling live in the sibling subpackage's own test tree, `packages/starlayer/tests/graph/vendor/spec_snapshots/` (run `python3 tests/graph/vendor/spec_snapshots/refresh_snapshots.py` from `packages/starlayer/` + `git diff` to see what moved). Before starting work on the SPARQL 1.2 algebra/grammar specifically, check there for drift, and re-verify this package's own encoding (`vocab.py`, `triple_term.py`, `_grammar12.py`) against anything that changed — `packages/starlayer/docs/graph/rdf12_sparql12_gap_analysis.md` covers both RDF 1.2 and SPARQL 1.2 in one document. No CI job watches the W3C TR-track automatically — this is a manual check.

## Design

rdflib's own SPARQL algebra (`rdflib.plugins.sparql.algebra`) is already a tree of `CompValue`/`Expr` nodes — each just a named dict (`name` + typed keys, e.g. `BGP(triples=...)`, `Filter(expr=..., p=...)`). That maps onto RDF almost mechanically: `node.name` → `rdf:type salg:<name>`, each `key: value` → `salg:<key>` predicate, recursively encoded. **One generic recursive encoder/decoder** (`to_rdf.py`/`from_rdf.py`) handles every operator and expression builtin uniformly — including introspecting rdflib's live parser grammar at import time to rebuild the expression-name → eval-function table (`from_rdf._discover_expr_evalfns`), rather than hand-transcribing rdflib's ~60 builtins. See `starsparql/vocab.py`'s module docstring for the full encoding rules and the handful of shapes needing their own convention (triple patterns, variables, property paths, VALUES rows, bare-Python-string bookkeeping values, Update's quads-by-graph maps).

## Current capabilities

- Full algebra-level round-trip (encode → decode → re-execute, compared by actual query result, not regenerated text) for `SELECT`/`ASK`/`CONSTRUCT`/`DESCRIBE`, `BGP`/`FILTER`/`OPTIONAL`/`UNION`/`MINUS`/`SERVICE` (structural only), property paths, aggregates/`GROUP BY`/`HAVING`, `ORDER BY`/`LIMIT`/`OFFSET`, subqueries, `VALUES`, and full SPARQL Update (all ten operations).
- `BASE`/`PREFIX` prologue round-trip (`query.prologue`/`update.prologue`, not part of the algebra tree itself).
- A genuine, native SPARQL 1.2 algebra representation — real `TripleTermNode`s (`<<( s p o )>>`/`TRIPLE(s, p, o)`) as first-class nodes, plus annotation/reification-shorthand syntax (`<<s p o>>`, `<<s p o ~ r>>`, `s p o ~ r`, `s p o {| ... |}`). Ingestion goes through this project's own `parse12.py`, which extends rdflib's real grammar in place (`_grammar12.py`) — no dependency on any text-rewrite pipeline. **`TripleTermNode` vs. the spec's own formal algebra, resolved 2026-09-28**: confirmed directly against the SPARQL 1.2 Query spec's §18.2 "Algebraic Syntax" (the formal algebra's own exhaustive list of legal query expressions) that there is no `TripleTerm` construct in the formal algebra at all — a triple term in pattern position is just an ordinary recursively-nested triple-pattern tuple (§18.1.3's own inductive "Triple Pattern" definition), and in expression position it's explicitly documented sugar for the ordinary `TRIPLE(...)` function call (§17.4.6). `TripleTermNode` (a distinct `CompValue` subclass) is therefore confirmed to be a pragmatic implementation necessity — rdflib's own `reorderTriples`/`_knownTerms`/`_addVars`/`analyse` machinery needs a hashable, orderable, traversable node, which a bare nested tuple can't be inside rdflib's algebra — not something the spec's own minimalism calls for. Not a gap to fix; the previously-open question is answered.
- Direct in-process execution with **no SPARQL text round-trip at all**: `lower_rdf11.py` lowers the decoded 1.2 algebra tree straight to a directly-runnable 1.1 `Query`/`Update` object (`rdf11_to_query`/`rdf11_to_update`). Text serialization (`rdf11_to_sparql11_text`/`rdf11_update_to_sparql11_text`) still exists for callers that need real text (a remote store requiring a plain string).
- `salg:QueryCollection` — serializing a *set* of independent queries as one RDF graph/Turtle file.
- SHACL shapes (`ontology/sparql_shapes.py`, backed by a real RDFS ontology in `ontology/salg-ontology.ttl`) validating the structure of an algebra RDF graph before decoding — covers every operator/expression builtin/Update operation above.
- `semantic_checks.find_unbound_projected_variables(data_graph)` — the one cross-referential check named in the former "Known gaps" entry below (a `Project.PV` naming a variable never bound anywhere in its own pattern subtree), added 2026-09-28. Deliberately *not* a SHACL shape (that would mean re-deriving SPARQL's own variable-scoping rules inside SHACL, risking drift from rdflib's real semantics) — decodes the graph and reuses rdflib's own `_addVars` bookkeeping directly (`Project.p._vars`, the pattern *one level below* Project — `Project._vars` itself is contaminated, since `_addVars` folds `PV` into the union unconditionally). Covers both Query and Update (Modify's own `.where`, which needs the bookkeeping pass run explicitly — stock rdflib never runs it there). Not a general SPARQL well-formedness validator; scoped to this one named case only.
- A W3C SPARQL 1.2 conformance test suite harness (`packages/starlayer/tests/sparql/w3c_sparql12/test_w3c_sparql12.py`) run end-to-end against this pipeline's own translation (not just self-consistency). Seven known, deliberately-unfixed `test_syntax_positive` cases (`basic-tripleterm-01`/`basic-tripleterm-03`/`bnode-tripleterm-01`/`bnode-tripleterm-02`/`bnode-tripleterm-03`/`compound-tripleterm-subject`/`nested-tripleterm-02`) are `xfail(strict=True)`, not plain passes or failures — documented divergences, not bugs in this project: they correctly reject text the suite labels `PositiveSyntaxTest` because it constructs a triple term directly as a pattern's *subject* — never legal RDF 1.2 regardless of parsing as SPARQL text (see `packages/starlayer/docs/sparql/w3c-sparql12-test-suite-issues.md` Issue 1 for the full spec citation and why five more fixtures than originally found turned out to share this same root cause). `strict=True` so an upstream suite fix would surface as an unexpected pass (a real failure), not silent drift. `list-anonreifier-01` and its sibling `list-tripleterm-01` both now pass outright (2026-10-12 - see that same-day entry below) - the empty-collection-as-reifier-object case the first of those two exercised was a real, confirmed implementation gap, not suite ambiguity, despite that fixture's own text flagging it as an open question.
- **`sqe:` (`sqe/`), added 2026-10-05** — a second, deliberately different RDF representation of a query, alongside `salg:` above: a human-readable, flat tree sourced from the *raw parse tree* (pre-`translateQuery`, not the resolved algebra), paired with its own SHACL shapes designed for UI-editor field-level validation rather than just structural conformance. `salg:`'s algebra is the wrong substrate for hand/UI editing on purpose, not by oversight — `translateQuery` is exactly the step that turns a flat `WHERE { a OPTIONAL { b } }` into a nested `LeftJoin(BGP(a), BGP(b))` operator tree and resolves prefixed names away. See `sqe/vocab.py`'s own module docstring for the full design (shares the `spexpr:` expression/variable/path vocabulary, and holds no `salg:` terms at all) and its coverage: since 2026-10-18 every query form and clause except `DESCRIBE` and Update (see the 2026-10-18 entry at the end; the first version covered far less, and earlier text here saying sqe handled "queries" in general overstated it). `sqe/to_text.py` is the one place in this package that deliberately does *not* reuse `translateAlgebra` for text output — confirmed that function never reads `query.prologue` at all (see "Known non-obvious facts" below), so a bespoke renderer is the only way to make regenerated text actually use the original `PREFIX` declarations `to_rdf.py` preserves.
- `starlayergraph`'s old ~2,164-line regex-based `sparql12_to_11.py` text rewriter has been fully removed and replaced by this pipeline everywhere.
- Nested reifier-shorthand (`<<s p o>>`/`s p o ~ r`, in either grammar, as the subject or object of *another* reifier-shorthand term, e.g. `<< <<:s :p :o>> :p2 :o2 >>`) is fully supported and correctly resolves to a chain of two `rdf:reifies` links — confirmed 2026-09-28 by direct testing against `starlayergraph`'s own Turtle 1.2 parser, `starsparql`'s query grammar, and both live reference engines (Fuseki 5.5.0, Oxigraph), all four producing the identical triple set. The RDF 1.2 subject-position restriction (a *ground* `<<( )>>` triple term is never legal as a subject, even nested inside a reifier-shorthand's own subject slot) is correctly enforced here and by Oxigraph; Fuseki 5.5.0/Jena ARQ was found *not* to enforce it (accepts and materializes a non-conformant triple term whose own subject is another triple term) — a real conformance gap in that engine, not something to match. These two items were previously listed under "Known gaps" below as unimplemented; that was stale (the underlying support already existed, the note just hadn't caught up), corrected 2026-09-28.

Not implemented: `ASK`/`DESCRIBE` text serialization (no `_AlgebraTranslator` branch exists for either — same class of gap `CONSTRUCT` had before it was added), a real Oxigraph backend as a second execution leg, and syntax-layer round-trip beyond the prologue (original `PName` spelling, formatting, comments — algebra-layer round-trip is semantically canonical but not textually faithful).

## Known non-obvious facts (confirmed by running real code — trust these, but re-verify if rdflib's version changes)

- **A bare Python `str` in the algebra tree is not safe to encode as `rdflib.Literal`.** `Literal("=") == "="` is `False` in rdflib, and the two hash differently. `RelationalExpression.op`, `OrderCondition.order`, VALUES' `UNDEF` sentinel, and Update's `GraphRefAll` keywords are all genuine bare `str` in the live algebra (from a bare `pyparsing.Keyword` match, not a real-term grammar production). Fix in place: any bare `str` gets tagged with the reserved datatype `SALG.PyStr` on encode, decoded back to a bare `str` — by value shape, not by an allowlist.
- **`rdflib.plugins.sparql.algebra.translateAlgebra` never reads `query.prologue` at all.** Its text output is byte-identical whether the prologue is populated or empty — don't expect regenerated query text to use prefixed names; that would require patching rdflib itself.
- **RDF 1.2 (`starlayergraph`) queries need no special handling at the plain algebra layer.** `starlayergraph` rewrites `<<( )>>`/`isTRIPLE`/`LANGDIR`/etc. to plain SPARQL 1.1 text *before* calling rdflib's `translateQuery` — so `query.algebra` never contains a `TripleTermNode` via that path. (The native `parse12.py` path, used for Phase 6+ features, is different — see above.)
- **`_vars`/`lazy` bookkeeping must be recomputed after decoding a Query's algebra, but NOT after decoding an Update's.** `translateQuery` runs `_addVars`/`analyse` on the finished tree; `translateUpdate` never does, even for a `Modify`'s WHERE clause. `from_rdf.rdf_to_query` recomputes these; `from_rdf.rdf_to_update` correctly does not.
- **A triple term can never be legal as another triple term's own subject or predicate — enforced at construction, not just in the grammar.** The RDF 1.2 Turtle grammar's `ttSubject ::= iri | BlankNode` has no `tripleTerm` alternative, unconditionally (not just in "expression position" — an earlier version of this rule was wrong about that, see `triple_term.py`'s `InvalidTripleTermError`). The grammar itself stays permissive (matches what the W3C suite's `PositiveSyntaxTest` labels expect it to parse as text); `TripleTermNode.validate()` is the real semantic backstop, called from both `_grammar12.py`'s `_promote` and `from_rdf.py`'s decode branch, so nothing can construct an invalid one and have it survive downstream.
- **Import order matters: `starsparql/__init__.py` imports `parse12` first, before anything else in the package.** `from_rdf.py` snapshots rdflib's live parser grammar at import time (`_discover_expr_evalfns`); `parse12.py` mutates that same shared grammar in place (`grammar12.install()`). If anything imports the bare package before `parse12` runs, later query evaluation silently corrupts (queries that should match return 0 rows). This is why the import order in `__init__.py` is load-bearing, not stylistic — don't reorder it.
- **A ground triple term at ordinary BGP pattern position must not be lowered via a fresh `BIND` variable** — rdflib's `evalExtend` does not enforce "BIND target must be previously unbound" (`c.merge(...)` unconditionally overwrites), so a `BIND`-based lowering can silently produce a false match if that variable is also bound by the BGP's own triple match. `lower_rdf11.py` computes the value eagerly in Python instead and substitutes a literal term.
- **A Turtle-authoring gotcha, now moot** (kept for history): the hand-authored shapes used to be a single ~1700-line Python triple-quoted string (`SHAPES_TURTLE` in `sparql_shapes.py`), which meant every embedded `sh:select` query body's own `"""..."""` delimiters needed Python-level backslash-escaping (`\"\"\"`) — a genuine unescaped `"` inside an `sh:message` would break the *outer* Python string, not just Turtle's own parser. Moved to a standalone `ontology/sparql_shapes.ttl` file 2026-08-16 (mirroring `salg-ontology.ttl`'s own already-established pattern), so this no longer applies — edit `sparql_shapes.ttl` directly as plain Turtle, no Python escaping to think about.
- `SALG.term` (attribute access) silently resolves to `rdflib.Namespace`'s own `.term(name)` **method**, not the `salg:term` URIRef — use bracket access (`SALG["term"]`) in hand-written Python; `to_rdf.py`'s own generic encoder already does.

## Testing discipline: a "conforms" test is not the same as an execution test

A query/update list that only gets `query_to_rdf()`/`update_to_rdf()` + SHACL-shape-validated (does the *encoding* conform) is not proof the decode+execute path works — the shape check never runs `rdf_to_query`/`lower_rdf11`, so it can't see whether the reconstructed tree is actually *evaluable*. This gap shipped two real bugs before anyone noticed: `FILTER (NOT) EXISTS` with more than one triple in its block crashed at execution (rdflib requires a real Python instance attribute, not just a dict-stored value, to survive its own `.graph` resolution — the generic tree-rebuilding in `to_rdf.py`/`lower_rdf11.py`/`from_rdf.py` only preserved the dict-stored copy), and `BIND(SUBSTR(...) AS ?z)` silently never bound `?z` (a key-name collision between `Slice.start`/`.length` and `Builtin_SUBSTR`'s own same-named parameters in `from_rdf._PLAIN_VALUE_KEYS`). Neither was a rare edge case — `EXPRESSION_FAMILY_QUERIES` had covered EXISTS and SUBSTR for years, just never *executed* them.

**Any new query/update shape added to a "conforms" list needs a companion execution-comparison test**, not just a structural-validation one — parse it, run it through the real `lower_rdf11`/`StarLayerGraph` (or `StarLayerDataset`) path, and compare the result against plain `rdflib` executing the same text on the same data (rdflib is a free, trustworthy oracle for anything it can already parse — no need to hand-compute expected values). `test_lower_rdf11.py`'s `_run_lowered` helper is the established pattern; see `test_filter_exists_with_multi_triple_block_executes`/`test_substr_binds_correctly` for the shape a regression test following this should take. This only applies where rdflib *has* an oracle to diff against — RDF-1.2-specific behavior (triple terms, `dirLangString`, annotation syntax) has none, and keeps relying on execution-based self-consistency plus the W3C suite instead.

## Design history

Dated entries below record why things are the way they are. Read one when you work on that topic; the block above is what you need first.


## Expressions are rendered by `expr_text.py`, not by rdflib's `translateAlgebra` (2026-10-25, GitHub issue #80)

`ssyn_to_text._render_expr_text` (used by `srl.ruleset_to_text` and the SSYN text) wrapped an expression in a throwaway query and sliced it out of rdflib's `translateAlgebra` output. That dropped the parentheses of arithmetic (`(?y - 1) * 2` came back `?y - 1 * 2`), the flags argument of `REGEX`/`REPLACE`, and printed `{UnaryMinus}`, `{Function}`, `{Builtin_isTRIPLE}` for node kinds it does not know. `expr_text.render_expression` walks the tree itself (raw parse trees with their single-child wrapper chains, or simplified ones), puts parentheses only where precedence needs them, and raises `NotImplementedError` for `EXISTS` and aggregates, where the old path is still the fallback. Round trips of SRL text are checked by evaluating both rule sets (`tests/sparql/unit/test_srl_text_roundtrip.py`) and, structurally, by `test_srl_to_text.py`. The engine ignores `REPLACE` flags (rdflib item 10), so that flag is only checked in the text.

## `_grammar12.py`'s `install(force=True)` recovery hatch was quietly bloating rdflib's shared grammar objects forever (2026-10-12)

Found via a real retrospective performance audit, not a targeted investigation: `tests/sparql/w3c_sparql12/test_w3c_sparql12.py` (221 tests, one pytest process) took 137s, with `--durations` showing a small number of individually catastrophic outliers (`order-1`/`order-2`: 18s *each*, several `test_syntax_negative` cases: 2-6s each) - yet the exact same test, run completely alone, took 0.36s. Bisected by running an increasing prefix of the file's own earlier tests followed by `order-1` alone: flat ~0.18s up to 100 preceding tests, then **explosive** growth - 1.34s at 125, 11.18s at 150. That range (~96-158) is exactly the file's `NegativeSyntaxTest`/`NegativeUpdateSyntaxTest` block - malformed SPARQL 1.2 text that's *supposed* to fail parsing.

**Root cause**: `parse12.py`'s own `_parse_with_recovery()` catches `ParseBaseException` and calls `grammar12.install(force=True)` as a one-retry recovery hatch for a rare, hard-to-reproduce pytest-collection-time grammar corruption (see this file's own "Gotcha" section in `starlayer/graph/CLAUDE.md`). But *every* negative-syntax test raises that exact exception *by design*, triggering the "rare recovery" path on every single one of them - and `install(force=True)`'s own mutations were unconditional `.append()`/`.exprs.insert()` calls into rdflib's **shared, global, process-wide** pyparsing grammar objects (`BuiltInCall`, `GraphNode`, `GraphTerm`, `VarOrTerm`, `PrimaryExpression`, `DataBlockValue`, `TriplesSameSubjectPath`, `TriplesSameSubject`), with no "is this already there" check - its own docstring even acknowledged the inefficiency, framing it as acceptable because it was assumed to be "a recovery hatch, not a hot path." Confirmed directly: `BuiltInCall.exprs` grew from 10 to 170 entries after just 20 forced reinstalls. Since these objects are referenced recursively throughout the whole SPARQL grammar, every later parse (in this file, and - since the corruption is process-wide, not file-scoped - potentially any SPARQL-1.2-parsing test run afterward in the same pytest session) pays a cost proportional to how bloated the grammar has become so far, compounding combinatorially.

**Fix**: two new helpers, `_append_once(rule, production)`/`_insert_once(rule, index, production)` - the same "is it already there" check `_already_installed()` already uses for its own top-level gate, applied per-mutation instead of only once for the whole function. Every one of `install()`'s ~20 individual `.append()`/`.exprs.insert()` call sites now goes through one of these. `force=True` still re-verifies every mutation unconditionally (preserving the real recovery behavior for genuine corruption), but "re-verify" now means "confirm each production is present, add only what's missing" rather than "duplicate everything regardless." Plain `install()`'s own existing top-level `_already_installed()` short-circuit is unchanged.

**Impact, measured**: `BuiltInCall.exprs`/`GraphNode.exprs` no longer grow at all across 20 forced reinstalls (confirmed via direct inspection). `test_w3c_sparql12.py`: 137s → 3.4s (~40x), identical 8 pre-existing, already-documented W3C syntax-divergence failures (see "Current capabilities"/"Known gaps" above - unaffected by this fix, confirmed via `git stash` that they fail identically on unmodified `main`). Grammar extensions re-verified still work correctly post-fix (triple-term-as-object, `isTRIPLE()`, plain queries). ## Two W3C harness forks' `bindings_match()` had an unpruned factorial brute-force search (2026-10-12)

Found in the same retrospective audit, immediately after the grammar fix above: `results-reifiedtriples-1j` still took ~3.3s *even in isolation* (not a cross-test artifact like the grammar bug - a real, inherent cost of this one fixture). `tests/sparql/w3c_sparql12/harness.py::bindings_match()`'s own docstring already named the risk: "real W3C SPARQL 1.2 test fixtures never have more than a handful of distinct anonymous identifiers... so this stays fast in practice" - a brute-force `itertools.permutations(expected_keys)` search over every possible blank-node relabeling. This one fixture has **9** distinct anonymous identifiers, not "a handful" - 9! = 362,880 permutations tried with zero pruning.

**Fix**: `_opaque_key_signature(key, bindings)` - a renaming-invariant fingerprint for one opaque key (the sorted, multiplicity-preserving collection of canonical row-shapes it occurs in, with every *other* opaque key in those rows rendered through a shared wildcard rather than its own identity). `bindings_match()` now partitions `actual_keys`/`expected_keys` into equivalence classes by this signature first, and only permutes *within* one class - most of this fixture's 9 keys turned out to already be structurally distinguishable from each other (different variable, different co-occurring non-opaque context), collapsing the search space dramatically. Sound by construction, not just empirically faster: two keys that *could* map to each other under some valid bijection always share a signature, so grouping by it can only reduce the search space, never exclude a valid answer - the final arbiter is still the exact same `_canon_bindings_bmap(actual, bmap) == target` check as before, just evaluated over far fewer candidate bijections. Worst case (every key shares one indistinguishable group) falls back to exactly the original all-at-once search.

Applied identically to the sibling fork, `tests/graph/w3c_sparql12/harness.py` - a confirmed, deliberate duplication (not an import), so the fix needed applying twice, not once.

**Impact, measured**: `results-reifiedtriples-1j` alone: 3.34s → 0.19s. `tests/graph/w3c_sparql12/test_w3c_sparql12_eval.py` (113 tests, also hits live Oxigraph/Fuseki when reachable): 21.02s → 2.45s.

## RDF 1.2 Query sec 17.4.3's whole "Functions on Strings" family retrofitted for dirLangString support (2026-10-13)

Found via a retrospective check of which W3C SPARQL 1.2 suite categories this project's own `download_w3c_sparql12_tests.py` even fetches: only 4 of the suite's 10 (`syntax-triple-terms-positive/-negative`, `eval-triple-terms`, `expression`) - `lang-basedir`, the category covering the direction-tagged-literal functions, had never been pulled in or exercised at all. A direct, hands-on check (bypassing the downloader to run the fixtures manually) found every one of `STRLEN`/`SUBSTR`/`UCASE`/`LCASE`/`STRSTARTS`/`STRENDS`/`CONTAINS`/`STRBEFORE`/`STRAFTER`/`CONCAT`/`REGEX`/`REPLACE`/`ENCODE_FOR_URI` rejected a dirLangString argument outright - one shared root cause: rdflib's own `operators.string()` helper, called by every one of these stock evalfns, raises for any literal whose `.datatype` isn't exactly `xsd:string`, and a dirLangString value is internally stored with a non-standard `dirlang:`-prefixed datatype IRI (see `starlayer.graph.model.encoding`). `langMATCHES` is the one function in this family deliberately left untouched - its own signature (17.4.2.11) only ever takes plain `xsd:string` arguments, so it was never affected.

**An earlier, wrong diagnosis caught and corrected before building anything**: a first pass concluded `LANGDIR`/`hasLANGDIR`/`hasLANG`/`STRLANGDIR` were *also* broken ("no evalfn registered" crashes) - actually a bug in the diagnosis itself, not the code: the throwaway test script called `to_rdf.query_to_rdf` directly instead of `lower_rdf11.query_to_rdf11` (which runs the actual SPARQL-1.2-to-1.1 lowering *before* encoding), so none of the real dirLangString-aware lowering ever ran. Re-tested through the correct entry point before writing a single line of fix code; all four already worked.

**Design**: reuse rdflib's own stock evalfn for the real string-processing logic (regex matching, substring arithmetic, case-folding, URI-encoding) rather than reimplementing it - each new function (`starlayer/graph/query/custom_functions.py::_register_dirlang_string_functions`) classifies its "string literal" argument(s) into `(lexical, language, direction)` via `decode_dirlang_datatype()`, strips tagging down to a bare `Literal(lexical)` (which trivially passes `operators.string()`'s own gate), calls the real rdflib function via a small `SimpleNamespace` shim standing in for its usual `Expr`, then re-wraps the bare result in the correct kind per that function's own spec-mandated propagation rule (read directly from the vendored `tests/graph/vendor/spec_snapshots/sparql12-query.txt`, not guessed - the argument-compatibility table for `STRSTARTS`/`STRENDS`/`CONTAINS`/`STRBEFORE`/`STRAFTER`, the "same kind as arg1" rule for `SUBSTR`/`STRBEFORE`/`STRAFTER`/`UCASE`/`LCASE`/`REPLACE`, `CONCAT`'s own distinct 3-way rule). `lower_rdf11.py`'s `_lower_expr` intercepts every one of these 13 builtin names unconditionally (the same blanket-interception precedent `LANG()` already established) and routes them to a `Function(...)` call against the new custom function's URI - `DIRLANG_STRING_FN`, duplicated in both modules per this file's established cross-package-duplication convention (see `TT_HASH_FN`/`DIRLANG_CONSTRUCT_FN`).

**`DATATYPE()` fixed alongside, same root class of bug but a correctness leak rather than a crash**: it was reporting starlayer.graph's own internal `dirlang:en--ltr`-shaped encoding IRI verbatim instead of the real `rdf:dirLangString` - `_dirlang_datatype_expr()` added, the same "unwrap the internal encoding at the boundary, fall back to stock otherwise" shape `_dirlang_lang_expr()`/`_dirlang_langdir_expr()` already use.

**Three real literal-identity bugs found and fixed along the way, each via rdflib's own stricter-than-expected term equality** (`Literal("x") != Literal("x", datatype=XSD.string)`, confirmed live) **- the plain/no-tag result case must be a bare `Literal(lexical)`, never an explicitly `xsd:string`-typed one**, to match both every W3C expected-result `.srj` fixture (which renders the plain case with no `"datatype"` key at all) and stock rdflib's own pre-existing `Builtin_CONCAT`/`Builtin_STRBEFORE`/`Builtin_STRAFTER` (confirmed via their own source: `Literal(...)` with no datatype argument for exactly this case). Found by writing real regression tests against the actual W3C fixtures, not just unit-testing the new functions in isolation - exactly the "a conforms test is not the same as an execution test" discipline this file's own "Testing discipline" section already warns about, playing out a third time.

**Two more adjacent, pre-existing bugs found and fixed in the same family, found via trying to get a *full* pass of the W3C `lang-basedir` fixtures rather than stopping once the three originally-reported functions worked**:
- `hasLANG()`/`hasLANGDIR()` crashed (propagated as unbound, not `false`) for a non-literal RDF term (`hasLANG(<http://example/>)`) - both build on `DATATYPE()` internally, which requires a literal and raises otherwise; confirmed against RDF 1.2 Query sec 17.4.2.10/.11's own example tables that both functions must return `false` for a non-literal (unlike `LANG()`/`LANGDIR()` themselves, which *do* correctly error on one - checked both tables side by side before fixing, not assumed symmetric). Fixed by wrapping each one's existing expression in `COALESCE(expr, false)` - the real SPARQL mechanism for exactly this "catch an expression-evaluation error, substitute a default" shape.
- `STRLANGDIR()`'s own construction function (`custom_functions.py::_dirlang_construct_fn`) validated only its `direction` argument, and did so wrong (lowercased before comparing, so `"LTR"` passed when sec 17.4.2.17's own example table says it must error - direction is case-sensitive, unlike language). Three fixes: `lex` now validated via `operators.string()` (rejecting a non-literal like a bare IRI, matching stock `Builtin_STRLANG`'s identical check on its own analogous argument); `lang` must now be non-empty (previously silently built an unrestorable dirLangString literal that crashed later, elsewhere, with an unrelated Python `ValueError` instead of leaving the binding unbound); `direction` is now compared before lowercasing, so only an exact `"ltr"`/`"rtl"` passes. One existing test (`test_dirlangstring.py::test_strlangdir_result_restored_to_dirlangstring`) had itself relied on the wrong, lenient direction-casing behavior (`"LTR"`, unchecked against the spec when written) - fixed to use `"ltr"`, preserving the test's real intent.

**Two implementation bugs found only by writing full execution-level regression tests covering the actual propagation rules, not just the three originally-reported cases**:
- `node.get("length")`/`node.get("flags")` (checking whether `SUBSTR`/`REGEX`/`REPLACE`'s optional trailing argument was actually present) is not a reliable "is this key absent" check on this pyparsing-derived `CompValue` type - confirmed live that `.get()` on a genuinely-absent `Optional(...)` grammar field returns the key's own name as a string, not `None`, while plain attribute access (`getattr(node, "length", None)`, the same convention stock rdflib's own evalfns use throughout) correctly returns `None`. This silently broke every 2-arg `SUBSTR`/`REGEX`/3-arg `REPLACE` call (appending a spurious extra argument), caught by a real SHACL-pipeline regression test (`test_shnex_node_expressions.py`'s own `regex`/`replace` cases) that exercises these functions through a *different* call path than any fixture this retrofit was built against.
- Stock rdflib's own `Builtin_REPLACE` has an independent, pre-existing bug, unrelated to dirLangString entirely: `re.sub(str(pattern), replacement, text, cFlag)` passes the regex-flags value as `re.sub`'s 4th positional parameter, which is `count`, not `flags` (confirmed via a live Python `DeprecationWarning`, "'count' is passed as positional argument", and a `REPLACE(..., "i")` call that silently did nothing). This retrofit's own design (shim + reuse the real stock evalfn) would have inherited this bug for the first time this project ever exercises `Builtin_REPLACE` with a flags argument - worked around by not delegating to the stock function for `REPLACE` specifically; `_replace()` now does its own `re.sub(..., flags=c_flags)` call directly, reusing stock `Builtin_REGEX`'s own (correct) flag-character-to-`re`-module-flag mapping.

**One round-trip gap found and deliberately not chased**: `CONCAT()`'s zero-argument form lowers to a `Function` call with an empty `expr=[]` argument list - but an empty Python list doesn't survive this project's own generic RDF encode/decode round-trip (`to_rdf.py`/`from_rdf.py`) intact; it comes back as the bare `rdf:nil` term, not `[]`, the first time this project ever builds a genuinely-empty `Function` argument list. Since `CONCAT()` with zero arguments is a spec-mandated compile-time constant (`""`, sec 17.4.3.10's own errata-query-4 rule) regardless of this gap, `_lower_expr`'s own `Builtin_CONCAT` branch just inlines that constant directly rather than emitting a call at all - correct, but doesn't fix or further investigate the underlying round-trip limitation, which could resurface for any other future list-valued field that happens to go empty.

New test file: `tests/sparql/unit/test_dirlang_string_functions.py` (40 cases) - argument-compatibility and kind-propagation for every function in the retrofitted family, `CONCAT`'s full 3-way rule (not just the one combination the W3C fixture happens to cover), `REGEX`/`REPLACE` with and without flags, the `DATATYPE()` fix, `hasLANG()`/`hasLANGDIR()` on a non-literal (plus a same-family sanity check that `LANG()`/`LANGDIR()` still correctly error on one), and `STRLANGDIR()`'s three validation fixes - all execution-level (run the real query, compare the actual result), per this file's own "Testing discipline" section.

## `StarQuery` added; `RuleSet.infer()`/`.query()` gain `inference=`/`schema=` (2026-10-14)

Two related "Function" items from `docs/guides/Notes on guides and other comments`: "create a SPARQL equivalent to StarGraph and StarSchema. Do the same with SRL." Design settled via a dedicated design document first (`packages/starlayer/docs/sparql_srl_object_model_design.md`, written before any code, per direct user request) - read that file for the full options considered and why each was accepted/rejected; this entry covers only what shipped.

**`StarQuery`** (new file, `star_query.py`, flat-exported from `starlayer.sparql` and promoted to the top-level `starlayer` package too, alongside `StarLayerGraph`/`StarLayerDataset`/`StarShaclSchema` - `starlayer/__init__.py`'s own docstring already frames that top level as "pick which one you want," and a query is a fourth real pick alongside a graph/dataset/schema): binds a query (prepared once via `prepare_query_12`) plus every option `StarLayerGraph.query()` otherwise takes per call (`entailment`, `initNs`, `initBindings`, `infer`, `engine`, `timeout`) - `.run(graph, **overrides)` executes against any graph, any bound option overridable for one call without disturbing what's bound. Mirrors `StarShaclSchema`'s own constructor-binding shape directly.

**A real, previously-unknown `StarLayerGraph.query()` bug found while building this, not assumed away**: `entailment=ENTAILMENT.RDF`/`ENTAILMENT.RDFS` rewrite a query's own algebra to express the entailment rule - but that rewrite only ever happens inside `query_cache.prepare_query_cached`, which `StarLayerGraph.query()` only calls on its `isinstance(query_object, str)` branch. Hand it an already-prepared `Query` object instead - exactly what `StarQuery`'s own "prepare once" design does - with `entailment=ENTAILMENT.RDFS`, and the rewrite silently never runs: confirmed live, the identical query returns the correct entailed row against raw text, and an empty result against a pre-prepared `Query` object, no error either way. Checked whether fixing `StarLayerGraph.query()` itself was feasible first: its own rewrite step mutates a `CompValue` algebra tree in place, and a plain `copy.deepcopy` of one fails outright (`CompValue.__init__()` has no zero-argument reconstruction path pickle/copy needs) - a real, safe fix there would need a dedicated algebra-copying mechanism, a larger and riskier change to a heavily-shared method than this feature needed. Worked around in `StarQuery.run()` instead: it stores the original query text alongside the prepared object, and for exactly `entailment=ENTAILMENT.RDF`/`RDFS` (bound or per-call override), passes the *text* to `graph.query()` instead of the prepared object, so the existing, correct rewrite path runs - every other regime (`None`, `OWL-RDF-Based`, `OWL-Direct`) uses the prepared object directly, since those don't rewrite the query's algebra at all (`OWL-RDF-Based`/`OWL-Direct` union with a cached delta instead). Flagged in `StarLayerGraph.query()`'s own docstring too (`starlayer_graph.py`), not just here, so a caller who hits this directly (not through `StarQuery`) has somewhere to find the explanation.

**`RuleSet.infer()`/`.query()` gain `inference=`; `infer()` also gains `schema=`** (`_srl_ast.py`) - both **per-call keyword-only parameters, deliberately not new stored fields on the `RuleSet` dataclass itself**: `RuleSet` is also the value `ruleset_to_tree()`/`tree_to_ruleset()` round-trip to/from RDF (`srl.py`), and a stored "bound schema"/"bound entailment regime" field would either leak into that encoding or need excluding from it, for no benefit over a plain argument - this was the deciding technical constraint, not a style preference, and is recorded in both the design doc and the method's own docstring so it isn't re-litigated from scratch later.

- `inference=` (an `ENTAILMENT.*` regime, or iterable) pre-entails `base_graph` (`base_graph.infer(entailment=inference, mode="full")`) before the rule set runs against it - the same "entailment feeds inference" relationship SHACL's own `sh:entailment`-before-rules already has in this codebase. Requires a real `StarLayerGraph` as `base_graph` when used (plain rdflib `Graph` has no `.infer()`) - `None` (default) is unaffected, so every existing caller passing a plain `Graph()` is untouched.
- `schema=` (`infer()` only - `query()` returns rows, not a graph, so there's nothing to validate) accepts **either** a `starlayer.shacl.StarShaclSchema` instance **or** a bare shapes graph ("allow both," direct user instruction) - normalized with one `isinstance` check, wrapping a bare graph in a throwaway `StarShaclSchema(shacl_graph=schema)` first. When given, validates the inferred result and changes `infer()`'s own return shape: a `starlayer.shacl.RulesResult(inferred_graph=..., validation=...)` instead of a bare graph - reusing `RulesResult`'s own existing two-field shape verbatim (the identical underlying concept `StarShaclSchema.apply_rules()` already returns: inferred triples plus a validation of them) rather than inventing a parallel result type. `schema=None` (the default) returns the original bare graph, unchanged - confirmed via the full existing test suite passing with zero modifications needed for this.
- **`starlayer.sparql` gains a real, direct dependency on `starlayer.shacl`** for `schema=` (a local import inside `infer()`, not a top-level one) - confirmed via `grep` that neither `srl.py` nor `_srl_ast.py` imported anything from `starlayer.shacl` before this. Accepted per explicit user instruction ("I do not worry about the dependency") - smaller in kind than the existing `starlayer.graph`⇄`starlayer.shacl` two-way dependency already elsewhere in this project (e.g. `StarLayerGraph.derive()`).

New tests: `tests/sparql/unit/test_star_query.py` (6 cases, including a direct regression guard reproducing the entailment-on-a-prepared-Query bug above and confirming `StarQuery` doesn't reintroduce it, plus a spy-based test confirming `prepare_query_12` really only runs once across multiple `.run()` calls). `tests/sparql/unit/test_srl_eval.py` gained `TestInferAndQueryInferenceParameter` (5 cases) and `TestInferSchemaParameter` (4 cases) - the latter including a genuine non-conformance case (not just the happy path) and confirming both the bare-shapes-graph and `StarShaclSchema`-instance forms of `schema=` work identically.

## `sqe:SelectQueryShape` gains a real `sh:sparql` constraint for an unbound projected variable (2026-10-15)

Direct follow-up, same conversation: while demonstrating `sqe_validate()` in the notebook, the user asked for an example query that's valid SPARQL but fails SHACL validation because "outputs don't match inputs" - a `SELECT` projecting a variable the `WHERE` clause never binds. Confirmed live this didn't already exist for `sqe:` - `sqe_validate()` conformed on `SELECT ?s ?z WHERE { ?s ex:knows ?o }` despite `?z` never being bound. `salg:` already has the equivalent check (`salg:noUnboundProjectedVariables`, a custom pySHACL `ConstraintComponent` reusing rdflib's `_addVars` bookkeeping on a *resolved* algebra's `Project` node), but that mechanism doesn't apply to `sqe:`'s own raw, pre-`translateQuery` tree shape, which has no resolved `Project`/`_vars` structure to reuse at all.

**A real fork on implementation mechanism, resolved by direct user instruction, not assumed.** The first proposal mirrored `salg:`'s own custom-Python-`ConstraintComponent` pattern (new `sqe/semantic_checks.py`, a `register_sqe_native_components()`, the works) - built, and the walk logic verified correct against six scenarios (plain unbound, all bound, bound via `OPTIONAL`/`UNION`/`BIND`, and confirming `FILTER` alone never counts as binding). The user then clarified they specifically wanted a **declarative `sh:sparql` constraint** - a literal SPARQL query as text inside the shapes graph, no custom Python component at all. The semantic_checks.py module was deleted (replaced, not kept as dead code) once the SPARQL-query version was proven to produce identical results across the same six scenarios.

**The query itself**, added as a `sh:SPARQLConstraint` on the existing `sqe:SelectQueryShape` (matching `sqe:WhereListShape`'s own established style - inline `PREFIX` lines, no `sh:prefixes`):

```sparql
SELECT $this ?var
WHERE {
    $this sqe:projection/rdf:rest*/rdf:first ?var .
    FILTER ( datatype(?var) = spexpr:Variable )
    FILTER NOT EXISTS {
        $this (sqe:where|sqe:alternatives|rdf:rest|rdf:first)* ?node .
        { ?node a sqe:TriplePattern ; (sqe:subject|sqe:predicate|sqe:object) ?var . }
        UNION { ?node a sqe:Bind ; sqe:var ?var . }
    }
}
```

The reachability closure `(sqe:where|sqe:alternatives|rdf:rest|rdf:first)*` is the key trick - a single SPARQL 1.1 property-path alternation reaches every element node (`TriplePattern`/`Optional`/`Union`/`Filter`/`Bind`) anywhere in the `WHERE` clause's own nested structure, regardless of how deeply `OPTIONAL`/`UNION` nest, without needing a recursive SPARQL query (not expressible in plain SPARQL 1.1 anyway) or any Python-side tree walk. `sqe:Filter` nodes are correctly never matched by either `UNION` branch, so a variable referenced only inside a `FILTER` still fails - matching `_addVars`'s own identical treatment of a resolved `Filter` node (constrains, never binds).

**Edited `starontology.trig` directly, not the standalone `sqe_shapes.ttl` mirror** - that file is a generated publish target (`scripts/build_starontology.py`), not a source. A small one-off script (not shipped) loaded the dataset, located the `sqe_shacl` named graph by its own resource-IRI context, added the four new triples (`sh:SPARQLConstraint` BNode + its `sh:message`/`sh:select`, plus `sqe:SelectQueryShape sh:sparql <constraint>`), and re-serialized - verified before trusting it: total dataset quad count went from 5165 to 5169 (exactly +4), named-graph count unchanged at 15, and the target graph round-tripped from 142 to 146 triples identically on a fresh re-parse. `scripts/build_starontology.py` re-run afterward to refresh the standalone mirror (confirmed isomorphic, all 12 entries).

Re-running the identical cold-start call immediately afterward, with no other process competing, took 3.9s - consistent with every other cold/uncached `meta_validate()` cost already documented in this file's own earlier entries (not a regression this change introduced). Root cause of the 932s outlier: two earlier, still-running background `pytest` processes (started while initially investigating this feature, accumulating wall-clock time but very little actual CPU time - a symptom of contention, not computation) were still alive and competing for system resources at the exact moment that measurement ran; killing them and re-measuring on a quiet system reproduced the normal ~4s figure reliably, confirmed three times. The lesson, not previously written down: a wildly anomalous single timing measurement on a dev machine with other long-running background processes should be re-verified on a quiet system before being treated as a real regression - here it would have meant abandoning or hedging a perfectly correct, reasonably-costed shape over a measurement artifact.

## `sqe:` SHACL validation made robust and complete - four real gaps closed, found by auditing the real shapes graph directly (2026-10-15, same conversation)

Direct follow-up: asked for a plan to make `sqe:`'s SHACL validation "fully robust and complete." Rather than guessing at gaps, dumped the real `sqe_shacl` graph (146 triples, 13 shapes at the time) and live-probed each one by deliberately corrupting a conforming tree and checking whether `sqe_validate()` actually caught it - the same discipline this file's own "Testing discipline" section already establishes for `salg:`. "Complete" is scoped to `sqe:`'s current v1 feature set (`SELECT`/`ASK`/`CONSTRUCT`) - no shapes added for vocabulary `sqe:` doesn't encode yet (aggregates/subqueries/`VALUES`/Update).

**Four gaps found, each confirmed live before and after the fix:**

1. **`sqe:ConstructQuery`'s `sqe:template` had zero structural shape** - bare `sh:minCount 1 ; sh:maxCount 1`, no `sh:node` - the whole template could be replaced with a bare string literal and still conform. ## sqe widened to the whole of SPARQL query syntax, and tested for it (2026-10-18)

A probe of 34 questions a developer or agent would ask of the code knowledge graph found that sqe (then covering only triple patterns, `OPTIONAL`, `UNION`, `FILTER`, `BIND`) expressed 11 of them, and that a solution modifier such as `ORDER BY ... LIMIT` was **silently dropped** from the decoded query, so it returned different rows with no error. Earlier notes and docs that described sqe as handling queries in general were wrong; the decision was to widen sqe, not fall back to `salg:`.

**Now covered:** `DISTINCT`/`REDUCED`, `ORDER BY`, `LIMIT`/`OFFSET`, `SELECT *`, `CONSTRUCT WHERE`, projected `(expr AS ?v)`, aggregates with `GROUP BY`/`HAVING`, sub-selects, `VALUES` (inline and trailing), `MINUS`, `GRAPH`, `EXISTS`/`NOT EXISTS`, every expression builtin, and the SPARQL 1.2 additions (triple terms, reifiers, annotations, base-direction strings and `LANGDIR`/`hasLANG`/`STRLANGDIR`/`TRIPLE`/`SUBJECT`/...). **Not covered:** `DESCRIBE` and Update. Anything unmodelled raises `NotImplementedError` rather than being dropped. Reified-triple and annotation shorthand is stored expanded (a `rdf:reifies` triple plus ordinary triples).

**How, in short:** the query body (projection, modifiers, values) is encoded by one function shared by a root query and a sub-select (`sqe:SubSelect` is a `sqe:SelectQuery` that is not a `sqe:Query`); a sub-select that is the whole group is stored as the sole element of its list and decodes back to the parse tree's `{ SELECT ... }` shape. Text is rendered by `sqe/expr_text.py` from the tree, not through rdflib's `translateAlgebra` placeholder translator (which could not render aggregates, `EXISTS`, the 1.2 builtins or unary operators). `sqe_parse_to_tree` now parses with `parse_query_12`. The SHACL constraint that every used variable is bound walks the new elements (aliases, `VALUES`, `GRAPH`, sub-select projections count as binding; a sub-select's inner variables are treated leniently).

**Namespaces.** Triple terms, `EXISTS` and aggregates in an sqe tree are sqe/`spexpr:` nodes; the 1.2 builtins were added to the shared `spexpr:` family table (they used to encode as `salg:`); the direction-string datatype namespace moved from `salg:dirlang/` to `spexpr:dirlang/` (the old namespace is still decoded). `ssyn_to_text._simplify_expr_immutable` now keeps `TripleTermNode`, and `serialize12` renders unary `+`/`-` and triple terms inside list arguments.

**Executing a decoded 1.2 query.** A `Query` object that uses SPARQL 1.2 syntax cannot be executed directly (neither can one from `prepare_query_12`; 1.2 runs as text), so the tests regenerate it to text first for the 1.2-only features.

**Shapes.** An adversarial audit (corrupt each property, see what still validates) found and closed: `sqe:groupBy`, `sqe:having`, `sqe:projection` (also on sub-selects), `sqe:vars`, `sqe:rows`, a trailing `sqe:values` and `sqe:prologuePrefix`/`sqe:base` accepted junk. The ontology also declared `rdfs:domain` on `sqe:expr`, `var`, `subject`, `predicate` and `object`, which gave an Alias the type Filter and a TripleTerm the type TriplePattern under inference; those domains are gone.

**Testing the regular query path.** The same generated queries were run through StarLayer, plain rdflib and Oxigraph. This found and fixed bugs outside sqe: the 1.2 serializer dropped operand parentheses and left placeholders for unary operators and `IN` lists; `CONSTRUCT` kept template triples that are not valid RDF; an explicit `GROUP BY` over no rows returned a row; and a `FILTER` in a nested group saw variables bound outside the group (`patch_evalfilter_forgotten_vars` now evaluates over the group's own variables; filters in `EXISTS`, the triple-term lowering's own filters and `OPTIONAL` keep the wider view). See `docs/upstream-issues/rdflib-upstream-issues.md`, items 16 to 18.

**A separate bug found on the way:** `CONSTRUCT ... ORDER BY ... LIMIT` crashed in `StarLayerGraph.query` (`KeyError: 'PV'`) because `_lower_construct_query` assumed the `Project` was directly under the construct; it now walks down through the `Slice`.

**Results.** Probe 34/34. 161 of 167 W3C query fixtures round-trip; the other six are expected failures that are not sqe's: `!!` and codepoint-escape fixtures our own parser also rejects, and three suite errors (a triple term as a subject). The opt-in test set above holds these checks.

## `parse_ruleset()` now also validates against the `srl:` shapes (2026-10-17)

After the Python §4.2 well-formedness check, `parse_ruleset(text, base=None, *, validate=True)` encodes the rule set as RDF (`ruleset_to_tree`) and runs `srl_validate`; a rule set that does not conform raises `SRLParseError("... does not conform to the srl: shapes: <result messages>")`. `validate=False` skips it. **Cost:** about 140 ms per parse against about 6 ms without, because the check builds the RDF tree and runs SHACL (with `meta_shacl` now off by default, see `shacl/CLAUDE.md`); a caller parsing many trusted rule sets should pass `validate=False`. The shipped shapes and ontology graphs are now built once and cached (`_validation_graphs()`); validating leaves them unchanged (tested). Before this, only `srl_validate()` ran the shapes, so a hand-written rule set never saw them. Checked first: 35 valid expressions (builtins, casts, `IN`, `UUID()`, a custom function IRI, ...) and four `FILTER` forms all pass the shapes, so no false rejections found; the only known case the shapes reject and the Python check also rejects is an aggregate inside `SET`. ## RDF 1.2 triple terms, reified triples and annotations in SRL rules (2026-10-17)

The SRL grammar's triple groups (head templates, body patterns, DATA blocks) now use rdflib's own `TriplesSameSubject`, which this project's SPARQL 1.2 grammar (`_grammar12.install()`) already extends in place. It replaces the small hand-written `;`-only grammar and adds, with no SRL-specific code: `,` object lists, `[ ... ]` blank-node property lists, `( ... )` collections, triple terms `<<( s p o )>>`, reified triples `<< s p o >>`, reifiers `~ r` and annotations `{| ... |}`. The last three expand, as in SPARQL, to a reifier plus `reifier rdf:reifies <<( s p o )>>` plus the annotation triples. (Triple terms in subject/object position were in fact already parsing before this, by accident, because the SRL grammar shared rdflib's `VarOrTerm`/`GraphTerm` objects; what was missing was everything after parsing.)

- **Evaluation** (`srl_eval.py`). A run of body triple patterns that contains a triple term is matched by running it as a SPARQL 1.2 query against a `StarLayerGraph` (`_match_with_query`) and joining with the incoming solutions; runs without one still use rdflib's `evalBGP`. A head triple term is built with the variables substituted (`_graph_term` makes a `starlayer.graph` `TripleTerm`); one that would be invalid RDF 1.2 (a literal as its subject) is skipped, as a `CONSTRUCT` skips an invalid triple. Variable collection, blank-node-to-variable replacement and the `query()` goal pattern all look inside triple terms.
- **Graph kind.** Evaluation runs over a `StarLayerGraph` when the rule set mentions a triple term or the base graph is a `StarLayerGraph`, otherwise over a plain `Graph` as before. **This also fixes a crash that predates the feature:** `infer()` on a `StarLayerGraph` base graph holding triple terms raised `AssertionError: ... must be an rdflib term` even when no rule mentioned one. A plain base graph with rules that use triple terms is copied into a `StarLayerGraph`, and the result is a `StarLayerGraph`.
- **Well-formedness** (`srl_semantic_checks.py`). Variables inside a triple term count as bound/used; a triple term as a *subject or predicate* is rejected (`triple_term_in_subject`/`_predicate`; RDF 1.2 allows one only as an object); a variable in a DATA block is rejected (`variable_in_data`), which the old grammar did structurally and `TriplesSameSubject` does not.
- **Text and RDF.** `ruleset_to_text` renders `<<( s p o )>>`; the RDF encoding already handled the node (round trip and the `srl:` shapes both pass). Reified triples and annotations round-trip in their expanded form (a triple plus `rdf:reifies` triple), not as the shorthand they were written in.
- Tests: `tests/sparql/unit/test_srl_triple_terms.py` (28 cases).
- **Property paths in rule bodies** (added the same day): the body and `NOT` groups use rdflib's `TriplesSameSubjectPath`; `_expand_path` turns `/` and `^` into plain triple patterns (a fresh blank node between the steps of a sequence, subject and object swapped for an inverse) and raises `SRLParseError` for anything else. This matches the spec exactly: its path grammar (§7.6) is only `/`, `^` and parentheses, and §5 says arbitrary-length paths are written with recursion. Head templates and DATA blocks keep the non-path `TriplesSameSubject`. Kept strict on purpose: no `|`, `*`, `+`, `?`, `!` extension. A path round-trips in its expanded form. Tests: `test_srl_property_paths.py` (16 cases).
- **Still not supported:** aggregation.

## `IMPORTS` supported, through a caller-supplied loader (2026-10-17)

Support for imports is optional in the spec (§4.5: reading documents has security implications; a processor that does not support them MUST reject a rule set that has any), and `infer()` used to reject every one. Now `srl.resolve_imports(ruleset, loader, *, location=None)` reads each import and returns the *resolved* rule set (§4.5), and `RuleSet.infer()`/`.query()`/`.plan()` take `imports_loader=` and call it first. **There is no default loader**: nothing is read unless the caller says how (`loader(iri) -> SRL text | RuleSet`; a dict's `__getitem__` works for tests and for verified copies, which the spec mentions). Without a loader the old `SRLImportsNotSupportedError` still applies, so existing callers are unchanged.

Follows Appendix B's example algorithm: each document is imported once (a visited set, seeded with the root's `location=`), so a diamond or a cycle neither repeats nor loops; the importing rule set's rules come first, then each import's in order; DATA blocks are an RDF merge, so a blank node in an imported document is renamed apart from a same-labelled one elsewhere (`_rename_blank_nodes`, which also looks inside triple terms). Text returned by the loader is parsed with `base=` the import IRI, so relative IRIs inside it resolve against where it came from, and goes through the normal `parse_ruleset` checks (well-formedness and the `srl:` shapes). A loader that raises, or text that does not parse, is an `SRLImportError(SRLError)` naming the import, as §4.5 requires. The original rule set is not changed.

Not done: a built-in file or HTTP loader (deliberately; the security model is "the caller decides"), and caching of loaded documents across calls. Tests: `test_srl_imports.py` (14 cases).

## sqe no longer depends on the salg package (2026-10-19)

An audit found the sqe ontology and shapes files were clean (no salg terms; their only `owl:imports` is `spexpr:ShapesGraph`), but `sqe/shapes.py` still built its validation graphs from `salg/sparql_shapes.py` and `salg/sparql_ontology.py`, so every sqe validation loaded all of salg's shapes and ontology. Both moved to neutral modules (`starlayer/sparql/expr_families.py`, `starlayer/sparql/expr_validation.py`); `salg/expr_families.py` is a re-export and `salg/sparql_shapes.py`/`sparql_ontology.py` import from them. The shared encoder (`to_rdf.py`) also imports the family table from the new place instead of from inside `salg/`. A test parses and validates a query in a fresh process and asserts no `starlayer.sparql.salg` module was loaded, and another scans every sqe module for a salg import. Behaviour is unchanged: the sparql suite, the opt-in sqe set and the shape audit pass as before.

## SQE text rendering (2026-10-25, GitHub issue #81)

`sqe_tree_to_text` wrote any IRI under a declared namespace as a prefixed name, so `<http://e/p#frag>` came out as `:p#frag` (invalid; `#` and `/` are not in `PN_LOCAL`): the local part is now checked against the same `PN_LOCAL` pattern the Turtle writer uses (`serializers.turtle12._PN_LOCAL`) and the IRI is written in full otherwise (also in `sqe/expr_text.py`). A base-direction string in a triple pattern is written `"x"@en--ltr` (it printed the internal datatype IRI) and a tab in a string is escaped. **`FROM` / `FROM NAMED` raise `NotImplementedError`** in `sqe_parse_to_tree` instead of being dropped (the module promised "anything else raises rather than being dropped"; the clauses change which graphs a query matches). Still open in #81: a negated property set with an inverse member (`!(^:p)`) cannot be rendered because rdflib's parser drops the IRI after `^` inside a negated set (see #77).

## SRL evaluation fixes from the third hunt (2026-10-25, GitHub issue #96)

A blank node inside a *head triple term* now makes the rule run-once (`_srl_ast._triple_term_has_variable` counts blank nodes): it got a fresh node every pass, so `infer()` never ended. A head instance with a literal subject or a predicate that is not an IRI is skipped, like `CONSTRUCT` (`srl_eval._eval_rule`). `EXISTS` / `NOT EXISTS` in `FILTER` / `SET` are rejected when the rule set is parsed (`aggregate_in_expression`; use a `NOT { }` negation element): the evaluator has no graph pattern to run and crashed with an `AttributeError`. `infer(schema=)` validates the base graph plus the inferred triples (it validated the inferred triples alone). **Still open in #96:** `TRIPLE()` / `<<( )>>` inside `SET` / `FILTER`, an rdflib `Dataset` as the base graph, `DATA`-block blank nodes keep their source labels, a spurious `StratificationError` when a variable repeats across positions, and `inference=` on a plain rdflib `Graph`.

## Lowering fixes from the third hunt (2026-10-26, GitHub issue #134)

A variable inside a triple term used to be treated as "already bound" if any *other* part of the query bound it (`_collect_mandatory_plain_vars`, scope-insensitive), and the constraint became `Filter(accessor(?tt) = ?v)`. Where the join had not bound `?v` at that point the filter errored and dropped the row: the right side of a `MINUS`, a `VALUES` row with `UNDEF`, and the inside of a `GROUP BY` whose key the projection re-binds (`Extend ?x = SAMPLE(?x)`) all lost their rows (`MINUS` removed nothing, `GROUP BY ?x` returned no rows, `VALUES ?x { :a UNDEF }` lost the `UNDEF` row). Now `_collect_shared_vars` lists the variables something else may bind (any BGP term position, a `VALUES` column, a `BIND` target, a variable in two triple terms; aggregate-projection `Extend`s excluded). A component variable that is in the same BGP's own term positions is still a `Filter`; one in the shared set gets `Extend ?v = IF(BOUND(?v), ?v, accessor)` plus `Filter(?v = accessor)` (correct whether or not the join bound it, no `evalExtend` overwrite); anything else is a plain `Extend` (it is the only source). `_hash_call` now lowers the subject and predicate of `TRIPLE(...)` too, so `TRIPLE(SUBJECT(?t), PREDICATE(?t), OBJECT(?t))` no longer raises "What do I do with this CompValue?". Tests: `tests/graph/unit/test_lowering_hunt3.py`.
