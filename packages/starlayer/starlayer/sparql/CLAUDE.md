# CLAUDE.md

Project-specific instructions for Claude Code sessions working in this repo.

## Purpose

Translate SPARQL 1.2 queries into and out of an RDF representation of their algebra, so a query can be stored, versioned, annotated, and queried about at the same granularity as any other RDF data — and eventually, so a query can be *produced* as structured RDF (e.g. by an LLM) rather than as an opaque string.

Sibling package: `../graph` (`starlayergraph`), this project's own RDF 1.2 triplestore/execution engine. The two packages have an intentional two-way dependency — `starsparql` is treated as part of `starlayergraph`'s own SPARQL engine layer, not an independent generic library, and `starlayergraph` depends back on `starsparql` to consume `parse12`/`to_rdf`/`from_rdf`/`lower_rdf11` directly. Don't try to "fix" this into a one-way dependency — it's a deliberate design decision, not an oversight.

## Tracking upstream spec changes (SPARQL 1.2 is still pre-Recommendation)

This package has no spec-tracking infrastructure of its own yet — SPARQL 1.2's actual spec-text snapshots (`sparql12-query.txt`/`sparql12-update.txt`) and refresh tooling live in the sibling subpackage's own test tree, `packages/starlayer/tests/graph/vendor/spec_snapshots/` (run `python3 tests/graph/vendor/spec_snapshots/refresh_snapshots.py` from `packages/starlayer/` + `git diff` to see what moved). Before starting work on the SPARQL 1.2 algebra/grammar specifically, check there for drift, and re-verify this package's own encoding (`vocab.py`, `triple_term.py`, `grammar12.py`) against anything that changed — `packages/starlayer/docs/graph/rdf12_sparql12_gap_analysis.md` covers both RDF 1.2 and SPARQL 1.2 in one document. No CI job watches the W3C TR-track automatically — this is a manual check.

## Design

rdflib's own SPARQL algebra (`rdflib.plugins.sparql.algebra`) is already a tree of `CompValue`/`Expr` nodes — each just a named dict (`name` + typed keys, e.g. `BGP(triples=...)`, `Filter(expr=..., p=...)`). That maps onto RDF almost mechanically: `node.name` → `rdf:type salg:<name>`, each `key: value` → `salg:<key>` predicate, recursively encoded. **One generic recursive encoder/decoder** (`to_rdf.py`/`from_rdf.py`) handles every operator and expression builtin uniformly — including introspecting rdflib's live parser grammar at import time to rebuild the expression-name → eval-function table (`from_rdf._discover_expr_evalfns`), rather than hand-transcribing rdflib's ~60 builtins. See `starsparql/vocab.py`'s module docstring for the full encoding rules and the handful of shapes needing their own convention (triple patterns, variables, property paths, VALUES rows, bare-Python-string bookkeeping values, Update's quads-by-graph maps).

## Current capabilities

- Full algebra-level round-trip (encode → decode → re-execute, compared by actual query result, not regenerated text) for `SELECT`/`ASK`/`CONSTRUCT`/`DESCRIBE`, `BGP`/`FILTER`/`OPTIONAL`/`UNION`/`MINUS`/`SERVICE` (structural only), property paths, aggregates/`GROUP BY`/`HAVING`, `ORDER BY`/`LIMIT`/`OFFSET`, subqueries, `VALUES`, and full SPARQL Update (all ten operations).
- `BASE`/`PREFIX` prologue round-trip (`query.prologue`/`update.prologue`, not part of the algebra tree itself).
- A genuine, native SPARQL 1.2 algebra representation — real `TripleTermNode`s (`<<( s p o )>>`/`TRIPLE(s, p, o)`) as first-class nodes, plus annotation/reification-shorthand syntax (`<<s p o>>`, `<<s p o ~ r>>`, `s p o ~ r`, `s p o {| ... |}`). Ingestion goes through this project's own `parse12.py`, which extends rdflib's real grammar in place (`grammar12.py`) — no dependency on any text-rewrite pipeline. **`TripleTermNode` vs. the spec's own formal algebra, resolved 2026-09-28**: confirmed directly against the SPARQL 1.2 Query spec's §18.2 "Algebraic Syntax" (the formal algebra's own exhaustive list of legal query expressions) that there is no `TripleTerm` construct in the formal algebra at all — a triple term in pattern position is just an ordinary recursively-nested triple-pattern tuple (§18.1.3's own inductive "Triple Pattern" definition), and in expression position it's explicitly documented sugar for the ordinary `TRIPLE(...)` function call (§17.4.6). `TripleTermNode` (a distinct `CompValue` subclass) is therefore confirmed to be a pragmatic implementation necessity — rdflib's own `reorderTriples`/`_knownTerms`/`_addVars`/`analyse` machinery needs a hashable, orderable, traversable node, which a bare nested tuple can't be inside rdflib's algebra — not something the spec's own minimalism calls for. Not a gap to fix; the previously-open question is answered.
- Direct in-process execution with **no SPARQL text round-trip at all**: `lower_rdf11.py` lowers the decoded 1.2 algebra tree straight to a directly-runnable 1.1 `Query`/`Update` object (`rdf11_to_query`/`rdf11_to_update`). Text serialization (`rdf11_to_sparql11_text`/`rdf11_update_to_sparql11_text`) still exists for callers that need real text (a remote store requiring a plain string).
- `salg:QueryCollection` — serializing a *set* of independent queries as one RDF graph/Turtle file.
- SHACL shapes (`ontology/sparql_shapes.py`, backed by a real RDFS ontology in `ontology/salg-ontology.ttl`) validating the structure of an algebra RDF graph before decoding — covers every operator/expression builtin/Update operation above.
- `semantic_checks.find_unbound_projected_variables(data_graph)` — the one cross-referential check named in the former "Known gaps" entry below (a `Project.PV` naming a variable never bound anywhere in its own pattern subtree), added 2026-09-28. Deliberately *not* a SHACL shape (that would mean re-deriving SPARQL's own variable-scoping rules inside SHACL, risking drift from rdflib's real semantics) — decodes the graph and reuses rdflib's own `_addVars` bookkeeping directly (`Project.p._vars`, the pattern *one level below* Project — `Project._vars` itself is contaminated, since `_addVars` folds `PV` into the union unconditionally). Covers both Query and Update (Modify's own `.where`, which needs the bookkeeping pass run explicitly — stock rdflib never runs it there). Not a general SPARQL well-formedness validator; scoped to this one named case only.
- A W3C SPARQL 1.2 conformance test suite harness (`tests/w3c_sparql12/test_w3c_sparql12.py`) run end-to-end against this pipeline's own translation (not just self-consistency). Eight known, deliberately-unfixed failures are documented divergences, not bugs in this project — seven (`basic-tripleterm-01`/`basic-tripleterm-03`/`bnode-tripleterm-01`/`bnode-tripleterm-02`/`bnode-tripleterm-03`/`compound-tripleterm-subject`/`nested-tripleterm-02`) correctly reject text the suite labels `PositiveSyntaxTest` because it constructs a triple term directly as a pattern's *subject* — never legal RDF 1.2 regardless of parsing as SPARQL text (see `docs/w3c-sparql12-test-suite-issues.md` Issue 1 for the full spec citation and why five more fixtures than originally found turned out to share this same root cause); one (`list-anonreifier-01`) is left open because the fixture's own text flags genuine spec ambiguity (see "Known gaps" below). Its sibling `list-tripleterm-01` — previously in the same "genuinely ambiguous" bucket — now passes as an incidental side effect of the subject-position fix above, *not* because the underlying ambiguity was resolved: its own first line independently uses the explicit `<<( )>>` form as a pattern subject (the now-fixed bug), so it's rejected there before parsing ever reaches the still-unresolved empty-collection question on its third line. `list-anonreifier-01` uses the reifier-shorthand form throughout instead (legal in subject position), so it never hits that earlier trigger and still genuinely exercises the open ambiguity alone.
- `starlayergraph`'s old ~2,164-line regex-based `sparql12_to_11.py` text rewriter has been fully removed and replaced by this pipeline everywhere.
- Nested reifier-shorthand (`<<s p o>>`/`s p o ~ r`, in either grammar, as the subject or object of *another* reifier-shorthand term, e.g. `<< <<:s :p :o>> :p2 :o2 >>`) is fully supported and correctly resolves to a chain of two `rdf:reifies` links — confirmed 2026-09-28 by direct testing against `starlayergraph`'s own Turtle 1.2 parser, `starsparql`'s query grammar, and both live reference engines (Fuseki 5.5.0, Oxigraph), all four producing the identical triple set. The RDF 1.2 subject-position restriction (a *ground* `<<( )>>` triple term is never legal as a subject, even nested inside a reifier-shorthand's own subject slot) is correctly enforced here and by Oxigraph; Fuseki 5.5.0/Jena ARQ was found *not* to enforce it (accepts and materializes a non-conformant triple term whose own subject is another triple term) — a real conformance gap in that engine, not something to match. These two items were previously listed under "Known gaps" below as unimplemented; that was stale (the underlying support already existed, the note just hadn't caught up), corrected 2026-09-28.

Not implemented: `ASK`/`DESCRIBE` text serialization (no `_AlgebraTranslator` branch exists for either — same class of gap `CONSTRUCT` had before it was added), a real Oxigraph backend as a second execution leg, and syntax-layer round-trip beyond the prologue (original `PName` spelling, formatting, comments — algebra-layer round-trip is semantically canonical but not textually faithful).

## Known non-obvious facts (confirmed by running real code — trust these, but re-verify if rdflib's version changes)

- **A bare Python `str` in the algebra tree is not safe to encode as `rdflib.Literal`.** `Literal("=") == "="` is `False` in rdflib, and the two hash differently. `RelationalExpression.op`, `OrderCondition.order`, VALUES' `UNDEF` sentinel, and Update's `GraphRefAll` keywords are all genuine bare `str` in the live algebra (from a bare `pyparsing.Keyword` match, not a real-term grammar production). Fix in place: any bare `str` gets tagged with the reserved datatype `SALG.PyStr` on encode, decoded back to a bare `str` — by value shape, not by an allowlist.
- **`rdflib.plugins.sparql.algebra.translateAlgebra` never reads `query.prologue` at all.** Its text output is byte-identical whether the prologue is populated or empty — don't expect regenerated query text to use prefixed names; that would require patching rdflib itself.
- **RDF 1.2 (`starlayergraph`) queries need no special handling at the plain algebra layer.** `starlayergraph` rewrites `<<( )>>`/`isTRIPLE`/`LANGDIR`/etc. to plain SPARQL 1.1 text *before* calling rdflib's `translateQuery` — so `query.algebra` never contains a `TripleTermNode` via that path. (The native `parse12.py` path, used for Phase 6+ features, is different — see above.)
- **`_vars`/`lazy` bookkeeping must be recomputed after decoding a Query's algebra, but NOT after decoding an Update's.** `translateQuery` runs `_addVars`/`analyse` on the finished tree; `translateUpdate` never does, even for a `Modify`'s WHERE clause. `from_rdf.rdf_to_query` recomputes these; `from_rdf.rdf_to_update` correctly does not.
- **A triple term can never be legal as another triple term's own subject or predicate — enforced at construction, not just in the grammar.** The RDF 1.2 Turtle grammar's `ttSubject ::= iri | BlankNode` has no `tripleTerm` alternative, unconditionally (not just in "expression position" — an earlier version of this rule was wrong about that, see `triple_term.py`'s `InvalidTripleTermError`). The grammar itself stays permissive (matches what the W3C suite's `PositiveSyntaxTest` labels expect it to parse as text); `TripleTermNode.validate()` is the real semantic backstop, called from both `grammar12.py`'s `_promote` and `from_rdf.py`'s decode branch, so nothing can construct an invalid one and have it survive downstream.
- **Import order matters: `starsparql/__init__.py` imports `parse12` first, before anything else in the package.** `from_rdf.py` snapshots rdflib's live parser grammar at import time (`_discover_expr_evalfns`); `parse12.py` mutates that same shared grammar in place (`grammar12.install()`). If anything imports the bare package before `parse12` runs, later query evaluation silently corrupts (queries that should match return 0 rows). This is why the import order in `__init__.py` is load-bearing, not stylistic — don't reorder it.
- **A ground triple term at ordinary BGP pattern position must not be lowered via a fresh `BIND` variable** — rdflib's `evalExtend` does not enforce "BIND target must be previously unbound" (`c.merge(...)` unconditionally overwrites), so a `BIND`-based lowering can silently produce a false match if that variable is also bound by the BGP's own triple match. `lower_rdf11.py` computes the value eagerly in Python instead and substitutes a literal term.
- **A Turtle-authoring gotcha, now moot** (kept for history): the hand-authored shapes used to be a single ~1700-line Python triple-quoted string (`SHAPES_TURTLE` in `sparql_shapes.py`), which meant every embedded `sh:select` query body's own `"""..."""` delimiters needed Python-level backslash-escaping (`\"\"\"`) — a genuine unescaped `"` inside an `sh:message` would break the *outer* Python string, not just Turtle's own parser. Moved to a standalone `ontology/sparql_shapes.ttl` file 2026-08-16 (mirroring `salg-ontology.ttl`'s own already-established pattern), so this no longer applies — edit `sparql_shapes.ttl` directly as plain Turtle, no Python escaping to think about.
- `SALG.term` (attribute access) silently resolves to `rdflib.Namespace`'s own `.term(name)` **method**, not the `salg:term` URIRef — use bracket access (`SALG["term"]`) in hand-written Python; `to_rdf.py`'s own generic encoder already does.

## Testing discipline: a "conforms" test is not the same as an execution test

A query/update list that only gets `query_to_rdf()`/`update_to_rdf()` + SHACL-shape-validated (does the *encoding* conform) is not proof the decode+execute path works — the shape check never runs `rdf_to_query`/`lower_rdf11`, so it can't see whether the reconstructed tree is actually *evaluable*. This gap shipped two real bugs before anyone noticed: `FILTER (NOT) EXISTS` with more than one triple in its block crashed at execution (rdflib requires a real Python instance attribute, not just a dict-stored value, to survive its own `.graph` resolution — the generic tree-rebuilding in `to_rdf.py`/`lower_rdf11.py`/`from_rdf.py` only preserved the dict-stored copy), and `BIND(SUBSTR(...) AS ?z)` silently never bound `?z` (a key-name collision between `Slice.start`/`.length` and `Builtin_SUBSTR`'s own same-named parameters in `from_rdf._PLAIN_VALUE_KEYS`). Neither was a rare edge case — `EXPRESSION_FAMILY_QUERIES` had covered EXISTS and SUBSTR for years, just never *executed* them.

**Any new query/update shape added to a "conforms" list needs a companion execution-comparison test**, not just a structural-validation one — parse it, run it through the real `lower_rdf11`/`StarLayerGraph` (or `StarLayerDataset`) path, and compare the result against plain `rdflib` executing the same text on the same data (rdflib is a free, trustworthy oracle for anything it can already parse — no need to hand-compute expected values). `test_lower_rdf11.py`'s `_run_lowered` helper is the established pattern; see `test_filter_exists_with_multi_triple_block_executes`/`test_substr_binds_correctly` for the shape a regression test following this should take. This only applies where rdflib *has* an oracle to diff against — RDF-1.2-specific behavior (triple terms, `dirLangString`, annotation syntax) has none, and keeps relying on execution-based self-consistency plus the W3C suite instead.

- `starsparql/lower_rdf11.py` — tree-level SPARQL 1.2 algebra → 1.1 algebra lowering, both Query and Update sides; the preferred execution path (`rdf11_to_query`/`rdf11_to_update`, no text involved).
- SRL/SPARQL-RL (`WD-sparql12-rl-20260919`) — a separate, general-purpose Datalog-style rules language, not part of the `sh:` vocabulary (see `packages/shacl/docs/shacl12-gap-matrix.md` for the spec-status writeup). Fully implemented — parsing, AST-as-RDF, SHACL shapes, well-formedness checking, and the stratified evaluation engine — see `docs/functionality-overview.md`'s "Currently covered".
  - `starsparql/srl_ast.py` — plain dataclasses for the SRL abstract syntax tree, field names taken verbatim from the spec's own §4.1 "Component Notation" table (`RuleSet`/`Rule`/`Data`/`TriplePattern`/`FilterElement`/`NegationElement`/`AssignmentElement`).
  - `starsparql/srl_grammar.py` — `parse_ruleset(text)`, a pyparsing grammar reusing rdflib's own `Expression`/`Var`/`iri`/terminal productions directly (imported from `rdflib.plugins.sparql.parser`) for everything the spec's own text says is unchanged from SPARQL, hand-writing only the genuinely new SRL productions. Two-pass, mirroring rdflib's own `parseQuery`/`translateQuery` split: parse raw, then resolve every prefixed name in one tree pass via `rdflib.plugins.sparql.algebra.translatePName`/`traverse` (confirmed reusable unmodified against this grammar's own `Comp`/`Param`-built CompValue shapes), then convert into `srl_ast` dataclasses.
  - `starsparql/srl_vocab.py` — the `srl:` namespace. A `filter.expr`/`assign.expr` expression tree and every term value delegate straight to the existing `salg:`-namespaced generic encoder (`to_rdf._encode`/`from_rdf._decode`) rather than minting a parallel expression vocabulary — see its module docstring.
  - `starsparql/srl_to_rdf.py` / `srl_from_rdf.py` — `ruleset_to_rdf`/`rdf_to_ruleset`, the AST↔RDF round trip for the SRL-specific container shapes only (term/expression leaves reuse `to_rdf`/`from_rdf` directly, see above).
  - `starsparql/srl_shapes.py` — structural SHACL shapes over `srl:` graphs (the real shapes/ontology live in the sibling `starontology` package as `srl_shapes.ttl`/`srl-ontology.ttl`, registered in `starlayer.ontology.registry` as `srl_owl`/`srl_shacl`). List-valued fields use `sh:sparql`-based list shapes, not recursive `rdf:first`/`rdf:rest` NodeShapes — same `salg:TriplePatternListShape`-style pattern `sparql_shapes.ttl` already established, for the same reason (pyshacl's shape-recursion guard). A `filter.expr`/`assign.expr` is validated by the *existing* `salg:ExpressionShape`, not a separate `srl:` expression vocabulary.
  - `starsparql/srl_semantic_checks.py` — `check_ruleset`/`check_rule`, §4.2's Well-formedness Conditions (unbound head/filter/assignment variables, a `SET(...)` reusing an already-bound variable) — a cross-referential, sequence-position-dependent check, deliberately **not** a SHACL shape, mirroring `semantic_checks.find_unbound_projected_variables`'s own precedent for exactly the same reason.
  - `starsparql/srl_eval.py` — the evaluation engine: `build_dependency_graph`/`stratify` (§4.3.2/§4.4.2, direct pseudocode translations, raising `StratificationError` if §4.4.1's condition is violated), `eval_rule`/`eval_rule_elements` (§6.4), and the top-level `srl_infer`/`srl_query` operations (§4.1's `Infer`/`Query`, `evaluate_ruleset` under the hood) — named with an `srl_` prefix rather than the spec's own bare `Infer`/`Query`, deliberately, to avoid colliding with `StarLayerGraph.infer(profile=...)`/`.query()` if both are imported into the same namespace. Built on rdflib's own real `evalBGP`/expression-evaluation machinery (`rdflib.plugins.sparql.evaluate`) rather than reimplementing SPARQL's join/expression semantics a second time — see the module's own docstring for the exact reuse points. Verified end-to-end by reproducing §6.6's worked example (exact dependency edges, exact stratification, exact 13-triple inferred graph, including the stratification-correctness property the spec itself calls out).
  - **A genuinely surprising, directly-spec-confirmed subtlety**: `WHERE DATA {...}`/`NOT DATA {...}` matches only the *original* base graph passed to `infer()`, never the rule set's own top-level `DATA {}` blocks — §6.5's own pseudocode passes `G0` (not its separately-defined `GD = G0 ∪ D` variable, despite the name collision with `evalRule`'s own `GD` parameter) at every `evalRule` call site. Confirmed via direct byte-for-byte reading of the raw spec HTML, not an inference from prose; see `srl_eval.evaluate_ruleset`'s own docstring and `test_srl_eval.py::test_where_data_matches_only_the_original_base_graph`.
  - **Known scope reductions in the grammar (documented in `srl_grammar.py`'s own module docstring, not oversights)**: only `;`-chained same-subject property lists are supported (needed by the §6.6 worked example's own R5), not `,`-chained object lists; no property paths beyond a bare IRI/`a` predicate (the spec's own path grammar is already far more restricted than full SPARQL); no reified-triple/triple-term syntax yet in pattern/template/data position (`srl_ast.Term` already types this in for a follow-up grammar widening); `IMPORTS` is a hard rejection (`SRLImportsNotSupportedError`), not resolved (§4.5 explicitly permits this); `query()` is implemented on top of `infer()` rather than the spec's permitted selective-rule-evaluation optimization.
- `tests/w3c_sparql12/` (harness, downloader, and both W3C-suite test files) — the W3C SPARQL 1.2 conformance suite harness (`download_w3c_sparql12_tests.py` fetches it from `w3c/rdf-tests`; a hand-written SPARQL JSON Results parser, `harness.py::parse_srj`, exists because rdflib's own built-in one doesn't understand the RDF 1.2 `"type": "triple"` result-term shape). `test_w3c_sparql12_oxigraph_roundtrip.py` additionally requires a live Oxigraph/Fuseki instance and self-skips otherwise.
- `tests/unit/test_shacl_shapes.py` — valid queries/updates conform; deliberately malformed graphs fail with the expected violation.
- `tests/integration/test_adversarial_roundtrip.py` — hand-authored adversarial cases (not W3C fixtures) proving translation round-trip against a live Oxigraph/Fuseki instance; self-skips if neither is reachable.
- `tests/unit/` — everything else: one file per feature area, no live infra needed.

## Known gaps (deliberately not chased, not oversights)

- **A collection-order-dependent test flake, found 2026-09-28, not yet root-caused.** `tests/unit/test_lower_rdf11.py::test_eval_select_via_lowering[...eval-triple-terms/manifest#op-2]` (and the identical fixture via `test_w3c_sparql12.py::test_eval_select`) fails with an empty actual-results list when the *whole* `tests/unit/` directory is collected (imported) together — but passes when run alone, or in most smaller combinations. Confirmed via `-k` filtering (only op-2 executes, everything else just gets collected) that this is a **collection-time**, not execution-order, effect — some other test module's mere import corrupts shared state before op-2 ever runs. Confirmed via `git stash` on `from_rdf.py` (this session's own biggest change) that the flake reproduces identically with that file fully reverted to its pre-session state — **not caused by anything in this session's work** (the `_LIST_VALUED_KEYS` fix, `semantic_checks.py`, or `native_components.py` — each independently ruled out via `--ignore`). `op-2` itself compares `TripleTerm`-valued bindings differing only in numeric literal lexical form (`"123"^^xsd:integer` vs `"123.0"^^xsd:decimal`) - suspect this is related to the already-documented `_TT_HASH_MEMO` content-addressing collision risk `starlayergraph/model/encoding.py::term_key()`'s own docstring describes (a global, process-wide memo table that a value-equal-but-lexically-different literal could plausibly collide in), but this hasn't been confirmed against the actual mechanism yet - bisection stopped once non-involvement of this session's changes was established, not carried through to a root cause. Worth root-causing properly in a future session; low urgency since it doesn't affect real usage (an in-process quirk of running a large test suite, not user-facing behavior).
- The W3C harness's `StarLayerGraph()` construction isn't dataset-capable, so named-graph fixtures (`.trig`/`.nq`) using `GRAPH ?g { }` patterns can't work regardless of query-text correctness.
- `list-anonreifier-01` (`NegativeSyntaxTest`) — an empty collection `()` as a reifier term's object still parses when the fixture expects rejection. Deliberately left open: the fixture's own text carries a `# TODO: See if this should be throwing an error` comment — genuine spec ambiguity, not a clear gap. Its sibling `list-tripleterm-01` used to fail for the same documented reason but now passes (see the "Current capabilities" note above) — not because this ambiguity was resolved, purely because that fixture's first line independently trips the subject-position check below before parsing ever reaches its own copy of the same empty-collection case.
- Seven W3C `PositiveSyntaxTest` fixtures (`basic-tripleterm-01`/`-03`, `bnode-tripleterm-01`/`-02`/`-03`, `compound-tripleterm-subject`, `nested-tripleterm-02`) construct a triple term directly as an ordinary pattern's *subject* — never legal RDF 1.2 (a triple term is only ever an object, per RDF 1.2 Concepts' own triple-formation rules; see `starsparql/triple_term.py`'s `InvalidTripleTermError` rule 2, added 2026-08-15). Not a gap in this project — `_reject_triple_term_pattern_subjects` correctly rejects all seven; believed to be a suite defect, written up for upstream reporting in `docs/w3c-sparql12-test-suite-issues.md` Issue 1. (Related nuance, not a contradiction: the SPARQL Query spec's own §18.1.3 frames a triple-pattern-in-subject-position as "will fail to match" — an always-empty *evaluation* outcome — rather than explicitly mandating a construction-time error; rejecting early is a defensible fail-fast choice the spec doesn't forbid, not a stricter-than-spec bug.)
