# starsparql implementation notes

This document captures the internal design of `starsparql` and is intended for maintainers and advanced contributors. It is not required reading for normal package use.

## Design

`rdflib` already represents SPARQL algebra as a tree of `CompValue` and `Expr` objects. Those nodes have a predictable structure:

- `node.name` -> `rdf:type salg:<name>`
- each `key: value` -> `salg:<key>` predicate, recursively encoded
- nested nodes become nested RDF resources
- lists become RDF lists
- RDF terms remain RDF terms

The project maps that structure directly into RDF so queries can be stored and analyzed as graph data.

The encoder/decoder is intentionally generic. It does not define one conversion function per operator. Instead, it uses the same recursive logic for whichever algebra operators rdflib exposes, and it rebuilds the expression/eval mapping from rdflib's live grammar at import time.

That design keeps the package aligned with rdflib changes without requiring a custom hand-maintained mapping for every new operator or built-in.

## Internal execution model

The normal execution path does not serialize to SPARQL text. A decoded SPARQL 1.2 algebra tree is lowered into a directly runnable rdflib `Query` or `Update` object, and that object is executed against the in-memory `StarLayerGraph` or `StarLayerDataset` store.

This is the default path for local execution: parse the query, convert the algebra to a runnable rdflib object, and evaluate it directly against the in-memory graph implementation. No SPARQL text is required for this flow.

A conversion back to SPARQL 1.1 or SPARQL 1.2 text is still available for external backends or remote stores that require a plain string query. In those cases, the package can serialize the lowered query or update back to text before sending it to the backend.

## RDF query vocabulary

The project includes a schema for the RDF representation of the SPARQL algebra. This vocabulary is used to validate generated or hand-authored algebra graphs before conversion back into executable queries.

The validation layer deliberately checks structure, not just text form. This is especially useful when a query is constructed by a program or generated by an LLM and needs validation before execution.

## Known implementation details

- Bare Python strings in the algebra tree are not safe to encode as `rdflib.Literal` values.
- Grammar keyword tokens such as `UNDEF`, `DEFAULT`, and `SILENT` are tracked using a reserved internal marker instead of a plain literal.
- `query.prologue` and `update.prologue` are not part of the algebra tree and are handled separately when needed for correct `BASE` relative resolution.
- Triple terms are first-class values in the SPARQL 1.2 algebra, but they are still subject to validity checks to ensure they are not used in illegal positions.

## Project-specific notes

- `starsparql.parse12` extends rdflib's grammar to support SPARQL 1.2 syntax and RDF 1.2 triple terms.
- The package supports round-tripping of the SPARQL algebra and preserves semantics rather than original source formatting.
- A real W3C conformance suite is used to verify the end-to-end parse → encode → decode → re-execute flow.

## Reference files

- `starsparql/vocab.py` — RDF vocabulary and encoding rules
- `starsparql/to_rdf.py` — encode algebra to RDF
- `starsparql/from_rdf.py` — decode RDF back to algebra
- `starsparql/lower_rdf11.py` — lower algebra to executable SPARQL 1.1 objects
- `starsparql/ontology/sparql_shapes.py` — SHACL validation of algebra RDF
- `tests/test_w3c_sparql12.py` — conformance checks

See the package `CLAUDE.md` for additional notes on current gaps and implementation status.
