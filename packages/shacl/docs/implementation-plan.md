# starshacl Implementation Plan

*Last reviewed: 2026-08-01*

starshacl is a `pyshacl` wrapper that adds native RDF 1.2 triple-term support and full SHACL 1.2 Core coverage. The architecture is "pySHACL wrapper with a growing set of native carve-outs" - not a from-scratch rebuild of pySHACL. See `docs/shacl12-gap-matrix.md`'s "Note on Architecture Direction" for why, and what that means for adding new features.

## Current Status

- **SHACL 1.2 Core**: fully implemented. See `docs/shacl12-gap-matrix.md`'s Full Changelog Coverage table.
- **The other five SHACL 1.2 documents** (SPARQL Extensions, Node Expressions, Rules, User Interfaces, Profiling): covered to the depth documented in `docs/compatibility.md`'s RDF / SHACL Version Support section and `docs/shacl12-gap-matrix.md`'s per-document table.
- **RDF 1.1 and RDF 1.2** (triple terms, `rdf:dirLangString`) share one validation/rules path - no separate runtime modes.
- **Known pySHACL bugs and starshacl's workarounds**: `docs/pyshacl-upstream-issues.md` and `docs/compatibility.md`'s "starshacl and pySHACL" section.
- **Test suite**: 789 passed, 7 skipped (6 Oxigraph/Fuseki-gated, clean without a running instance; 1 W3C-suite parse-health placeholder, expected now that no fixtures fail to parse), 1 xfailed (W3C SHACL 1.2 test suite finding - reasoned and `strict=True`; a plain-`rdflib` fixture-formatting quirk deliberately left unpatched, `seconds-example`, see `docs/shacl12-gap-matrix.md`'s "W3C SHACL 1.2 Test Suite Integration" section). Two earlier rounds of "permanently out of scope"/"already-documented deliberate limitation" xfails (11 fixtures total) were revisited 2026-08-01 and fixed: `starlayergraph` now monkeypatches 2 confirmed plain-rdflib SPARQL-evaluator bugs directly (integer-multiplication type promotion, decimal-result canonical lexical form), `sh:subsetOf` now supports any SHACL property path (not just a simple IRI) via pySHACL's own `shacl_path_to_sparql_path`, and `shnex:instancesOf` now walks `rdfs:subClassOf` directly instead of relying on the caller's `inference=` setting - see `docs/starlayergraph-upstream-change-log.md`'s 2026-08-01 entry and `docs/shacl12-gap-matrix.md`'s Phase 1/2 writeups.
- What changed and why, in detail: `CHANGELOG.md` and `git log`.

**Spec baseline caveat**: all six SHACL 1.2 documents are tracked against Working Draft (First Public Working Draft for User Interfaces) TR-track snapshots - none are Candidate Recommendation yet. Re-verify wording against the live TR pages before relying on it. RDF 1.2 itself (tracked by `starlayergraph`) reached Candidate Recommendation 2026-04-07 - one stage ahead of any SHACL 1.2 document.

**W3C test suite**: the Working Group has since published an official SHACL 1.2 test suite (`w3c/data-shapes`'s `shacl12-test-suite/`, still actively growing). Phases 1 (`sht:Validate`), 2 (`sht:EvalNodeExpr`), and 3 (`sht:Infer`) are all integrated and **every fixable finding has been fixed** - see `docs/w3c-shacl12-test-suite-plan.md` for the plan and `docs/shacl12-gap-matrix.md`'s "W3C SHACL 1.2 Test Suite Integration" section for the full list (a core `shnex:` correctness bug, the entire previously-missing `sparql:` node-expression namespace, 5 `starlayergraph` parser/lexical bugs, a `starlayergraph` monkeypatch for 2 confirmed plain-`rdflib` SPARQL arithmetic bugs, generalized `sh:subsetOf` to any SHACL property path, generalized `shnex:instancesOf` to walk `rdfs:subClassOf`, 2 confirmed pySHACL bugs (`docs/pyshacl-upstream-issues.md` Issues 5-6), and roughly 20 starshacl findings ranging from single-line fixes to new SHACL 1.2 features - `sh:nodeByExpression`, SELECT-based `sh:targetNode`, per-constraint `sh:severity`/`sh:deactivated` annotations, `sh:values` on property shapes, ambient prefix discovery, and global (shape-independent) `sh:SPARQLRule`). ## 2026-08-26 Gap-Closure Plan

Four items, ordered by implementation risk (lowest first) except item 4, appended after user request to include it rather than reordering the list. Each fits one of the established architecture patterns in "Note on Architecture Direction" above rather than inventing a new one - see `docs/shacl12-gap-matrix.md`'s "Not Covered / Deferred" table for the full gap description and spec citations behind each.

### 1. Content-level SPARQL query text validation (`sh:select`/`sh:ask`/`sh:construct`) - **Done, 2026-08-26**

Implemented as designed below, with one simplification found during implementation: scanning the whole shapes graph directly for `(None, sh:select/ask/construct, Literal)` triples covers `sh:sparql` constraints and custom `sh:ConstraintComponent` validators uniformly (same predicates regardless of parent node type), so no separate handling was needed for `sh:validator`/`sh:nodeValidator`/`sh:propertyValidator`. Also found and fixed a real latent bug in `meta_validate()` itself while touching this file: it had no `return` statement in its success path despite its `-> tuple[bool, Any, str]` signature (harmless today since the one caller in `validator.py` never captured the return value, but a real defect against its own documented contract).

`starshacl/meta_shapes.py::check_sparql_query_text()` + `_collect_query_prefixes()` (a standalone reimplementation of pySHACL's `SPARQLQueryHelper.collect_prefixes()` against a plain graph, no `Shape`/`ShapesGraph` wrapper needed), wired into `validator.py::validate()` right after the existing `meta_validate()` call, same `meta_shacl` gate. Confirmed empirically (not just asserted) that a shape relying only on Turtle's own `@prefix` (no `sh:declare`/`sh:prefixes`) was *already* broken at real execution time before this check existed (`resolvePName` raises `Unknown namespace prefix`) - this preflight now catches that class of error before validation even runs, rather than only at first real use.

Tests: `tests/integration/test_meta_shapes_extensions.py::TestSparqlQueryTextValidation` (6 cases - malformed `sh:select`/`sh:ask`/`sh:construct` each raise, a well-formed query passes, ambient-`sh:declare`-only prefix resolution passes, and one full end-to-end `StarShaclValidator.validate(meta_shacl=True)` pass through a real ASK-based custom `sh:ConstraintComponent`). Full package suite: 851 passed (845 baseline + 6 new), 0 regressions.

### 2. `sh:resultAnnotation` / `sh:annotationProperty` / `sh:annotationVarName` / `sh:annotationValue` - **Done (plain `sh:sparql` only), 2026-08-26**

**Goal**: a SPARQL-based constraint's `sh:resultAnnotation` declarations inject extra triples onto each `sh:ValidationResult` node it produces - e.g. `?result ex:matchedValue ?boundVar` sourced from that constraint's own SELECT result row.

**Correction to the earlier read of this gap**: "unimplemented in pySHACL itself" is true, but doesn't mean unimplementable in starshacl - most of starshacl's own feature surface is exactly this: a targeted patch or new registration on top of pySHACL's engine (see "Note on Architecture Direction" above, all 11 patterns). This one has a concrete, already-identified hook.

**Actual hook found while implementing, better than what was planned**: not `SPARQLBasedConstraint.evaluate()`'s call sites (they only see the already-*built* `(desc, r_node, r_triples)` reports, no further access to per-row bindings once returned) - `ConstraintComponent.make_v_result()` itself receives both `source_constraint` (the `sh:sparql` node, exactly where `sh:resultAnnotation` sits) and `bound_vars` (the SELECT row's own bindings) as real keyword parameters, confirmed by reading `_evaluate_sparql_constraint`'s own `rept_kwargs = {'source_constraint': sparql_constraint.node, ...}`. Overriding `make_v_result` itself - already done once on this same class (`SparqlConstraintComponentWithSeverity` in `native_components.py::_build_sparql_constraint_component`, which overrides `_evaluate_sparql_constraint` for the unrelated `sh:sparql`-level `sh:severity` extension) - is simpler than patching `evaluate()`'s call sites and needed no changes outside that one existing class.

**Scope narrowed during implementation**: custom `sh:ConstraintComponent` validators (`BoundShapeValidatorComponent` in `pyshacl/constraints/sparql/sparql_based_constraint_components.py`) turned out **not** to reach `make_v_result` with either `source_constraint` or `bound_vars` at all - confirmed by reading that file directly: `source_constraint` is explicitly commented out there (`# 'source_constraint': self.validator.node,`) and no `bound_vars=` kwarg is passed anywhere in it; SELECT-row values instead flow through a separate, `make_v_result`-independent message-templating path (`query_helper.bind_messages`). Supporting `sh:resultAnnotation` there would need a real second change (threading bound vars through `BoundShapeValidatorComponent.evaluate()` itself, not just another `make_v_result` override) - deliberately not done in this pass. **Only plain `sh:sparql` constraints support `sh:resultAnnotation` today**; custom-component support is a real, separate follow-up if a concrete need arises.

Implementation: `starshacl/native_components.py`'s `_build_sparql_constraint_component()` - new `make_v_result` override on `SparqlConstraintComponentWithSeverity`, plus a new module-level `_result_annotation_triples(sg, source_constraint, r_node, bound_vars)` helper. `bound_vars` normalization handles both shapes it actually arrives in (a plain dict for the common 2-tuple violation case, or a `(t, p, v, vars_dict)` 4-tuple for the path-valued case) - anything else (a bare `True`/`(t, p, v)` violation with no SELECT row at all) only supports the fixed `sh:annotationValue` form, since there's no row to resolve `sh:annotationVarName` against.

**Regression tests**: `tests/integration/test_sparql_shacl_integration.py` (3 new cases - `sh:annotationVarName` sourced from a real SELECT row, fixed `sh:annotationValue`, and a no-`sh:resultAnnotation` constraint proving zero behavior change when the feature isn't used). Full package suite: 854 passed (851 + 3 new), 0 regressions.

### 3. SHACL 1.2 UI widget-selection algorithm (`shui:WidgetScore`/`shui:WidgetAcceptMatcher`)

**Goal**: given a shape, a focus node, a data graph, and a scoring graph, deterministically select the best-matching `shui:editor`/`shui:viewer` widget per the spec's own §3.2 "Select Function" procedure (already fully quoted in the gap-matrix row for this item).

**Prerequisite, must happen first**: the gap-matrix row flags that formal RDF vocabulary definitions (property ranges/cardinalities) for `shui:WidgetScore`/`shui:WidgetAcceptMatcher`/`shui:score`/`shui:dataGraphShape`/`shui:shapesGraphShape` weren't extractable from the fetched spec text - unclear whether that was a fetch limitation or the FPWD genuinely hasn't finished them. Re-fetch and re-read `https://www.w3.org/TR/shacl12-ui/` directly (verbatim quotes, not a summarized fetch) before writing any code - if the vocabulary genuinely isn't finalized upstream, this item should wait, not guess at a shape.

**Approach**: not a pySHACL patch at all - the matcher check is "two ordinary SHACL validations" per the spec's own text (shape node against the scoring graph, focus node against the data graph), so this is new code built entirely on the existing public `StarShaclValidator.validate()` API. New module, e.g. `starshacl/ui_widget_selection.py`, exposing something like `select_widget(shape_node, focus_node, *, data_graph, shapes_graph, scoring_graph, role)`:
1. If the shape has an explicit `shui:editor`/`shui:viewer`, look up its `shui:WidgetAcceptMatcher` (matched via `shui:widget`); no matcher → accept immediately; matcher returns `true` → accept; `false` → fall through to step 2.
2. Otherwise run the **score** function: collect every applicable `shui:WidgetScore` into a ranked array (ranking rule needs re-confirming against the live spec alongside the vocabulary check above).
3. Walk the ranked list, running the matcher check (`validate(shape_node_shapes, scoring_graph)` + `validate(focus_node_shapes, data_graph)`) on each until one passes.

**Effort**: medium-large - genuinely new public surface, not a gap-fix, but low *risk* since it can't affect existing `validate()`/`apply_rules()` behavior (additive-only, a new entry point).

**Regression tests**: once the vocabulary is confirmed, build fixtures mirroring the spec's own worked examples if any exist in the FPWD; at minimum, explicit-widget-with-no-matcher, explicit-widget-with-matcher-reject-then-fallback, and score-ranking-with-multiple-candidates cases.

**Prerequisite re-checked 2026-08-26 - split result, holding on implementation.** Fetched the live document directly (`https://www.w3.org/TR/shacl12-ui/`, still `WD-shacl12-ui-20260526`, unchanged) plus the external file it points to for formal definitions, `https://www.w3.org/TR/shacl12-ui/widgets/score-validator.ttl` (fetched raw, twice independently, not summarized both times):
- **`shui:WidgetScore` is now confirmed formally defined** - a real `sh:NodeShape` (`shui:ScoreShape`) targeting `shui:WidgetScore`: `shui:widget` (exactly 1, `sh:nodeKind sh:BlankNodeOrIRI`), `shui:score` (exactly 1, `xsd:decimal` or `xsd:integer`), `shui:dataGraphShape`/`shui:shapesGraphShape` (both optional, `BlankNodeOrIRI`). This half of the earlier "residual gap" is resolved - it was a real spec gap in the 2026-08-15 baseline, not a fetch-tool artifact, and has since been filled in.
- **`shui:WidgetAcceptMatcher` still has no formal shape anywhere** - confirmed by two independent targeted fetches of the same file, not a fetch limitation. The algorithm prose (Select Function §3.2, Matcher Function §3.4) uses the same three properties on it (`shui:widget`, `shui:dataGraphShape`, `shui:shapesGraphShape`) with identical semantics to `WidgetScore`'s, but states no cardinality or type constraint for any of them.

Since the matcher check is step 1 of the algorithm and also gates the fallback out of score-ranking, building a shape for it now means guessing at half the mechanism. Per this item's own stated gate above ("if the vocabulary genuinely isn't finalized upstream, this item should wait, not guess at a shape") - **holding, not implementing**, until `shui:WidgetAcceptMatcher` gets the same formal treatment `shui:WidgetScore` just did. Re-check `https://www.w3.org/TR/shacl12-ui/widgets/` for a sibling validator file (e.g. a `matcher-validator.ttl`) next time this is revisited, in addition to re-reading §3 itself.

### 4. `sh:RuleSet` / `sh:hasRule` / `sh:includesRuleSet` (rule-set selection) - **Done, 2026-08-26**

**Promoted from deferred to planned on user request** - originally grouped with the rest of the Rules-family work (SRL/SPARQL-RL) and deferred alongside it, since this is itself a rule-*execution* feature; now explicitly in scope.

**Goal**: `apply_rules()` gains a way to run only a named, caller-selected subset of a shapes graph's rules, per SPARQL Extensions §8.2.1/§8.6 (added 2026-08-21, `WD-shacl12-sparql-20260821`): a rule set is declared via `sh:RuleSet` (a class; instances need a real IRI), populated via `sh:hasRule` (rule set → member rule), and composed via `sh:includesRuleSet` (rule set → included rule set, transitive). A rules engine "takes as input a data graph, a shapes graph and an optional rule set (defaulting to the default rule set of the shapes graph)... the set of all rules in the graph."

**Current behavior is the spec's own default, not a bug**: `apply_rules()` already runs every rule in the shapes graph with no selection mechanism - that's precisely the spec's stated default rule set, so nothing regresses for any caller who never mentions `sh:RuleSet`. This item only adds the *selection* capability for a caller who does.

**Vocabulary stability caveat**: the predicate names churned twice within the same upstream PR before landing (`sh:ruleSet`→`sh:memberRule`→`sh:hasRule`, `sh:importsRuleSet`→`sh:includedRuleSet`→`sh:includesRuleSet`) and were one week old at last check (2026-08-26). Re-fetch `https://www.w3.org/TR/shacl12-sparql/` §8.2.1/§8.6 directly, verbatim, immediately before implementing - don't rely on this plan's names without re-confirming, the same discipline applied to the UI item's vocab above.

**Approach**: two separate execution paths need the same filter, since starshacl's rule execution is split across pySHACL's own shape-attached-rule loop and starshacl's own global-rule pass.
- **Closure computation**: given a selected `sh:RuleSet` IRI, compute its member rules as a fixed-point/worklist closure over `sh:hasRule` (direct members) and `sh:includesRuleSet` (transitively-included rule sets' own members) - reuse the monotonic worklist technique from `_cross_node_reachable_shapes` (pattern 11 above), not a DFS-with-memo, for the same cycle-correctness reason documented there (a naive DFS memoizes a traversal-order-dependent answer, confirmed unsound for cyclic graphs via `PYTHONHASHSEED` variation). Precompute once per `apply_rules()` call, not per rule.
- **Shape-attached rules** (`sh:rule`, executed internally by pySHACL under `advanced=True`): extend the existing `_patch_rule_apply_for_source_rule_provenance`-style wrap of `TripleRule.apply`/`SPARQLRule.apply` (`validator.py`) - or add a second, similarly-scoped patch alongside it - so that when a rule set is selected (another `contextvars.ContextVar`, same no-op-by-default discipline as the provenance buffer), a rule node not in the computed membership set causes `apply()` to return immediately (0 modified, no triples added) instead of calling `original()`. This is a real behavior change when opted into (unlike the provenance patch, which only *observes*), so needs care that skipped rules don't leave the fixed-point rule-iteration loop confused about convergence (a skipped rule should count as "added nothing," which is already how convergence detection works for a rule that legitimately matches nothing).
- **Global rules** (`_global_sparql_rules`/`_global_sparql_rule_triples`, starshacl's own code, no patch needed): add the same membership check directly - skip a `sh:SPARQLRule` node not in the selected set before running its `sh:construct`.
- **`apply_rules()` signature**: new optional `rule_set: URIRef | None = None` (or accept the `sh:RuleSet` node directly) parameter, threaded through to both paths above.

**Effort**: medium - the closure computation is a small, well-precedented piece of code (literally reuse the existing worklist helper's shape); the two-execution-path filtering is the real work, and needs the same care `_patch_rule_apply_for_source_rule_provenance` already took around idempotent patching and context-local state so nested/concurrent `apply_rules()` calls with different rule sets don't leak into each other.

**Regression tests**: a shapes graph with two `sh:RuleSet`s, disjoint rule membership, confirming `rule_set=A` runs only A's rules and `rule_set=B` only B's; transitive inclusion (`sh:includesRuleSet` two levels deep, plus a cycle, mirroring the existing cyclic-composition test style in `tests/integration/test_native_component_composition.py`); no `rule_set` given still runs every rule (regression guard for the default-unaffected claim above); a rule set selected that has zero matching rules (should run rules with no effect, not error).

**Prerequisite re-checked live 2026-08-26, immediately before implementing.** `https://www.w3.org/TR/shacl12-sparql/` is still `WD-shacl12-sparql-20260821` (unchanged since the last check) - `sh:RuleSet`/`sh:hasRule`/`sh:includesRuleSet` confirmed stable, quoted verbatim: *"The property `sh:hasRule` can be used to declare that a rule set has a given rule as a member. The default rule set of a graph is the set of all rules in the graph. Rule sets can use the property `sh:includesRuleSet` to (transitively) include other rule sets."* Also confirmed the "default rule set" statement is unconditional - no stated exclusion for a rule that also happens to be a named `sh:RuleSet` member - so `apply_rules()`'s existing no-`rule_set` behavior (run every rule) needed no correction.

**Implemented largely as designed, one simplification found while implementing**: `ConstraintComponent.make_v_result` wasn't involved here at all (that was item 2's hook) - the actual integration points were exactly the two named above.
- `_rule_set_members()` (`validator.py`) - the closure, as planned, though simpler than `_cross_node_reachable_shapes`'s own fixed-point machinery: a single ordinary visited-set BFS from one root (not that function's multi-root bottom-up memoization pattern, which is the specific shape that was unsound under cycles) is already correct for cycles on its own, so no need to import that function's own worklist structure verbatim.
- `_patch_rule_apply_for_rule_set_filtering()` - a new, independent patch (own contextvar `_rule_set_filter`, own idempotency tag), deliberately *not* folded into the existing `_patch_rule_apply_for_source_rule_provenance` - keeps that already-tested, working feature untouched. Confirmed the two compose correctly regardless of which installs first in a process (each wraps whatever `rule_cls.apply` already is and unconditionally delegates), including together in the same call (`test_rule_set_and_source_rule_provenance_compose`): a rule filtered out here produces no provenance triple either, since it never reaches the real underlying `apply()` for the provenance wrapper to diff.
- `_global_sparql_rules`/`_global_sparql_rule_triples` gained an `allowed_rule_nodes` parameter, applied as a straightforward filter.
- `apply_rules()` gained `rule_set: Any | None = None`. One thing not called out in the original design: `shacl_graph` is now normalized (`normalize_graph_inputs`) once, up front, and that single reference is reused for the closure computation, `self.validate()`, and the global-rules pass - needed so the rule/rule-set nodes `_rule_set_members()` reads are guaranteed to be the *same* nodes (same blank-node identities) everything else sees, rather than risking two independent normalizations producing different copies.

Manually verified end to end (not just via the test suite) for all four cases: default running every rule, `rule_set=A` isolating just A's rules on both the global-`sh:SPARQLRule` and shape-attached-`sh:TripleRule` paths, a 3-node `sh:includesRuleSet` cycle (A→B→C→A) correctly reaching all three rules from any starting point, and an empty rule set running nothing without error.

Tests: `tests/integration/test_rule_set_selection.py` (8 cases, new file - both execution paths, transitive+cyclic inclusion, empty-set no-op, and provenance composition). Full package suite: 862 passed (854 + 8 new), 0 regressions.

**Correction**: the previous "no known feature gaps remain" claim here no longer held once the W3C test suite (item 4) surfaced several genuine ones the hand-written test suite hadn't caught - all have since been fixed (see item 4 above). Everything still open is tracked in one of: `docs/shacl12-gap-matrix.md`'s "Not Covered / Deferred" table (deliberate, documented scope boundaries), `tests/w3c_shacl12/known_failures.py` (confirmed permanently out-of-scope or deliberate-limitation entries only, as of 2026-08-01), or upstream reporting/tracking work (items 1-2 above) - not silently missing.

## Working Principles

- One integrated validation/rules engine behavior for RDF 1.1 and RDF 1.2 inputs - no separate runtime modes.
- Semantics that are genuinely unimplemented (e.g. a case the spec itself disallows) hard-fail with a clear error; a shape the native fast path doesn't recognize but pySHACL can still process falls back to the generic pySHACL-encoded path rather than hard-failing.
- New native-pass additions should fit one of the established architectural patterns (see `docs/shacl12-gap-matrix.md`'s "Note on Architecture Direction") rather than inventing a new one without reason.
