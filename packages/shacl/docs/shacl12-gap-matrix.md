## Tracking Upstream Spec Changes

All six SHACL 1.2 documents are still W3C **Working Drafts** (First Public Working Draft for UI) - none has reached Candidate Recommendation, so wording, vocabulary, and even scope can still change. This repo has no automated way to detect that (no CI job watches the W3C TR-track), so it's a manual check - this section exists so that check is concrete and repeatable rather than "go re-read the spec" with no defined procedure.

**Recorded baseline**: every claim in this file's per-document table and "Full Changelog Coverage"/"Not Covered / Deferred" tables was verified live against the TR-track URLs listed at the top of this file, **as of 2026-07-19**. Treat that date as the last-confirmed-current point for everything in this file; anything checked after should update this date (and the per-row content, not just the date).

**How to check what changed since the recorded baseline** (do both - they answer different questions):

1. **Per-document commit history** at [github.com/w3c/data-shapes](https://github.com/w3c/data-shapes), the spec source repo. Each document has its own subdirectory (`shacl12-core/`, `shacl12-sparql/`, `shacl12-node-expr/`, `shacl12-rules/`, `shacl12-ui/`, `shacl12-profiling/`) - there is no single unified changelog file, so check each directory's commit history separately, filtered to commits after this file's recorded baseline date. This is the authoritative "what actually changed" signal, since it's the real diff against spec source, not a summary.
2. **Each published TR page's own "Status of This Document" section** (top of every `https://www.w3.org/TR/shacl12-*/` page) - describes the document's current maturity stage and sometimes calls out notable recent changes in prose. Faster to check than a commit history, but not guaranteed to mention every substantive change - use it as a quick signal, not a substitute for (1) when something in this repo actually depends on exact spec wording.

**When to check**: before starting any new work that touches SHACL 1.2 behavior specifically (not every routine change to this repo), and periodically even absent active work - these are moving drafts, and a silent behavior-relevant change upstream won't announce itself otherwise. There's no fixed cadence enforced; use judgment based on how long it's been since the recorded baseline above.

**What to do when a real change is found**: update the specific row in this file's per-document table or "Full Changelog Coverage"/"Not Covered / Deferred" tables (not just this section), add or adjust regression tests if the change affects actual validator behavior (most packaging/organizational changes won't), note it in `CHANGELOG.md` if it results in a code change, and bump this section's recorded baseline date. A wording-only change with no behavioral delta still gets a one-line note (so the next person doesn't re-investigate something already checked) but doesn't need a full re-verification of every row.

## Unified Engine Goal

One integrated validation/rules engine behavior for RDF 1.1 and RDF 1.2 inputs, not separate runtime modes: native fast-path evaluation runs automatically whenever a graph contains triple terms, and any shape/data combination the native path doesn't recognize falls back to the generic pySHACL-encoded path. Semantics that are genuinely unimplemented (e.g. reification with a non-simple-IRI `sh:path`, which the spec itself disallows) hard-fail instead of silently falling back.

## Note on Architecture Direction

The actual architecture is "pySHACL wrapper with a growing set of native carve-outs": most ordinary (non-triple-term) SHACL Core validation still runs through pySHACL's own engine, with native passes handling everything pySHACL can't. New native additions should fit one of these established patterns:

1. **Merge-after** — run pySHACL normally, compute additional violations natively, merge into the report. **Retired**: this pattern had a known correctness gap (results run *outside* pySHACL's own recursive shape evaluation, so they're wrong, not just incomplete, whenever the predicate appears inside `sh:not`/`sh:and`/`sh:or`/`sh:xone`, or is combined with `sh:deactivated`/`sh:severity` - confirmed for `sh:someValue` before it was the first predicate migrated to pattern 10). Every predicate that used this pattern is now migrated to pattern 10 (see its entry below for the full list) - no predicate uses merge-after anymore, and no new addition should either.
2. **Target-injection** — pre-compute extra target nodes, inject as `sh:targetNode` triples before pySHACL runs (new target types: `sh:targetWhere`, `sh:shape`, implicit class targets). Not subject to pattern 1's old composition gap and not a migration candidate: pySHACL has no equivalent registry for *target* predicates (confirmed by reading `pyshacl/shape.py` - targets are hardcoded methods, not a pluggable map like constraints are), so pre-computing and injecting via `sh:targetNode` remains the only correct approach for this one.
3. **Strip-and-replace** — pySHACL actively mishandles or crashes on the input, so strip the triggering triples from what it sees and evaluate correctly natively. **Retired**: shared pattern 1's composition gap, and was worse in one way - the strip happened regardless of composition context, so a triggering triple nested only inside `sh:and`/`sh:not` could be stripped from what pySHACL saw while the native pass also found no independently-targeted focus nodes to evaluate, making the constraint disappear entirely rather than just misfire. Every predicate that used this pattern (path-valued property pairs, `sh:closed sh:ByTypes`, list-valued `sh:class`/`sh:datatype`/`sh:nodeKind`, `sh:datatype rdf:dirLangString`, `sh:languageIn`, `sh:uniqueLang`) is now migrated to pattern 10, each as a component that *shadows* pySHACL's existing one for the same predicate (see pattern 10's entry below).
4. **Report-annotation** — pySHACL's behavior is already correct, just make it explicit in the report (`sh:conformanceDisallows`). Not a per-shape constraint, so not subject to the pattern-1 composition gap.
5. **Opt-in parameterized lookup** — a `validate()` keyword the spec frames as implementation-parameterizable (`rdfs_subclass_reasoning_includes_shapes_graph`).
6. **Shapes-graph import preprocessing** — resolve `owl:imports` before any other pass runs (`_resolve_shapes_graph_imports`).
7. **Adapter-layer value-type encoding** — teach `TripleTermAdapter` to encode/decode a new value type at all (`DirLangString`).
8. **Targeted upstream-bug runtime patch** — patch pySHACL itself at runtime, reserved for bugs this well-isolated and this verified (`sh:filterShape`'s `Shape.validate` calling-convention fix).
9. **Inject-into-data-graph-then-strip** — copy triples into a copy of the *data* graph before pySHACL runs (the wrong-but-satisfiable place a buggy lookup checks), then remove them from the result (`sh:intersection`).
10. **Native constraint-component registration** — register a real `pyshacl.constraints.constraint_component.ConstraintComponent` subclass into pySHACL's own module-level dispatch map (`pyshacl.constraints.CONSTRAINT_PARAMETERS_MAP`), the exact mechanism pySHACL uses for its own ~28 core components (`starshacl/native_components.py::register_native_components`). Because pySHACL's `sh:not`/`sh:and`/`sh:or`/`sh:xone` components recurse via genuine `Shape.validate()` calls, and `sh:deactivated`/`sh:severity` are handled generically once per shape (not per-component) in `Shape.validate()` itself, a registered component gets correct composition, deactivation, and severity handling for free - not reimplemented. Preferred pattern for any predicate that's a self-contained per-shape constraint (supersedes pattern 1 for new work). Predicates whose value is itself a referenced shape (e.g. `sh:someValue`, `sh:memberShape`) need one extra step, `ensure_shape_typed`: pySHACL's shape-graph loader only auto-recognizes shapes reachable via a fixed set of predicates (`sh:property`, `sh:node`, `sh:not`, `sh:qualifiedValueShape`, `sh:and`/`sh:or`/`sh:xone` list members), not the constraint registry itself, so the referenced shape's value must be explicitly typed `sh:NodeShape`/`sh:PropertyShape` in a copy of the shapes graph before pySHACL sees it. Predicates whose semantics depend on RDF-1.2 triple-term identity (`sh:reifierShape`/`sh:reificationRequired`) initially looked unreachable this way: a registered component's `evaluate()` runs on the graph *after* `TripleTermAdapter.encode_graph()` has already flattened triple terms into content-addressed URIs, so `(focus, path, value)` needs to become the *same* URI `encode_graph()` assigned before an `rdf:reifies` lookup can match anything. This turned out to already be solved: `encode_graph()` returns a `_SparqlAwareEncodedGraph` (`starshacl/adapters.py`) carrying a back-reference to the exact adapter instance that did the encoding (`_tt_adapter`, built earlier for SPARQL/rules wiring) - re-encoding the triple term through that same adapter/registry reproduces the identical URI. The one wrinkle: `target_graph` as handed to a component is pySHACL's own `RdfLibDataGraph` wrapper (`pyshacl/graph_abstraction.py`), not the `_SparqlAwareEncodedGraph` directly - the adapter back-reference lives one level down, on `target_graph.impl` (confirmed empirically; not documented by pySHACL). **Migration complete**: every predicate that was ever on the merge-after (pattern 1) or strip-and-replace (pattern 3) path is now registered here - `sh:someValue`, `sh:singleLine`, `sh:subsetOf`, `sh:rootClass`, `sh:uniqueValuesFor`, `sh:memberShape`, `sh:minListLength`, `sh:maxListLength`, `sh:uniqueMembers`, `sh:reifierShape`, `sh:reificationRequired`, `sh:closed`/`sh:ignoredProperties` (incl. `sh:ByTypes`), `sh:class`, `sh:nodeKind`, `sh:datatype` (incl. `rdf:dirLangString`), `sh:languageIn`, `sh:uniqueLang`, `sh:equals`, `sh:disjoint`, `sh:lessThan`, `sh:lessThanOrEquals`. The predicates that shadow an existing pySHACL component (`sh:closed`, `sh:class`, `sh:nodeKind`, `sh:datatype`, and the four property-pair predicates) delegate to a real instance of pySHACL's own original component whenever the shape only uses the plain, pre-existing form, falling back to native evaluation only once the new SHACL 1.2 form (a list value, a complex path, `sh:ByTypes`, `rdf:dirLangString`) is actually present - byte-for-byte parity for the common case, not a reimplementation risk. `starshacl/validator.py`'s entire merge-after/strip-and-replace machinery (`_NativePassProperties`, `_find_native_pass_properties`, `_run_native_passes`, `_append_native_results`, `_strip_triples`, and every per-predicate finder/evaluator/stripper) was removed once nothing used it anymore - only the target-injection (pattern 2), report-annotation (pattern 4), pattern 11 below, and a handful of other single-purpose patterns remain outside pattern 10.
11. **Full-batch composition branch for cross-node predicates** — a follow-on to pattern 10, for the one class of predicate pattern 10 alone can't make correct: a constraint that's inherently about comparing focus nodes *to each other* (currently just `sh:uniqueValuesFor`). Every pySHACL composition mechanism whose evaluation invokes a nested/referenced shape once *per individual value node* - `sh:not`/`sh:and`/`sh:or`/`sh:xone` (`pyshacl/constraints/core/logical_constraints.py`), `sh:node` and `sh:qualifiedValueShape` (`pyshacl/constraints/core/shape_based_constraints.py`) - has this problem: a cross-node constraint reached this way always sees exactly one candidate, vacuously conforming (or, negated through `sh:not`, vacuously violating) regardless of the real data, since there's never a second node in view to collide with. `sh:property` is not itself patched - its target must be a *property* shape, which `sh:uniqueValuesFor` can't sit on directly - but the real-world path through it (`sh:property`'s path resolves to value nodes, handed one at a time to that property shape's own `sh:node`) is covered because `sh:node` is patched at whatever depth it's reached from. Registering the predicate itself as a pattern-10 component can't fix any of this - the fix has to live in the *composing* mechanism, not the composed shape.

    `starshacl/native_components.py`'s `_build_and_component`/`_build_or_component`/`_build_xone_component`/`_build_not_component`/`_build_node_component`/`_build_qualified_value_shape_component` shadow pySHACL's own six components. For a nested shape that doesn't need it, evaluation delegates *entirely* to a real instance of pySHACL's own unmodified component (literally the same code object) - zero behavior change for the overwhelming majority of shapes. Once a nested shape does need it, that shape is invoked *once* with `focus` set to every value node the operator resolved (not one at a time), and per-value conformance is recovered from the returned violation reports' own `sh:focusNode` markers (every native component here, and every pySHACL core component, sets one via `make_v_result`) - ordinary shapes evaluate per-node exactly as pySHACL would, combined with the full-batch result using each mechanism's own logic (AND/OR/XONE/NOT for the logical operators, per-node-shape conjunction for `sh:node`, the min/max-count/sibling-disjoint counting logic for `sh:qualifiedValueShape`).

    **Detection is transitive, not shallow, and precomputed once per shapes graph.** The naive check - "does this directly-nested shape itself declare a cross-node predicate" - misses nesting more than one level deep (e.g. `sh:and` containing an `sh:and` containing the `sh:uniqueValuesFor` shape: the middle shape doesn't declare it, only something *it* composes does) and misses cases where the composition mechanism changes partway down the tree (e.g. `sh:and` containing a shape reached only via `sh:node`). `_cross_node_reachable_shapes` (`starshacl/native_components.py`) instead computes, once per distinct shapes-graph object, the full transitive closure: every shape node whose composition tree - walked through `sh:and`/`sh:or`/`sh:xone`/`sh:not`/`sh:node`/`sh:qualifiedValueShape` in any combination - reaches a shape declaring `sh:uniqueValuesFor`. `_shape_needs_full_batch(shape)` is then an O(1) membership check against this table rather than a live graph walk. The table is cached in a `WeakKeyDictionary` (content-keyed, since rdflib's `Graph.__eq__`/`__hash__` key off `identifier` rather than Python object identity - harmless here because `encode_graph()` never sets an explicit `identifier`, so each call gets a fresh random default) - confirmed empirically that every registered component evaluating shapes from the same `validate()` call shares the identical (encoded) shapes-graph object, so the table is computed exactly once per `validate()` call and the cache entry is dropped automatically once that graph is garbage-collected. This same precomputed table is what lets the multi-level nesting case self-resolve without any special-casing in the operators themselves: each level of `sh:and`/`sh:or`/`sh:xone`/`sh:not`/`sh:node`/`sh:qualifiedValueShape` independently re-checks the (now-transitive) condition and re-enters full-batch mode if needed, and `Shape.validate(focus=list_of_many)` already fans a list focus back out into a proper multi-key `focus_value_nodes` dict at each level - so the *only* change needed to fix nesting was making the detection recursive, not restructuring how any of the six components propagate a batch.

    The reachability computation itself went through two implementations. The first was a DFS with memoization and a stack-based cycle guard - it looked correct and passed every test written for it at the time, but a dedicated review pass (prompted by a direct question about whether cycles were actually exercised, not just handled in principle) found it was unsound: memoizing a node's answer using its cycle guard's early `False` return is only valid for that specific traversal order, not the node's true global reachability, so a shape whose only path to a cross-node predicate went *through* a cycle (`A` composes `B`, `B` composes `A`, `A` also composes `C` which declares `sh:uniqueValuesFor` - `B`'s correct answer is True via `A -> C`) would silently and permanently get memoized as `False` if the DFS happened to visit the cyclic neighbor before the real one - confirmed to be genuinely order-dependent (varies by `PYTHONHASHSEED`, since set iteration order for URIRef/str-keyed sets depends on it) rather than a corner case that never fires. Replaced with monotonic fixed-point/worklist propagation (repeatedly mark a node reachable if anything it composes is already marked, until nothing changes), which is correct regardless of traversal order or how a cycle is shaped - a standard technique for reachability-with-cycles, and simpler to reason about than DFS+memo would need to be made correct (which requires SCC condensation). Regression-tested across six fixed `PYTHONHASHSEED` values in subprocesses, not just the one seed a single test run happens to get.

    Composition of `sh:uniqueValuesFor` is now fully correct and data-sensitive through all six mechanisms, at any nesting depth, and through any mixture of them - confirmed with duplicate and non-duplicate data through `sh:and`/`sh:or`/`sh:xone`/`sh:not` (including multiple independent cross-node shapes in one list, mixed cross-node/ordinary lists, and blank-node vs. named nested shapes), two-level-deep `sh:and(sh:and(...))` nesting, direct `sh:node` (including zero-value-node and self-referencing-recursion edge cases), the indirect `sh:property`-path-then-`sh:node` case, `sh:qualifiedValueShape` (`sh:qualifiedMinCount` and `sh:qualifiedMaxCount` both), and `sh:and` containing a shape reached only via `sh:node` (mixed-mechanism nesting). `sh:qualifiedValueShapesDisjoint`'s sibling-shape check needed a second pass: the same dedicated review found the branch condition only checked whether the *primary* `sh:qualifiedValueShape` needed full-batch treatment, never a disjoint *sibling* shape - since pySHACL's own sibling-conformance check has the identical per-value pattern, a cross-node predicate reached only through a sibling silently fell through to the unpatched path and was vacuously satisfied regardless of real data. Fixed by hoisting sibling resolution into the branch condition itself (`_resolve_sibling_shapes`/`_needs_full_batch_for`), not just the already-committed-to mixed-evaluation path. Regression coverage: `tests/integration/test_native_component_composition.py` (117 cases as of this fix).

## Meta-SHACL Policy

All three profiles (`validation`, `rules`, `debug`) default `meta_shacl=True`; callers may override with `meta_shacl=False`. This is meant to catch malformed shape graphs early and avoid mistaking shape defects for data defects during debugging - but until this was investigated, that guarantee only held for SHACL 1.0/1.1 predicates.

**starshacl no longer delegates to pySHACL's own `meta_shacl` kwarg.** pySHACL's mechanism has no extension point (`pyshacl/entrypoints.py::meta_validate`/`with_metashacl_shacl_graph_cache` always validates against its own hardcoded, process-cached `shacl-shacl.pickle` - no parameter exists to supply additional or replacement meta-shapes), so it never learned about anything starshacl adds. This produced two confirmed problems under the default `meta_shacl=True`:

1. The 11 brand-new SHACL 1.2 predicates (`sh:someValue`, `sh:singleLine`, `sh:subsetOf`, `sh:rootClass`, `sh:uniqueValuesFor`, `sh:memberShape`, `sh:minListLength`, `sh:maxListLength`, `sh:uniqueMembers`, `sh:reifierShape`, `sh:reificationRequired`) had no meta-shape rule at all, so malformed uses silently passed (`sh:uniqueValuesFor "not a property"` conformed with zero complaint).
2. 8 shadowed predicates whose value space SHACL 1.2 *widened* - list-valued `sh:class`/`sh:datatype`/`sh:nodeKind`, path-valued `sh:equals`/`sh:disjoint`/`sh:lessThan`/`sh:lessThanOrEquals`, and `sh:closed sh:ByTypes` - were **actively rejected**: pySHACL's bundled meta-shapes still enforce the old SHACL 1.0/1.1 single-IRI/boolean-only shape, so a perfectly valid SHACL 1.2 shape using any of these forms raised `ReportableRuntimeError` under starshacl's own default settings, even though `starshacl/native_components.py` fully supports them. Confirmed empirically for all 8 forms; invisible previously because `tests/integration/test_native_component_composition.py`'s test harness always passes `meta_shacl=False` explicitly.

`starshacl/meta_shapes.py` replaces pySHACL's mechanism with starshacl's own preflight (`meta_validate`, wired into `validator.py::validate()` in place of forwarding the `meta_shacl` kwarg), assembling: pySHACL's own base `shacl-shacl.ttl` graph (loaded fresh into an independent copy - pySHACL's own process-wide cache is never mutated) with the 8 now-too-strict triples surgically removed (located dynamically via `sh:path`, never by hardcoded blank node ID - confirmed empirically that rdflib assigns fresh blank node identifiers on every separate parse of the same source file), plus `starshacl/assets/shacl12-validation-shapes.ttl` (additive well-formedness rules for the 11 new predicates, replacement rules for the 8 widened ones), plus `starshacl/assets/shacl12-presentation-shapes.ttl` (purely descriptive `rdfs:label`/`sh:name`/`sh:description`/`sh:order`/`sh:group` metadata, no validation semantics), plus any caller-supplied `meta_shapes_extra` graphs - all unioned into one graph. Removing the old triples matters: SHACL constraints on the same path combine via AND, so a relaxed rule added *alongside* an unremoved strict one would still reject the SHACL 1.2 form.

### Official SHACL 1.2 meta-shapes (`shsh:`) comparison

Until 2026-08-01, `starshacl/assets/shacl12-validation-shapes.ttl` was written independently, based on this project's own reading of the SHACL 1.2 Working Drafts - not derived from or diffed against any official meta-shapes artifact, because none had been identified. One exists: `w3c/data-shapes`'s `gh-pages` branch ships a separate, actively-developed `shacl12-vocabularies/shacl-shacl.ttl` (headed "THIS VERSION IS UNDER DEVELOPMENT BY THE DATA-SHAPES (SHACL 1.2) WG"), distinct from the file the vendored *test suite* happens to still use as its own "eat your own dogfood" fixture (`tests/vendor/shacl12-test-suite/tests/core/complex/shacl-shacl-data-shapes.ttl`, which is - confusingly - just the stale, unmodified 2017 SHACL 1.0/1.1 file, not the 1.2 one). Now vendored at `tests/vendor/shacl12-vocabularies/shacl-shacl.ttl` (see that directory's own `VENDORED_FROM.md`) and diffed both against our own supplementary shapes and against pySHACL's bundled 2017 base (to separate "genuinely new in the 1.2 draft" from "we already inherit this unmodified").

**Ahead of the official draft**: 6 of our 11 supported new predicates have no rule at all yet in the WG's own file - `sh:someValue`, `sh:uniqueValuesFor`, `sh:subsetOf`, `sh:rootClass`, `sh:reifierShape`, `sh:reificationRequired`. Confirmed by full-text search of the vendored snapshot, not just a sampled check. Nothing to reconcile here; just re-check when the WG catches up.

**Where both have coverage, mostly consistent**: `sh:singleLine`, `sh:minListLength`, `sh:maxListLength`, `sh:uniqueMembers` - byte-for-byte equivalent constraint semantics (same `sh:datatype`/`sh:maxCount`/`sh:minInclusive` values) in both files. `sh:class`/`sh:datatype`'s list-widening is functionally equivalent but implemented differently: the official file reuses the *new* `sh:memberShape` predicate recursively on itself (`sh:or ( [sh:nodeKind sh:IRI] [sh:memberShape [sh:nodeKind sh:IRI]] )`), ours uses a standalone reusable helper shape (`stsh:IRIOrListOfIRIsShape`) that walks the RDF-list structure directly - no identified behavioral difference, just a style difference (theirs is arguably more elegant, dogfooding the new predicate to validate itself).

**`sh:memberShape` divergence - fixed 2026-08-01, aligned with the official draft.** Ours (`stsh:ShapeReferenceShape`, still shared with `sh:someValue`/`sh:reifierShape`, which the official draft doesn't cover at all) required `sh:node shsh:ShapeShape` (accepted *either* a node-shape or a property-shape reference) with `sh:maxCount 1`. Now matches the official draft exactly: `sh:node shsh:NodeShapeShape` specifically (a property-shape reference is rejected - it has no natural "does this node conform" semantics without an implicit `sh:path`, unlike a node shape) with no cardinality cap. The literal-vacuously-passes guard (`sh:nodeKind sh:BlankNodeOrIRI`, needed because every one of `shsh:NodeShapeShape`'s own checks is a `maxCount 0` "must not have" rule, trivially true for a property-less literal) is kept inline rather than via the shared helper, since only `sh:memberShape` needs this narrower shape.

**4 genuine gaps found, all closed 2026-08-01** (checked against pySHACL's 2017 base first, to confirm each is new in 1.2, not something already inherited unmodified) - all added to `shacl12-validation-shapes.ttl`, all mirror the official draft's own shape/severity choices exactly:
- **`sh:DataGraph`/`owl:imports` well-formedness** (`stsh:DataGraphImportsShape`, `sh:severity sh:Info`) - the "SHACL Data Graphs" / `sh:DataGraph` concept, which neither pySHACL's bundled base nor our own supplementary shapes had any awareness of before.
- **`sh:in`/`sh:xone` satisfiability checks** (`stsh:InXoneSatisfiabilityShapes`, `sh:minListLength 1`) - a `sh:in`/`sh:xone` list with fewer than 1 member is unsatisfiable/trivial. `sh:in` matches the official draft exactly (`sh:severity sh:Warning`, confirmed genuinely soft - `allow_warnings=True` lets it through cleanly). `sh:xone` deliberately **diverges** from the official draft's own Warning choice, corrected to `sh:Violation`: pySHACL's own shape *loader* unconditionally rejects an empty `sh:and`/`sh:or`/`sh:xone` list with a raw `ShapeLoadError` the moment real validation runs, regardless of `allow_warnings` - confirmed live for all three predicates. Labeling it Warning would advertise a working opt-out that doesn't exist, trading a clear meta-shacl report now for an uglier crash later; Violation is an honest reflection of what's actually unconditionally enforced. Test coverage confirms the distinction precisely: `test_empty_sh_xone_list_still_rejected_by_meta_shacl_even_with_allow_warnings` asserts the rejection specifically comes from meta-shacl (checks for "metashacl" in the message, not just any exception) - written after discovering a naive `pytest.raises(Exception)` version passed regardless of severity, since pySHACL's own independent crash satisfies it either way; confirmed to fail correctly when the severity is temporarily reverted to Warning.
- **`sh:ignoredProperties`/`sh:languageIn` minimum-length check** (`stsh:IgnoredPropertiesLanguageInMinListLengthShapes`, `sh:minListLength 1`, no severity override so it's a hard `sh:Violation` like the official draft) - purely additive on top of the list-of-IRI/list-of-string member check pySHACL's 2017 base already has and which we already inherit unmodified (that part was never a gap).
- (`sh:shapesGraph`/`sh:entailment` `nodeKind sh:IRI` checks and `sh:and`/`sh:or`/`sh:xone` member-of-shapes checks were confirmed **not** gaps - already present, unmodified, in pySHACL's own 2017 base, pre-existing SHACL 1.0/1.1 concepts, not new in 1.2 - nothing to change there.)

**Implementation gap found and fixed 2026-08-01, while verifying the Info/Warning severities actually behave as intended**: `starshacl/meta_shapes.py::meta_validate` calls plain `pyshacl.validate()` directly and raises on any non-conforming result - by default this means `sh:Info`/`sh:Warning`-severity meta-shacl results block just as hard as `sh:Violation` does, since pySHACL's own default `sh:conformanceDisallows` set is `{Violation, Warning, Info}`, confirmed empirically (this is pySHACL's own correct, spec-compliant default - not a bug to route around, unlike `sh:Debug`/`sh:Trace`, which pySHACL has zero awareness of and which `validator.py::_annotate_conformance_disallows` separately corrects for the *main* validation pass; nothing in the meta-shapes graph uses those two severities, so that correction doesn't apply here). `meta_validate()` itself already forwards arbitrary `**kwargs` straight to `pyshacl.validate()`, so `allow_warnings=True`/`allow_infos=True` already worked correctly when passed directly to `meta_validate()` - the actual gap was one call site: `validator.py`'s own invocation (`meta_validate(shacl_graph, inference=..., extra_graphs=...)`) never forwarded the caller's `allow_warnings`/`allow_infos` from `StarShaclValidator.validate()`'s own `options` at all. Fixed by adding `allow_warnings=options.get("allow_warnings"), allow_infos=options.get("allow_infos")` to that call - a caller who opts into lenient data-conformance treatment for these two severities now equally opts into lenient meta-shacl preflight treatment for them, rather than the preflight silently ignoring that choice. `meta_validate` still can't reuse `StarShaclValidator.validate()`'s own pipeline wholesale for this (or anything else) - that pipeline's target-augmentation/native-component-shape-typing steps operate on `shacl_graph` specifically because it's about to be used as *shapes* against the caller's *data*, an inverted role from meta-validation (where the caller's shapes graph plays *data*, checked against the *meta-shapes* graph as shapes) - routing through it would apply that machinery backwards, and would need explicit `meta_shacl=False` to avoid infinite recursion (since `validate()` itself calls `meta_validate` internally). Test coverage: `test_allow_infos_on_validate_relaxes_info_severity_meta_shacl_check`/`test_allow_warnings_on_validate_relaxes_warning_severity_meta_shacl_check`, both confirmed to fail against the pre-fix call site via a temporary revert.

Test coverage: `tests/integration/test_meta_shapes_extensions.py` - `test_member_shape_value_must_be_a_node_shape_not_a_property_shape`/`test_member_shape_value_as_a_node_shape_still_passes`, and one reject/accept pair per closed gap (`test_data_graph_owl_imports_without_ontology_type_now_caught`, `test_empty_sh_in_list_now_caught`, `test_empty_sh_xone_list_now_caught`, `test_empty_sh_ignored_properties_now_caught`, `test_empty_sh_language_in_now_caught`, plus their "still passes" counterparts) - all 6 reject-side tests confirmed to genuinely fail against the pre-fix shapes file via a temporary in-place revert, not just checked once at the end.

Re-fetch and re-diff `tests/vendor/shacl12-vocabularies/shacl-shacl.ttl` periodically (no sync script exists for it yet, unlike the test suite's own `scripts/sync_w3c_shacl12_suite.py`) - it's an explicit, unstable work in progress (no version/date stamp, still missing 6 of the 11 predicates this project already implements), so re-check when the WG's draft grows.

**Dual-use by design**: this is also meant to work as a standalone artifact for downstream SHACL tooling (e.g. a shapes-graph editor), not just starshacl's internal preflight. The two `.ttl` files are real, hand-editable files (not Python string literals), ship with the installed package (`[tool.setuptools.package-data]`), and are deliberately *not* a vendored fork of pySHACL's/W3C's SHACL 1.0/1.1 base - a downstream consumer composes them with their own base and their own additional rules the same way starshacl does, via `meta_shapes_extra` (or the equivalent merge for a non-Python consumer): validation and presentation concerns are separate files precisely so a consumer can take either independently.

Regression coverage: `tests/integration/test_meta_shapes_extensions.py` (21 cases - all 8 previously-rejected forms now pass, malformed new-predicate uses now caught cleanly instead of silently passing or crashing raw, the `meta_shapes_extra` hook enforced end-to-end, and the existing `tests/integration/test_meta_shacl_integration.py` ill-formed-shape regression control still passes unchanged).

- **Harness gap**: `conformance-disallows-001` needed the test harness to read `mf:result`'s `sh:conformanceDisallows` and configure `validate()` accordingly - fixed in `test_w3c_validate.py::_conformance_disallows_kwargs`.

- **`sh:values` used directly on a property shape** (a `sh:select`/`sh:sparqlExpr`-computed value set overriding `sh:path`'s own value computation, checked by every other constraint on that shape) - `property-select-001`/`property-sparqlExpr-001` - implemented by patching `pyshacl.shape.Shape.value_nodes` (the one method every constraint component already calls generically), so no per-constraint-component special-casing was needed. Deliberately distinct from `sh:PropertyRule`'s own, unrelated "new `sh:values`" mechanism (a `sh:rule` shorthand for *constructing* triples during `apply_rules()`, coincidentally sharing the same predicate name) - that one remains genuinely unimplemented, see the "Not Covered / Deferred" table below.

**Fixed 2026-08-01** (moved out of this phase's xfail list): `subsetOf-002` (compound sequence-path comparison, `( ex:property2 ex:property3 )`) - `SubsetOfConstraintComponent.__init__` (`native_components.py`) previously only accepted a simple-IRI comparison path (`isinstance(self.other_path, URIRef)`, silently conforming otherwise). Now converts the comparison path via pySHACL's own `pyshacl.helper.path_helper.shacl_path_to_sparql_path` - already used elsewhere in pySHACL for ordinary `sh:path` evaluation - so any SHACL property path (sequence, inverse, alternative, etc.) works, not just an IRI. This was a narrower "do the minimal thing" scoping choice from the original implementation, not a structural limitation.

### Phase 2 - `sht:EvalNodeExpr` (142 passed, 1 xfailed)

Exercises `starshacl/node_expressions.py` directly. Found and fixed, in `starshacl` itself:

- **A core correctness bug affecting nearly every `shnex:` operator that takes a list-of-values argument** (`count`/`min`/`max`/`sum`/`orderBy`/`limit`/`offset`/`flatMap`/`findFirst`/`matchAll`/`remove`/`filterShape`/`nodesMatching`, via `_nodes_arg()`/`shnex:nodes`) - a bare RDF list argument (e.g. `shnex:count ( 4 3 3 )`) reached pySHACL's own `nodes_from_node_expression`, which has no code path for a plain list-of-constants at all (only `sh:union`/`sh:intersection` get list treatment, by unwrapping the list themselves) - a 2+-element list misfired as a bogus FunctionExpression call, a 0-1-element list raised `StopIteration`. Fixed in `eval_expr()`/`_sub()` (see that module's own docstring for the full, corrected root-cause writeup - the diagnosis was refined twice during investigation).
- A cluster of smaller, independently-confirmed bugs surfaced once list arguments worked: `orderBy`'s per-item comparator didn't rebind the `"focusNode"` scope variable (silently comparing every item against the same stale value, leaving the list unsorted); a missing comparator value sorted last instead of first; `shnex:var` raised on an unbound variable instead of returning no nodes (SPARQL's own unbound-variable semantics); a triple-term or `DirLangString` constant crashed instead of evaluating to itself; `shnex:distinct`/`shnex:remove` used RDF *value* equality (via Python's `in`) instead of RDF 1.2's own literal *term*-equality (lexical form must match, not just value); `shnex:intersection` didn't deduplicate its result; `shnex:sum` used `Literal(python_float)` for its result, which always infers `xsd:double` regardless of input types instead of following SPARQL/XPath's own numeric type promotion rules; `shnex:conformsToShape` was entirely unimplemented (not in the module's own operator list).
- **The entire `sparql:` namespace** (`http://www.w3.org/ns/sparql#`, ~74 SPARQL 1.1/1.2 built-in functions/operators exposed as node expressions - e.g. `sparql:strlen`, `sparql:greater-than`, `sparql:isTriple`) was completely unimplemented, a wholly separate vocabulary from `shnex:`. Implemented in a new module, `starshacl/sparql_node_expressions.py`, by translating each call into a small `SELECT (<expr> AS ?result) WHERE {}` SPARQL query evaluated via `data_graph.query()` with arguments bound through `initBindings` - reuses rdflib's own (and, for the RDF-1.2-specific functions, `starlayergraph`'s own) already-correct SPARQL evaluator wholesale instead of hand-reimplementing ~74 functions. `sparql:bound`/`coalesce`/`if` (need to *not* eagerly evaluate every argument) and the `DirLangString`-introspection functions (`hasLang`/`hasLangdir`/`langdir`/`strlangdir`, which operate on starlayergraph's own internal type, not anything rdflib's SPARQL engine natively knows) are evaluated directly in Python instead.
- Found and fixed one more `starlayergraph` bug along the way (`shnex:distinct`/`remove`'s term-equality tests specifically needed it): typed-literal construction silently discarded a non-canonical lexical form (`"04"^^xsd:integer` became `"4"^^xsd:integer`) - see `docs/starlayergraph-upstream-change-log.md`'s 2026-07-31 entry.
- **Found and fixed a separate real-pipeline wiring gap, not just an `eval_expr()`-level one**: `starshacl/validator.py` only called `patch_node_expressions_for_shnex()` (which wires *both* `shnex:` and, as of this session, `sparql:` support into pySHACL's real dispatch) when the shapes graph contained a `shnex:`-namespaced predicate - a shapes graph using *only* `sparql:` node expressions (a legitimate, W3C-suite-confirmed case) never triggered it, so `sparql:` expressions crashed via `validate()`/`apply_rules()` even though `eval_expr()`/`sparql_node_expressions.py` themselves were already correct. Fixed by widening the trigger check to also look for `sparql:`-namespaced predicates.
- **Found and fixed a second, deeper real-pipeline gap specific to RDF 1.2 triple terms**, raised by direct user challenge ("are we using starlayergraph so we get triple terms?") rather than by the test suite itself: in real `validate()`/`apply_rules()` usage, the `data_graph` a node expression actually receives is pySHACL's own `RdfLibDataGraph` wrapping a *plain* `rdflib.Graph` with no triple-term awareness or adapter reference at all - so `sparql:isTriple`/`subject`/`predicate`/`object` over a real, data-graph-sourced triple term silently produced wrong (non-conforming) results even though `eval_expr()`/`sparql_node_expressions.py`'s own direct-call test coverage all passed. Fixed via a three-layer chain: decoding the raw value via the shared `TripleTermAdapter`, converting the result to a plain 3-tuple, and registering it into a disposable scratch `StarLayerGraph` before querying (since `starlayergraph`'s `_encode_init_bindings` deliberately resolves an unregistered triple-term value to an unmatchable fresh `BNode`).
- **This same investigation surfaced one narrower regression, since fixed directly in `starlayergraph`**: constructing a *new* triple term via `sparql:triple`/`TRIPLE(?a,?b,?c)` from three initBindings-only arguments (no WHERE-clause graph pattern) used to return zero SPARQL result rows, even though *verifying/decomposing* an existing triple term worked correctly. The `triple-example` fixture had previously passed, but only by accident (its own `mf:result` content coincidentally registered the exact triple term as an ordinary parsing side effect) - masking the gap a *second* time, since the harness's imperative `pytest.xfail()` call never self-corrects the way a `strict=True` decorator would once a fix lands underneath it. Root-caused to `starlayergraph/query/sparql12_to_11.py`'s SPARQL 1.2-to-1.1 rewriter conflating "non-ground" with "must be a graph-pattern match" regardless of whether the triple term appeared in an actual pattern-term slot or a plain expression position - fixed by tracking paren-nesting depth to distinguish the two. See `docs/starlayergraph-upstream-change-log.md`'s 2026-07-31 "Fixed" entry for the full root-cause writeup.

All fixes verified against the real vendored fixtures iteratively (fix -> re-run -> confirm the specific named failure now passes), not just checked once at the end.

The 1 remaining Phase 2 xfail is a deliberately-unpatched fixture-formatting quirk, not open work:

- **`seconds-example`**: `Builtin_SECONDS()` returns `"0"` for zero seconds, but this fixture expects the zero-padded `"00"`. Note `"0"` is *not* actually XSD decimal's true canonical form either (that's `"0.0"` - the same decimal-point-required rule the `CEIL`/`FLOOR`/`ROUND`/division fix below enforces) - but zero-padding to two digits isn't XSD canonicalization at all, it's ISO-8601-style time formatting that `SECONDS()`'s own specification (a numeric `xsd:decimal` *value*, not a substring of the input's lexical form) doesn't require. Looks like a fixture-authoring artifact rather than a genuine interoperability requirement, corroborated against three independent engines (rdflib, Fuseki/Jena-ARQ, Oxigraph - all three agree with each other and disagree with the fixture); left unpatched since even a correct canonical-form fix would produce `"0.0"`, not `"00"`. Write-up for reporting upstream to `w3c/data-shapes`: `docs/w3c-shacl12-test-suite-issues.md`.

**Fixed 2026-08-01** (moved out of this phase's xfail list): 5 of the 6 fixtures previously grouped under "confirmed plain-`rdflib` bug/quirk, out of scope" - `multiply-example`, `ceil-example`, `floor-example`, `round-example`, `divide-example` - all traced to two genuine rdflib bugs (`MultiplicativeExpression` never applying SPARQL 1.1's numeric type-promotion rules for `*`; `CEIL`/`FLOOR`/`ROUND`/division losing XSD decimal's required canonical `.0` lexical form), both now patched at import time in `starlayergraph` itself (`starlayergraph/query/operator_patches.py`) rather than left as permanent, unfixable gaps - see `docs/starlayergraph-upstream-change-log.md`'s 2026-08-01 entry for the full root-cause writeup and why this is safe to patch globally.

**Fixed 2026-08-01** (moved out of this phase's xfail list): `instancesOf-base-class` - `shnex:instancesOf` previously matched `rdf:type` directly against the data graph with no subclass awareness at all, relying on the caller's `inference=` setting like the rest of this codebase. Now walks `rdfs:subClassOf` via the same `_transitive_subclasses` helper `sh:ShapeClass`'s implicit-target discovery uses (searching both the data and shapes graphs), independent of `inference=` - a deliberate departure from the "defer to the caller" convention, justified because a node expression has no access to whatever `inference=` the caller passed to `validate()`/`apply_rules()` (unlike a constraint component, which always runs inside that context). See `starshacl/node_expressions.py`'s module docstring for the full reasoning.

### Phase 3 - `sht:Infer` (6 passed, 0 xfailed)

Exercises `StarShaclValidator.apply_rules()` end-to-end (`tests/w3c_shacl12/test_w3c_infer.py`): snapshot the data graph, run `apply_rules()`, diff the resulting graph's triples against the snapshot, compare the added set against `mf:result`'s `rdf:List` of `( subject predicate object )` triples. All 6 entries live in `tests/sparql/rules/`, reachable from the top-level manifest via `sparql/manifest.ttl`'s `mf:include <rules/manifest.ttl>` (distinct from the separate, SRL-text-syntax `tests/rules/` directory, which remains out of scope - see "Not Covered / Deferred" above).

- **`global-symmetric`** exercised a genuine new SHACL 1.2 feature: a "global" `sh:SPARQLRule` node not referenced by any shape's `sh:rule` property, meant to execute once against the whole graph regardless of target matching - invisible to pySHACL's own `gather_rules()`, which only discovers rules reachable from a shape. Implemented in `validator.py` (`_global_sparql_rules`/`_global_sparql_rule_triples`, called from `apply_rules()`), scoped to `sh:SPARQLRule` only - see the "Not Covered / Deferred" table's row for why `sh:TripleRule` wasn't extended the same way.

**Fixed 2026-08-01** (moved out of this phase's xfail list): the 4 `rectangle-*` fixtures (`rectangle-simple`, `rectangle-condition`, `rectangle-order`, `rectangle-prefixes`) all hit the same `MultiplicativeExpression` rdflib bug as Phase 2's `multiply-example` (`?width * ?height` for two `xsd:integer` operands evaluated as `xsd:decimal`, not `xsd:integer`) - now fixed by the same `starlayergraph` monkeypatch. Every other aspect of `sh:SPARQLRule` execution these fixtures exercise (CONSTRUCT templates, `$this` binding, `sh:condition`-gated applicability, `sh:order` sequencing across two rules, and ambient `sh:declare` prefix discovery via `sh:ShapesGraph` for `sh:rule` specifically) was already correct.
