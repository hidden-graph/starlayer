# Changelog

## Unreleased

### Added

- **`format="manchester"` (alias `"omn"`) for `StarLayerGraph.parse()`.** A native, pure-Python parser for OWL 2 Manchester Syntax (`starlayergraph/parsers/manchester_parser.py`) - no Java/OWL API dependency, consistent with every other format this project reads. Covers all frame types (`Class:`, `ObjectProperty:`, `DataProperty:`, `AnnotationProperty:`, `Individual:`, `Datatype:`) and their clauses, the full class-expression grammar (`and`/`or`/`not`/`that`, `some`/`only`/`onlysome`/`value`/`Self`, qualified and unqualified `min`/`max`/`exactly`, `{...}` enumeration, `inverse`), data ranges with facet restrictions (`xsd:int[>= 0, <= 150]`, DataOneOf, data `and`/`or`), property chains, `HasKey:`, `DisjointUnionOf:`, positive and negative `Facts:`, frame-level `Annotations:`, and every top-level Misc axiom - mapped to RDF per the OWL 2 Mapping to RDF Graphs spec. Inline per-axiom annotations are supported too (`SubClassOf: Annotations: rdfs:comment "why" B` → `owl:Axiom` reification alongside the plain axiom triple, on every clause where one list item maps to one axiom triple), distinct from the simpler, non-reifying frame-level `Annotations:` clause. Deliberately unsupported (raising `ManchesterSyntaxError`, never silently dropped or mis-parsed): SWRL `Rule:`, inline annotations on the six top-level Misc axioms specifically (their pairwise-chain/`AllDisjoint*` encoding has no single item-to-triple correspondence to reify), and a couple of reserved-but-dead OWL API keywords. Full conformance tracking, including what's deliberately not matched and why, in `docs/manchester_syntax_gap_analysis.md` - derived by decompiling OWL API 5.1.20's own keyword table plus empirical cross-checks against its real parser (an external, uncommitted oracle - not a project dependency) via `starlayergraph.compare.isomorphic()`. Tests: `tests/unit/test_manchester_parser.py`.

- **`format="manchester"` (alias `"omn"`) for `StarLayerGraph.serialize()`** - the reverse direction (`starlayergraph/serializers/manchester.py`). A genuinely different problem from parsing: reconstructs the same internal AST `manchester_parser.py` builds, but by *recognizing* RDF patterns (blank-node restrictions, `rdf:List` chains, `owl:Axiom` reification blocks) rather than deterministically producing them, then renders that AST to text with precedence-aware parenthesization. Targets the same construct coverage as the parser, with a few reconstructions deliberately scoped out because the RDF shape involved is inherently ambiguous, not from missing effort (`SuperClassOf:`/`SuperPropertyOf:` and `onlysome` are pure surface sugar with no RDF-level trace, so they always come back in their expanded/canonical form; `EquivalentClasses:`/`SameIndividual:`/binary `DisjointClasses:`/`DisjointProperties:`/`DifferentIndividuals:` Misc axioms are RDF-indistinguishable from the same triples split across per-subject frames, so those always come back that way too - only the unambiguous >2-member `AllDisjointClasses`/`AllDisjointProperties`/`AllDifferent` shape is reconstructed as a real Misc axiom). Verified by round-tripping `parse_manchester()` output through the serializer and back (isomorphic across every construct tested) and by confirming the real OWL API oracle accepts the serializer's output without a syntax error. Tests: `tests/unit/test_manchester_serializer.py`.

- **`engine=` parameter for `StarLayerGraph.infer(profile="owl-dl")`, plus a second engine to choose from.** Previously `profile="owl-dl"` meant exactly one reasoner (HermiT via `owlready2`); now the caller picks per call: `engine="hermit"` (default, unchanged behavior - sound and complete for all of OWL 2 DL) or `engine="rustdl"` (new - a pure-Rust SROIQ reasoner, no JVM, via `starlayergraph/graph/owl_dl_rustdl.py`; sound but only empirically near-complete on full SROIQ, and its property-assertion materialization is a documented "sound under-approximation" that omits disjunctive-derived edges - confirmed live against this project's own logic-puzzle guide example, it reproduces disjunctive *class* entailments but not forced *property* assignments the way `engine="hermit"` does). An invalid `engine=` value raises `ValueError`; passing a non-default `engine=` for any profile other than `"owl-dl"` also raises `ValueError`, rather than silently doing nothing. **`owlready2` moved from a core dependency to the optional `starlayergraph[hermit]` extra**, alongside the new `starlayergraph[rustdl]` extra (`rustdl>=0.4`) - both engines now have the identical "not installed by default, opt in, loud actionable `RuntimeError` naming the exact `pip install` command if missing at call time" shape, rather than one being special. Tests: `tests/unit/test_infer_owl_dl.py` (updated), `tests/unit/test_infer_owl_dl_rustdl.py` (new).

- **`entailment="direct"` for `StarLayerGraph.query()`** - the query-time counterpart to `infer(profile="owl-dl", engine=...)`, mirroring `entailment="owl-rl"`'s design exactly: queries a live union of `self` and a small cached OWL-DL entailment delta, refreshed on the same `infer=`-governed cadence. New `engine=` kwarg on `query()` (`"hermit"` default / `"rustdl"`) selects which reasoner computes that delta - only meaningful with `entailment="direct"`, raises `ValueError` if combined with any other `entailment=`. Caching is keyed per-engine (`self._owl_dl_cache[engine]`), not a single shared slot, so switching engines between calls on an unmutated graph doesn't invalidate the other engine's cached result. `query()`'s own docstring carries a prominent cost warning `entailment="owl-rl"` never needed: genuine tableau DL reasoning is routinely orders of magnitude slower than `owlrl`'s forward chaining, and `infer="changed"` only bounds how *often* that cost is paid, not how *expensive* any single recomputation is. Raises `InconsistentOntologyError` uncaught, same contract `infer(profile="owl-dl")` already has. Tests: `tests/unit/test_entailment_direct.py`.

- **Native (`backend="rdf-1.2"`) graphs no longer need an explicit `identifier=` to keep `query()`/`update()` and `infer()`/`triples()` looking at the same data.** Previously, a native `StarLayerGraph` constructed without `identifier=` got a random `BNode` (rdflib's own default) - `query()`/`update()` send SPARQL text straight through unscoped (the endpoint's own default graph), while `infer()`/`triples()`/plain iteration wrap patterns in `GRAPH <self.identifier> { ... }` unless `self.identifier` is exactly `DATASET_DEFAULT_GRAPH_ID`, so the two halves of the API silently disagreed about which graph was "self's data" - no error, just an empty result from the latter. `StarLayerGraph.__init__` now defaults `identifier=DATASET_DEFAULT_GRAPH_ID` automatically whenever `backend='rdf-1.2'` and the caller supplies no identifier of their own (a positionally- or explicitly-passed real identifier is left untouched). Tests: `tests/unit/test_conformance.py::TestNativeIdentifierDefault`, `tests/integration/test_entailment_native.py::test_no_explicit_identifier_needed_anymore`.

- **Manchester Syntax's own AST as RDF** (`starlayergraph/ontology/to_ast_rdf.py` + `ontology/manchester-ast-ontology.ttl`/`manchester_shapes.ttl`), mirroring the sibling `starsparql` package's `salg:` treatment of SPARQL query algebra: `parse_manchester_ast()` reuses `manchester_parser.py`'s own tokenizer/grammar unchanged (via a small set of previously-no-op AST-capture hooks) to encode a document's frames/clauses/class-and-property-expressions/data-ranges as `manch:` RDF *before* OWL compilation - one level upstream of, and a genuinely different capability from, the existing parser/serializer pair, which both go through compiled OWL RDF and so can't recover `SuperClassOf:`/`SuperPropertyOf:`'s direction or `onlysome`'s desugaring. `rdf_ast_to_manchester_ast()`/`manchester_ast_to_text()` decode a `manch:` graph back into a real, executable `Document` object and then Manchester text (a genuinely new serializer, not adapted from the OWL-RDF-based one), so a document can be encoded, edited via plain RDF graph surgery, and re-serialized. Fidelity scope matches `salg:`'s own bar for SPARQL - the parser's existing internal AST as-is, not a new non-desugaring surface tokenizer pass - with one correctness-driven exception: `SuperClassOf:`/`SuperPropertyOf:` carry an explicit `manch:reversed` flag, since (unlike every other spelling choice) which keyword was written flips which side of the compiled `rdfs:subClassOf`/`subPropertyOf` triple the frame's own subject lands on - found via this feature's own round-trip test, which would otherwise have silently reversed re-serialized semantics. SHACL shapes (`manchester_shapes.py`) validate structural well-formedness, including per-clause-class item-value-type checks (e.g. a `DataPropRangeClause`'s items must be a `DataRange`, not a `ClassExpression`) and per-Misc-axiom item-family checks. Guide: `docs/guides/05g-manchester-syntax-as-rdf.ipynb`. Tests: `tests/unit/test_manchester_ast.py`, `tests/unit/test_manchester_ast_shapes.py`.

- **A SKOS ontology and SHACL shapes graph** (`starlayergraph/ontology/skos-ontology.ttl` + `skos_shapes.ttl`/`.py`). Unlike Manchester/SPARQL, SKOS needs no encode/decode layer at all - a thesaurus is already plain RDF the moment it's authored - so this is purely a validator pair: `skos-ontology.ttl` is an OWL/RDFS restatement of the W3C SKOS Reference's own formal axioms (`# S<n>` comments cite the spec's own numbered axioms directly, over the real `skos:` namespace, not a project-local one), and `skos_shapes.ttl` checks the same document's own numbered "Documented Consistency and Integrity Conditions" - class disjointness (S9: `Concept`/`ConceptScheme`; S37: `Collection` and, listed explicitly, `OrderedCollection`), lexical-label constraints (S13 pairwise-disjoint `prefLabel`/`altLabel`/`hiddenLabel`; S14 at most one `prefLabel` per language), semantic-relation domain/range (S19/S20: `Concept` on both ends of `broader`/`narrower`/`related`/etc.), and property disjointness (S27: `related` vs. the hierarchical relations; S46: `exactMatch` vs. `broadMatch`/`narrowMatch`/`relatedMatch`) - all expressed in SHACL Core alone (`sh:disjoint`, `sh:not`+`sh:class`, `sh:targetSubjectsOf`/`sh:targetObjectsOf`). One shape needs `sh:sparql` (the only one in this file): `OrderedCollectionMemberListConsistencyShape` checks the spec's own §9.4 prose expectation - not one of the numbered S-conditions - that `skos:memberList` and `skos:member` describe the same set for a given `skos:OrderedCollection`, walking the `rdf:List` via `rdf:rest*/rdf:first` and comparing both directions. One non-normative best-practice recommendation is included too - `ConceptPrefLabelRecommendedShape` ("a `Concept` should have a `prefLabel`") - at `sh:severity sh:Info`, so it never flips `conforms` on its own: `skos_shapes.py::validate()` now passes `allow_infos=True` through unconditionally, since pyshacl's own `conforms` computation doesn't actually distinguish severity levels without it (confirmed empirically - an `sh:Info`-only result still flipped `conforms` to `False` until this flag was added; `pyshacl.shape.Shape.validate()`'s `allow_infos`/`allow_warnings` executor flags are what a caller has to opt into for `sh:Info`/`sh:Warning` results to stay non-blocking). One real bug found and fixed while building the rest of this: validating with `ont_graph=skos_ontology_graph()` + `inference="rdfs"` (the `manch:`/`salg:` pattern) made the S19/S20 shape tautologically vacuous, since the ontology's own faithfully-restated `rdfs:domain`/`range` axioms on `skos:semanticRelation` auto-entail exactly the `skos:Concept` type that shape exists to check for - `skos_shapes.py::validate()` deliberately runs with neither, and the three disjointness shapes list `skos:OrderedCollection` explicitly rather than relying on RDFS `rdfs:subClassOf` entailment from `skos:Collection`. Tests: `tests/unit/test_skos_shapes.py`.

- **`StarLayerGraph.derive(template_shape=None, *, ignored_properties=None, use_default_ignored_properties=True)`** - infer a SHACL shape from a graph's own data (`starlayergraph/graph/shape_derivation.py`), one `sh:NodeShape` per distinct `rdf:type` found (deriving from classes, never per-node or heuristic clustering). Closed by construction, with `rdf:type` always in `sh:ignoredProperties` (pyshacl's own `ClosedConstraintComponent` doesn't exempt it automatically - confirmed by reading its source, not assumed) plus an opt-outable default bookkeeping list (`rdfs:label`/`comment`, `dcterms:created`/`modified`). Value-kind analysis recognizes four first-class kinds, not three - `Literal`/`URIRef`/`BNode`/**`TripleTerm`** (`sh:nodeKind sh:TripleTerm`, or SHACL 1.2's list-valued `sh:nodeKind` for a genuinely mixed-kind property, e.g. `sh:nodeKind ( sh:IRI sh:TripleTerm )`) - real RDF-1.2 awareness, not an afterthought. With a `template_shape`, does a "best-effort validate-and-relax everything" merge: every SHACL Core constraint component with a principled data-driven fix (`sh:minCount`/`maxCount`, `sh:datatype`, `sh:class`, `sh:nodeKind`, `sh:min/maxInclusive`/`Exclusive`, `sh:min/maxLength`, `sh:languageIn`, additive `sh:in` widening) is recomputed from the *true* current data, not patched around the one violating value; components with no generic fix (`sh:pattern`, `sh:equals`/`sh:disjoint`/`sh:lessThan(OrEquals)`) are dropped with an `rdfs:comment` note explaining why; opaque `sh:sparql`-based/custom constraint components are left untouched (also annotated) since there's no way to know whether a failure is a real data problem or a genuinely important check. Any predicate/class present in the data with no matching template coverage gets a freshly-derived addition. Every result is self-checked via a real `starshacl.validate()` call before being returned - a bug in this algorithm raises rather than silently shipping a shape that fails against its own source data. **Always goes through `starshacl`, never bare `pyshacl`** - a template shape or the data itself may be genuine RDF 1.2 content (triple terms) that only `starshacl` understands - `packages/graph` now depends on `packages/shacl` for this, an intentional circular dependency mirroring the existing `graph`⇄`sparql` one this monorepo already ships (confirmed working the same way; the actual Python import stays lazy/inside the function to avoid a circular import at load time). Tests: `tests/unit/test_shape_derivation.py`.

- **`starlayergraph.ontology.list_shacl_libraries()`/`get_shacl_library(name)`** - a registry of every ontology/SHACL-shapes pair this stack ships (`starlayergraph/ontology/registry.py`), so a caller can discover and load any of them by name without knowing which package or file it actually lives in. Four libraries registered: `"manchester"` (`manch:`), `"skos"` (`skos:`), `"sparql"` (`salg:`, from the sibling `starsparql` package), and `"shacl"` (the SHACL 1.2 meta-shapes themselves, from `starshacl` - the one entry with no separate OWL ontology, `ontology_graph=None` rather than a stub). Each `ShaclLibrary` exposes lazy `ontology_graph()`/`shapes_graph()`/`validate()` loaders - `list_shacl_libraries()` never requires every optional dependency (`pyshacl`, etc.) installed just to enumerate what exists; only calling a library's own loader needs what that library's own module needs. Lives in `starlayergraph` (not `starshacl`/`starsparql`) since it's the only package already depending on both siblings. Deliberately **not** registering "generic RDF" (no SHACL shape for a generic RDF editor exists yet) or "OWL RDF" (names no concrete artifact in this codebase) - both left out entirely rather than shipped as a stub whose loaders would immediately raise. Tests: `tests/unit/test_ontology_registry.py`.

### Fixed

- **Blank-node label collision across repeated `StarLayerGraph.parse()` calls.** Turtle 1.2 parsing (`format="turtle12"`/`"longturtle12"`) minted anonymous-node labels (`_:sl_N`, `_:si_N`) from a counter that restarted at 0 on every call. Calling `.parse()` more than once on the same graph, where more than one call's Turtle body contained an anonymous `[ ... ]` node, could silently merge unrelated blank nodes that happened to land on the same number into a single node, corrupting the graph. Found live while building a guide example that used two separate `.parse()` calls; every call site elsewhere in this codebase happened to use a single call, which is why this had never surfaced. Fixed by seeding the counter with a random per-call offset (`starlayergraph/parsers/turtle_parser.py`) so labels from different calls can never collide. Regression test: `tests/unit/test_turtle_parser.py::TestBlankNodeUniquenessAcrossCalls`.

- **`infer(profile="owl-dl", engine="rustdl")`'s confirmed hang on a common OWL 2 DL idiom - now caught pre-flight instead of hanging.** A property declared both `owl:FunctionalProperty` and `owl:InverseFunctionalProperty`, used in a `someValuesFrom` restriction whose filler is an `owl:oneOf` nominal enumeration (the only OWL-DL-expressible way to force a genuinely disjunctive property assignment at all - `05e-owl-dl-reasoning.ipynb`'s own §1.b/§4 use it throughout, not an exotic construct), hangs RustDL's `materialize_inferred_class_assertions()` indefinitely. `owl_dl_rustdl.py::_check_rustdl_hang_risk()` catches this via a real `starshacl` SHACL shape over the *compiled* OWL 2 RDF Mapping triples (`owl:Restriction`/`onProperty`/`someValuesFrom`/`oneOf`) - deliberately not gated through this project's own `manch:` vocabulary, since the pattern looks identical regardless of how the ontology was authored (Manchester Syntax, Turtle, RDF/XML, or direct triple insertion) and a `manch:`-only check would silently miss every non-Manchester-authored case - raising `rustdl.UnsupportedAxiomError`, the same exception type the existing `HasKey:`/role-chain rejections already raise. Re-running the guide's own §1.b puzzle against the currently-installed `rustdl` version during this fix surfaced a second, more significant finding: that example previously demonstrated `materialize_inferred_property_assertions()`'s documented "sound under-approximation" behavior (a completed call, silently missing the forced-by-elimination pairings) - it no longer does; it now hangs, a confirmed *change in failure mode* between whatever `rustdl` version that claim was last verified against and 0.4.31 (now installed), silent until this guide was re-executed. `owl_dl_rustdl.py`'s own module docstring corrected accordingly, and a new "Tracking rustdl's own evolving capabilities" section added to `CLAUDE.md` - this project has no live, re-verifiable example of the property-assertion under-approximation behavior anymore, only RustDL's own stated design intent for it. `05e-owl-dl-reasoning.ipynb` §5/§6 updated and re-executed to demonstrate the fast rejection instead of the stale framing. Tests: `tests/unit/test_infer_owl_dl_rustdl.py::TestOwlDlRustdlHangRisk`.

- **`infer(profile="owl-dl", timeout=...)`/`query(entailment="direct", timeout=...)` - a general wall-clock timeout, shared by both engines.** Defense-in-depth for any hang neither engine has a known, structurally-detectable pattern for yet (the one *known* RustDL hang pattern above is already caught separately, in milliseconds, before ever reaching this timeout). Default `starlayergraph/graph/_timeout.DEFAULT_TIMEOUT_SECONDS` (120s); pass `timeout=None` to disable entirely. Implemented as a real subprocess/process-*group* kill (`_timeout.run_with_timeout()`), not a cooperative cancellation - confirmed empirically that neither a JVM subprocess wait (HermiT, via `owlready2.sync_reasoner()`) nor an opaque native PyO3 call (RustDL) reliably yields back to Python's own interpreter loop for a `signal.alarm()`/`threading.Event`-based approach to work, and a background thread can't actually be killed from Python once started - only OS-level process termination reliably bounds either one. The child process calls `os.setpgrp()` as its first action so `os.killpg()` on timeout takes down the *entire* process tree, not just the immediate child - critical for HermiT specifically, whose own call chain spawns a further `java` subprocess that would otherwise be orphaned and left running (the exact bug class already found and fixed elsewhere in this project); confirmed via a live test that spawns a real grandchild process and verifies it doesn't survive the kill. Uses `multiprocessing`'s `"spawn"` start method explicitly (not the platform default), since forking a process with JVM/native library state already loaded is a real, documented risk. The actual blocking reasoner call in each engine (`owl_dl.py::_run_hermit_subprocess()`, `owl_dl_rustdl.py::_run_rustdl_subprocess()`) is now a module-level, picklable-by-reference function run inside this subprocess, with only a small status tuple (not the full result) crossing the process boundary via a queue - the real ontology/results still go through temp files, matching this project's own already-established pattern for both engines. Raising `_timeout.ReasoningTimeoutError` (a `RuntimeError` subclass) never leaves an orphaned process behind. Tests: `tests/unit/test_timeout.py` (the mechanism itself, via synthetic workers - fast success, a real hang, a crashed-without-a-result child, and the grandchild-survival check), plus wiring coverage in `test_infer_owl_dl.py::TestOwlDlTimeout`, `test_infer_owl_dl_rustdl.py::TestOwlDlRustdlTimeout`, and `test_entailment_direct.py`.
