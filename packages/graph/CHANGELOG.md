# Changelog

## Unreleased

### Added

- **`format="manchester"` (alias `"omn"`) for `StarLayerGraph.parse()`.** A native, pure-Python parser for OWL 2 Manchester Syntax (`starlayergraph/parsers/manchester_parser.py`) - no Java/OWL API dependency, consistent with every other format this project reads. Covers all frame types (`Class:`, `ObjectProperty:`, `DataProperty:`, `AnnotationProperty:`, `Individual:`, `Datatype:`) and their clauses, the full class-expression grammar (`and`/`or`/`not`/`that`, `some`/`only`/`onlysome`/`value`/`Self`, qualified and unqualified `min`/`max`/`exactly`, `{...}` enumeration, `inverse`), data ranges with facet restrictions (`xsd:int[>= 0, <= 150]`, DataOneOf, data `and`/`or`), property chains, `HasKey:`, `DisjointUnionOf:`, positive and negative `Facts:`, frame-level `Annotations:`, and every top-level Misc axiom - mapped to RDF per the OWL 2 Mapping to RDF Graphs spec. Inline per-axiom annotations are supported too (`SubClassOf: Annotations: rdfs:comment "why" B` → `owl:Axiom` reification alongside the plain axiom triple, on every clause where one list item maps to one axiom triple), distinct from the simpler, non-reifying frame-level `Annotations:` clause. Deliberately unsupported (raising `ManchesterSyntaxError`, never silently dropped or mis-parsed): SWRL `Rule:`, inline annotations on the six top-level Misc axioms specifically (their pairwise-chain/`AllDisjoint*` encoding has no single item-to-triple correspondence to reify), and a couple of reserved-but-dead OWL API keywords. Full conformance tracking, including what's deliberately not matched and why, in `docs/manchester_syntax_gap_analysis.md` - derived by decompiling OWL API 5.1.20's own keyword table plus empirical cross-checks against its real parser (an external, uncommitted oracle - not a project dependency) via `starlayergraph.compare.isomorphic()`. Tests: `tests/unit/test_manchester_parser.py`.

- **`format="manchester"` (alias `"omn"`) for `StarLayerGraph.serialize()`** - the reverse direction (`starlayergraph/serializers/manchester.py`). A genuinely different problem from parsing: reconstructs the same internal AST `manchester_parser.py` builds, but by *recognizing* RDF patterns (blank-node restrictions, `rdf:List` chains, `owl:Axiom` reification blocks) rather than deterministically producing them, then renders that AST to text with precedence-aware parenthesization. Targets the same construct coverage as the parser, with a few reconstructions deliberately scoped out because the RDF shape involved is inherently ambiguous, not from missing effort (`SuperClassOf:`/`SuperPropertyOf:` and `onlysome` are pure surface sugar with no RDF-level trace, so they always come back in their expanded/canonical form; `EquivalentClasses:`/`SameIndividual:`/binary `DisjointClasses:`/`DisjointProperties:`/`DifferentIndividuals:` Misc axioms are RDF-indistinguishable from the same triples split across per-subject frames, so those always come back that way too - only the unambiguous >2-member `AllDisjointClasses`/`AllDisjointProperties`/`AllDifferent` shape is reconstructed as a real Misc axiom). Verified by round-tripping `parse_manchester()` output through the serializer and back (isomorphic across every construct tested) and by confirming the real OWL API oracle accepts the serializer's output without a syntax error. Tests: `tests/unit/test_manchester_serializer.py`.

- **`engine=` parameter for `StarLayerGraph.infer(profile="owl-dl")`, plus a second engine to choose from.** Previously `profile="owl-dl"` meant exactly one reasoner (HermiT via `owlready2`); now the caller picks per call: `engine="hermit"` (default, unchanged behavior - sound and complete for all of OWL 2 DL) or `engine="rustdl"` (new - a pure-Rust SROIQ reasoner, no JVM, via `starlayergraph/graph/owl_dl_rustdl.py`; sound but only empirically near-complete on full SROIQ, and its property-assertion materialization is a documented "sound under-approximation" that omits disjunctive-derived edges - confirmed live against this project's own logic-puzzle guide example, it reproduces disjunctive *class* entailments but not forced *property* assignments the way `engine="hermit"` does). An invalid `engine=` value raises `ValueError`; passing a non-default `engine=` for any profile other than `"owl-dl"` also raises `ValueError`, rather than silently doing nothing. **`owlready2` moved from a core dependency to the optional `starlayergraph[hermit]` extra**, alongside the new `starlayergraph[rustdl]` extra (`rustdl>=0.4`) - both engines now have the identical "not installed by default, opt in, loud actionable `RuntimeError` naming the exact `pip install` command if missing at call time" shape, rather than one being special. Tests: `tests/unit/test_infer_owl_dl.py` (updated), `tests/unit/test_infer_owl_dl_rustdl.py` (new).

- **`entailment="direct"` for `StarLayerGraph.query()`** - the query-time counterpart to `infer(profile="owl-dl", engine=...)`, mirroring `entailment="owl-rl"`'s design exactly: queries a live union of `self` and a small cached OWL-DL entailment delta, refreshed on the same `infer=`-governed cadence. New `engine=` kwarg on `query()` (`"hermit"` default / `"rustdl"`) selects which reasoner computes that delta - only meaningful with `entailment="direct"`, raises `ValueError` if combined with any other `entailment=`. Caching is keyed per-engine (`self._owl_dl_cache[engine]`), not a single shared slot, so switching engines between calls on an unmutated graph doesn't invalidate the other engine's cached result. `query()`'s own docstring carries a prominent cost warning `entailment="owl-rl"` never needed: genuine tableau DL reasoning is routinely orders of magnitude slower than `owlrl`'s forward chaining, and `infer="changed"` only bounds how *often* that cost is paid, not how *expensive* any single recomputation is. Raises `InconsistentOntologyError` uncaught, same contract `infer(profile="owl-dl")` already has. Tests: `tests/unit/test_entailment_direct.py`.

- **Native (`backend="rdf-1.2"`) graphs no longer need an explicit `identifier=` to keep `query()`/`update()` and `infer()`/`triples()` looking at the same data.** Previously, a native `StarLayerGraph` constructed without `identifier=` got a random `BNode` (rdflib's own default) - `query()`/`update()` send SPARQL text straight through unscoped (the endpoint's own default graph), while `infer()`/`triples()`/plain iteration wrap patterns in `GRAPH <self.identifier> { ... }` unless `self.identifier` is exactly `DATASET_DEFAULT_GRAPH_ID`, so the two halves of the API silently disagreed about which graph was "self's data" - no error, just an empty result from the latter. `StarLayerGraph.__init__` now defaults `identifier=DATASET_DEFAULT_GRAPH_ID` automatically whenever `backend='rdf-1.2'` and the caller supplies no identifier of their own (a positionally- or explicitly-passed real identifier is left untouched). Tests: `tests/unit/test_conformance.py::TestNativeIdentifierDefault`, `tests/integration/test_entailment_native.py::test_no_explicit_identifier_needed_anymore`.

### Fixed

- **Blank-node label collision across repeated `StarLayerGraph.parse()` calls.** Turtle 1.2 parsing (`format="turtle12"`/`"longturtle12"`) minted anonymous-node labels (`_:sl_N`, `_:si_N`) from a counter that restarted at 0 on every call. Calling `.parse()` more than once on the same graph, where more than one call's Turtle body contained an anonymous `[ ... ]` node, could silently merge unrelated blank nodes that happened to land on the same number into a single node, corrupting the graph. Found live while building a guide example that used two separate `.parse()` calls; every call site elsewhere in this codebase happened to use a single call, which is why this had never surfaced. Fixed by seeding the counter with a random per-call offset (`starlayergraph/parsers/turtle_parser.py`) so labels from different calls can never collide. Regression test: `tests/unit/test_turtle_parser.py::TestBlankNodeUniquenessAcrossCalls`.
