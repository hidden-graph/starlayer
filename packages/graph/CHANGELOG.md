# Changelog

## Unreleased

RDF 1.2/SPARQL 1.2 conformance hardening since 0.1.0:

- **RDF 1.2 VERSION-directive conformance checking** (`RDF12ConformanceWarning`) across Turtle, N-Triples, N-Quads, TriG, RDF/XML, SPARQL, and the native `rdf-1.2` backend.
- **Full W3C conformance** — the Turtle 1.2 test suite went from 29 to 103 tests (added the syntax-conformance cases alongside eval), which surfaced and fixed real gaps: stricter `TurtleSyntaxError` handling, predicate/subject position validation for triple terms and reified triples, annotation-block arity, VERSION directive grammar, base-direction case sensitivity, and surrogate-escape rejection.
- **`isomorphic()`** now correctly handles TripleTerms containing blank nodes, and is more rigorous generally (was previously using rdflib's own approximate check).
- Fixed several SPARQL 1.2→1.1 rewriter bugs (WHERE-less queries, bare `TRIPLE()` in a SELECT projection, nested `isTRIPLE()`).
- Adopted Apache Jena's real TriX convention; fixed an RDF/XML `rdf:version` data-corruption bug.
- Removed the obsolete `rdf-star` backend mode (superseded by `rdf-1.2`).
- Assorted smaller fixes: `tt:HASH` collision risk, the `sqlalchemy` extra failing to install on a fresh environment, query/update state leaking across calls.
- **Performance: `StarLayerGraph.query()`/`StarLayerDataset.query()` no longer re-rewrite and re-parse the same query text on every call.** Callers that evaluate the same query repeatedly with only `initBindings` differing — the exact pattern used by SHACL-AF `sh:construct` rules and `sh:sparql` constraints, evaluated once per focus node — now hit a per-instance prepared-query cache (`starlayergraph.query.query_cache.prepare_query_cached`, keyed on query text + effective namespaces + base IRI) instead of redoing the SPARQL 1.2→1.1 rewrite and rdflib's own SPARQL parse every time. ~4.5x faster per repeated call in a microbenchmark; the win scales with how many times a query is re-evaluated per unmutated graph, which for rule-heavy validations grows with graph size. **Follow-up fix**: the cache initially assumed passing a pre-parsed `Query` object to `Graph.query()` was safe for any store (a documented rdflib capability in the general case) — confirmed via real Fuseki testing that `rdflib.plugins.stores.sparqlstore.SPARQLStore`/`SPARQLUpdateStore` (used for *any* remote HTTP SPARQL endpoint, not just Fuseki) hard-require a plain string and raised `AssertionError` otherwise. `StarLayerGraph.query()` now checks `starlayergraph.query.query_cache.store_accepts_prepared_query` and falls back to a plain rewritten string for these stores — no regression, and no lost benefit either, since these stores forward the query text to a remote server, so local rdflib-side re-parsing was never the bottleneck there. `StarLayerDataset.query()` was never affected (it always executes against its own always-in-memory `_build_raw_execution_graph()`, regardless of the dataset's own backing store).
- **Fixed: `StarLayerGraph.parse(format='turtle12'/'longturtle12'/'trig12')` on a native (`backend='rdf-1.2'`) graph wrote the rdf-1.1 backend's own tt:HASH skolemized encoding directly into the store, for *any* backend.** These three parse branches called `super().add(triple)` (rdflib's base `Graph.add()`), bypassing the backend-aware `StarLayerGraph.add()` override that routes triple-term values to `_native_add()` for real `<<( )>>` storage - so a triple term parsed from text (as opposed to added via the `.add()` Python API, which was never affected) never decoded correctly on a native-backend graph: `.triples()` returned the raw `rdf:subject`/`rdf:predicate`/`rdf:object` encoding fragments instead of a `TripleTerm` object, and `rdf:reifies` lookups against such data never matched. Confirmed to affect both simple and nested triple terms. Fixed by decoding the skolemized encoding back into real `TripleTerm` objects (`starlayergraph.parsers.turtle_parser.decode_tt_encoded_triples`) before writing native-backend data, so it goes through `self.add()` → `_native_add()` instead; the rdf-1.1 backend path is untouched (its tt:HASH encoding *is* that backend's own on-disk representation, so writing it directly was always correct there). Found via a downstream consumer's `sh:reifierShape`/`sh:reificationRequired` breaking end-to-end against a live Oxigraph backend.
- **Fixed: same bug, separate code path — `StarLayerDataset.parse(format='trig12')` on a native-backend dataset had the identical problem.** Its per-context write loop called the module-level `_raw_graph_add` (rdflib's base `Graph.add()`, aliased at import time) unconditionally regardless of backend, never routing through the per-context `StarLayerGraph.add()` override. This is a distinct implementation from `StarLayerGraph.parse()`'s trig12 branch (the dataset builds one context per named graph via `parse_trig12_named()`, rather than merging all graphs into one via `parse_trig12()`), so fixing the graph-level path did not fix this one. Confirmed via real Oxigraph *and* Fuseki testing: a triple term parsed into a named graph never came back as a `TripleTerm` from `ds.get_context(...).triples()`. Fixed the same way — decode the tt:HASH encoding back into real `TripleTerm` objects before writing, per named-graph context, only on the native-backend path; the rdf-1.1 backend path (`_raw_graph_add` + `_build_registry_from_store()`) is untouched.
- **Fixed: `StarLayerDataset.query()` had no native-backend (`rdf-1.2`) dispatch at all, and crashed with `TypeError: unknown binding type` on any query result containing a triple-term-valued binding** (e.g. `SELECT ?tt WHERE { GRAPH ?g { ?s rdf:reifies ?tt } }`). Unlike `StarLayerGraph.query()`, which routed to its own native-only query logic for `self._is_native`, `StarLayerDataset.query()` always queried a plain in-memory copy built by `_build_raw_execution_graph()` — for a native-backend context, that copy is built by reading through rdflib's base `Graph.triples()` (a plain SPARQL 1.1 `SELECT ?s ?p ?o` against the remote store), which cannot represent a `"type":"triple"` JSON binding. Plain-triple dataset queries were unaffected; only triple-term-valued results crashed. Fixed by giving `StarLayerDataset` the same native-backend query dispatch as `StarLayerGraph` (a native-backed dataset's per-context graphs all share one store, so cross-graph queries are the same underlying HTTP operation — graph scoping comes entirely from the query's own `GRAPH` clauses, same as the single-graph path). Confirmed via real Oxigraph and Fuseki testing for SELECT, ASK, and CONSTRUCT.
- **Fixed: `StarLayerDataset.update()` crashed with `HTTP 400` on any update text containing its own `GRAPH <uri> { }` clause, against a remote store on *both* backends** — not a triple-term bug at all, but an rdflib/`SPARQLStore` quirk: `Dataset(store=...).update()` always wraps the whole update text in an extra `GRAPH <urn:x-rdflib:default> { }` block (`SPARQLStore._is_contextual()` doesn't recognize `Dataset`'s own default-graph sentinel — a `URIRef`, which subclasses `str` — as exempt from wrapping; only the literal string `"__UNION__"` is special-cased), nesting illegally around any update that already has its own `GRAPH` clause, which is the normal way to target a named graph from dataset-level SPARQL. Confirmed via real Oxigraph and Fuseki testing with a plain `INSERT DATA { GRAPH <uri> {...} }` containing no triple terms at all. Fixed by bypassing rdflib's `Dataset.update()` dispatch and sending the update over HTTP directly for any store with query/update endpoints, for both backends (rdf-1.2 unmodified, rdf-1.1 still rewritten to the tt:HASH encoding first).
- **Refactor: deduplicated `StarLayerGraph`'s and `StarLayerDataset`'s native-backend (`rdf-1.2`) dispatch logic into shared functions in `starlayergraph.backends.native`** (`resolve_store_http`, `check_native_version_conformance`, `native_query`, `native_update`), rather than each class carrying its own near-identical copy. This is what let the query/update bugs above exist in the first place — a fix landing in one class's copy had no way to reach the other's. Both classes' `.query()`/`.update()` now call the same functions; `StarLayerGraph._native_query()` and `StarLayerDataset._native_query()` no longer exist as separate methods. No behavior change beyond the two fixes above; confirmed via the full integration suite against real Oxigraph and Fuseki.
- **Fixed: `StarLayerGraph.from_rdflib(some_dataset)` crashed with `ValueError: too many values to unpack (expected 3, got 4)`** on any `Dataset`/`ConjunctiveGraph` input. The internal `turtle_parser._skolemize_encoding()` helper it calls did bare `for s, p, o in g:` iteration, which assumes `g` is triple-shaped; a `Dataset` yields 4-tuples `(s, p, o, context)` from `__iter__`. Fixed by reading via `g.triples((None, None, None))` instead — the same call `Graph.__iter__` itself delegates to, so behavior for a plain `Graph` is unchanged, but for a `Dataset` it correctly returns 3-tuples and — importantly — respects whatever `default_union` the dataset was constructed with (rdflib default: `False`), rather than crashing or silently unioning every named graph regardless of that setting. A `Dataset(default_union=False)` (the default, and what `StarLayerDataset` itself uses) now copies only the default graph into the resulting `StarLayerGraph`, matching the dataset's own declared semantics; `default_union=True` copies everything, same as iterating the dataset directly would.
- **Fixed: `StarLayerDataset.triples()` ignored `default_union` entirely and always returned the union of every named graph**, contradicting its own documented default-graph-isolation contract (`default_union=False` is the class's stated default, matching plain rdflib `Dataset`). Found while verifying the `from_rdflib()` fix above: that fix relies on the source dataset's `.triples()` correctly respecting `default_union`, which plain `rdflib.Dataset` does but `StarLayerDataset` did not — so a `StarLayerDataset(default_union=False)` (the default) still leaked named-graph content through `from_rdflib()` despite the fix. Fixed by making `triples()` branch on `self.default_union`: `True` keeps the existing behavior (union via `quads()`); `False` now delegates to the default graph's own `StarLayerGraph.triples()` only (TT restoration and encoding-triple filtering still apply either way). `tests/unit/test_dataset.py::TestQuads::test_triples_union_view` was itself asserting the buggy union-regardless-of-flag behavior against a default-constructed (`default_union=False`) dataset; updated to construct with `default_union=True` explicitly, plus a new `test_triples_default_union_false_excludes_named_graphs` covering the correct default behavior.
- **Fixed: same `default_union` propagation gap, two more places — `StarLayerDataset.query()` and `.update()` silently ignored `default_union=True`.** Both build their own internal `Dataset` wrapper to execute against (`_build_raw_execution_graph()` for `.query()`'s in-memory-backend path; a `Dataset(store=self.store)` for `.update()`'s), and both constructed it with rdflib's default (`default_union=False`) regardless of `self.default_union` — so on a `StarLayerDataset(default_union=True)`, a GRAPH-less `SELECT`/`WHERE` pattern silently matched nothing from any named graph instead of seeing their union, exactly the `.triples()` bug above but two more call sites. Fixed by forwarding `default_union=self.default_union` to both. (A GRAPH-less `INSERT`/`DELETE` template still targets the dataset's own default graph either way — `default_union` only widens what a GRAPH-less `WHERE` can match, not where an update writes to; confirmed this matches plain `rdflib.Dataset`'s own behavior exactly, not a StarLayer-specific quirk.) New `TestDefaultUnionPropagation` test class in `tests/unit/test_dataset.py` exercises `default_union` across `.query()` and `.update()` together, alongside the existing `.triples()` coverage, rather than one-off tests per bug found.
- **Fixed 4 Turtle 1.2 parsing bugs found via a downstream consumer running the real-world W3C SHACL 1.2 test suite through `format='turtle12'`** (this suite is not part of this repo - see the downstream project's own test-suite-integration docs):
  - **`next_token()`'s plain-token fallback only stopped at whitespace or `<`**, so a token immediately followed by `(`, `[`, `{`, `"`, `'`, `,`, or `;` with no separating space (e.g. `sh:resultPath(...)`, valid Turtle - none of these characters can appear inside a PrefixedName/IRI token, so no space is needed to disambiguate) glued the delimiter onto the preceding token instead of starting a new one. Widened the fallback scan's stop-character set (`starlayergraph/parsers/lexer.py`).
  - **RDF collection (`( ... )`) members never got the same bare-literal string→Python-value coercion (`coerce_object()`) an ordinary (non-list) object already receives in `extract_fields()`** - a collection containing a bare numeric/boolean literal (e.g. `( 42 )`, `( true false )`) reached final term conversion as a raw string and was rejected as an "unrecognized term" (`_to_node()` already handles Python `bool`/`int`/`float` correctly; it just never received them for list members). Fixed by calling `coerce_object()` on each collection element in `expand_triple_set()` (`starlayergraph/parsers/syntax.py`) - safe unconditionally, since a bracket/quote-wrapped member never matches `coerce_object`'s literal patterns.
  - **A `#` comment starting after other content on the same line was never stripped** - only a comment occupying a *whole* line was recognized (a pre-filter in `StarLayerTurtleParser.parse()`). Fed the trailing comment text into the grammar as if it were real content, producing spurious "unexpected trailing content" errors. Fixed by stripping `#`-to-end-of-line directly in the statement-splitting/directive-scanning character loops (`_split_statements_impl`/`_scan_directive_end` in `starlayergraph/parsers/syntax.py`), gated on not being inside a string or an `<IRI>` (which may legitimately contain a literal `#` fragment).
  - **`StarLayerGraph.parse(location=..., format='turtle12', publicID=...)` never resolved relative IRIs (including a bare `<>`) against `publicID`** - `StarLayerTurtleParser.parse()` had no parameter to accept a seed base at all; only an in-document `@base`/`BASE` directive ever set `current_base`. Fixed by adding a `base` parameter to `StarLayerTurtleParser.parse()` (seeds `current_base`; an in-document `@base` still overrides it from that point on, `urljoin`'d against it exactly as a second `@base` would be) and having `StarLayerGraph.parse()`'s `turtle12`/`longturtle12` branch pass `publicID`, falling back to `location`'s own resolved `file://` IRI when `publicID` isn't given - matching the convention rdflib's own parsers follow.

- **Fixed: ECHAR escapes `\b`/`\f` (backspace/form-feed) never decoded in string literals** — `turtle_parser._unescape()` and `ntriples12._unescape_nt()` both handled the full RDF 1.1/1.2 ECHAR table except these two, silently leaving the literal two-character text `\b`/`\f` in the decoded string instead of the real control characters (U+0008/U+000C) the grammar defines them as. Found via a downstream consumer's `sh:singleLine` fixture, which needs a real form-feed to trigger. New coverage: `tests/unit/test_turtle_parser.py::TestPlainTurtle::test_form_feed_and_backspace_escapes_decode`, and a new `tests/unit/test_ntriples12.py` (previously zero coverage for this parser).

Found via the downstream `starsparql` project's adversarial round-trip tests. See `docs/rdflib-upstream-issues.md` Issue 4's addendum for the full root-cause writeup.
- **Patched a confirmed plain-rdflib bug: `translateAlgebra` drops the `*` for `SELECT * WHERE { <fully-ground pattern> }`** (a WHERE clause with zero variables anywhere — an unusual but valid "does this fact exist" query), regenerating invalid, unparseable `SELECT {...}` text instead. Also found via the downstream `starsparql` project's adversarial round-trip tests; unrelated to RDF 1.2/triple terms. See `docs/rdflib-upstream-issues.md` Issue 7.
- **Fixed: `native.py`'s SPARQL JSON result parser (`_parse_json_term`) crashed with an unhandled, confusing double-fault when a native backend's query result contained a `"triple"` binding whose own subject was itself a triple term** — not valid RDF 1.2 (a triple term's subject may never itself be a triple term), and something a spec-conformant engine should never actually return, but confirmed a real Fuseki 5.5.0 bug can produce it in practice (`TRIPLE(subject, ...)` fails to validate a triple-term-valued `subject` the way it already validates `predicate` — see `docs/fuseki-upstream-issues.md` Issue 1). `TripleTerm.__init__`'s own validation correctly rejected constructing it, but raised *before* assigning any of its `__slots__`, so anything that tried to `repr()`/`str()` the half-constructed instance afterward (traceback formatting, notably) hit a *second*, unrelated `AttributeError`, obscuring the real problem. Fixed two ways: `_parse_json_term` now catches this specific `ValueError` and re-raises one clear, single error identifying the actual cause (a native-engine conformance issue, not a bug in this library) instead of letting the raw exception propagate into the double-fault; separately, `TripleTerm.__str__`/`__repr__` are now defensive against a half-constructed instance regardless of cause, so this class of secondary crash can't recur even from an unrelated future failure path.
- **Investigated and closed all 4 known in-memory-backend-specific limitations in the W3C SPARQL 1.2 eval suite: `op-2`, `order-1`, `order-2`, `construct-5`.** Confirmed all 4 were specific to the in-memory (`rdf-1.1`, `tt:HASH` content-addressed URI encoding + SPARQL 1.2→1.1 text rewrite) backend, not a gap in RDF 1.2/SPARQL 1.2 support generally — the native (Oxigraph) backend already passed all 4 cleanly with zero query rewriting. All 4 are now genuinely **fixed**, not just documented:
  - `op-2`: `starlayergraph/query/evaluate_patches.py::patch_relational_expression_tt_hash_equality` patches `=`/`!=` to decode a `tt:HASH` URI's encoding triples on the fly and recursively re-apply RDF 1.2 value-equality (instead of stock rdflib's plain URIRef string equality, which could only ever agree with `sameTerm`); `starlayergraph/model/encoding.py::canonicalize_query_result_value` separately canonicalizes a numeric-XSD literal's lexical form specifically for SPARQL SELECT *results* (parsing/storage still deliberately preserves exact lexical form as written, per `parsers/syntax.py::coerce_object`'s own tested contract).
  - `construct-5`: root cause was `sparql12_to_11.py::_try_split_construct_where` only recognizing the explicit `CONSTRUCT { template } WHERE { where }` two-block form — the `CONSTRUCT WHERE { pattern }` shorthand fell through to a single-pass rewrite treating `pattern` as an ordinary (non-template) WHERE clause, so an annotation block inside it only ever got WHERE-matching reifier semantics, never the template's own fresh-per-solution one. Fixed by teaching that function to recognize the shorthand and feed the same source text as both halves to the existing (already-correct) two-pass rewrite, which independently mints fresh internal variable names for each pass.
  - `order-1`/`order-2`: two fixes. First, `starlayergraph/query/evaluate_patches.py::patch_order_by_tt_hash_term_kind` gives a `tt:HASH` URI its own `ORDER BY` term-kind bucket after literal, per RDF 1.2 (stock rdflib's `_val` has no bucket for triple terms at all, predating RDF 1.2). This exposed a *separate*, pre-existing bug: an unconstrained BGP match (this fixture's own subquery shape) could incidentally match the backend's own internal encoding triples — reproduces with stock, unpatched `ORDER BY` too, previously just masked by the old wrong sort order coincidentally excluding the leaked rows. A first, blanket "filter every BGP match against an encoding triple" fix regressed a real, previously-passing test (`basic-5`, whose rewritten form legitimately needs to match those same triples to decode a triple-term pattern containing a variable) and was reverted. The corrected, precise version — `starlayergraph/query/evaluate_patches.py::patch_bgp_skips_encoding_triples` — only filters a match where the *pattern's own* predicate position was unconstrained (a variable, not yet bound) before matching, never one where the pattern itself already specifies the predicate as a literal `rdf:subject`/`predicate`/`object` IRI (exactly the shape every rewriter-generated decode pattern uses) — the precise signal the first attempt was missing, and it closes both tests with zero regressions.
  
  All 7 originally-`xfail`'d tests across this work (these 4, plus the 3 Oxigraph decimal-lexical-form ones documented separately above) are now genuinely fixed.
- **Found and fixed 2 more real bugs (one in this repo, one a confirmed plain-rdflib bug) via a follow-up investigation: 6 W3C SPARQL 1.2 fixtures failing in the downstream `starsparql` project's own test suite when it runs its algebra-regenerated query text against this repo's in-memory backend.** First isolated whether these were algebra-round-trip bugs or in-memory-backend bugs: confirmed via the downstream project's own Oxigraph/Fuseki round-trip suite that all 6 already agree perfectly between original and regenerated text against two independent real engines — ruling out the algebra pipeline. Then isolated each case into a standalone test *inside this repo* (`tests/w3c_sparql12/test_algebra_regenerated_queries.py`, hardcoded original/regenerated query pairs, no dependency on the sibling project or a live engine) to triage precisely:
  - 3 of the 6 (`graphs-1`, `graphs-2`, `expr-1`) turned out to be a **false positive** — a test-infrastructure bug in the downstream project's own suite (always constructing a plain `StarLayerGraph()` instead of `StarLayerDataset()` for TriG/named-graph data), not a real starlayergraph or algebra bug at all.
  - `triple-on-undefs` was also a **false positive** — the shared W3C test harness's own `bindings_match`/`_canon_term` crashed on a `None`/`UNDEF` value instead of comparing it; the actual query results were already identical. Fixed the harness (`tests/w3c_sparql12/harness.py`) to treat `None` as a distinct, comparable sentinel.
  - `pattern-6` was a **real bug** in `starlayergraph/query/sparql12_to_11.py`'s own SPARQL 1.2→1.1 rewriter: its "is this term ground (a fixed, computable value) or does it need pattern-matching" check (`_rewrite_term`) only excluded `?`/`$`-prefixed variables, not blank nodes — so a triple term whose subject/object was a blank node (which the downstream project's algebra-regenerated text produces for an anonymous reifier, e.g. nested reification shorthand like `<< <<:s :p :o>> :p2 :o2 >>`) got routed into the "compute via `BIND(<tt#fn/hash>(...) AS ...)`" branch instead of the "match via `rdf:subject`/`predicate`/`object`" branch — but a blank node can never legally appear as a function-call argument in SPARQL at all, so this produced unparseable rewritten text. Fixed by also excluding `_:`/`[`-prefixed terms from the "ground" check — a query's own blank node labels are existentially-quantified pattern variables, not fixed values, same as an ordinary `?var`.
  - `expr-2` was a **real, confirmed pre-existing plain-rdflib evaluator bug** (`evalLazyJoin` hardcoding its evaluation order — see `docs/rdflib-upstream-issues.md` Issue 8 for the full write-up and fix, `starlayergraph/query/evaluate_patches.py::patch_lazy_join_expr_dependency_order`).

  - **Fixed: `starlayergraph/parsers/syntax.py::extract_fields()` silently produced zero triples for a non-empty bracketed property list (Turtle's `blankNodePropertyList`) used as a statement's own *subject*** — `[ :q :z ] .` or `[ :q :z ] :b :c .` — as opposed to the already-correctly-handled object-position case (`:s :p [ :q :z ] .`).   - **Confirmed (real, upstream, not fixable here): Fuseki 5.5.0's `TRIPLE()` validates its `predicate` argument but not its `subject` argument** — any invalid value (a `Literal`, a triple term) is silently accepted as `subject` instead of leaving the result unbound, confirmed against a second independent engine (Oxigraph, which correctly rejects both) and confirmed to survive an actual write (not just a query result — `INSERT`+read-back returns the identical invalid stored term). See `docs/fuseki-upstream-issues.md` Issue 1 for the full write-up and a standalone, starlayergraph-independent Python reproduction. The 3 W3C fixtures this affects (`triple-on-literals`, `triple-on-str-literals`, `triple-on-triple-terms`) are marked `xfail(strict=True)` in `_FUSEKI_KNOWN_DIVERGENCES`, matching the existing `_OXIGRAPH_KNOWN_DIVERGENCES` pattern.
  - **Fixed a related gap this surfaced in this repo's own code**: `starlayergraph.model.triple.TripleTerm.__init__` only rejected a nested-`TripleTerm` subject, not the full RDF 1.2 rule (`ttSubject ::= iri | BlankNode`, `verb ::= iri`) — so decoding a native-backend query result affected by the Fuseki bug above (a `Literal`-valued subject) silently constructed an equally-invalid `TripleTerm` Python object with no error anywhere in the chain. Now enforces the same full rule the in-memory backend's own `TRIPLE()` implementation already did (`starlayergraph/query/sparql12_to_11.py::_tt_hash_fn`). `starlayergraph/backends/native.py`'s existing catch-and-clarify handler (which turns a `TripleTerm` construction failure into one clear "native engine returned invalid RDF 1.2" error instead of a confusing double-fault) needed no structural change, just updated wording. New `tests/unit/test_triple.py` (10 tests).
- **Fixed: `TRIPLE()`, `isTRIPLE(TRIPLE(...))`, `SUBJECT()`/`PREDICATE()`/`OBJECT()`, and `STRLANGDIR()` silently returned unbound results against a genuinely remote `backend='rdf-1.1'` store** (a real SPARQL 1.1 HTTP endpoint via `SPARQLStore`/`SPARQLUpdateStore` — e.g. Fuseki run in plain 1.1 mode; not `backend='rdf-1.2'`, and not any in-process store like the default in-memory backend or SQLite via `rdflib-sqlalchemy`, both confirmed unaffected). Root cause: the SPARQL 1.2→1.1 rewriter (`starlayergraph.query.sparql12_to_11`) implements these via custom SPARQL extension functions (`register_custom_function`) — a process-local-only registration, invisible to a real remote engine. Per SPARQL 1.1's own extension-function error semantics, a `BIND` calling an unrecognized function doesn't fail the query; it just leaves that row's target variable unbound — so this was a silent-wrong-answer bug, not an exception. Fixed by decomposing the query before sending it: parse the rewritten text into a real algebra tree, strip every `Extend` that (transitively) depends on one of starlayergraph's custom functions, send the remaining plain-SPARQL-1.1 part to the remote store in one round trip, then evaluate the stripped expressions locally — reusing the exact same, already-registered, already-correct function implementations — per result row, once the now-known bound values are back. New `starlayergraph/query/remote_decompose.py`; wired into `StarLayerGraph.query()`'s existing string-only-store branch. Confirmed via real Fuseki testing: new `TestFusekiRdf11SparqlFunctions` in `tests/integration/test_fuseki_backend.py` (previously 3 of its 5 cases failed against the pre-fix code).

- **Replaced `starlayergraph/query/sparql12_to_11.py` — the ~2,164-line hand-rolled, regex/text-based SPARQL 1.2→1.1 rewriter — with the sibling `starsparql` package's real grammar/algebra pipeline.** SPARQL 1.2 query/update text is now parsed via an actual grammar extension of rdflib's own SPARQL parser (`starsparql.parse12`), then lowered algebra-tree-to-algebra-tree (`lower_rdf11.py`) to plain SPARQL 1.1 (the same `tt:HASH` content-addressed encoding as before) — never string manipulation. `starlayergraph` now declares a real dependency on `starsparql` (see `pyproject.toml`); the two packages already depended on each other in the other direction, an intentional two-way relationship (`starsparql` is this project's own SPARQL engine layer, not an independent library). Public API is unchanged: `StarLayerGraph`/`StarLayerDataset.query()`/`.update()`, and `starlayergraph.query.parseQuery`/`prepareQuery`/`parseUpdate`/`prepareUpdate`/`processUpdate`, all keep their existing signatures and return types.
  - **Dropped**: the `isTripleTerm(?x)` filter-function alias for the spec name `isTRIPLE(?x)` — a starlayergraph-only, pre-spec-stabilization spelling the old rewriter special-cased before rdflib's real parser ever saw the query text. `isTRIPLE()` (RDF 1.2 §17.4.6) is unaffected.
  - **Fixed, not just replaced — a real spec-conformance bug the old rewriter had**: a triple term nested in *subject* position (`<<( <<( :a :b :c )>> :p :o )>>`) is syntactically parseable SPARQL (the W3C suite even labels this shape a `PositiveSyntaxTest`) but not a legal RDF 1.2 term — nesting is legal only in *object* position (RDF 1.2 §grammar-production-tripleTerm). The old rewriter silently accepted it; confirmed via a live Oxigraph instance rejecting exactly this shape (HTTP 500) that the old behavior was the bug. The new pipeline correctly raises `starsparql.triple_term.InvalidTripleTermError`.
  - **Real bugs found and fixed during the migration, in `starsparql` itself** (all with new regression coverage in that project's own test suite):
    - `lower_rdf11.py::_lower_modify` read `node.get("delete")`/`.get("insert")` expecting `None` back for an INSERT-only or DELETE-only `Modify` (the common case) — but `CompValue.get(key)`'s signature (`get(self, a, variables=False, errors=False)`) has no default parameter and falls back to returning the key *string itself*, not `None`, for a missing key. Silently handed the string `"delete"` where a clause or `None` was expected, crashing on `.name` access. Fixed by switching to attribute access (`node.delete`), which correctly returns `None` via `CompValue.__getattr__`.
    - A ground triple term used as an ordinary *value* in `InsertData`/`DeleteData` (not a `Modify` template) had its `tt:HASH` computed correctly but its own encoding triples (`rdf:subject`/`predicate`/`object`) were never persisted to the graph — only registered in an ephemeral, process-global lookup cache. `has_triple_term()`/`triple_terms()` (which rebuild their registry from the store's own *persisted* encoding triples) never saw a triple term introduced this way. Fixed by giving `InsertData` its own lowering, which — like the already-correct `Modify`-template case — actually emits the encoding triples, not just the hash.
    - `prepare_query_12`/`prepare_update_12` had no `base`/`initNs` parameters at all, unlike plain rdflib's own `prepareQuery`/`prepareUpdate` — added, with identical precedence semantics (`initNs` seeds the query's Prologue first, the query's own `PREFIX`/`BASE` declarations apply after and override).
    - Added a genuine SPARQL 1.1 Update-algebra-to-text serializer (`rdf11_update_to_sparql11_text`) — needed for `native_update()`'s remote-rdf-1.1-store text path, which previously had no non-text-rewriting way to reach a store that hard-requires a string. Covers `InsertData`/`DeleteData`/`DeleteWhere`/`Modify` (including `WITH`/`USING`) and all 7 graph-management operations (`Load`/`Clear`/`Drop`/`Create`/`Add`/`Move`/`Copy`).
    - `starlayergraph.query.remote_decompose` (which lets a query depending on starlayergraph's custom SPARQL functions still run against a genuinely remote store, by stripping the dependent algebra nodes and re-evaluating them locally per result row) only knew how to strip `Extend` nodes — but the new pipeline can lower a non-ground triple-term pattern's predicate constraint into a bare `FILTER(PREDICATE(?tt) = :knows)`, a custom-function call directly inside a `Filter`'s own expression, a shape the old text rewriter never produced. Sent to a real remote engine as-is, that `FILTER` raises on the unknown function and SPARQL's own `FILTER` semantics exclude the row — silently, every row, no exception. Found via live Fuseki testing, not unit tests. Fixed by extending `decompose_for_remote()` to also strip qualifying `Filter` nodes and re-check them locally after the round trip (`row_passes_filters`).
  - **Fixed a real, long-standing pytest/pyparsing interaction** that could corrupt `starsparql`'s grammar installation (`TRIPLE()`-family syntax would stop parsing partway through a run) when its first import happened lazily, from inside application code, during pytest's own collection phase while its assertion-rewrite import hook was active — nothing to do with which pipeline a given test exercised. Fixed by having `tests/conftest.py` eagerly import and install the grammar at collection time. Confirmed via full-suite runs with no test exclusions needed anymore.
  - Custom SPARQL function registration (`TT_HASH_FN`, the `SUBJECT`/`PREDICATE`/`OBJECT` accessors, `STRLANGDIR`) — previously a side effect of importing the old rewriter module — now lives in its own `starlayergraph/query/custom_functions.py`, imported eagerly from `starlayergraph/__init__.py`.
  - The `VERSION "label"` SPARQL prologue directive's handling (stripping it before parsing, since no SPARQL grammar — old or new — has a production for it) now lives in `starlayergraph/query/version_directive.py`, a small, self-contained module — a plain, unambiguous leading-prefix strip, not the kind of nested-structure fragility that motivated replacing the rest of the old rewriter.

## 0.1.0 — 2026-05-14

Initial public release.

### Features

- **`StarLayerGraph`** — drop-in replacement for `rdflib.Graph` with full RDF 1.2 support
- **Triple terms** — `TripleTerm` objects as first-class Python values; content-addressed internal encoding (`tt:HASH`)
- **All annotation forms** — parses and serializes `{| |}`, `~ :r`, `<<( )>>`, and `<< >>` syntax
- **SPARQL 1.2** — triple-term patterns rewritten to SPARQL 1.1 for `rdflib` compatibility; `isTripleTerm()`, `SUBJECT()`, `PREDICATE()`, `OBJECT()` functions supported
- **CONSTRUCT queries** — result graph is a `StarLayerGraph` with TripleTerms correctly restored
- **8 serialization formats** — `turtle12`, `longturtle12`, `nt12`, `nq12`, `trig12`, `trix12`, `rdfxml12`, `jsonld12`
- **W3C conformance** — passes the W3C Turtle 1.2 test suite (29 `TestTurtleEval` cases)
- **Multiple backends** — in-memory (default), SQL via `rdflib-sqlalchemy`, Apache Fuseki (`rdf-1.1` and `rdf-star` modes), Oxigraph (`rdf-1.2` native mode)
- **PEP 561** — `py.typed` marker included; package is typed
