## Deferred / open follow-ups

- **rdflib 8 compatibility.** Currently built on and tested against rdflib 7.6.0 (`pyproject.toml` requires `rdflib>=7.0`). rdflib 8.0.0a0 (pre-release) was tested too; revisit compatibility when a stable rdflib 8 release ships.

- **More examples.** Only two exist today; no example covers `StarLayerDataset` (multi-graph). Decide what's worth adding.

- **SPARQL 1.2 Protocol gap analysis done (2026-09-27), no action needed.** Full writeup: `docs/sparql12_protocol_gap_analysis.md`. Bottom line: the 1.2 revision changes almost nothing at the protocol level (mostly editorial; the one new HTTP `QUERY` method and the `version` announcement mechanism are both optional). `starlayergraph/backends/native.py` (the only code this spec's requirements land on - this project has no server-side SPARQL endpoint anywhere) already conforms to everything it needs to; its single-submission-mode choices (POST-direct for both query and update, `GRAPH`-clause-based dataset scoping instead of protocol-level parameters) are documented, deliberate design choices, not gaps. Three small, genuinely optional loose ends if ever revisited: round-tripping the already-computed in-band `VERSION` value onto the wire's out-of-band `version` parameter; verifying `Content-Type` before parsing a CONSTRUCT response; distinguishing HTTP 400 from 500 at the four HTTP call sites.

- **RDF 1.2 Interoperability spec gap analysis done (2026-09-27), not implementation-ready.** Full writeup: `docs/rdf_interop_gap_analysis.md`. This spec (`rdf:PropositionForm`-based Full↔Basic encoding for triple terms) is still an Editor's Draft with its `basic-decode` algorithm literally unwritten ("Write this algorithm") and an open question on whether RDF 1.1 interop is even in scope - not comparable in maturity to the seven CR/WD documents `rdf12_sparql12_gap_analysis.md` tracks. This project already has three independently-designed, narrower analogs solving related problems differently (`compare.py::_decompose()`'s private-namespace blank-node encoding for canonicalization/reasoner bridges; `_intern_tt()`'s content-addressed URIRef encoding for in-memory storage) - none worth retrofitting onto the spec's vocabulary, since both are internal details no external caller ever observes. The one genuinely live payoff, if this spec matures: `serializers/jsonld12.py` could stop raising `ValueError` on RDF 1.2 content and instead encode/decode through `basic-encode`/`basic-decode`, since JSON-LD still has no RDF 1.2 companion spec of its own. Revisit once (if) this reaches Working Draft.

- **Already shipped, this bullet was stale: "RDF serialization of SPARQL queries."** Was carried here as "a genuine new feature... needs design before starting," but the real thing already exists and has a full guide: `starsparql.query_to_rdf()`/`rdf_to_query()` (encode a parsed `Query`'s algebra as RDF via the `SALG` vocabulary, edit it as RDF, decode back into a real, runnable `Query`), plus `starsparql.ontology_graph()`/`shapes_graph()` for validating the encoded representation with RDFS reasoning. Confirmed live (2026-09-26) against `docs/guides/05c-sparql-query-as-rdf.ipynb`'s own working 8-step walkthrough - no remaining gap noted anywhere in that guide's own "Further work," which instead just cross-links `sh:sparql`/`sh:SPARQLRule` (04b/04c) as reusing the same functions from inside SHACL.

- **SPARQL entailment regimes: RDF + RDFS + OWL-RL (via query rewrite / live-union delta caching) and native-backend delegation all shipped.** `entailment` is a per-*query* choice (`StarLayerGraph.query(..., entailment=...)`), not a graph-level setting - the same graph answers different regimes on different calls. `entailment="rdf"` rewrites the query at query time for the SPARQL spec's separate, weaker RDF Entailment regime (`starsparql/entailment_rdf.py`) - just rdfD2 ("every term used anywhere as a predicate is entailed `rdf:type rdf:Property`"), deliberately excluding rdfD1 (existential datatype-witness blank nodes) and the fixed/container-membership RDF axiomatic triples, for the same "vocabulary-level noise" reasoning `entailment="rdfs"` already applies to its own excluded rules; also rejected outright against `backend="rdf-1.2"` for the same reason `"rdfs"` is. `entailment="rdfs"` rewrites the query at query time for the full RDFS ruleset's "data" rules (`rdf:type`/`rdfs:subClassOf`, `rdfs:domain`/`rdfs:range`, `rdfs:subPropertyOf` - `starsparql/entailment_rdfs.py`, spliced into `query_cache.py::prepare_query_cached`), no data copy; deliberately excludes the "vocabulary-level" rules (universal `rdfs:Resource` typing, the fixed axiomatic triples - see that module's own docstring for the rule-by-rule reasoning). It's currently rejected outright against `backend="rdf-1.2"` (native), since the rewrite only applies to the default query path. `entailment="owl-rl"` covers what rewriting can't express (`owl:equivalentClass`, `owl:TransitiveProperty`, etc.) by querying the **live union** of `self` and a small cached delta of just its newly-entailed triples (`StarLayerGraph.infer(profile="owl-rl", mode="delta")`, `self._owl_rl_cache`, `_UnionForQuery` - a `rdflib.graph.ReadOnlyGraphAggregate` fixed to not double-count property-path results), reused per the separate `infer=` kwarg exactly as before (`"changed"`/`"always"`/`"cached"`); works for any backend, and composes automatically with a backend that already reasons on its own (e.g. a `--rdfs=`-configured Fuseki dataset), since `self` is read live and the delta only ever contains what wasn't already there. For a native (`backend="rdf-1.2"`) `self`, or any `self` with registered triple terms, a live view of `self` isn't representation-safe to union with `delta` (different term-encodings), so both sides come from the same decomposition instead, refreshed together on the same cadence - see `infer()`'s and `query()`'s own docstrings. `infer()` itself remains available directly for a caller who wants to keep one materialized snapshot around on their own terms - `profile=` chooses the ruleset (`"rdfs"`, `"owl-rl"`, or `"rdfs+owl-rl"`, the combined RDFS+OWL-RL semantics class - genuinely more than `"owl-rl"` alone, confirmed via `owlrl`'s own rule dispatch: `OWLRL_Semantics.rules()` never invokes `RDFS_Semantics.rules()`) and `mode=` chooses the output shape (`"full"` default - a new graph with everything; `"delta"` - a new graph with just what's new; `"in-place"` - adds just the delta into self directly, the equivalent of `owlrl.DeductiveClosure(...).expand(self)`, but crash-safe and representation-safe for any self, including native and triple-term-bearing ones, since only the delta - never a re-decomposed copy of self's own data - is ever added). `entailment="native"` (only legal with `backend="rdf-1.2"`) delegates entailment to the endpoint itself - the native path already passes queries straight through unmodified, so this needed no new query-path code, just validation plus `packages/graph/docs/fuseki-reasoning-setup.md` (two verified Fuseki configurations: the `--rdfs=FILE` CLI flag, and a full assembler config for OWL reasoners) and a self-skipping live integration test (`tests/integration/test_entailment_native.py`, which also directly demonstrates the backend-composes-for-free property against a real reasoning-enabled dataset). See `tests/unit/test_entailment.py`, `tests/unit/test_infer.py`, `packages/sparql/tests/unit/test_entailment_rdf.py`/`test_entailment_rdfs.py`, and `docs/guides/02b-graphs-inferencing.ipynb`/`03b-sparql-inferencing.ipynb`/`05b-backend-graph-databases.ipynb`.

- **`infer(profile="owl-dl", engine=...)` — pluggable OWL 2 DL reasoning, two engines, shipped for graph-level materialization; query-time `entailment="direct"` is still future work.** A genuinely different computational model from every other `profile` (owlrl's forward-chaining rules) - tableau-based, so it derives disjunctive entailments owlrl structurally cannot (e.g. `C subClassOf (A or B)`, `not-A(x) ⊢ B(x)`, confirmed live as the oracle test for this profile) and does consistency checking an inconsistent ontology can't silently slip past. An inconsistent ontology raises `starlayergraph.graph.owl_dl.InconsistentOntologyError` outright, rather than the partial, easy-to-miss `err:error` triple `profile="owl-rl"`'s own consistency checking (via `owlrl`) embeds silently into the result - true of both engines below.
  - **`engine="hermit"` (default) — `owlready2` + Java HermiT, `starlayergraph/graph/owl_dl.py`.** Sound *and* complete for all of OWL 2 DL (SROIQ). Deliberately HermiT only, never Pellet (`owlready2` bundles both behind `sync_reasoner()`/`sync_reasoner_pellet()`): HermiT is LGPL, Pellet is AGPL - a materially stronger copyleft obligation - and one conformant OWL 2 DL reasoner is sufficient for this regime. `owlready2` is now an optional extra (`pip install starlayergraph[hermit]`), not core - see the RustDL entry below for why this moved, at the same time RustDL was added, rather than staying a special case. A real Java runtime on PATH is a further prerequisite pip alone can't satisfy (a missing JVM raises a distinct `RuntimeError` from `owl_dl._require_java()`, not an `ImportError`). Bridge mechanics: `self` is decomposed the same way the `owlrl` path already does (`compare._decompose()`, for the same triple-term-flattening reason), serialized to a temp RDF/XML file, loaded into a fresh, disposable `owlready2.World()` per call (never the process-global `default_world` - confirmed live that bare `sync_reasoner()` silently reasons over the wrong world if not passed one explicitly), reasoned over, and re-exported/re-parsed back into a plain `rdflib.Graph`. One correctness gap found and fixed during implementation, not anticipated in the original design: HermiT's own CLI realization output only reports each individual's *most specific* type(s), not every ancestor class up the `rdfs:subClassOf` hierarchy (confirmed live - a plain `Manager rdfs:subClassOf Employee` plus `alice a Manager` came back from HermiT as just `Type(alice, Manager)`, never `Type(alice, Employee)`, even though the `SubClassOf(Manager, Employee)` edge itself was reported) - would have been a real regression versus every `owlrl`-backed profile's full transitive closure. Fixed by a small post-processing pass (`owl_dl._complete_type_closure()`) that walks the reported `rdfs:subClassOf` edges and propagates each individual's type(s) up through them, restoring the same full-closure guarantee the other profiles already give, and reused as-is by `engine="rustdl"` below. See `packages/graph/tests/unit/test_infer_owl_dl.py`.
  - **`engine="rustdl"` — a pure-Rust SROIQ reasoner, `starlayergraph/graph/owl_dl_rustdl.py`.** Raised 2026-09-25 as a prospective HermiT *replacement* (to drop the Java runtime dependency); initial assessment that same day concluded "not a good fit yet" because its completeness guarantee is weaker than HermiT's - RustDL's own docs: complete by construction only on the EL/Horn fragment, elsewhere "the classifier trusts the wedge's `Sat` verdicts - empirically near-complete on the measured corpus, not *provably* complete." Revisited 2026-09-26 once the *replacement* framing was dropped in favor of a *second, opt-in engine* - a real, permanent tradeoff (no JVM, weaker completeness guarantee) rather than a strictly-better or strictly-worse option, so both now ship side by side and the caller picks per call via `engine=`. `rustdl` is an optional extra (`pip install starlayergraph[rustdl]`), matching `[hermit]`'s shape exactly (that symmetry - not `owlready2` staying core while `rustdl` is opt-in - is why `owlready2` moved to `[hermit]` at the same time). Two further gaps confirmed empirically while integrating, on top of the completeness caveat above, both load-bearing for anyone choosing this engine: (1) RustDL's RDF/XML parser rejects an anonymous class-expression node with no explicit `rdf:type` of its own (`rdflib`'s own writer leaves this implicit; HermiT tolerates it, RustDL raises `ParseError`) - handled transparently by a targeted pre-serialization pass (`owl_dl_rustdl._infer_missing_owl_types()`) that types only nodes an OWL/RDFS-vocabulary-specific position unambiguously identifies as a class expression, never a blanket "every untyped subject," to avoid mistyping an untyped property or individual; (2) `materialize_inferred_property_assertions()` is, by RustDL's own docs, a "sound under-approximation (no anonymous-witness or disjunctive-derived edges)" - confirmed live against this project's own logic-puzzle guide example (`05e-owl-dl-reasoning.ipynb` §1.b): it returns only the already-asserted fact, none of the forced-by-elimination pairings `engine="hermit"` derives for the same data. Disjunctive *class* entailments are unaffected by this (confirmed live, identical to HermiT on the same §1.a-style example) - it's specifically forced *property* assignments coming back from a bare `infer()` call with no search that this engine can't reproduce via these bridge functions. `HasKey:`/long role chains (`SubPropertyChain:` >2 properties) - both real Manchester-syntax constructs this project's own parser emits - raise `rustdl.UnsupportedAxiomError` outright rather than being silently dropped. See `packages/graph/tests/unit/test_infer_owl_dl_rustdl.py`.

  **Query-time consumption shipped 2026-09-26: `query(..., entailment="direct", engine=...)`.** Mirrors `entailment="owl-rl"`'s live-union-with-a-cached-delta design exactly (`self._owl_dl_cache`/`self._owl_dl_snapshot_cache`, both keyed by `engine` rather than a single shared slot - HermiT's and RustDL's delta genuinely differ for the same graph, so switching `engine=` between calls must not thrash a single cache entry every time) - same `infer=` cadence kwarg, same fast-path/fallback-path split. Went ahead once real `infer()` performance data existed to design the cost tradeoff around (the §4.g scaling numbers above: ~20-individual CSP example took several seconds per call, ~30-individual didn't finish in 60s) - `query()`'s own docstring now carries a prominent cost warning `entailment="owl-rl"` never needed, since `infer="changed"` only bounds *how often* the cost is paid, not *how expensive* any single recomputation is. `engine=` is only meaningful with `entailment="direct"`; a non-default value with any other `entailment=` raises `ValueError`, mirroring `infer()`'s own `profile`/`engine` validation. See `tests/unit/test_entailment_direct.py`.

  **Confirmed 2026-09-26, not yet fixed: `engine="rustdl"` can hang indefinitely, not just answer incompletely, on a common OWL 2 DL idiom.** Found while re-executing `05e-owl-dl-reasoning.ipynb` after this session's own guide-review pass took far longer than expected - bisected precisely (isolated four variants, timed each): a property declared *both* `owl:FunctionalProperty` and `owl:InverseFunctionalProperty`, used in a restriction whose `owl:someValuesFrom` targets an `owl:oneOf` nominal enumeration, hangs RustDL's `materialize_inferred_class_assertions()` indefinitely (confirmed: 4+ minutes at ~300% CPU, zero completion, on a 3-individual, 24-triple toy ontology - every ingredient alone completes in under 0.02s). This is exactly the "bijection via nominals" pattern this guide's own §1.b and §4 use throughout, not an exotic construct. HermiT handles the identical isolated case correctly in 0.61s - confirmed RustDL-specific, not a general reasoning-difficulty issue. Full design for the fix - (A) a pre-flight structural check in `owl_dl_rustdl.py` that raises `rustdl.UnsupportedAxiomError` for this exact pattern before ever calling into the hanging function, joining the existing HasKey/role-chain rejections, plus a regression test proving HermiT doesn't have the same gap; and (B) a general wall-clock timeout (120s default, same for both engines, via a new subprocess-based `starlayergraph/graph/_timeout.py` - the only reliable way to bound an opaque, uninterruptible blocking call, whether a JVM subprocess or an in-process native PyO3 call, with careful process-*group* teardown on timeout so no orphaned `java`/grandchild process is ever left running, the exact bug class found and fixed twice elsewhere in this same session) - is written up in full at `/Users/johnclements/.claude/plans/clever-napping-mountain.md`, approved in shape but not yet implemented. Pick that plan up as-is rather than re-deriving the bisection or the process-group design from scratch.

- **SPARQL entailment regimes not planned (and why).** Of the six regimes the [SPARQL 1.1/1.2 Entailment Regimes](https://www.w3.org/TR/sparql12-entailment/) spec defines, three have no plans to be built: **OWL 2 RDF-Based Semantics** (full, beyond the RL fragment already covered by `entailment="owl-rl"`) - undecidable in general (OWL Full has roughly first-order expressive power plus RDF's own reflective quirks); `owlrl`, the only OWL-RL dependency in this stack, implements the RL fragment specifically *because* that's the version with a terminating rule-based algorithm at all. **D-Entailment** (datatype canonicalization, e.g. recognizing `"01"^^xsd:integer` and `"1"^^xsd:integer` as the same *value*) - needs a full XSD datatype-map implementation inside the query engine's own term-equality logic; narrow and orthogonal to what this project exists for (RDF 1.2: triple terms, direction-tagged literals), and confirmed live against Jena's own docs that a Fuseki/Jena backend doesn't cover this either - an explicitly stated, deliberate gap in Jena's RDFS reasoner, not something delegating to a backend (`entailment="native"`) would close. **RIF Core Entailment** - no RIF interpreter anywhere in this stack, and no spec-conformance test infrastructure to verify one against even if built. **OWL 2 Direct Semantics** is no longer in this "not planned" bucket at all - `infer(profile="owl-dl")` above covers the graph-materialization half of it; only the query-time `entailment="direct"` half remains unshipped, tracked as deliberate future work rather than a rejected gap.

- **Fixed 2026-09-26: a native (`backend="rdf-1.2"`) graph constructed with no explicit `identifier=` used to silently see no data via `infer()`/`triples()`, even though `query()`/`update()` saw it fine.** `query()`/`update()` send SPARQL text straight through *unscoped* (the endpoint's own default graph), while `infer()`/`triples()`/plain iteration wrap every pattern in `GRAPH <self.identifier> { ... }` via `_native_scoped()` - unless `self.identifier` is exactly `DATASET_DEFAULT_GRAPH_ID`, the one sentinel `_native_scoped()` treats as "the endpoint's own default graph, no wrapper needed." A native graph constructed without an explicit `identifier=` got a random `BNode` by default (plain rdflib's own default), which satisfied neither exemption - so the two halves of the API silently disagreed about which graph was "self's data," no error, just an empty result from the `infer()`/`triples()` side. `StarLayerGraph.__init__` now defaults `identifier=DATASET_DEFAULT_GRAPH_ID` automatically whenever `backend='rdf-1.2'` and the caller supplies no identifier of their own (covers both omitting it and passing `identifier=None` explicitly - rdflib's own `Graph.__init__` already treats those the same way; a positionally- or explicitly-passed real identifier is left untouched). Chose defaulting over raising: raising would need a check at every `_native_scoped()` call site, and couldn't distinguish "wrong scope" from "a real named graph that's legitimately still empty" after the fact anyway - defaulting fixes it once, at construction, before any call site can see the inconsistency. Confirmed not a regression for two independently-constructed native graphs against the same store: `query()`/`update()` already shared the same live default-graph view regardless of identifier, so only `infer()`/`triples()` were ever (uselessly) isolated by the old random-BNode default - the fix makes them agree with what `query()`/`update()` already showed, it doesn't introduce new sharing that wasn't already effectively there. `tests/unit/test_conformance.py::TestNativeIdentifierDefault`, `tests/integration/test_entailment_native.py::test_no_explicit_identifier_needed_anymore`.

## Keeping in step with RDF 1.2/SPARQL 1.2 as the spec finalizes

RDF 1.2 was at **Candidate Recommendation** (published 2026-04-07) as of this writing — not yet a final W3C Recommendation. Everything in this project (the gap analysis, the rewriter, the format modules) is checked against that CR-stage text. This project's own stated purpose (README: "intended to remain relevant until rdflib is updated to incorporate the final RDF 1.2 specification") means it has a deliberately limited lifespan, and needs periodic re-checking rather than a one-time gap analysis. Concrete steps for whoever picks this up as the spec progresses:

1. **Re-run the gap analysis at each W3C stage transition** (CR → PR → REC). CR-stage text can still change in response to implementation/horizontal-review feedback before Proposed Recommendation; re-diff `docs/rdf12_sparql12_gap_analysis.md` against the current editor's draft whenever the spec's status changes, not just once. `tests/vendor/spec_snapshots/refresh_snapshots.py` automates the "what actually changed" half of that: it re-fetches all seven tracked documents and overwrites the saved snapshots, so `git diff tests/vendor/spec_snapshots/` shows exactly what moved since the last review instead of requiring a full re-read.
2. **Watch the CR exit criteria / implementation report.** The RDF-star Working Group's CR exit requires a set of independent conforming implementations. Whichever engines end up counted (Oxigraph and Fuseki are the two this project already tracks) are worth re-verifying starlayergraph's rewriter against each time one of them ships a release claiming closer conformance — a live three-way comparison against the in-memory backend (see `tests/integration/test_cross_backend_parity.py`) is the reusable tool for that, not a one-off.
3. **Watch for a real JSON-LD RDF-1.2 companion spec.** `jsonld12` currently has no RDF 1.2 content to represent at all — it delegates plain RDF 1.1 content to rdflib's own JSON-LD writer/parser and raises `ValueError` for a triple term or `dirLangString` (see `starlayergraph/serializers/jsonld12.py`'s own docstring and `docs/rdf12_sparql12_gap_analysis.md` §6). If the JSON-LD Working Group ever publishes an RDF-1.2-aware revision with its own native representation for quoted/triple terms, add real support for that representation instead of the current explicit-refusal behavior, and update the module's docstring and the callout in `docs/starlayergraph_vs_rdflib.md` accordingly. TriX has no standards body actively developing it, so `trix12` is unlikely to ever gain a real target to converge on — its "starlayergraph convention, not a spec" status is probably permanent, and the documentation callout is the whole fix rather than a placeholder for a future code change.
4. **Once rdflib ships native RDF 1.2 support** — re-evaluate this project's continued existence, per its own stated scope. At that point: (a) consider deprecating starlayergraph's SPARQL 1.2→1.1 rewriter and in-memory triple-term encoding in favor of delegating straight to rdflib, and (b) check whether the `turtle12`/`nt12`/`nq12`/`trig12`/`rdfxml12` format modules can be dropped in favor of rdflib's own native parsers/serializers.
